# 26 · `0.2.0.01` — Vault deprecation → env-only secrets

## Goal

Delete `src/services/vault.py` (AES-256-GCM + PBKDF2 + audit log + flock + key-fingerprint preamble; 436 LOC), `src/cli/vault.py` (155 LOC), `src/cli/init.py` (103 LOC), `tests/test_vault.py` (300+ LOC), and the vault sections of `tests/test_cli.py` (~150 LOC). Switch every consumer to pydantic-settings env-loading already wired through `src/config.py`. Ship Alembic `0004_drop_vault_columns.py` dropping `Settings.llm_api_key_fingerprint` + `discord_webhook_configured` + `telegram_bot_configured` + `portfolio_webhook_configured` + `scraper_proxy_configured` (5 columns; runtime presence becomes env-derived). Rewrite `_settings_llm.html` + `_settings_deployment.html` so the API-key input field disappears (replaced by env-presence indicator) and the rose vault-locked banner disappears (no longer applicable). Land the operational-surface deletions: `~/.naavik/secrets.enc{,.lock,.bak.*}`, `~/.naavik/key.bin`, `~/.naavik/logs/vault-audit.log` are no longer written, no longer read. The plan ships **WITHOUT** an export shim — Option A (pure docs path) is the recommended migration story; the ~handful of existing self-hosters edit `.env` once.

Survives this plan: `naavik serve` (dies in `0.2.0.02`), `naavik-alembic` (forever — alembic's own CLI surface, not a Naavik feature), the `_settings_notifications.html` template body's overall layout (only the "stored encrypted at `~/.naavik/secrets.enc`" copy needs surgery + `discord_webhook_configured` / `telegram_bot_configured` references convert to env-derived).

## Why now

Three pressures, ordered by force:

1. **Sunset directive codified in `AGENTS.md § Key Conventions § CLI` since 2026-05-10.** Every plan since plan 10c has been told to stop extending the vault. Plan 23 (PR #69) added `require_authed_session` to 41 mutation routes; plan 24 (A.29) shipped the phase numbering scheme; plan 25 (`0.1.1`) deleted 2616 LOC of bash. Vault deprecation is the next domino: every downstream Settings / env work depends on it. The `_settings_llm.html` form currently HTMX-PUTs API keys to `vault_svc.set(...)`; until that path dies, every Settings UI extension carries vault drag.

2. **Standard self-hosted-app pattern is what every other app does.** Self-hosters expect `cp .env.example .env`, edit, restart. AES-256-GCM with a server-derived PBKDF2 key buys the operator nothing — the master key is `SECRET_KEY` in the same env var that already has to be available at boot for JWT signing. The on-disk encryption is theater against an attacker who already has the SECRET_KEY (because they have the process env, because the process is running). Filesystem permissions (`chmod 0600 .env`) are the actually-relevant defense, and they apply to `.env` too. The Argon2id task `0.2.1.03` (DEF-17, vault PBKDF2 → Argon2id) becomes moot post-merge — flagged in ROADMAP as "may close on `0.2.0.01` merge".

3. **`0.2.0.02` (CLI sunset) is queued and waiting.** ROADMAP § 0.2.0 row 0.2.0.02 explicitly says "depends on `0.2.0.01`; after vault deprecation ships, the only `naavik` subcommand left is `serve`". `init` / `vault status` / `vault rotate-key` are the bulk of CLI surface, and they exist solely to bootstrap + maintain the vault. Sequencing locks tight: 0.2.0.01 deletes vault + the three CLI subcommands that touch it; 0.2.0.02 collapses the residual `serve` shim. The plans can land in adjacent PRs.

Why `0.2.0.01` specifically (HIGH priority within `0.2.0`): every job-scraping sub-task (`0.2.0.05`–`0.2.0.14`) lives in a Settings UI that the form-based vault PUT currently colors. Doing scrapers first means re-wiring those forms twice (once for scrapers, once for vault deprecation). Doing vault deprecation first lets the scraper Settings extensions ship onto an env-clean surface from day one.

### D.1 — Migration story for existing self-hosters

Three options for the ~handful of current self-hosters whose `~/.naavik/secrets.enc` carries non-trivial state (most likely: an LLM API key, possibly Discord webhook URL).

**Option matrix.**

| Option | A — Pure docs path (release notes only) | B — One-shot CLI shim `naavik vault export-to-env` | C — One-shot Python script `scripts/migrate-vault-to-env.py` |
| --- | --- | --- | --- |
| Capability | Zero migration code. User reads release note: "if you have an existing `~/.naavik/secrets.enc`, delete it + re-enter values into `.env`". | One command (`uv run naavik vault export-to-env`) decrypts → emits `.env` template → user moves into place → deletes vault. Most ergonomic. | Identical UX to B, but as a one-off script invoked via `uv run python scripts/migrate-vault-to-env.py`. Not extending `src/cli/`. |
| Cost | 0 LOC + 1 paragraph in CHANGELOG | ~80 LOC in `src/cli/vault.py` (new subcommand) + ~40 LOC test + CHANGELOG paragraph. Then DELETED in same PR (commit 5). | ~60 LOC in `scripts/migrate-vault-to-env.py` + ~30 LOC test + CHANGELOG paragraph. Self-contained outside `src/`. |
| Risk | LOW — but real for the few self-hosters with vault state. They lose minutes re-entering 2–4 API keys; not data loss because keys are recoverable from provider dashboards. | LOW operationally; **HIGH sunset-rule risk** — extends CLI even for a single PR's lifespan. Sets precedent that CLI extensions are OK "if temporary". `architect-sunset-guard` skill forbids this explicitly: "Do NOT bend rule 'just this once' because CLI command feels operationally cleaner." | LOW. Standalone script doesn't extend `src/cli/`, so no sunset-rule violation. Cleanup is "remove file" not "remove subcommand + restructure parser". |
| Maintenance | None — code never exists. | Need to remember to delete in same PR; reviewer overhead. Adds CLI surface area, however briefly. | Minimal — script is one file, gets deleted post-merge or kept as historical reference (move to `docs/misc/`). |
| Lock-in | None | Sets sticky precedent: "the team adds CLI features when it's 'really just one-time'". Worst long-term cost. | None — scripts dir already exists for this kind of one-off (see `scripts/README.md` convention post-`0.1.1`). |
| Audience size | ~3-5 self-hosters max (per repo activity); owner + a few external installers | Same | Same |

**Recommendation: Option A — pure docs path.** Justification across three axes:

- **Sunset rigor.** Option B extends `src/cli/` for the EXACT lifespan of `0.2.0.01` → `0.2.0.02`. That's the strongest possible argument for the sunset rule and the strongest possible argument against it ("just one PR"). The architect-sunset-guard skill is explicit: don't bend "just this once". Option C technically routes around the rule (script is outside `src/cli/`), but the user-facing surface is still "one more way to learn the tool" for the migration window, and `scripts/README.md` post-`0.1.1` reserves `scripts/` for project-wide use, agent-system tooling lives in `.claude/naavik_ops/`. We'd be introducing a migration concept that contradicts the doc.

- **Audience size.** The vault has shipped in production builds since plan 10b (2026-05-03). Practical user base: owner (Shyam) + the contributors who self-hosted to test PRs. Even being generous, that's a single-digit number of vault files. The ergonomics gain of B/C is real but absolute: ~3-5 people save ~5 minutes each. Total time saved: < 30 minutes. Doc + clear release note is cheaper than ANY code path.

- **Recoverability.** Vault state is API keys + webhook URLs. API keys are recoverable from provider dashboards (Anthropic / OpenAI consoles); webhook URLs are recoverable from Discord/Telegram bot settings. Nothing is data-loss-on-deletion. Worst case: a 2-minute click-through.

**Trade-off accepted.** Self-hosters lose ~5 minutes during the upgrade window; we save 80 LOC + the sunset-rule precedent + reviewer overhead. The CHANGELOG `Removed` section + release-note + the existing `naavik vault status` (which still works pre-upgrade) lets users dump their scope list before they upgrade. We commit to writing a very clear migration paragraph in the release notes for `0.2.0`.

**Rationale recorded for `memory`:** decision-id `0.2.0.01-migration-story`, verdict `A`, captured at plan approval via `.claude/naavik-ops memory record-decision`.

### D.2 — Pre-upgrade snapshot capture for self-hosters (auxiliary to D.1)

Option A loses the operator's vault scope list at deletion time unless we tell them how to capture it BEFORE running `pip install / docker pull / nix build` on the new release. Two options to surface this:

**Option matrix.**

| Option | A — Release-notes-only: "run `naavik vault status` before upgrading" | B — Pre-flight check in app boot: refuse to start if `~/.naavik/secrets.enc` exists AND `NAAVIK_VAULT_MIGRATION_COMPLETE=1` is unset |
| --- | --- | --- |
| Capability | Operator's responsibility | Forces operator to acknowledge before app runs |
| Cost | 0 LOC | ~15 LOC in `main.py` lifespan + 1 env var |
| Risk | Operator skips the docs | Operator finds the app refusing to boot in production, panics, escalates |
| Lock-in | None | Sticky env var that lingers in deployment configs |

**Recommendation: A.** Self-host updates are deliberate; the operator who pulls a `0.2.0` release reads the release notes the same way they read `0.1.0` and `0.1.1` release notes. A pre-flight check in B is "scary-by-default", surfaces in production-restart paths, and adds a fourth env var (`NAAVIK_VAULT_MIGRATION_COMPLETE`) we then have to remove in 6 months. The release-note paragraph reads:

```markdown
### Upgrading from 0.1.x with a populated vault

If you previously used Settings UI to save an LLM API key or webhook URL, those values live encrypted in `~/.naavik/secrets.enc`. Capture the scope list before upgrading:

  $ uv run naavik vault status      # if running from source
  $ docker compose exec naavik naavik vault status     # if running self-host docker

Note each scope/key shown. They will be re-entered as env vars in `.env` after the upgrade (see § Configuration in the README). Then proceed with the upgrade and delete the now-orphaned files:

  $ rm -f ~/.naavik/secrets.enc ~/.naavik/key.bin
  $ rm -f ~/.naavik/secrets.enc.lock ~/.naavik/secrets.enc.bak.*
  $ rm -rf ~/.naavik/logs/vault-audit.log

(`naavik vault status` is removed in this release; the snippet above is the LAST time it works.)
```

**Trade-off accepted.** Some fraction of inattentive operators will upgrade without capturing first, find the app boots fine (DB has Settings rows pointing at `llm_api_key_fingerprint` that's now meaningless, but boot doesn't depend on the vault), and lose API-key configuration silently. They'll notice on first LLM call (401), open Settings, see "configured via env: ✗", and fix the env. Self-hosted-app standard pattern. Acceptable.

### D.3 — Alembic migration shape

**Option matrix.**

| Option | A — Single migration `0004_drop_vault_columns.py` (drops all 5 columns + 1 nullable) | B — Two migrations: `0004_drop_secret_indicators` + `0005_drop_fingerprint` |
| --- | --- | --- |
| Capability | Atomic. One revision applies + reverts cleanly. | Step-by-step; each migration has narrow blast radius. |
| Cost | ~40 LOC | ~70 LOC across two files |
| Risk | Downgrade fully restores; one apply attempt | Two apply attempts; intermediate state if upgrade halts mid-way |
| Maintenance | LOW | Higher — two files to remember during future grep-for-vault-residue audits |
| Lock-in | None | None |

**Recommendation: A — single migration.** All 6 columns (`llm_api_key_fingerprint` str, `discord_webhook_configured` bool, `telegram_bot_configured` bool, `portfolio_webhook_configured` bool, `scraper_proxy_configured` bool — that's 5; treat the 5 as one atomic dropwave) belong to the same "vault is gone" change. There's no value to a step-by-step where each migration is independently revertable, because the schema is meaningless mid-way (no consumer reads only-some-columns). One migration matches the conceptual change.

**Migration file spec** (commit 2 deliverable):

```python
# migrations/versions/0004_drop_vault_columns.py
"""Drop vault-derived columns from Settings.

Revision ID: 0004_drop_vault_cols
Revises: 0003_user_must_change_pw
Create Date: 2026-05-19

Plan 26 (0.2.0.01): vault deprecation. The five columns dropped here all
tracked vault-derived state — booleans flipped by `settings_service.update_*`
on vault writes, and a fingerprint that lets the UI show "key set" without
holding the key. Post-vault, secret presence is runtime-derived from env
vars via `services/env_secrets.py`; the columns are dead weight.

Downgrade restores the columns with their default values (False for the
booleans, NULL for fingerprint). It does NOT restore prior values — the
vault is gone, so there's nothing to read back. Self-hosters needing the
previous schema would re-enter via Settings UI after rollback. This is
acceptable: downgrade is a recovery path for a botched 0.2.0 release,
not a routine operation.
"""

from __future__ import annotations
from collections.abc import Sequence
import sqlalchemy as sa
from alembic import op

revision: str = "0004_drop_vault_cols"
down_revision: str | None = "0003_user_must_change_pw"
branch_labels: str | Sequence[str] | None = None
depends_on: str | Sequence[str] | None = None


def upgrade() -> None:
    op.drop_column("settings", "llm_api_key_fingerprint")
    op.drop_column("settings", "discord_webhook_configured")
    op.drop_column("settings", "telegram_bot_configured")
    op.drop_column("settings", "portfolio_webhook_configured")
    op.drop_column("settings", "scraper_proxy_configured")


def downgrade() -> None:
    op.add_column(
        "settings",
        sa.Column("llm_api_key_fingerprint", sa.String(), nullable=True),
    )
    op.add_column(
        "settings",
        sa.Column(
            "discord_webhook_configured",
            sa.Boolean(),
            nullable=False,
            server_default=sa.false(),
        ),
    )
    op.add_column(
        "settings",
        sa.Column(
            "telegram_bot_configured",
            sa.Boolean(),
            nullable=False,
            server_default=sa.false(),
        ),
    )
    op.add_column(
        "settings",
        sa.Column(
            "portfolio_webhook_configured",
            sa.Boolean(),
            nullable=False,
            server_default=sa.false(),
        ),
    )
    op.add_column(
        "settings",
        sa.Column(
            "scraper_proxy_configured",
            sa.Boolean(),
            nullable=False,
            server_default=sa.false(),
        ),
    )
```

Companion update to `src/models/settings.py` (commit 2 same file set): remove the 5 columns from the SQLModel definition. Companion update to `src/db/sample_data_models.py` + `src/db/sample_data.py`: remove field declarations + sample seeds.

Round-trip test path: `uv run alembic upgrade head && uv run alembic downgrade -1 && uv run alembic upgrade head` on a fresh DB; assert no errors.

### D.4 — Env-presence indicator design (replaces `_configured` booleans + fingerprint)

The boolean columns served the UI: "is Discord configured? show (configured) vs blank". Post-vault, we read the env var at request time and surface `configured: bool` in the API response without persisting it. Two options for where the read lives.

**Option matrix.**

| Option | A — Per-request property on Settings (lazy `@computed_field`) | B — Service helper `services/env_secrets.py:is_provider_configured(name)` |
| --- | --- | --- |
| Capability | Settings instance "knows" its own env state; tight coupling | Service layer encapsulates env reads; Settings stays a pure DB row |
| Cost | ~30 LOC across Settings + 5 properties | ~50 LOC across new module + 5-6 functions |
| Risk | SQLModel `@computed_field` interaction with `table=True` is tricky; risk of accidentally writing it. Settings model leaks env-awareness into the DB layer (architectural smell). | Standard service-layer split. Easy to test. |
| Maintenance | Future readers expect Settings to be pure DB row | Conventional Naavik layout: services own logic, models stay declarative |
| Lock-in | Soft — refactoring away later is non-trivial because consumers `settings.discord_webhook_configured` style access | None — service helper is composable |

**Recommendation: B — service helper.** Settings is a DB row per `DATA_MODEL.md § C`. Mixing env reads into it violates the "no business logic on models" Naavik convention (per `AGENTS.md § Code Style`). A small module `src/services/env_secrets.py` with one function per env var (or a single function with a dispatch dict) keeps the responsibility where it belongs.

**Sketch** (commit 3 deliverable):

```python
# src/services/env_secrets.py
"""Env-presence indicators — post-vault replacement for `Settings.*_configured`.

Per ROADMAP row 0.2.0.01 (plan 26): the 5 `Settings._configured` boolean
columns + `Settings.llm_api_key_fingerprint` are dropped. Settings UI +
API surfaces still need to render "Anthropic: configured via env ✓ / ✗"
indicators without exposing values.

Each helper reads `config.settings` (pydantic-settings already loads from
`.env` + actual env). Empty / None means absent; non-empty means present.
NEVER returns the value itself; the caller cannot leak.
"""

from __future__ import annotations

from config import settings as app_settings
from models.enums import LLMProvider


def llm_provider_configured(provider: LLMProvider) -> bool:
    """True iff an API key is set in env for the given provider.

    Ollama returns True iff `OLLAMA_BASE_URL` is non-empty (it's always
    set in defaults, so effectively always True — but the indicator
    follows the same shape as Anthropic/OpenAI for UI uniformity).
    """
    if provider is LLMProvider.ANTHROPIC:
        return bool(app_settings.anthropic_api_key)
    if provider is LLMProvider.OPENAI:
        return bool(app_settings.openai_api_key)
    if provider is LLMProvider.OLLAMA:
        return bool(app_settings.ollama_base_url)
    return False


def discord_webhook_configured() -> bool:
    return bool(app_settings.discord_webhook_url)


def telegram_bot_configured() -> bool:
    return bool(app_settings.telegram_bot_token)


def portfolio_webhook_configured() -> bool:
    return bool(app_settings.portfolio_webhook_url)


def env_indicators_for_llm_tab() -> dict[str, bool]:
    """Bundle for `_settings_llm.html` template context."""
    return {
        "anthropic": llm_provider_configured(LLMProvider.ANTHROPIC),
        "openai": llm_provider_configured(LLMProvider.OPENAI),
        "ollama": llm_provider_configured(LLMProvider.OLLAMA),
    }


def env_indicators_for_notifications_tab() -> dict[str, bool]:
    return {
        "discord": discord_webhook_configured(),
        "telegram": telegram_bot_configured(),
        "portfolio": portfolio_webhook_configured(),
    }
```

| `s.discord_webhook_configured` | `env_secrets.discord_webhook_configured()` |

### D.5 — `PUT /api/v1/settings/llm` becomes partially read-only

`src/api/settings.py:put_llm` currently routes `api_key` payload values through `vault_svc.set(...)` and `settings_service.update_llm(api_key=...)`. Post-vault, the body field still arrives (HTML form fields are static), but the handler must reject any `api_key` value with a 422 + clear message "API keys are now configured via env vars; see README § Configuration", OR silently ignore.

**Option matrix.**

| Option | A — 422 reject when `api_key` non-empty | B — Silently strip `api_key` from payload; rest of PUT proceeds | C — Drop `api_key` from form entirely (template change only); ignore in handler if anyone POSTs raw JSON |
| --- | --- | --- | --- |
| Capability | Loud failure — user sees error | Quiet success; user thinks they saved a key when nothing changed | Removed surface — no opportunity to send |
| Cost | ~5 LOC + 1 test | ~3 LOC + 1 test | ~0 in handler (just don't read it) + the template delete in D.6 |
| Risk | First-upgrade self-hoster who didn't read release notes hits 422 confusion. But they'd hit this exactly once. | Silent data loss is a known UX trap. User saves "valid-looking key", checks Settings later, sees ✗, panics. | Belt + suspenders. |
| Maintenance | Standard 422 pattern | Standard ignore-pattern | None |
| Lock-in | None | None | None |

**Recommendation: C + A.** Drop the `api_key` field from the HTML form (this is the D.6 template work). Additionally, in the handler, if `api_key` arrives non-empty (a non-UI client, or a stale cached form), return a clean 422 with explicit error text. Quiet ignore (B) is the worst UX. The user-facing form never sends the field; the handler defends against legacy clients with a clean 422.

**Handler sketch** (commit 4 in `src/api/settings.py`):

```python
@router.put("/api/v1/settings/llm", name="api_settings_llm_put")
async def put_llm(
    request: Request,
    session: AsyncSession = Depends(get_session),
    _user: User | None = Depends(require_authed_session),
):
    is_form = _is_form_request(request)
    if is_form:
        form = await request.form()
        payload = {k: v for k, v in form.items() if str(v).strip()}
    else:
        try:
            payload = await request.json()
        except Exception:
            payload = {}
        if not isinstance(payload, dict):
            payload = {}

    # Plan 26 (0.2.0.01): API keys are env-only post-vault. Reject any
    # legacy client trying to persist via this endpoint.
    if payload.get("api_key") or payload.get("ollama_base_url"):
        return JSONResponse(
            status_code=422,
            content={
                "detail": (
                    "API keys + Ollama base URL are configured via env vars "
                    "(ANTHROPIC_API_KEY / OPENAI_API_KEY / OLLAMA_BASE_URL) "
                    "starting in 0.2.0. See README § Configuration."
                ),
            },
        )

    provider = payload.get("llm_provider")
    fallback_provider = payload.get("llm_fallback_provider")
    s = await settings_service.update_llm(
        session,
        user_id=1,
        provider=LLMProviderEnum(provider) if provider else None,
        model=payload.get("llm_model"),
        fallback_provider=(LLMProviderEnum(fallback_provider) if fallback_provider else None),
    )
    # ... rest unchanged
```

`settings_service.update_llm` loses the `api_key` parameter (signature simplifies) and never invokes vault. `update_notifications` symmetrically loses `discord_webhook_url` + `telegram_bot_token` params.

ATS credentials are a special case. Today they go through `vault.set("ats", board.value, json.dumps(cookies))` because cookies + 2FA backups are JSON blobs, not simple strings. Post-vault, there are three options:

**Sub-decision matrix (vault-rewire for ATS credentials):**

| Option | A — Move to env (one var per board, JSON-encoded value) | B — Stay in DB as encrypted-at-rest column on `ATSCredential` (new column) | C — Stay in DB as plaintext column on `ATSCredential` (DB-at-rest encryption is the user's responsibility) | D — Defer to `0.2.0.06+` (ATS adapter plans) — return None from `resolve_secret` until then |
| --- | --- | --- | --- | --- |
| Capability | Static config; cookie refresh needs restart | DB-encrypted bytes; refresh works via UI | Plain bytes in `ATSCredential.cookie_data` | Removes vault dep without committing to replacement |
| Cost | ~10 LOC | ~50 LOC + new Alembic column + key derivation (re-inventing vault) | ~30 LOC | ~10 LOC; defer to follow-up plan |
| Risk | Operator pain — cookies expire; restart loop | Re-introduces "Naavik encrypts secrets at rest" — exactly what 0.2.0.01 deletes | DB compromise = cookies leak. Less bad than expected (cookies are short-lived, scoped to one ATS) | None today; the only consumer (`ats/dispatch`) is in Phase 2 path, not Phase 1 |
| Maintenance | Static | High — reinvents vault under a different name | Low | Low until ATS adapters resume |
| Lock-in | None — easy to refactor to DB later | High | Moderate — schema change | None |

**Recommendation: D — return None.** ATS adapters (`0.2.0.06+`) are not in Phase 1 / `0.1.0` / `0.1.1`. Greenhouse / Lever / Ashby ship under `0.1.0.23` (already executed); Workday / LinkedIn / Indeed / Generic are queued in `0.2.3.01`. The current `services/ats_credentials.py:resolve_secret` is wired but no Phase 1 caller actually invokes it (`services/ats/__init__.py:dispatch` exists; tests use stubbed adapters). Two concrete options for `0.2.0.01`:

1. **D.1: Delete `services/ats_credentials.py:store_secret` + `resolve_secret` + `delete_secret`.** Keep `get_credential_metadata` / `list_credential_metadata` / `upsert_credential_metadata` — those work with the DB-only `ATSCredential` row (which has `has_credential: bool`, `login_status`, etc., no secret material). Phase 2.X adapter plans add the new storage model when actually needed.
2. **D.2: Stub `resolve_secret` to return None + log a one-shot warning.** Slightly more conservative; same end state.

D.1 is the cleaner break. Use it. Plan 26 § Risk + mitigation flags this as a deferred decision; the follow-up plan (Workday adapter or LinkedIn adapter, whichever ships first in 0.2.X) re-introduces the secret storage model as DB-encrypted-bytes or per-board OAuth-style env (likely DB-encrypted-bytes, but that's `0.2.X`'s call).

```markdown
- `.env.example` — full inventory of secret slots with documentation of `NAAVIK_DEBUG` interaction, `chmod 0600 .env` guidance, and the post-vault security model.

### Operations

- **UX regression: rotating an LLM API key is now `edit .env + restart`.** No equivalent of `naavik vault rotate-key`. This matches the pattern of every other self-hosted app (n8n, Grafana, Authentik): secrets are env vars.
- **Migration for existing self-hosters**:
  ```
  # BEFORE upgrading:
  $ uv run naavik vault status     # capture your scope list
  # AFTER upgrading:
  $ cp .env.example .env && chmod 0600 .env
  # edit .env with the values from the captured scope list

  ```
- Audit log (`~/.naavik/logs/vault-audit.log`) is gone. Operator visibility into "who accessed which secret" comes from the application access log + the request-tracing pipeline (Phase 2.5).
```
