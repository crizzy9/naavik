# 38 · `0.2.0.13` — rate limiting + anti-detection

## Goal

Promote the conservative defaults baked into the six site scrapers (`rate_limit_per_minute` + `random_delay_seconds` class attributes from plan 33) into operator-tunable per-source Settings, swap our hand-rolled `Crawl4AIClient._respect_rate_limit` for Crawl4AI 0.8's native `RateLimiter` so 429 / 503 responses get exponential backoff for free, add a curated User-Agent rotation pool to dilute scraper fingerprints, replace `url_guard._resolve_host`'s unbounded `@lru_cache` with `cachetools.TTLCache(ttl=60)` to bound DNS-rebinding TOCTOU, and surface per-source RL telemetry into `JobScrapeRun.raw_meta` so operators can tell when a source is being throttled. On approval the plan content graduates into `docs/design/SCRAPER_BASE.md § G` (which today reserves this exact interface), closing the substrate hardening loop opened in plan 29. Out of scope: proxy / IP rotation (DEF-15 / `0.2.3.03` Phase 6+), `UndetectedAdapter` engagement (`0.2.0.13c` follow-up gated on observed 403-rate), robots.txt honoring (industry-precedent skip; § D.5).

## Why now

Five forces, ordered by load:

1. **Plan 33 left a stack of explicit forward refs at this row.** Five items already pin `0.2.0.13` as their landing site: (a) `SCRAPER_BASE.md § G` ("`Settings.{linkedin,...}_rate_limit_per_minute`, burst tolerance + 429 backoff, IP rotation, `UndetectedAdapter`"); (b) `SCRAPER_BASE.md § C.2 last bullet` ("`0.2.0.13` lifts these into `Settings` fields"); (c) `SCRAPER_SITES.md § H` cross-ref ("`0.2.0.13` per-source rate-limit tuning via Settings"); (d) plan-33 architect-review deviation (`rate_limit_per_minute: int → float` — engineer typed `int` so LinkedIn's 0.4 effective rate was floored to `1`); (e) `Indeed.py:7` ("`UndetectedAdapter` engagement reserved for `0.2.0.13` if measured 403-rate exceeds ~5%"). Shipping later means each downstream plan re-litigates these.

2. **Hacker filed `0.2.0.13a` against PR #102 and recommended folding here.** The MEDIUM-impact DNS-rebinding TOCTOU window in `url_guard._resolve_host` (`@lru_cache(maxsize=256)` with no TTL extends the window to process lifetime) was filed as Issue #105 with a note "may fold into 0.2.0.13 rate-limiting work" (ROADMAP.md:227). It's a small fix (~10 LOC + 2 tests) that shares the same files this plan already touches, so folding avoids a second PR-cycle.

3. **`scheduler/scraping.py:152-155` already passes the class-level defaults into `Crawl4AIClient` — but nothing reads `Settings` per source.** The cron resolves `scraper_cls.rate_limit_per_minute` + `scraper_cls.random_delay_seconds` (class attrs) and constructs the client fresh per firing. Operators today cannot tune LinkedIn from 1 → 2 req/min without editing `src/scraper/sites/linkedin.py` and rebuilding. The wiring exists; the indirection through Settings is the missing piece.

4. **Crawl4AI 0.8.6 already ships the rate-limit primitive we hand-rolled.** `Crawl4AIClient._respect_rate_limit` (`crawl4ai_client.py:171-180`) is ~10 LOC of token-bucket + jitter that Crawl4AI's `RateLimiter` does natively, plus exponential backoff on 429 / 503 that we don't have at all. The official `MemoryAdaptiveDispatcher(rate_limiter=RateLimiter(...))` integration is documented at https://docs.crawl4ai.com/advanced/multi-url-crawling/ and works in `stream_many` today. Replacing our shim removes a maintenance surface and gains 429-recovery for free.

5. **Indeed (and to a lesser extent LinkedIn) will start seeing real 403/429 traffic the moment `0.2.0.10` cron starts firing under load.** `Indeed.py:7` already names this plan as the landing spot for `UndetectedAdapter` if measured 403-rate exceeds ~5%. The plumbing this plan adds (per-source Settings + RL telemetry into `JobScrapeRun.raw_meta`) is the prerequisite for that observation — without it operators don't know they're being blocked. The `UndetectedAdapter` engagement itself defers to `0.2.0.13c` follow-up (§ D.4 OQ.2), but the observation substrate ships here.

### D.1 — Per-source rate-limit configuration locus

The crux call. Six site scrapers today carry `rate_limit_per_minute` + `random_delay_seconds` as class attributes (e.g. `linkedin.py:59-60`: `1` and `(3.0, 7.0)`). The cron reads those at construct time (`scheduler/scraping.py:152-155`). Operators want to tune per-source caps without editing code.

**Option matrix.**

| Option | A — Single `Settings.scraper_rate_limits: dict` JSONB col, keyed by `JobSource.value` (recommended) | B — 6 × 3 = 18 individual `Settings.{source}_rate_limit_per_minute` + `_delay_lo` + `_delay_hi` columns | C — Keep class attrs only; expose via env vars (`LINKEDIN_RATE_LIMIT_PER_MINUTE` etc.) |
| --- | --- | --- | --- |
| Capability | One JSON column. `RateLimitConfig` Pydantic v2 model validates: `{"linkedin": {"rpm": 1.0, "delay_lo": 3.0, "delay_hi": 7.0}, ...}`. New source = new key, no migration. Per-user (multi-user-ready). | Strongly-typed. Settings UI form maps one-to-one. Per-user. | Operator override via `.env`; same simple shape as ATS company lists. Single-tenant only. |
| Cost — schema | Alembic 0008 adds 1 nullable JSONB col + 1 server_default `{}`. ~15 LOC migration. `RateLimitConfig` model + resolver helper ~40 LOC. | Alembic 0008 adds 18 nullable cols (6 sources × 3 fields). ~80 LOC migration. Settings UI form has 18 form rows. | Zero schema. `config.py` adds 18 fields + 18 validators. `.env.example` adds 18 rows. README adds 18 rows. |
| Cost — code | Single `get_rate_limit(settings, source) -> RateLimitConfig` helper resolves Settings.dict → class-attr fallback. ~20 LOC. | Resolver enumerates 18 columns. Add-new-source means 3 new columns + 3 migration steps. | Per-instance only; resolver reads `app_settings.linkedin_rate_limit_per_minute` etc. |
| Risk — schema drift | LOW — JSON schema validated by Pydantic v2; new sources add a key without migration. Existing `JSONB` server_default `{}` matches the pattern used by `sources_enabled` / `source_schedules` / `consecutive_scrape_failures` (per `models/settings.py:69-105`). | MEDIUM — 18 nullable columns is the most schema growth Settings has ever taken. Adding a 7th source = 3 more columns. | LOW now; MEDIUM later — env-only blocks multi-user (cloud tier wants per-user rate dials for cost reasons). |
| Risk — UI form | LOW — Settings · Sources tab (existing form in plan 36) renders 6 cards × 3 inputs from one JSON read. | LOW — 18 form fields; visually noisy but works. | n/a — no UI surface. |
| Maintenance | New source → 1 JSON key + 1 fallback in class-attr table. Adding burst-tolerance / 429-retry-count later is a key addition, not a migration. | New source → 3 columns + alembic + form rows + tests. | New source → 3 env vars + config validators + docs. |
| Lock-in | None — JSON shape is internal; can shape-shift via Pydantic v2 model_validator if needed. | High — column shape locked once data lands. | High — env-var contract is public. |
| Convention parity | Matches `Settings.sources_enabled` / `Settings.source_schedules` / `Settings.notifications_enabled` / `Settings.consecutive_scrape_failures` — all four are `JSONB dict` columns keyed by source value. The "per-source operator dial" pattern is the established Settings idiom. | Diverges from the established pattern. | Diverges + breaks multi-user. |

**Recommendation: A — single `Settings.scraper_rate_limits: dict` JSONB column, keyed by `JobSource.value`.**

**Reason 1: convention parity.** `models/settings.py:69-76` shipped four parallel "per-source JSON column" patterns: `sources_enabled` (which sources are active), `source_schedules` (cron expressions), `notifications_enabled` (catalog of fired events), `consecutive_scrape_failures` (per-source FAILED counter). Adding `scraper_rate_limits` keeps the existing operator-mental-model intact — Settings · Sources card shows one card per source, each card has its own dials.

**Reason 2: empty-dict-is-default fits the existing fallback shape.** Cron currently reads `settings.sources_enabled.get(source.value, True)` (default-enabled). The same fallback works here: `_resolve_rate_limit(settings, source) -> RateLimitConfig` does `settings.scraper_rate_limits.get(source.value, _CLASS_ATTR_FALLBACK[source.value])`. New sources, unconfigured operators, and dev orchestrator startup all get sane defaults.

**Reason 3: Settings UI form scales.** Plan 36 § Approval row `0.2.0.11a` (the deferred SCREENS.md / COMPONENTS.md graduation for `/discover`) already promised a Settings · Sources card per source. Each card extends naturally to host an RL sub-form (3 inputs: `rpm` + `delay_lo` + `delay_hi`). Six cards × 3 inputs vs 18 standalone form rows is the UX win.

**Trade-off accepted.** Operators see one consolidated JSON-backed surface vs 18 distinct columns. The Settings UI form-handler reads + writes one nested dict instead of 18 atomic fields. Form validation routes through a single `RateLimitConfig` Pydantic model — slightly more involved than 18 atomic validators but encapsulates the cross-field invariant (`delay_lo <= delay_hi`).

**Shape.**

```python
# src/scraper/rate_limit.py (new)
class RateLimitConfig(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    rpm: float = Field(ge=0.1, le=600.0)        # 0.1 floors at 1 req per 10min
    delay_lo: float = Field(ge=0.0, le=600.0)
    delay_hi: float = Field(ge=0.0, le=600.0)

    @model_validator(mode="after")
    def _delay_order(self) -> RateLimitConfig:
        if self.delay_lo > self.delay_hi:
            raise ValueError("delay_lo must be <= delay_hi")
        return self


# Class-attribute fallback table — one source of truth that mirrors the
# values in src/scraper/sites/*.py at ship time.
_CLASS_ATTR_FALLBACK: dict[str, RateLimitConfig] = {
    JobSource.LINKEDIN.value:   RateLimitConfig(rpm=0.4, delay_lo=3.0,  delay_hi=7.0),
    JobSource.WORKDAY.value:    RateLimitConfig(rpm=2.0, delay_lo=20.0, delay_hi=40.0),
    JobSource.GREENHOUSE.value: RateLimitConfig(rpm=20.0, delay_lo=1.5, delay_hi=3.0),
    JobSource.LEVER.value:      RateLimitConfig(rpm=20.0, delay_lo=1.5, delay_hi=3.0),
    JobSource.ASHBY.value:      RateLimitConfig(rpm=20.0, delay_lo=1.5, delay_hi=3.0),
    JobSource.INDEED.value:     RateLimitConfig(rpm=2.0, delay_lo=20.0, delay_hi=40.0),
}


def resolve_rate_limit(settings: Settings, source: JobSource) -> RateLimitConfig:
    raw = (settings.scraper_rate_limits or {}).get(source.value)
    if raw is None:
        return _CLASS_ATTR_FALLBACK[source.value]
    try:
        return RateLimitConfig.model_validate(raw)
    except ValidationError as exc:
        log.warning("invalid rate_limit_config for %s; falling back: %s", source.value, exc)
        return _CLASS_ATTR_FALLBACK[source.value]
```

**Locked decision:** **A** — single `Settings.scraper_rate_limits: dict` JSONB column.

### D.2 — Rate-limit implementation: keep our shim or adopt Crawl4AI's `RateLimiter`?

`Crawl4AIClient._respect_rate_limit` (`crawl4ai_client.py:171-180`) is 10 LOC of token-bucket + jitter that handles the steady-state per-request pacing. It does NOT handle 429 / 503 backoff; a Crawl4AI request that gets rate-limited fails outright (we log via `safe_msg(result.error_message)` and return `None`). Crawl4AI 0.8.6 ships `RateLimiter` with exponential backoff on 429 / 503, jitter, and max-retries — pluggable into `MemoryAdaptiveDispatcher` (which `stream_many` already uses).

**Option matrix.**

| Option | A — Adopt Crawl4AI's `RateLimiter` (recommended; delete our shim) | B — Keep our shim, add hand-rolled exponential backoff on 429 / 503 | C — Hybrid: our shim for per-request pacing + Crawl4AI's only for backoff |
| --- | --- | --- | --- |
| Capability | Steady-state pacing + 429/503 exponential backoff + max-retries — all from the library. Same dispatcher integration we already use in `stream_many`. | Same capabilities, all hand-rolled. ~80 LOC of new code. | Two RL layers stacked. Surprising — pacing fires our jitter, then Crawl4AI's RL also fires its base_delay on the same request. |
| Cost — code | Delete `_respect_rate_limit` (~10 LOC). Add `RateLimiter` construction in `Crawl4AIClient.__init__` (~10 LOC). Plumb into `arun` via `crawler.arun(..., rate_limiter=...)` for `fetch_html` + via `dispatcher=...` for `stream_many` (already wired). Net: ~zero LOC growth. | ~80 LOC of new code in `Crawl4AIClient`: 429-detection (parse `result.status_code` from Crawl4AI's response), exponential backoff, jitter, max-retries. Tests for all of that. | ~30 LOC of glue + the same test surface as A. Two layers of RL semantics to keep aligned. |
| Risk — library bugs | LOW — Crawl4AI 0.8.6 is the version we already pin; RateLimiter is shipped with `MemoryAdaptiveDispatcher` (which `stream_many` already uses). If Crawl4AI breaks RL in 0.9, that's a `crawl4ai_client.py:84-111` patch — single file. | MEDIUM — we own the bug surface. 429-detection is fiddly (Crawl4AI's `result.status_code` semantics are not well-documented). | HIGH — two RL layers means doubled bug surface + ordering questions. |
| Risk — semantic mismatch | LOW — `RateLimiter(base_delay=(delay_lo, delay_hi), max_delay=60.0, max_retries=2, rate_limit_codes=[429, 503])` maps 1:1 to our per-source dial. | LOW — we control the semantics. | n/a — by design ambiguous. |
| Maintenance | Crawl4AI ships fixes upstream. Our wrapper stays thin. | Every RL behavior fix is our patch. | Worst — we maintain the integration point. |
| Lock-in | Some — if Crawl4AI's RL semantics drift, we patch one layer. Acceptable; we're already locked to 0.8.6 by `crawl4ai==0.8.6` pin. | None — full control. | Same as A. |
| Existing test surface | `tests/test_crawl4ai_client.py` already mocks `AsyncWebCrawler` via `_FakeAsyncCrawler`; the new tests inject a `_FakeRateLimiter` to assert RL ordering. | Tests need to simulate a 429 response from `_FakeAsyncCrawler` + assert exponential backoff fires (more involved). | Same as A + B. |

**Recommendation: A — adopt Crawl4AI's `RateLimiter`.**

**Reason 1: we lose nothing.** The library RL is a strict superset of our shim. Per-request pacing → check. Jitter → check. Plus 429/503 backoff which we don't have.

**Reason 2: we gain 429 recovery for free.** Today, an Indeed / LinkedIn 429 returns `None` from `fetch_html` (logged via `safe_msg`), the scraper's tier-1 `self._errors.append(...)` records it, and the scrape continues. With Crawl4AI's RL, the same 429 triggers exponential backoff (1s → 2s → 4s up to 60s cap) and retries up to `max_retries=2`. The "transient 429 on otherwise-healthy session" case stops bleeding listings.

**Reason 3: maintenance cost is upstream.** Crawl4AI's release notes for v0.7.8 and v0.8.x show active RL bug fixes (linked from official docs at https://docs.crawl4ai.com/blog/releases/). Riding upstream is cheaper than maintaining our own.

**Trade-off accepted.** We add a coupling to Crawl4AI's `RateLimiter` API (which is documented but not part of a stable contract). Mitigation: the coupling lives in `crawl4ai_client.py` — one file. Crawl4AI's RL signature is unchanged across 0.7.8 → 0.8.6 per the changelog; future drift is a same-file patch.

**Shape.**

```python
# src/scraper/crawl4ai_client.py (modified)
from crawl4ai import (
    AsyncWebCrawler, BrowserConfig, CacheMode, CrawlerRunConfig,
    MemoryAdaptiveDispatcher, RateLimiter,
)

class Crawl4AIClient:
    def __init__(
        self,
        *,
        enable_stealth: bool = True,
        headless: bool = True,
        page_timeout_ms: int = 30_000,
        rate_limit_per_minute: float = 30.0,    # int → float per plan-33 deviation
        random_delay_seconds: tuple[float, float] = (1.0, 3.0),
        user_agent: str | None = None,
    ) -> None:
        # Crawl4AI's RL handles per-request pacing AND 429/503 backoff.
        # base_delay = our jitter; max_delay = cap on backoff growth;
        # max_retries = how many times to retry a 429/503 before giving up.
        self._rate_limiter = RateLimiter(
            base_delay=random_delay_seconds,
            max_delay=60.0,
            max_retries=2,
            rate_limit_codes=[429, 503],
        )
        self._browser_config = BrowserConfig(
            enable_stealth=enable_stealth,
            headless=headless,
            user_agent=user_agent,    # § D.3 — UA rotation
        )
        # Minimum-interval guard (the existing per-process token-bucket math)
        # stays — Crawl4AI's RL provides base_delay between requests but NOT
        # a strict "min N seconds between any two requests" floor. We keep
        # the floor for sources with very low rpm (LinkedIn = 0.4 → 150s).
        self._min_interval_s = 60.0 / max(0.1, rate_limit_per_minute)
        self._last_request_at: float = 0.0
        self._run_config = CrawlerRunConfig(
            cache_mode=CacheMode.BYPASS,
            page_timeout=page_timeout_ms,
        )

    async def fetch_html(self, url: str) -> str | None:
        # URL guard + HttpUrl validation (unchanged from 0.2.0.06a).
        ...
        await self._enforce_min_interval()
        # Crawl4AI's RL fires inside arun via the dispatcher.
        async with AsyncWebCrawler(config=self._browser_config) as crawler:
            result = await crawler.arun(
                url=str(validated),
                config=self._run_config,
                # Crawl4AI 0.8.6 accepts rate_limiter on single-URL arun too.
                rate_limiter=self._rate_limiter,
            )
        ...

    async def stream_many(self, urls: list[str]) -> AsyncIterator[...]:
        ...
        dispatcher = MemoryAdaptiveDispatcher(
            memory_threshold_percent=85.0,
            max_session_permit=max(1, int(self._rate_limit_per_minute) // 6),
            rate_limiter=self._rate_limiter,    # NEW
        )
        ...

    async def _enforce_min_interval(self) -> None:
        # Replaces the old _respect_rate_limit; just the floor, RL owns jitter.
        now = asyncio.get_running_loop().time()
        elapsed = now - self._last_request_at
        if elapsed < self._min_interval_s:
            await asyncio.sleep(self._min_interval_s - elapsed)
        self._last_request_at = asyncio.get_running_loop().time()
```

**Locked decision:** **A** — adopt `crawl4ai.RateLimiter`; replace `_respect_rate_limit` with `_enforce_min_interval` (floor) + library RL (jitter + backoff).

### D.3 — User-Agent rotation: yes/no, and where does the pool live?

Stealth mode (`enable_stealth=True`) patches `navigator.webdriver` and modifies browser fingerprints, but Crawl4AI's default UA is unchanged across requests — every Naavik scrape from a given operator looks like the same client. UA rotation thins the per-IP signature.

**Option matrix.**

| Option | A — Curated module-level pool of 8 modern UAs; round-robin per `Crawl4AIClient` instance (recommended) | B — Single hardcoded modern UA (no rotation) | C — Settings.scraper_user_agents JSON override |
| --- | --- | --- | --- |
| Capability | 8 distinct UA strings (latest Chrome Win/Mac/Linux, latest Firefox Win/Mac, latest Safari Mac, latest Chrome Android). Each `Crawl4AIClient.__init__` picks one (random or round-robin). One scraper instance per cron firing means 6 firings = 6 different UAs across the run. | Default UA shipped with Crawl4AI's `BrowserConfig`. Or one hardcoded. | Operator override; default pool if unset. |
| Cost | ~25 LOC: `_USER_AGENTS` module-level tuple in `src/scraper/user_agents.py` + selection helper. Tests assert pool size + rotation. | Zero. | Same as A + JSON shape + Settings UI form. |
| Risk — fingerprinting | LOW — UA rotation alone is shallow; LinkedIn / Indeed fingerprint on `sec-ch-ua` + canvas hash + WebGL + plugin enumeration. Crawl4AI stealth handles those. UA rotation reduces aggregated-log-traffic-pattern visibility — a defense-in-depth, not a primary control. | MEDIUM — every Naavik instance looks identical across requests. Easy to fingerprint as "Naavik traffic" if a vendor wanted to. | LOW + operator can break things by configuring stale UAs. |
| Risk — stale UAs | LOW — pool refresh is a one-line tuple update; refresh cadence ~quarterly aligns with Chrome stable cadence. Add a `# stale-after: YYYY-MM-DD` comment per row. | n/a. | HIGH — operator forgets to refresh; stale UA flags as bot. |
| Maintenance | Update one Python tuple every ~3 months. CI lint can assert "no UA older than 12 months" if we want to be paranoid. | None. | Two surfaces to maintain (default + operator overrides). |
| Lock-in | None. | None. | Some — once operators configure their own pools, Settings form locks in. |
| Industry precedent | Curated rotating pools are the default pattern for self-host scrapers (Scrapy's `random-user-agent` middleware, Crawlee's `pre_built_user_agents`). | Some sources (Browserless, Playwright defaults) use one. | Rare — most operator-facing UA controls are off/on flags, not custom pools. |

**Recommendation: A — curated module-level pool of 8 modern UAs; round-robin.**

**Reason 1: defense-in-depth.** UA rotation alone won't beat LinkedIn's fingerprinting, but stacked with stealth + jitter + random delays + per-source rate limits, it's a noticeable shift in our scraper's wire-level signature. The cost is ~25 LOC.

**Reason 2: no operator-facing surface to maintain.** Settings UI form stays clean. Operators can ignore UA rotation entirely — it just happens. Power users who want to swap UAs can edit `src/scraper/user_agents.py` and rebuild (low-frequency operation; same shape as the curated `_CLASS_ATTR_FALLBACK` rate-limit defaults).

**Reason 3: round-robin per `Crawl4AIClient` instance = per-firing rotation.** Scheduler constructs a fresh `Crawl4AIClient` per `_scrape_one_user` call (`scheduler/scraping.py:152-155`). Round-robin index lives on a module-level counter + lock — six firings (one per source) in one cron sweep see six different UAs.

**Trade-off accepted.** We carry the maintenance burden of refreshing 8 UA strings quarterly. Mitigation: a `# Last refreshed: YYYY-MM-DD` line at the top of the pool tuple + `tests/test_user_agents.py` smoke test (asserts pool size 8 + every entry contains a recognized browser product) so the refresh is visible.

**Pool composition (locked).** Eight modern UAs sampling Chrome / Firefox / Safari across Windows / macOS / Linux / Android. Sample shape:

```python
# src/scraper/user_agents.py (new)

_USER_AGENTS: tuple[str, ...] = (
    # Chrome on Windows 11
    "Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 ...",

_rotator_lock = threading.Lock()

def pick_user_agent() -> str:
    global _rotator_index
    with _rotator_lock:

```

### D.6 — DNS TTL fold-in (closes 0.2.0.13a)

`url_guard._resolve_host` (`src/scraper/url_guard.py:58-72`) uses `@lru_cache(maxsize=256)` with no TTL. Hacker filed Issue #105 (`ROADMAP.md:227` row `0.2.0.13a`): cached DNS extends the rebinding TOCTOU window to process lifetime. Naavik's cron-driven scraping makes this exploitable in theory: a domain that resolves to a public IP during initial check (URL guard passes) but rebinds to RFC1918 before the actual fetch (Crawl4AIClient reuses the cached resolution + sends traffic to internal network).

**Option matrix.**

| Option | A — Replace `@lru_cache` with `cachetools.TTLCache(maxsize=256, ttl=60)` (recommended) | B — Drop the cache entirely | C — Lower `maxsize` to 16 (smaller LRU = faster cycle) |
| --- | --- | --- | --- |
| Capability | DNS lookups cached for ≤60s per host. Rebind TOCTOU window bounded to 60s. | DNS lookups happen every URL composition. | Same as A without TTL guarantee. |
| Cost — dep | New base dep `cachetools>=5.0,<6` (Python 3.12 compatible; pure-Python; nixpkgs `python312Packages.cachetools` available; MIT). | None. | None. |
| Cost — code | ~5 LOC: import + replace decorator with method on a module-level `TTLCache`. Existing tests update to clear the new cache (instead of `_resolve_host.cache_clear()`). | ~3 LOC: remove `@lru_cache`. | ~1 LOC: change `maxsize`. |
| Risk — DNS load | LOW — cron-driven; ~100 listings/hour aggregate (well under 100 unique hosts in 60s). Each DNS lookup is ~10ms; even an uncached run adds ~1s/firing total. | LOW per request; possible scrapy-style fan-out concern at higher scale (not Phase 2). | MEDIUM — under high churn, 16 entries evicts old hosts faster than 60s could; we get a different bug (LRU eviction-driven cache-miss patterns). |
| Risk — thread safety | LOW — `cachetools.TTLCache` is not thread-safe by default, BUT our use is single-process + single-asyncio-loop. The synchronous DNS lookup happens inside `url_guard.is_safe_destination` called from async code; no actual concurrent access. If we ever fanned out via threads, we'd add a `threading.Lock` (or use `cachetools.func.ttl_cache`). | None. | Same as A. |
| Convention parity | `cachetools` is the established Python TTL idiom; pure stdlib options (`functools.lru_cache` + manual expiry) are sketchier. | n/a. | Same as A's parity loss. |

**Recommendation: A — `cachetools.TTLCache(maxsize=256, ttl=60)`.**

**Reason 1: hacker's recommended fix.** Issue #105 explicitly named TTLCache(ttl=60) as the fix. We're closing their note; staying on the recommended path keeps the audit trail clean.

**Reason 2: cachetools is small, pure-Python, MIT-licensed, in nixpkgs.** `nix_versions` lookup confirms `python312Packages.cachetools` ships with current nixpkgs. Add `cachetools>=5.0,<6` to `pyproject.toml` base deps; flake just-works.

**Reason 3: TOCTOU window of 60s is the explicit security trade-off the hacker requested.** Dropping the cache (Option B) is theoretically purer but eliminates batching benefits; option C is a halfway measure with no real guarantee.

**Trade-off accepted.** New base dep. Mitigation: cachetools is ~3000 LOC of pure Python; supply-chain risk is low (10M+ downloads/month per PyPI). Compare to rapidfuzz which we already added in `0.2.0.09`.

**Shape.**

```python
# src/scraper/url_guard.py (modified)
from cachetools import TTLCache

_DNS_CACHE: TTLCache[str, tuple[str, ...]] = TTLCache(maxsize=256, ttl=60.0)


def _resolve_host(host: str) -> tuple[str, ...]:
    cached = _DNS_CACHE.get(host)
    if cached is not None:
        return cached
    try:
        info = socket.getaddrinfo(host, None, type=socket.SOCK_STREAM)
    except OSError as exc:
        log.debug("DNS resolution failed: host=%s err=%s", host, exc)
        return ()
    addrs = tuple({addr[4][0] for addr in info})
    _DNS_CACHE[host] = addrs
    return addrs
```

Tests that previously called `_resolve_host.cache_clear()` switch to `_DNS_CACHE.clear()`. Trivial port.

**Locked decision:** **A** — `cachetools.TTLCache(maxsize=256, ttl=60)`. Folds `0.2.0.13a` Issue #105 into this PR.

### D.9 — Per-source 429 → consecutive_scrape_failures interaction

`scheduler/scraping.py:_scrape_one_user` increments `Settings.consecutive_scrape_failures[source]` on `JobScrapeStatus.FAILED` (plan 35 § D.5). With Crawl4AI's RL retrying 429/503 internally (max_retries=2), three outcomes are possible:

1. **Recovery within RL retries** — Crawl4AI hits 429, backs off, succeeds on retry. From the scraper's POV: `fetch_html` returns HTML, no error. `JobScrapeRun.status = SUCCESS` or `PARTIAL`. Counter resets.

2. **Exhaustion within one URL** — Crawl4AI hits 429 + retries + still 429. `fetch_html` returns `None`; subclass's tier-1 catch records the error. Other URLs in the same scrape may succeed → `JobScrapeRun.status = PARTIAL`. Counter resets (PARTIAL is success-ish per plan 35 § D.5).

3. **All URLs exhausted** — every URL hits 429 + retries. `JobScrapeRun.status = FAILED`. Counter increments.

The question: should case 2 (PARTIAL due to RL exhaustion) count differently from case 1 (PARTIAL due to other reasons — single 404, etc.)?

| Option | A — No change to plan-35 semantics; PARTIAL resets the counter regardless of cause (recommended) | B — Tighter: PARTIAL with `raw_meta.rate_limit.hits > N` counts as FAILED for the counter |
| --- | --- | --- |
| Capability | Counter tracks "scraper got NOTHING three times in a row." Aligns with operator mental model. | Counter tracks "scraper was throttled three times in a row." More nuanced. |
| Cost | Zero — already shipped in plan 35. | ~15 LOC in cron + threshold tunable + tests. |
| Risk — alert fatigue | LOW — admin alert fires only on threshold-cross (2→3). Three consecutive RL-exhausted runs is a real signal worth alerting. | MEDIUM — alert fires on a softer signal. |
| Maintenance | None. | Threshold to tune (PARTIAL hits N). |

**Recommendation: A — no change.** Plan 35's semantics are right: the counter reflects "we shipped zero jobs three times consecutively." RL exhaustion is one cause among many; treating it specially fragments the alerting story without adding actionable signal. If operators want RL-specific alerts in the future, that's a `0.5.0.NN` observability row, not this plan.

**Locked decision:** **A** — counter semantics unchanged.

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| Crawl4AI 0.8.6 `RateLimiter` API differs from official docs | LOW | HIGH (refactor blocked) | Build smoke test in W1 that runs `RateLimiter(base_delay=(1,3), max_delay=30.0, max_retries=2, rate_limit_codes=[429, 503])` against the pinned `crawl4ai==0.8.6` import + asserts constructor accepts. | UA pool refresh forgotten; UAs go stale | MEDIUM | LOW (browsers degrade signature gradually) | `tests/test_user_agents.py` asserts the `# Last refreshed:` comment is < 365 days old (fails CI when stale). Cheap forcing function. |
