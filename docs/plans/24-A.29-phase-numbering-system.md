# 24 · A.29 Phase numbering system

## Goal

Replace the GitHub Project **Priority field** (`CRITICAL` / `HIGH` / `MEDIUM` / `LOW` — 4 buckets, no within-bucket order) with a **4-level semver-aligned task ID schema** (`<MAJOR>.<MINOR>.<PATCH>[.<POSITION>]`, e.g. `0.2.0`, `0.2.0.01`, `0.2.1.07`) where:

1. **3-level IDs ARE release versions.** `0.1.0` is the Phase 1 / MVP release. `0.2.0` is the Phase 2 release. PATCH bumps (`0.2.1`, `0.2.2`, …) are **thematic patch-epics** grouping related deferred / follow-up tasks.
2. **4-level IDs ARE tasks within a release.** Position is 2-digit zero-padded (`01..99`) for lex-sort stability. Position is **NOT priority** — every task within a release MINOR is equally required for that release to cut.
3. **Each release cuts a git tag + GitHub Release** via `phase-tasks.sh release <version> --cut`, atomically syncing `pyproject.toml`, `nix/package.nix`, `CHANGELOG.md`, and `git tag`.
4. **Conventional Commits are enforced** by extending `.claude/hooks/git/prepare-commit-msg` so commit subjects map mechanically to CHANGELOG sections (Added / Fixed / Security / etc.) per `keepachangelog.com` v1.1.0.

Ship `scripts/phase-tasks.sh` as the sole writer for task-ID + release-version mutations, composing with `scripts/gh-project.sh` for Issue title rewrites + map cache updates. Migrate **every** existing ROADMAP row + GitHub Issue + Milestone + Project Epic from the legacy two-level scheme (`A.29`, `PC.6a`, `2.12`, `DEF-05`) to the new semver schema in one atomic runbook (`scripts/A.29-phase-renumber.sh`). Frozen done IDs survive retroactively via a `redirects` map in `.claude/github-issue-map.json`.

## Why

User direction 2026-05-18 (revision 2): *"Task IDs ARE semver release versions. Position is the ID slot within a release, not priority. PRs ship at minimum patch-level meaningful work. We need to renumber our current roadmap and phases and everything — all the changes need to be synchronized with this new system."*

The legacy Priority field had three concrete failures the new schema fixes:

1. **No within-bucket order.** Six items at HIGH = no answer to "which HIGH ships first?". Manager's `next-unblocked` resolves ties by Project-board insertion order — invisible to the operator reading ROADMAP. The Priority Queue table at `ROADMAP.md:95` is hand-maintained because the data needed to derive it isn't in any one field. The new schema replaces the table with **release-version grouping** + ID-driven ordering within a release: `0.2.0.01` ships in the same release as `0.2.0.14`, so they're equally required; ordering within is a forward-fill slot, not a priority statement.

2. **No release affordance.** Today `pyproject.toml` says `version = "0.1.0"` while Phase 1 shipped 2 weeks ago and we've shipped A.11–A.28 since — those should have bumped to `0.1.1`, `0.1.2`, …. The version is stale because there's no operational primitive for "cut a release." `phase-tasks.sh release <version> --cut` fixes that.

3. **CLI/vault sunset blocks operator surface growth.** Per AGENTS.md § Key Conventions § CLI, no new `naavik` subcommands. The script-based primitive (`scripts/phase-tasks.sh`) is the right surface — sibling of `gh-project.sh` + `agent-memory.sh`, not a CLI extension, not a vault scope.

The user-raised second-order issue: under strict 4-level lex-sort (`0.2.0.01 < 0.2.0.12`), today's "Phase 2 task `2.12` (vault sunset) is highest priority within Phase 2" becomes operationally **irrelevant** — Phase 2 = the `0.2.0` release; all sub-tasks `0.2.0.01..0.2.0.NN` are equally required for the release cut. Priority within a release dissolves into the release-cut gate. Same insight applies to DEF-01..DEF-25 (Phase 1 deferred backlog) — they're not "Phase 1 polish" anymore; they're **post-0.1.0 patch-epics** grouped thematically (security / UI / scrapers) and shipped as `0.2.1`, `0.2.2`, `0.2.3` minor-releases interleaved with the `0.2.0` cut.

The new directive — full retroactive renumber — expands migration scope from "Phase 2 only" to **every row + every ID + every cross-reference**. Migration runbook becomes the centerpiece deliverable (§ D.12 + § D.19).

ROADMAP row: `ROADMAP.md:465` (A.29 → `0.1.4.01` post-migration). GitHub: Issue #71. Sequencing override accepted 2026-05-18 — A.29 now ships **before** Tier-2 (vault + CLI sunset) so the sunset PRs land on the new schema. Closes Phase A milestone entirely after merge (Phase A → `0.1.0`–`0.1.3` retroactive mapping; A.29 itself = `0.1.4.01`).

## Proposal

The plan splits into **13 design decisions** (D.1–D.13 carrying forward from REV-1 plus **D.14–D.19** new) — each with option matrix or locked rationale — plus **5 build waves** (REV-1 had 4; release ceremony + retroactive renumber expand into a fifth). Decisions 1–8 + 11–13 were locked at the original brainstorm; D.14–D.19 land in this revision per user's REV-2 directive. Option matrices below re-validate each by surfacing the alternatives considered (or "no viable alternative — accept lock").

### D.1 — Position cap: 2-digit zero-padded `01–99` slots within a release MINOR

REVISED in REV-2: position is no longer a priority signal — it's an ID slot within a release MINOR. Every `0.2.0.NN` is equally required for the `0.2.0` cut. Forward-fill ordering for ID-assignment convenience only.

The position component still needs to be **lexicographically sortable as a string** AND **human-readable** AND **provide enough headroom** that a release doesn't run out of slots mid-flight.

| Option | Capability (slots) | Cost (refactor) | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **A. 2-digit `01–99` zero-padded** (LOCKED) | 99 per release | Low — `printf '%02d'` everywhere | Release exhausts at task 99 (unlikely; largest historic phase is Phase A at ~19 active + ~15 done = 34). When hit, split into a patch (`0.2.0` exhausts → next batch becomes `0.2.1`). | Trivial | Low — extends to 3-digit by widening regex |
| B. 3-digit `001–999` | 999 per release | Same as A + 1 char | Visually noisier; reads like a build number. | Same as A | Same as A |
| C. Unpadded `1–99` | Same as A but `10 < 9` lex-sort breaks | Cheap to write, expensive to sort | Lex-sort returns wrong order; every consumer needs a custom numeric comparator. | Forever-paying cost on every read site. | High |
| D. No position (3-level only — every PR = one task = one tag) | Simplest | Misreads user direction "PRs at minimum patch level" as "every PR cuts a tag" — see D.14.1 dismissal | Tag explosion (~30 tags per release-MINOR if each task tags) | OK | Medium |

**Recommendation: A.** Locked. Trade-off accepted: if any release MINOR exhausts 99 slots (would require scope explosion), promote the overflow into a follow-up PATCH or split the MINOR. **Reframe vs REV-1:** position no longer carries priority — it's purely a stable slot for script-driven sort within a release. Lex-sort stability is the only reason to retain zero-padding.

### D.2 — Three-level sub-phases superseded by semver MAJOR.MINOR.PATCH

REVISED in REV-2: the legacy "sub-phase" notion (`1.5.01`, `2.5.07`) goes away. Sub-phases dissolve into semver:

- "Phase 1.5 transitional bucket" → just a sequence of PATCH releases under MINOR 0.1 (`0.1.1`, `0.1.2`, …).
- "Phase 2.5 agent-system follow-ups" → folds into `0.1.X` patches (Phase A retroactive) OR into `0.2.X` thematic patches per D.14.2.

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **A. Pure 4-level semver `MAJOR.MINOR.PATCH.POSITION`** (LOCKED) | Releases + tasks in one schema; no parallel sub-phase axis | Migration cost — Phase 1.5/Phase 2.5 milestones dissolve | Medium — every reference to "Phase 1.5" needs rewrite | Low (single coherent schema) | Medium one-time, low forever |
| B. Keep sub-phase axis as 5-level (`0.1.5.0.01`) | Backwards compat with legacy "Phase 1.5" terminology | Schema gets ugly; consumers parse 5 dots | Medium | High | High |
| C. Two parallel schemas (sub-phases keep `1.5.01`, releases use `0.2.0`) | Avoid migration | Mixed schema forever; consumers branch on shape | Very high | Very high | Very high |

**Recommendation: A.** Locked. Trade-off accepted: every reference to "Phase 1.5" / "Phase 2.5" in archived plans + agent prompts + AGENT_OPS rewrites to the equivalent release-version. Migration script handles this mechanically.

REVISED in REV-2: under the original framing, position == priority. Under the new framing, position is a slot within a release, equally-required-with-its-siblings. Priority dissolves into **release-cut ordering** — `0.2.0` ships before `0.3.0` because MAJOR.MINOR sorts that way; within `0.2.0`, all sub-tasks are equally required.

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **A. Deprecate Priority field entirely** (LOCKED) | One source of truth — release-version. No within-release priority. | Rewrite `cmd_create_issue` to drop `--priority`; rewrite `cmd_next_unblocked` sort key; rewrite `cmd_sync` Priority-drift branch (delete); rewrite `cmd_backlog_by_epic` epic-priority logic | Medium — every caller assumes Priority exists; missing the rewrite anywhere yields silent fallback to default Priority | Trivial after migration | Low — Project field stays in the board (we don't delete option IDs via API); just stop reading/writing |

| C. Map position to Priority verbatim | One field, two readers | Field becomes a string not single-select | Worse than A | Worse than A | Very high |

**Recommendation: A.** Locked. The rationale flips from REV-1: instead of "position is the priority," it's "release-version IS the priority signal; within a release, no priority exists." Operator reads: "0.2.0 is the next release; all 0.2.0.NN sub-tasks must close before 0.2.0 cuts." Trade-off accepted: existing `priority:critical` / `priority:high` labels stay on Issues for backwards compat (`/sync-roadmap` won't touch them); only the *Project field* is removed from the write path. Migration: `scripts/A.29-phase-renumber.sh` leaves Priority field intact (we don't drop options via GraphQL — too risky) but every write site stops touching it. **The Project Priority field becomes vestigial — present in the board UI but unmaintained.** Optional cleanup after merge: delete the field via Project settings web UI (one click).

### D.11 — `scripts/phase-tasks.sh` interface spec (REVISED — adds release / deps / bump)

The script is the **sole writer** for task-ID + release-version mutations. It composes with `scripts/gh-project.sh` (Issue/Project Status/Body — sole writer for that surface) — they coexist, not replace.

#### D.11.1 — Subcommand surface (expanded)

```
phase-tasks.sh <subcommand> [args] [--dry-run]

# Read-only
list <version> [--status <s>] [--include-done]      # e.g. list 0.2.0 [--status open]
check                                                # lint ROADMAP vs Issue titles vs map cache vs pyproject.toml + flake.nix vs git tags
next-unblocked <version>                             # next open task in <version>, lex-asc, gated by deps

# Mutating (each acquires ~/.naavik/phase-tasks.lock flock)
insert <version>.<pos> "<title>" [--effort E]       # shift pos+ down by 1
defer <task-id> [--by N=1 | --to <new-pos>]         # move down within release
prioritize <task-id> [--by N | --to <new-pos>]      # move up within release
move <task-id> <new-version>.<new-pos>              # cross-release relocate
renumber <version>                                   # compact active gaps (skips done rows)
rename-release <old> <new>                           # bulk rename (e.g. 0.6.0 → 1.0.0)
deps <task-id> [add <dep-id> | remove <dep-id> | list | check]   # cross-task / cross-version dep graph

# Release ceremony (new — D.15)
bump <type> [--dry-run]                              # --major / --minor / --patch — preview which tasks ship in bumped version
release <version> [--cut] [--no-tag]                 # bundle release ceremony — pyproject + flake + CHANGELOG + git tag + GH release

# Sync (composition with gh-project.sh)
sync [--apply]                                       # rewrite Issue titles to match ROADMAP
```

#### D.11.2 — Per-subcommand contract (REVISED for 4-level IDs)

**`insert <version>.<pos> "<title>" [--effort E]`** — e.g. `insert 0.2.0.05 "AI extraction retry policy"`.
- Args: `version` is 3-level (e.g. `0.2.0`); `pos` is 2-digit (e.g. `05`); title quoted.
- Side effects:
  1. ROADMAP: find the release-version's table; rows with `pos ≥ <pos>` AND status != `[x]` shift down by 1; new row inserted at `<pos>` with title + status `[ ]` + Notes empty.
  2. Issue title rewrite per shifted Issue (composed via `gh issue edit #N --title "[<new-id>] <title>"`).
  3. New Issue creation via `scripts/gh-project.sh create-issue 0.2.0.05 "<title>" [--effort E] --milestone "0.2.0"`.
  4. Map cache update via `scripts/gh-project.sh` (it's the sole writer; `phase-tasks.sh` invokes it).
- Idempotency: re-running `insert 0.2.0.05 "Same title"` when `0.2.0.05` already has that title → no-op.
- Failure modes: shell metachar in title → reject; `<pos>` occupied by `[x]` row (frozen) → fail with diagnostic + suggest `insert 0.2.0.<pos+1>`; flock contention → retry with backoff.
- Atomicity: ROADMAP edits + Issue rewrites in transaction — write `ROADMAP.md.tmp` first, only `mv` after all GitHub ops complete; on failure delete `.tmp` + log.

**`defer <task-id> [--by N=1 | --to <new-pos>]`** — e.g. `defer 0.2.0.05 --by 2` shifts to `0.2.0.07`. Within same release-version only.

Failure mode: old release rollback succeeds but new release rollback fails → orphan ID. Mitigation: write `ROADMAP.md.tmp` covering BOTH source + dest releases; rollback if any Issue rewrite fails.

**`list <version> [--status <s>] [--include-done]`** — read-only. Parses ROADMAP § release-version. JSON or table output.

**`check`** — lint without mutating. Compares:
1. ROADMAP rows vs Issue titles (composed via `gh-project.sh`).
2. ROADMAP version-headers vs `.claude/github-issue-map.json:milestones` keys.
3. `pyproject.toml [project] version` field vs latest closed release MINOR.
4. `nix/package.nix` version attribute vs latest closed release MINOR.
5. `git tag --list` vs `.claude/github-issue-map.json:milestones` keys (every closed release should have a tag).
Reports drift per category. Exit 0 if clean. Exit 1 on any mismatch.

**`next-unblocked <version>`** — returns the next-open task ID in `<version>`, lex-asc, where:
- Task is `[ ]` or `[~]` in ROADMAP.
- All `blocked_by` deps (per D.17) are `[x]`.

**`renumber <version>`** — compact active gaps. Done rows unchanged, active rows compact (e.g. `0.2.0.01 [x], 0.2.0.02 [x], 0.2.0.04 [~], 0.2.0.06 [ ]` → `0.2.0.01 [x], 0.2.0.02 [x], 0.2.0.03 [~], 0.2.0.04 [ ]`).

Bulk: rewrites every `0.6.0.NN` ID to `1.0.0.NN`, every Issue title, every Milestone name, every plan-archive `Implements:` reference. High-risk; surface confirmation gate via AskUserQuestion if invoked from agent context.

**`deps <task-id> [add <dep-id> | remove <dep-id> | list | check]`** — see D.17.

**`release <version> [--cut] [--no-tag]`** — bundle release ceremony. See D.15.

**`sync [--apply]`** — composition wrapper. For each row in ROADMAP, ensure Issue title matches `[<task-id>] <title>` and map cache key matches. `--apply` rewrites; default dry-run.

### D.14 (NEW) — Semver version mapping schema

The schema itself. User locked the shape (`MAJOR.MINOR.PATCH[.POSITION]`); option matrix re-validates.

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **A. `MAJOR.MINOR.PATCH[.POSITION]`** (LOCKED, matches user example `0.2.0.1`) | 3-level = release; 4-level = task within release. Position zero-padded 2-digit. Pure semver alignment. | Migration cost (mapped above) | Medium | Low | Low |
| B. `MAJOR.MINOR.PATCH-pos.POSITION` (semver pre-release marker) | Explicit "task within release" semantics | Verbose; consumers parse two patterns | Medium (regex more complex) | High | Medium |

### D.15 (NEW) — Release ceremony: `phase-tasks.sh release <version> [--cut]`

Specifies the release-ceremony flow. The script bundles 10 mechanical steps that today are scattered across pyproject + flake + git + GitHub Releases UI.

**Flow:**

1. **Pre-flight gates.**
   - Verify all sub-tasks under `[Epic] <version>` are `[x]` (closed Issues + ROADMAP rows). Exit non-zero if any open.
   - Verify git tree clean. Exit non-zero if dirty.
   - Verify `git tag --list <version>` returns empty. Exit non-zero if tag exists.
   - Acquire `~/.naavik/phase-tasks.lock` flock.

2. **Compute CHANGELOG section.** Read closed Issues under `[Epic] <version>` + PR squash subjects + Conventional Commits classification (per D.16). Group by Added / Changed / Deprecated / Removed / Fixed / Security.

3. **Update `pyproject.toml`.** Set `[project] version = "<version>"` (3-level only — strip `.POSITION` if a task-level version was passed).

4. **Update `nix/package.nix`.** Set `version = "<version>";` attribute.

5. **Write CHANGELOG.md release section.** Prepend new release block to existing CHANGELOG. Format per D.16.

6. **Commit bookkeeping.** Single commit with subject `chore(release): <version>` + body listing closed Issues + breakdown by CHANGELOG section. Per AGENT_OPS § 8 BOOKKEEPING convention.

7. **`git tag <version>`.** Annotated tag with the same body as the release commit.

8. **Push tag to origin.** `git push origin <version>`.

9. **`gh release create <version> --notes-from-tag --generate-notes`.** Creates GitHub Release; auto-generates additional notes from PR list.

10. **Close the version's epic Issue.** Composed via `gh-project.sh set-status <epic-issue#> Done`.

**`--cut` flag** distinguishes dry-run (just print the plan) from actual mutation. Halts at user gate before step 6 (the commit point); user confirms with `--cut` or aborts. `--no-tag` skips steps 7–9 (used for migration commit; A.29 itself runs `release 0.1.4 --no-tag` because the tag gets created via the migration script post-merge).

**Cross-reference to A.27** (deferred to Phase 2.5 → now `0.2.X` patch-epic per D.6): A.27 (`develop` branch workflow move) MUST address version-tag implications when scheduled — release branches per MINOR? release-branch promotion ceremony? Doesn't matter now; A.27 owns it. Plan-frontmatter comment added in § Cross-references.

- `phase-tasks.sh deps <task-id> add <dep-id>` — records `<task-id> blocked_by <dep-id>`. Updates inverse on `<dep-id>` (`blocks` ← `<task-id>`). Idempotent.
- `phase-tasks.sh deps <task-id> remove <dep-id>` — inverse.
- `phase-tasks.sh deps <task-id> list` — prints both `blocks` + `blocked_by` for the task.
- `phase-tasks.sh deps check` — verify: (1) no cycles in DAG, (2) no closed-blocking-open inconsistency (closed task `[x]` listed in someone's `blocked_by` is OK; open task in `blocked_by` of a `[x]` task is an inversion), (3) all referenced IDs exist in the issue map.

**Integration:** `scripts/gh-project.sh:cmd_next_unblocked` consults the deps store. A task is "blocked" if any entry in its `blocked_by` is `[ ]` or `[~]`. `next-unblocked` returns the lex-asc-first ID that's not blocked.

**Cross-release deps:** explicitly supported (`0.2.1.05 blocked_by 0.2.0.07` — patch waits on a 0.2.0 task). Useful when a patch fix depends on a feature from the main release.

### D.18 (NEW) — Conventional Commits enforcement (extending `prepare-commit-msg`)

Extend `.claude/hooks/git/prepare-commit-msg` to validate commit format. Reject (exit 1) if commit subject doesn't match:

```
^(feat|fix|chore|docs|refactor|test|perf|build|ci|style|deprecate|remove)(\([a-z0-9-]+\))?!?: .+$
```

Plus body-level checks:
- `BREAKING CHANGE:` footer present → require `!` after type/scope (`feat!:` or `feat(auth)!:`).
- `BREAKING CHANGE:` in pre-1.0 (current scope) → allow MINOR bump; in post-1.0 → force MAJOR.

**Allowed bypass:** `git commit --no-verify` (per existing convention).

**Branch-aware enforcement:** the hook reads `git rev-parse --abbrev-ref HEAD`. On `main` (BOOKKEEPING commits) the hook **does NOT enforce** strict Conventional Commits (preserves existing "chore: bump roadmap" / "docs: update CLAUDE.md" patterns). On feature branches the hook DOES enforce.
