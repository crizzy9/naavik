# Plan 88 / `0.7.0.47` — Restore signup-form access when `signup_disabled`

## Goal

Reverse the dead-end introduced by `0.7.0.45` (PR #210 squash `2f63c4c`). When the operator explicitly hits `/login?mode=signup` on a single-user instance with an existing User row, the page MUST render the signup form (not the signin form) — paired with the existing amber banner explaining the gate AND a link to `/setup-help` for recovery options. Also restore the "First time? Create account" link on `/login` so the operator has a discoverable path to signup mode.

## Why this is urgent (owner bug report 2026-05-24)

> "My signup is still broken. I am not able to signup. The signup button cannot be found on the login screen anymore. … when i go to /login?mode=signup it still just doesnt work and looks like the login page only not a create account page."

Reproduced via live orchestrator (`.naavik/db` had `qa-plan86@example.com` from plan 86 QA + `allow_multiple_users=False`):

- `curl /login` → renders `Welcome back` signin form with NO `Create account` link anywhere.
- `curl /login?mode=signup` → renders `Welcome back` signin form + amber banner.

There is **no UI path** for the operator to (a) attempt a fresh signup (which would 403 with a useful inline error card) or (b) discover the recovery flow on `/setup-help`. The only escape is to manually `psql ... DELETE FROM "user"` or `rm -rf .naavik/db` — both undocumented from the surface they're stuck on.

## Root cause

`0.7.0.45` (commit `2f63c4c`) solved a real-but-minor UX problem (operator misclicks `/login?mode=signup`, sees banner-only with no signin form, has to manually navigate back to `/login`) by rewriting `is_signup = _requested_signup and not signup_disabled` at the top of `src/ui/templates/pages/login.html`. Side effect: every downstream branch (heading, form action, submit button label, password autocomplete, alt-mode CTA) collapses to signin mode when `signup_disabled=True`, even when the operator explicitly requested signup mode via the query string. The same commit hid the "First time? Create account" CTA on `/login` via `{% elif not signup_disabled %}`.

The "dead-end" the 0.7.0.45 commit referenced was overstated — the pre-0.7.0.45 banner already carried a "Sign in" link (line 39 of the pre-0.7.0.45 file: `<a href="/login" class="font-medium underline underline-offset-2 hover:text-amber-50">Sign in</a>`), and the signup form had an "Already have an account? Sign in" footer link. The fix introduced a worse asymmetry: the operator who genuinely needs to signup has no path forward.

## Design decision (no option matrix — defaults obvious)

| Option | Chosen | Rationale |
|---|---|---|
| **A** — Restore `is_signup = _requested_signup`; show banner above signup form when `signup_disabled` + `?mode=signup`; restore "First time? Create account" link unconditionally; banner gains `/setup-help` link | ✅ | Honors the operator's explicit intent (they typed `?mode=signup`); the banner contextualizes the gate; the form's existing "Already have account? Sign in" footer covers the "misclick recovery" the 0.7.0.45 fix targeted; the `/setup-help` link gives a destructive-recovery affordance for the forgotten-password case |
| B — Keep 0.7.0.45 behavior + add prominent "Need to reset?" link in the banner pointing to `/setup-help` | ✗ | Still removes the operator's explicit signup intent; the redirect-to-signin feels disrespectful when the operator typed `?mode=signup` |
| C — Auto-redirect `/login?mode=signup` → `/setup-help` when `signup_disabled` | ✗ | Surprising; throws the operator into a different page they didn't ask for |

**Selected:** Option A.
