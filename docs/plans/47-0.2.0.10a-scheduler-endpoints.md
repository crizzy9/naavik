# 47 · 0.2.0.10a — Operator scheduler endpoints (list / run / pause / resume)

## Goal

Ship the four operator-facing scheduler endpoints under `/api/v1/scheduler/*` that plan 35 § D.7 referenced as pre-existing but never actually shipped. These give the operator their only visibility-and-control surface over APScheduler-registered crons until the `0.2.5.04` scraper-run history UI ships: list registered jobs (id / next_run_time / trigger summary / paused), trigger a one-off NOW run of a registered job, pause a job, resume a paused job. Pure API plumbing on top of the lifespan-managed `AsyncIOScheduler` already exposed at `src/scheduler/__init__.py:33-35` via `get_scheduler()`.

## Why

ROADMAP row `0.2.0.10a` (line 199) filed via PR #109 architect review (Issue #110). Plan 35 § D.7 promised the endpoints; the engineer correctly skipped the smoke test when the router was absent. **Priority bumped LOW → MED 2026-05-20** via release-readiness audit — until `0.2.5.04` (scraper-run history page, LOW) ships, this is the operator's only path to (a) confirm crons registered, (b) trigger an out-of-band re-run after editing `Settings.linkedin_keywords` etc., (c) pause a misbehaving scraper without restarting the app or editing Postgres directly. Mechanical scope; ~150 LOC of new code + 8 tests.

## Proposal

### D.1 — New router `src/api/scheduler.py`

One module exposing 4 endpoints on `APIRouter(prefix="/api/v1/scheduler")`. Acquire the scheduler handle via the already-exposed `scheduler.get_scheduler()` (lifespan-set; see `src/scheduler/__init__.py:33-35`). Returns 503 if the lifespan failed and `get_scheduler()` is None (graceful path — scheduler boot is opt-in in tests / boot-edge dev cases per `src/main.py:99`).

Pydantic v2 response models co-located in the same file (per project convention — `src/api/settings.py` does the same; not enough surface for `src/models/`):

```python
class SchedulerJobInfo(BaseModel):
    id: str
    name: str
    next_run_time: datetime | None      # None when paused
    trigger: str                         # str(job.trigger) — "cron[*/30 * * * *]" or "interval[5400s]"
    max_instances: int
    coalesce: bool
    paused: bool                         # derived from next_run_time is None
    pending: bool                        # job.pending

class SchedulerJobList(BaseModel):
    running: bool                        # scheduler.running
    jobs: list[SchedulerJobInfo]
```

Endpoints (each `_user: User | None = Depends(require_authed_session)`; mutations also `_csrf: None = Depends(require_csrf)` — mirrors `src/api/auth.py:283-291` canonical pattern):

| Endpoint | Method | Status on success | Body |
|---|---|---|---|
| `/api/v1/scheduler/jobs` | GET | 200 | `SchedulerJobList` |
| `/api/v1/scheduler/jobs/{job_id}/run` | POST | 202 | `{"queued_job_id": "<job_id>-manual-<uuid8>", "scheduled_at": "<iso>"}` |
| `/api/v1/scheduler/jobs/{job_id}/pause` | POST | 200 | `SchedulerJobInfo` (post-pause snapshot) |
| `/api/v1/scheduler/jobs/{job_id}/resume` | POST | 200 | `SchedulerJobInfo` (post-resume snapshot) |

Error contract — unknown `job_id` raises `apscheduler.jobstores.base.JobLookupError`; map to `HTTPException(404, detail="job <id> not found")`. Scheduler not running → 503 `{"detail": "scheduler not started"}`. Re-export `require_csrf` from `src.api.auth` (the canonical home; same import used by plan 44).

**One-off run design (the only design decision).** APScheduler has no `run_job_now()`. Two viable options:

| Option | Pros | Cons | Pick |
|---|---|---|---|
| **A. `scheduler.modify_job(job_id, next_run_time=datetime.now(UTC))`** | One call; preserves trigger; APScheduler reschedules to "now" then resumes cron afterwards. | **Mutates the registered cron's next_run_time** — coalesce + max_instances cover idempotency, but the cron's natural cadence shifts forward until next firing realigns. | no |
| **B. `scheduler.add_job(job.func, DateTrigger(run_date=datetime.now(UTC)), id=f"{job_id}-manual-{uuid4().hex[:8]}", max_instances=1, coalesce=True)`** | Original cron untouched. New transient job runs once and self-removes. Idempotency per-invocation via unique `id`. | One extra row briefly in `apscheduler_jobs` table; auto-removed by APScheduler after fire. | **yes** |

Picked **B**. Original `scraping.<source>` cron's next_run_time is the operator's contract surface; we don't tamper with it. The `max_instances=1` on the original cron prevents the original from firing in parallel with the manual run if the natural cadence happens to hit during the manual window — APScheduler enforces uniqueness by `id`, and the manual `id` differs from the original by suffix so they're considered separate jobs (so `max_instances=1` on the original protects the original; identical `func` invocations from both jobs CAN overlap if the operator triggers manual during cron firing window, but the underlying `_scrape_source` body runs inside its own `async with async_session()` and is per-(user,source) isolated already — see `src/scheduler/scraping.py:218-224`). Acceptable for an operator-triggered command.

Resolve the function for the manual `add_job` from the source job's `job.func` reference (APScheduler 3.x `Job.func` returns the resolved callable). Pass `args=[]` / `kwargs={}` (the scraping cron bodies take no arguments by design — see `src/scheduler/scraping.py:230-251`).

### Risk + mitigation

| Risk | Likelihood | Impact | Mitigation |
| ---- | ---------- | ------ | ---------- |
| Concurrent manual `/run` invocations spawn N transient jobs (no rate limit) | LOW | LOW | Each transient job has a unique `id` suffix; APScheduler's per-job `max_instances=1` is irrelevant across distinct ids. The underlying `_scrape_source` body iterates Settings rows inside `async with async_session()` (`src/scheduler/scraping.py:220`) — race is bounded by per-source lock-free design. Acceptable for self-host. If abuse surfaces, a follow-up adds per-IP rate-limit using existing `is_rate_limited` (`src/services/auth.py:?`) pattern. |
| `JobLookupError` import path varies across APScheduler 3.x minor versions | LOW | LOW | Canonical is `from apscheduler.jobstores.base import JobLookupError` per APScheduler 3.10+ docs; pinned in `uv.lock`. Test 7 catches regressions. |
| `scheduler.get_scheduler()` returns None during cold-start race (lifespan `start()` still mid-flight) | LOW | LOW | The 503 branch in § D.1 handles it; the lifespan boots before the first request per FastAPI semantics (`lifespan` awaited before `yield` per `src/main.py:97`). Test 8 covers it. |
| Operator triggers `/run scraping.linkedin` during natural cron firing window → two concurrent `_scrape_source` invocations against same user × source | LOW | MEDIUM | `_scrape_one_user` re-reads `Settings` (`scraper_service.run_scraper` re-INSERTs `JobScrapeRun`); `upsert_job` is idempotent on `(user_id, source, external_id)` per plan 27. Dup runs at most produce two `JobScrapeRun` rows — operator sees both in `0.2.5.04` history UI. Acceptable; documented in § D.4 README note. |
| Re-exporting `require_csrf` creates a new import cycle if `src/api/scheduler.py` imports `src/api/auth.py` while `src/api/auth.py` ever imports from `src/api/` | NEGLIGIBLE | LOW | `src/api/auth.py` doesn't import from `src/api/scheduler.py`; same one-way pattern already in use at `src/ui/routes/discover.py` (plan 44). |

## Out of scope (deferred)

- **`/jobs/{job_id}` GET single-job-detail.** Not required for the 4-endpoint contract; `GET /jobs` already lists detail per job. Add later if `0.2.5.04` UI needs per-row detail beyond the list response.
- **`/jobs/{job_id}/history` GET recent `JobScrapeRun` rows.** That's `0.2.5.04`'s scope, not this row's.
- **DELETE / unregister job.** Crons are statically registered at lifespan boot; the operator's lever is pause/resume, not delete. Restarting the app is the supported way to drop a cron.
- **Per-user authorization on scheduler ops** (multi-tenant). Current substrate is single-operator self-host (`require_authed_session` returns any authed user). Multi-tenant scheduler authz is part of the auth refactor that retires fake-session; not in this row.

- Do NOT touch `src/services/vault.py` (vault deleted per 0.2.0.01).
- Do NOT add a new env var, on-disk path, port, or scheduled job — this is a pure HTTP read/control plane over existing crons.

- Do NOT add an Alembic migration — no schema change. The `apscheduler_jobs` table (the SQLAlchemyJobStore-managed pickle blob row store) handles transient job insert/delete itself; the operator-visible schema is unchanged.
