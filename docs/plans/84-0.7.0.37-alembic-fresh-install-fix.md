# 84 · 0.7.0.37 — Fix alembic 0001 fresh-install duplicate-column race

## Goal

Make `nix run .#dev` from an empty `.naavik/` directory boot cleanly to the
signup page. Today it crashes during `alembic upgrade head` because
`migrations/versions/0001_initial.py:41` calls
`SQLModel.metadata.create_all(checkfirst=False)`, which snapshots the LIVE
in-memory model state (every column added across 0001-0022). 0002 then
`op.add_column("settings", "allow_multiple_users", ...)` against a column
that already exists → `DuplicateColumnError`. Plan 84 rewrites 0001 to
emit explicit `op.create_table` calls for the 0001-era schema (no `create_all`
of live state) so the migration chain replays correctly from empty.

## Why

Owner directive 2026-05-21: force first-time signup via fresh-install
`nix run .#dev`. Plan 83 (PR #198) DELETED the auto-seed dev user + the
`~/.naavik/dev-credentials` artifact, intending the user to land on `/signup`.
Architect-as-reviewer of PR #198 ran the manual QA — fresh-install boots fail
on the alembic race; the user-visible signup flow cannot be exercised
end-to-end until this is fixed (filed as Issue #199 / `0.7.0.37` HIGH).

Why the bug went undetected for months: the race only fires on **fresh-install
(`rm -rf .naavik/` + boot)**. Incremental development (preserved `.naavik/db/`)
hits each migration once with empty target columns — no double-create. The
existing `tests/test_alembic_NNNN.py` files each spin up ephemeral sqlite +
`metadata.create_all(LIVE)` THEN apply one migration in isolation — they
verify the migration's intent against the live schema, not the migration
chain replay from `0001 → head`. Plan 83 chasing fresh-install UX was the
first surface that exercises the chain on an empty DB; the regression was
latent since plan 10 (commit `14dd578`, 2026-05-02).

Concrete race surface (worse than first reported in Issue #199):

- **43 `op.add_column` calls** across 0002-0022, against columns the current
  model includes → `create_all(LIVE)` creates them in 0001 → `add_column` in
  NNNN re-creates → `DuplicateColumn`. Half-list: `Settings.allow_multiple_users`
  (0002), `User.must_change_password` (0003), `Job.external_id` /
  `remote_policy` / `seniority_level` / etc. (0005), `Job.duplicate_of_id`
  (0006), 5 `Settings` scraper-input columns (0007), `Settings.scraper_rate_limits`
  (0008), `Settings.auto_apply_immediate_dispatch` (0011), 4 settings columns
  (0013), 2 settings JWT columns (0014), `Settings.auto_apply_adapter_confidence_threshold`
  (0016), `Profile.semantic_match_threshold` etc. (0017), 6 settings/application
  columns (0018), 2 settings columns (0019), `Profile.score_history` (0020),
  2 settings columns (0021).
- **30 `op.drop_column` calls** across 0004 / 0007 / 0008 / 0011 / 0014 /
  0016-0021, against columns the current model NO LONGER has → `create_all(LIVE)`
  doesn't create them in 0001 → `drop_column` in NNNN fails on missing column.
  Most-bitten: 0004 drops 5 vault-derived columns that no longer exist in
  `models.Settings`; even reaching 0004 in fresh-install boot would crash.
- **7 `op.create_table` calls** across 0010 / 0012 / 0013 / 0014 (×2) / 0017
  / 0005 (table = `job_scrape_run`) — all reference tables the LIVE model
  defines → `create_all(LIVE)` creates them in 0001 → `create_table` in NNNN
  re-creates → `DuplicateTable`.

Total: ~80 race points across the chain. Today's boot dies at the FIRST one
(0002's `add_column`) but the underlying foot-gun affects every subsequent
migration.

Why option A (`op.create_table` rewrite of 0001) over B/C/D — see § Proposal § D.1.

## Proposal

Single PR; 1-2 commits. Rewrites `migrations/versions/0001_initial.py` so it
no longer touches `SQLModel.metadata` at runtime. Adds a chain-replay test.
No application code changes; no schema changes; no new env / CLI / on-disk
artifact / port / scheduled job surface.

   existed at 2026-05-02 (commit `14dd578`).
3. Preserve every CHECK constraint per `docs/design/DATA_MODEL.md § E`
   (including the corrected `Application.applied_at` form covering DRAFT

5. Preserve every Postgres ENUM type backing the StrEnum vocabulary that
   existed at 0001 time (some ENUMs were added later — e.g. `visarestriction`
   in 0005, `remotepolicy` in 0005, `senioritylevel` in 0005, `jobscrapestatus`
   in 0005, `closedreason` in 0022 — exclude those from 0001).
6. Keep `op.execute("CREATE EXTENSION IF NOT EXISTS vector")` at the top of
   `upgrade()` (unchanged — plan 13 / `0001` decision; pgvector reservation
   pre-Phase 6).
7. `downgrade()` becomes the inverse: explicit `op.drop_table(...)` in
   reverse-dependency order + `op.execute("DROP EXTENSION IF EXISTS vector")`.
   Do NOT use `SQLModel.metadata.drop_all` (same footgun in reverse).
8. Remove the `import models` line (no longer needed — DDL is explicit).

Authoring estimate: ~600 LOC for `upgrade()` + ~50 LOC for `downgrade()`.

#### `tests/test_alembic_0001_chain_replay.py` — NEW

Verification harness that catches this class of regression for future plans:

```python
"""Round-trip: empty DB → alembic upgrade head → equals metadata.create_all(LIVE).

Tests the migration CHAIN (0001 → head) not individual migrations in isolation.
The existing tests/test_alembic_NNNN.py files each verify ONE migration against
the LIVE model state; they cannot catch a 0001-creates-too-much regression.
This test boots an empty Postgres (or sqlite for the fast path), runs alembic
upgrade head, then compares the result to metadata.create_all(LIVE). They must
be equivalent.
"""
import subprocess
from pathlib import Path
import pytest
import sqlalchemy as sa
from sqlmodel import SQLModel
import models  # registers metadata

def _columns_for_table(inspector, table):
    return {c["name"]: c["type"].__class__.__name__ for c in inspector.get_columns(table)}

@pytest.fixture
def chain_replayed_engine(tmp_path, monkeypatch):
    """Apply 0001 → head against an ephemeral sqlite, return engine."""
    db_path = tmp_path / "chain.db"
    url = f"sqlite:///{db_path}"
    monkeypatch.setenv("DATABASE_URL", url.replace("sqlite", "sqlite+aiosqlite"))
    subprocess.run(
        ["uv", "run", "alembic", "upgrade", "head"],
        check=True, capture_output=True, cwd=Path(__file__).parent.parent,
    )
    return sa.create_engine(url)

@pytest.fixture
def reference_engine(tmp_path):
    """metadata.create_all against ephemeral sqlite, return engine."""
    url = f"sqlite:///{tmp_path / 'reference.db'}"
    engine = sa.create_engine(url)
    SQLModel.metadata.create_all(engine)
    return engine

def test_chain_replay_table_set_matches_metadata(chain_replayed_engine, reference_engine):
    chain_tables = set(sa.inspect(chain_replayed_engine).get_table_names())
    ref_tables = set(sa.inspect(reference_engine).get_table_names())
    # alembic_version is in chain but not in metadata — exclude.
    assert chain_tables - {"alembic_version"} == ref_tables

def test_chain_replay_columns_match_metadata(chain_replayed_engine, reference_engine):
    chain_insp = sa.inspect(chain_replayed_engine)
    ref_insp = sa.inspect(reference_engine)
    for table in set(sa.inspect(reference_engine).get_table_names()):
        chain_cols = set(_columns_for_table(chain_insp, table).keys())
        ref_cols = set(_columns_for_table(ref_insp, table).keys())
        assert chain_cols == ref_cols, (
            f"Table '{table}' column-set diverges: chain only={chain_cols - ref_cols}, "
            f"metadata only={ref_cols - chain_cols}"
        )

def test_0001_does_not_use_metadata_create_all():
    """Regression guard for the 0.7.0.37 root cause.

    0001_initial.py must not call SQLModel.metadata.create_all — that snapshots
    the LIVE in-memory model state and races with 0002+ adds/drops. Fail loud
    if a future author re-introduces this footgun.
    """
    body = (Path(__file__).parent.parent / "migrations" / "versions" / "0001_initial.py").read_text()
    assert "metadata.create_all" not in body, (
        "0001_initial.py uses SQLModel.metadata.create_all — see ROADMAP 0.7.0.37 / Issue #199. "
        "Use explicit op.create_table calls for the 0001-era schema."
    )
```

If sqlite chain-replay is impractical (some 0005/0013/0017 migrations have
postgres-only `op.execute("CREATE TYPE ...")` / pgvector ops), gate the
table/column-set tests on a sqlite-friendly subset OR run against a real
postgres only when `NAAVIK_LIVE_DB=1` is set (existing convention per
`AGENTS.md` and `tests/test_jwt_rotation_routes.py:55`). The regression
guard `test_0001_does_not_use_metadata_create_all` MUST run unconditionally
(it's a static-text check; no DB needed).
