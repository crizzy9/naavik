# 45 · 0.2.0.11d — Jinja `csrf_token` template-context injection

## Goal

Close the cross-cutting `csrf_token` Jinja-context defect surfaced at PR #138's Manual QA gate (and pre-existing since plan 18, 2026-05-17): every HTMX POST currently sends `X-CSRF-Token: ""` in production because no code path threads the `naavik_csrf` cookie into the template context, so `base.html:28` interpolates the `csrf_token | default('')` filter to empty. Production HTMX clicks on `/discover` Save/Skip/Auto-submit and the `/auth/change-password` form all 403 against the (correctly-functioning) `require_csrf` gate until this lands. Fix wires `csrf_token` as a Starlette `Jinja2Templates(context_processors=[...])` callable at `src/ui/templates_setup.py` — one place, ~10 LOC, covers all 40 `TemplateResponse` callsites without per-handler edits, and future-proofs the convention.

## Why

ROADMAP row `0.2.0.11d` (line 204, filed via PR #138 hacker + architect parallel reviews; Issue #139) is the canonical follow-up. The defect lives in `src/ui/templates/base.html:7,28` where two interpolations expect a non-empty `csrf_token`:

```html
<meta name="csrf-token" content="{{ csrf_token | default('') }}">
<body hx-headers='{"X-CSRF-Token": "{{ csrf_token | default("") }}"}' …>
```

`grep -rn "csrf_token" src/` (run during architect research) confirms zero `csrf_token` keys are set on any `TemplateResponse` ctx dict — `templates_setup.py` registers four globals (`STATUS_DOT_COLORS`, `TAG_VOCAB`, `APP_Q_OPTIONS`, `APP_Q_LABEL_MAPS`, `app_q_label`), none of which is per-request. The `naavik_csrf` cookie IS set on login/signup/change-password by `_set_session_cookies()` (`src/api/auth.py:70-101`), and `validate_csrf()` (`src/services/auth.py:159-163`) reads it via the `Cookie(alias=CSRF_COOKIE)` parameter on `require_csrf` — but the template never gets to see it. The HTMX `hx-headers` global interpolation thus always renders `X-CSRF-Token: ""`, which fails the explicit empty-string check `if not cookie_token or not header_token` in `validate_csrf` → 403.

**HIGH because UX-blocking, not security.** The security boundary (`require_csrf`) is correct — `tests/test_discover_csrf.py` and `tests/test_auth.py:342-426` prove it via TestClient injection of cookie+header. But production HTMX flow can't satisfy the gate without this fix. Two browser-facing surfaces are degraded today:

1. **`/discover` Save / Skip / Auto-submit** — newly CSRF-gated in PR #138. Every honest swipe 403s.
2. **`/auth/change-password`** — CSRF-gated since plan 18 (2026-05-17). Every forced-rotation flow 403s. The defect was latent (path is reached only on first-login or voluntary change) so it never tripped CI; surfaced now because PR #138's manual QA actually clicked the HTMX UI instead of TestClient-injecting cookie+header.

`docs/design/JOB_UI.md § E.4` (graduated 2026-05-20 via PR #134) explicitly forward-points to this plan; this row also closes the architect's noted memory candidate: "template variable wiring requires evidence-backed risk row."

## Proposal

### D.1 — Option matrix: three fix shapes

The architect dispatch brief explicitly called the fix-shape choice out as a design decision. Three viable options:

**Option A — `Jinja2Templates(context_processors=[csrf_token_processor])` (native Starlette).** Pass a sync callable to `Jinja2Templates` at construction time in `templates_setup.py`. Starlette merges the dict returned by every registered processor into every `TemplateResponse(request, name, ctx)` call's context. Processor reads `request.cookies.get("naavik_csrf", "")` and returns `{"csrf_token": value}`.

**Option B — Per-handler `Depends(csrf_token_ctx)` + manual ctx-key add.** Define `def csrf_token_ctx(naavik_csrf: str | None = Cookie(default=None, alias="naavik_csrf")) -> str: return naavik_csrf or ""` as a FastAPI dependency. Every UI route that returns `templates.TemplateResponse(...)` adds `_csrf_token: str = Depends(csrf_token_ctx)` to its signature and `ctx["csrf_token"] = _csrf_token` to its dict.

**Option C — Wrap / monkey-patch `templates.TemplateResponse`.** Replace the method with a factory that inspects `request.cookies` and auto-injects `csrf_token` into the passed ctx dict before delegating to the original Starlette method. Implementation choices: monkey-patch (overwrite the bound method) or write a `_NaavikJinja2Templates` subclass that overrides `TemplateResponse`.

| Dimension | A: `context_processors` (native) | B: per-handler `Depends` | C: TemplateResponse wrapper |
|---|---|---|---|
| **Capability** | Covers all 40 `TemplateResponse` callsites with one registration. Native Starlette mechanism designed for exactly this (the documented example reads `request.cookies`). | Covers all 40 callsites only if engineer touches all 40 callsites correctly. | Covers all 40 callsites; reaches even ad-hoc third-party templates that use the shared `templates` instance. |
| **Cost** | ~5 LOC: 1 sync function + 1 constructor-arg edit at `src/ui/templates_setup.py:13`. | ~80 LOC: new dep helper + 40 callsite edits across 7 route modules. Engineer paper cut multiplier. | ~15 LOC: subclass / monkey-patch in `templates_setup.py`. Non-trivial to test in isolation. |
| **Risk** | Starlette restricts processors to **sync** callables (documented). The processor reads `request.cookies.get(...)`, which is sync property access — safe. No async I/O, no DB. Low risk. | High — drift trap. Future routes can silently forget the dep + ctx-key add. Engineer review of 40 callsites is error-prone. | Monkey-patching FastAPI/Starlette internals is non-idiomatic + couples to Starlette internals. A 1.x → 2.x Starlette upgrade may break the wrap. |
| **Maintenance** | Future routes auto-inherit `csrf_token`; one canonical source of truth. | Every future UI route needs the dep + ctx-key add — perpetual drift surface. | Future routes auto-inherit, but the indirection is hidden state — `grep csrf_token` won't reveal the source. |
| **Lock-in** | Standard documented API; replaceable. | Locks 40 handlers into the convention; refactor cost grows linearly. | Locks the codebase to Starlette internals across upgrades. |

### D.2 — Recommendation: Option A

**Lock Option A.** Lowest LOC, lowest risk, lowest maintenance, future-proof. Starlette's `context_processors` parameter was added expressly for "inject per-request value into every template context" use cases; the official docs use cookies as the example. The sync-only constraint is a non-issue because reading `request.cookies` is a sync property access — no async I/O involved. Option B's drift trap (40 callsites today, will grow to ~70 by end of 0.2.0) and Option C's hidden-state / Starlette-internal coupling both lose on every dimension that matters.

**Trade-off accepted.** Option A means `csrf_token` is implicitly available in every template — including pages that don't strictly need it (e.g. `/login`, `/onboarding`). That's strictly safer than the converse, and matches how the four existing globals (`STATUS_DOT_COLORS` etc.) already work.

### D.3 — Implementation

File: `src/ui/templates_setup.py`

Add a sync context-processor function and pass it to `Jinja2Templates` at construction. Drop-in change — no other files in `src/` touched.

```python
"""Shared Jinja2Templates instance + global registrations.

Every UI router imports `templates` from here so:
- `templates.env.globals` registrations (STATUS_DOT_COLORS, TAG_VOCAB, etc.) are
  visible everywhere
- Starlette `context_processors` (csrf_token, ...) inject per-request values
  into every TemplateResponse(request, name, ctx) render — covers all 40
  callsites without per-handler edits. Plan 45 (0.2.0.11d).
- A single template directory is configured once
"""

from fastapi.templating import Jinja2Templates
from starlette.requests import Request

from services.auth import CSRF_COOKIE
from ui.template_helpers import APP_Q_LABEL_MAPS, APP_Q_OPTIONS, app_q_label


def _csrf_token_ctx(request: Request) -> dict[str, str]:
    """Inject the `naavik_csrf` cookie value into every template context.

    Plan 45 (0.2.0.11d, 2026-05-20). Closes the cross-cutting defect where
    `base.html:28`'s `hx-headers` interpolation rendered `X-CSRF-Token: ""`
    because no route handler set `csrf_token` in the template context.

    Returns `""` (the existing `| default('')` filter fallback) when the
    cookie is absent — landing pages, unauthenticated callers, the
    onboarding fake-session — keeping the empty-token-rejects-empty-token
    invariant that `validate_csrf` already enforces.

    Sync per Starlette's documented constraint (async context processors
    are not supported); `request.cookies` is a sync property — safe.
    """
    return {"csrf_token": request.cookies.get(CSRF_COOKIE, "")}


templates = Jinja2Templates(
    directory="src/ui/templates",
    context_processors=[_csrf_token_ctx],
)

# … existing globals (STATUS_DOT_COLORS, TAG_VOCAB, …) unchanged …
```

Three substantive edits:

1. **Add import** `from starlette.requests import Request` (top of file).
2. **Add import** `from services.auth import CSRF_COOKIE` (top of file; avoids hardcoding the cookie name).
3. **Define `_csrf_token_ctx`** (sync function returning `dict[str, str]`).
4. **Pass `context_processors=[_csrf_token_ctx]` to `Jinja2Templates(...)` constructor**.

Net diff: ~12 LOC added in one file. Zero handler edits.

### D.4 — Tests

Two new tests, plus a small update to the existing `test_change_password_page_renders_with_banner_when_flagged` test to assert the fix is durable. All three are full-page render tests — they exercise the actual Jinja interpolation path that the HTMX flow uses in production.

**File: `tests/test_csrf_jinja_ctx.py` (new).**

```python
"""Plan 45 (0.2.0.11d) — `csrf_token` Jinja context-processor.

Two regression tests for the cross-cutting defect surfaced at PR #138's
Manual QA gate: rendered HTML must carry the cookie's CSRF value in
`base.html`'s `hx-headers` JSON attribute + the `<meta name="csrf-token">`
tag — not the empty-string `| default('')` fallback that the production
HTMX flow currently hits.

Both tests render through TestClient with a `naavik_csrf` cookie set; the
goal is to prove the context-processor reads the cookie + writes it to the
template ctx. Without the fix, the rendered string is `X-CSRF-Token: ""`;
with the fix it's `X-CSRF-Token: "<token>"`.

Per `architect-plan-quality-bar`, this is the "would-have-caught-it" test
that the existing `test_change_password_page_*` pair missed because they
ran with no cookies.
"""

from __future__ import annotations

import os

os.environ.setdefault("NAAVIK_BCRYPT_COST", "4")
os.environ["NAAVIK_PERSISTENCE"] = "memory"


def test_discover_page_renders_csrf_token_from_cookie() -> None:
    """Plan 45: rendering `/discover` with `naavik_csrf=<tok>` cookie set
    surfaces `<tok>` in `base.html`'s `hx-headers` JSON + `<meta>` tag.

    The pre-fix behavior was `X-CSRF-Token: ""` regardless of cookie
    presence. The post-fix behavior interpolates the cookie value.
    """
    from fastapi.testclient import TestClient

    from main import app
    from services.auth import require_authed_session

    async def _bypass_auth():
        return None

    app.dependency_overrides[require_authed_session] = _bypass_auth
    try:
        client = TestClient(app, raise_server_exceptions=True)
        tok = "test-csrf-token-aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"
        r = client.get("/discover", cookies={"naavik_csrf": tok})
    finally:
        app.dependency_overrides.pop(require_authed_session, None)

    assert r.status_code == 200
    # base.html:28 hx-headers interpolation
    assert f'"X-CSRF-Token": "{tok}"' in r.text
    # base.html:7 meta-tag interpolation
    assert f'name="csrf-token" content="{tok}"' in r.text


def test_change_password_page_renders_csrf_token_from_cookie() -> None:
    """Plan 45: rendering `/auth/change-password` with `naavik_csrf` set
    threads the cookie value into the page so the HTMX form-POST carries
    `X-CSRF-Token: <tok>` instead of `""` (the latent defect since plan 18).
    """
    from fastapi.testclient import TestClient

    from main import app
    from models import User
    from services.auth import get_current_user

    def _fake_user() -> User:
        return User(
            id=1,
            email="dev@local",
            password_hash="$2b$04$placeholder.hash.for.test.only",
            is_active=True,
            is_admin=True,
            must_change_password=True,
        )

    app.dependency_overrides[get_current_user] = _fake_user
    try:
        client = TestClient(app, raise_server_exceptions=True)
        tok = "test-csrf-token-bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb"
        r = client.get("/auth/change-password", cookies={"naavik_csrf": tok})
    finally:
        app.dependency_overrides.pop(get_current_user, None)

    assert r.status_code == 200
    assert f'"X-CSRF-Token": "{tok}"' in r.text
    assert f'name="csrf-token" content="{tok}"' in r.text


def test_discover_page_empty_csrf_token_when_cookie_absent() -> None:
    """Plan 45: absent `naavik_csrf` cookie → rendered `csrf_token` is `""`
    (preserves the `validate_csrf` empty-rejects-empty invariant).

    This is the "before fix" defect's stable rendering — useful as a guard
    against accidental misconfig (e.g. processor returning a fresh
    `issue_csrf_token()` would silently issue a new token per render and
    break the double-submit cookie/header pairing).
    """
    from fastapi.testclient import TestClient

    from main import app
    from services.auth import require_authed_session

    async def _bypass_auth():
        return None

    app.dependency_overrides[require_authed_session] = _bypass_auth
    try:
        client = TestClient(app, raise_server_exceptions=True)
        r = client.get("/discover")
    finally:
        app.dependency_overrides.pop(require_authed_session, None)

    assert r.status_code == 200
    assert '"X-CSRF-Token": ""' in r.text
```

### Risk + mitigation

| Risk | Likelihood | Impact | Mitigation |
|------|------------|--------|-----------|
| Context-processor receives a non-`Request` arg (e.g. a `WebSocket` or `Scope`) under some Starlette code path → AttributeError on `.cookies` | LOW | LOW | Starlette's `Jinja2Templates.TemplateResponse(request, name, ctx)` always passes a `Request` to processors; the new Starlette signature requires `request` as the first positional arg (already used at every callsite in `src/ui/routes/*`). No WebSocket templates exist. |
| Processor returns `""` when `naavik_csrf` cookie is absent → matches the existing empty-string defect, silently re-introduces the bug for unauthenticated landing pages | LOW | LOW | This is the **correct behavior**. `validate_csrf` rejects empty-cookie/empty-header pairs (`src/services/auth.py:159-163`); landing pages legitimately have no CSRF state. Issuing a fresh token per render (a tempting alternative) would BREAK the double-submit invariant because the rendered token wouldn't match the cookie. The `_set_session_cookies` flow on `/login`+`/signup`+`/change-password` is the canonical token-issuing path. **Risk closed by design** — the empty-string fallback is intentional. |
| Test `test_discover_page_empty_csrf_token_when_cookie_absent` regresses if a future processor issues a token on absent cookie | LOW | LOW | This test is the explicit guard against that. Keep it. |
| Per-render cost of `request.cookies.get(...)` adds measurable latency | LOW | LOW | `request.cookies` is a parsed `MultiDict` cached on the request; `.get(...)` is O(1). 40 callsites × <1μs is negligible. |
| Tests that bypass `auth_cookies` fixtures (rendering pages without setting `naavik_csrf`) now render an empty `csrf_token` — same as before; existing tests don't read `csrf_token` from the body | LOW | LOW | Confirmed by grep: zero existing tests assert on the rendered `csrf_token` string. § D.4 introduces the first three. |
| Starlette upgrades break the `context_processors` argument | LOW | LOW | Native API since Starlette 0.27 (2023); part of the stable public contract. Naavik pin is `>=0.30` via FastAPI. |
| `_csrf_token_ctx` is named with a leading underscore but is referenced by passing into the constructor — engineer mistakes it as a private helper not meant to be wired up | LOW | LOW | Leading underscore is idiomatic Python for "module-private"; the constructor-arg pass IS the wire-up. Tests prove it's wired (assert rendered HTML carries cookie value). |
