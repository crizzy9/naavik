# 35 · `0.2.0.10` — APScheduler periodic scraping (six per-source crons)

## Goal

Register six `scraping.<source>` cron jobs against the existing lifespan-managed `AsyncIOScheduler` so the six site scrapers shipped in `0.2.0.07` fire on schedule, persist Jobs through `scraper_service.run_scraper`, AI-enrich via `job_extractor.enrich_raw_job` when the user has an LLM provider configured, and feed the Discover UI with fresh listings without any operator intervention. The work is pure wiring — no new substrate. New file `src/scheduler/scraping.py` holds the six job bodies (one per `JobSource.value` in `scraper.sites:scrapers`); `src/scheduler/jobs.py:register_all` is extended to register them with operator-configurable cron expressions sourced from per-user `Settings.source_schedules` with `BACKEND.md § I.1` defaults; `Settings.sources_enabled` gates each firing; existing `Settings.{linkedin,workday,greenhouse,lever,ashby,indeed}_companies` lists drive `ScrapeQuery` content. On approval, the plan content graduates into `docs/design/SCHEDULER.md` — the canonical reference for APScheduler conventions, per-source cron defaults, failure-handling tiers, and the per-user dispatch contract every downstream cron (scoring, notifications, dedup-sweep, OAuth refresh) inherits.

Five forces, ordered by load:

### D.1 — Where do per-source schedules live?

The crux call. Plan 35 has to source one cron expression per source per user. Three placements.

| Option | A — `Settings.source_schedules: dict[str, str]` with hard-coded defaults if absent (recommended) | B — Hard-code in `scheduler/scraping.py`, no operator override | C — New env vars (`SCRAPING_LINKEDIN_CRON`, etc.) |
| --- | --- | --- | --- |
| Capability | Per-user override via Settings UI; default fallback to `BACKEND.md § I.1` if key absent. Already exists on the DB model (`models/settings.py:73-76`). Already updateable via `settings_service.update_sources` (`settings_service.py:86-105`). | Operator must edit code + redeploy to change a cron cadence. | Operator override via `.env`; defaults in `config.py`. Adds 6 env-var slots; LinkedIn schedule + Indeed schedule + 4 ATS-flavored schedules. |
| Cost | Zero new schema. Zero new code path. ~5 LOC helper to resolve `settings.source_schedules.get(source.value, _DEFAULTS[source.value])`. | Zero infrastructure. Single source of truth in code. | Zero new schema. ~24 LOC in `config.py` (6 new fields + 6 cron-string validators). Documentation in `.env.example` + `SCRAPER_SITES.md § H` + README § Configuration. |
| Risk | LOW — `source_schedules` is `dict` typed, no migration needed. Existing UI form-wiring in `settings/sources.html` (per `BACKEND.md § I.2`). Operator confusion if Settings UI is empty + defaults apply silently — mitigated by per-source UI placeholder showing the default. | MEDIUM — operator can't tune without a code change. Self-hosters running on slow hardware can't slow LinkedIn from 30min → 60min. | MEDIUM — env-var sprawl: each new source adds an env slot. 6 new slots is a lot for the post-vault env-only pattern. Also: multi-user instances (Phase 2+ cloud tier) can't have per-user cron schedules via env. |
| Maintenance | Add new source → key in `_DEFAULTS` dict + UI form row. | Add new source → edit `register_scraping_jobs` + redeploy. | Add new source → env var slot + config field + validator + UI surface. |
| Lock-in | None — `Settings.source_schedules` is JSON; can hold any future per-source cron expression. | Strong — operators expect to tune via Settings UI per `BACKEND.md § I.2 line 515`. Changing to env later is a UX regression. | Medium — env-only model assumes single-tenant. Multi-tenant cloud tier needs per-user, not per-instance. |

**Recommendation: A — `Settings.source_schedules: dict[str, str]` with hard-coded defaults if key absent.** Three reasons:

1. **The DB model already has the field.** `Settings.source_schedules: dict = Field(default_factory=dict, sa_column=Column(JSONB, ...))` at `models/settings.py:73-76`. The `settings_service.update_sources` mutator at `settings_service.py:86-105` accepts a `source_schedules` dict update. The Settings UI form-handler `update_sources` was wired in Wave 4 (plan 10) ready for this consumer. Plan 35 is the consumer; no new column, no new migration, no new mutator.

2. **`BACKEND.md § I.2 line 515` already promised this.** Quote: *"Configurable schedule. Per-source schedules editable via Settings · Sources tab; persisted to `Settings.source_schedules` (JSON)."* The contract names this exact field. Plan 35 honors the lock.

3. **Multi-user readiness.** Phase 2+ cloud tier will run multiple users on one instance. Each user wants their own schedules (cheap-tier user wants LinkedIn every 4 hours to save Crawl4AI costs; power user wants 15 min). Per-user `Settings.source_schedules` scales. Per-instance env vars don't.

**Trade-off accepted.** A operator running the dev orchestrator without ever opening Settings · Sources gets the hard-coded defaults (LinkedIn 30min etc.) silently. Mitigation: the Settings UI form (`0.2.0.11` UI work) displays the resolved cron string in a read-only placeholder when `source_schedules[source.value]` is unset. For 0.2.0.10 we just need the defaults baked into `scheduler/scraping.py:_DEFAULT_SCHEDULES` and a getter that falls back to them.

**Locked decision (zoom-through):** **A** — `Settings.source_schedules.get(source.value, _DEFAULT_SCHEDULES[source.value])`.

### D.2 — Per-user dispatch: how does one cron firing dispatch across users?

Phase 2 is single-user (Phase 1 plan 10b shipped `Settings.allow_multiple_users = False` default at `models/settings.py:89`). Phase 2+ cloud tier is multi-user. The cron has to work today (one user, one firing per source) and not require rewriting when multi-user lands.

| Option | A — Iterate `Settings` rows inside the job body (recommended, mirrors `process_auto_apply_queue` pattern) | B — One cron job per (user_id, source) — N×6 jobs in the jobstore | C — Hard-code `user_id=1` for Phase 2 |
| --- | --- | --- | --- |
| Capability | One job per source. Job body opens session, queries `select(Settings).where(sources_enabled[source.value] != False)`, runs `scraper_service.run_scraper(...)` per row. Multi-user adds zero infrastructure — just rows. | Pre-creates `scraping.linkedin.<user_id>` per (user, source) pair at signup. Each user_id gets independent schedule + independent JobScrapeRun. | Trivial: single firing, fixed user_id. |
| Cost | One job per source (6 total). Per-firing per-source: 1 session + N Settings rows queried + N `run_scraper` calls (one per active user). At N=1, ~zero overhead. | Per-user signup hook adds 6 jobs; per-user delete-account hook removes them. Net 6N jobs in the jobstore. For 100 users = 600 jobs. APScheduler handles 600 fine; the operational burden of orphaned jobs after user deletion is real. | Zero. |
| Risk | LOW — pattern matches `application_service.process_auto_apply_queue` at `application_service.py:524-603` which iterates all auto-apply-enabled users in one job firing. Failures isolate per-user (try/except around `run_scraper` per user). | MEDIUM — signup-flow coupling. User signs up at 14:00; APScheduler reschedule jobs must fire before the user expects scraping to start. User-delete hook drift = orphan crons running against deleted users. | HIGH — multi-user (Phase 2+) needs a rewrite. |
| Maintenance | Single per-source job; per-user is iteration internal. New source → 1 job to register. New user → 1 Settings row to seed. | Add new source: 1 new job per existing user → +N jobs. Add new user: 6 new jobs. Settings.source_schedules update → reschedule N×6 jobs in one transaction. Wave 6 plumbing. | None now; substantial later. |
| Lock-in | None — pattern survives multi-user transition without code changes. | Strong — once jobs are per-(user, source), backing out is painful. | Throwaway — requires rewrite to ship multi-user. |

**Recommendation: A — iterate Settings rows inside the job body.**

**Reason 1: mirror existing canonical pattern.** `application_service.process_auto_apply_queue(session, user_id=None, notify_fn=None)` iterates across `Application(status=DRAFT, queue_state=QUEUED_FOR_AUTO_APPLY)` joining to Settings per-user, gates on `s.auto_apply_enabled`, caps via `s.auto_apply_daily_cap`. The `scheduler/jobs.py:auto_apply` body is 27 LOC, mostly Settings/Application iteration. Plan 35 mirrors this shape exactly:

```python
async def _scrape_source(source: JobSource) -> None:
    from db.session import async_session
    from models import Settings
    from sqlmodel import select
    async with async_session() as session:
        active = (await session.exec(
            select(Settings).where(
                # Plan 35: scrape for users who have NOT explicitly disabled the source.
                # Settings.sources_enabled is JSONB dict; an absent key implies "default enabled".
                # The Settings UI (0.2.0.11) writes explicit False to disable.
            )
        )).all()
        for s in active:
            if s.sources_enabled.get(source.value, True) is False:
                continue
            await _scrape_one_user(session, settings=s, source=source)
        await session.commit()
```

**Reason 2: multi-user scaling.** Cloud tier (Phase 2+) lands; new users get a row in `Settings`; the cron picks them up on the next firing. Zero ops work. Per-(user,source) job model needs a signup hook + reschedule transaction that gets tested + reviewed once multi-user is the priority — Phase 2 is not the right time for that overhead.

**Reason 3: failure isolation is per-user, not per-cron.** If LinkedIn returns 429 to user A's session-pool, user B's firing should still try. `_scrape_one_user` wraps each per-user `run_scraper(...)` in a try/except → log + `notifications.notify_admin_error(...)` + continue to next user. APScheduler retry (`misfire_grace_time=300`) reschedules the whole cron firing on infrastructure-level failures (DB unreachable, scheduler thread died), not per-user JobScrapeRun-level failures (which are already tracked in the `JobScrapeRun.status` enum).

**Trade-off accepted.** One firing iterates serially across N users. At N=1 (Phase 2 today): no-op overhead. At N=100 (future cloud tier): ~100 × ~3 min per source = 5 hours of wall-clock; longer than the 60-min cron cadence. **Mitigation reserved for `0.2.0.13`** (rate-limiting + anti-detection): when N grows past ~10, lift `_scrape_source` into per-user-fanout via `asyncio.gather(*users, return_exceptions=True)` capped by `Settings.scraper_concurrency_max` (new field in `0.2.0.13`). For 0.2.0.10 single-user, serial loop ships.

**Locked decision:** **A** — iterate Settings rows inside the job body; serial per-user; asyncio.gather fanout deferred to `0.2.0.13`.

### D.3 — LLM provider resolution per firing

Each cron firing needs an `LLMProvider` to pass into `ScraperBase.__init__(..., provider=...)` so `_BaseSiteScraper._maybe_enrich` (sites/_base_site.py:46-84) calls `enrich_raw_job`. Two placements.

| Option | A — Resolve via `llm.get_provider(session, settings)` per-user-iteration in the cron body (recommended) | B — Construct provider once at `register_all` time |
| --- | --- | --- |
| Capability | Per-user provider preference honored (one user on Anthropic, another on Ollama). Resolves fresh each firing — provider change in Settings UI takes effect on next cron run. | Single provider for all users; provider preference changes require app restart. |
| Cost | One `llm.get_provider(...)` call per active user per firing — synchronous + cheap (already cached by SDK). | Provider constructed once at lifespan startup; held in scheduler-module global. |
| Risk | LOW — pattern matches `llm/__init__.py:25-71` get_provider. Provider-unavailable (e.g. no `ANTHROPIC_API_KEY` set) raises `LLMProviderError`; cron logs + continues. | MEDIUM — module global = singleton across users (wrong for multi-user); breaks the Wave-4 LLMProvider-per-user pattern. |
| Maintenance | Cron body owns provider resolution + degradation. | scheduler/__init__.py owns provider, scheduler/scraping.py owns dispatch — two surfaces to keep aligned. |
| Lock-in | None. | Refactor needed at multi-user-flip. |

**Recommendation: A — resolve per-user-iteration via `llm.get_provider(session, settings)`.**

**Graceful degradation when provider unavailable.** Wave 4's `llm.get_provider(session=session, user_id=settings.user_id)` raises `LLMProviderError(kind="auth_required")` when (a) the user has not picked a provider, or (b) the env var for their picked provider is unset. The cron catches this, logs at WARNING (not ERROR — operator hasn't configured AI), and runs the scraper with `provider=None`. The `_BaseSiteScraper._maybe_enrich` shim short-circuits on `provider is None` (`sites/_base_site.py:61`) → scrapers persist Jobs with the scraper-provided `*_hint` enums + null extraction metadata. Discover UI surfaces the Jobs without AI-enriched skills/tags; scorer (0.3.0) runs on what's there. **Scraping must NOT depend on AI being available** — that's the single-most-common self-hoster paper cut.

```python
async def _scrape_one_user(session, *, settings, source) -> None:
    try:
        provider = await llm.get_provider(session=session, user_id=settings.user_id)
    except LLMProviderError as exc:
        log.warning("LLM provider unavailable for user=%s source=%s: %s", settings.user_id, source.value, exc)
        provider = None
    scraper_cls = scrapers[source.value]
    client = Crawl4AIClient(
        rate_limit_per_minute=scraper_cls.rate_limit_per_minute,
        random_delay_seconds=scraper_cls.random_delay_seconds,
    )
    scraper = scraper_cls(
        client=client,
        session=session,
        user_id=settings.user_id,
        provider=provider,
    )
    await run_scraper(
        session,
        scraper=scraper,
        user_id=settings.user_id,
        query=_compose_query(source, settings),  # see D.4
        triggered_by="cron",
    )
```

**Locked decision:** **A** — provider resolved per-firing per-user; failure mode logs + falls back to `provider=None`.

### D.4 — `ScrapeQuery` composition: where do per-source inputs come from?

The cron passes `ScrapeQuery` to `run_scraper`. Each source has different input requirements:

| Source | Input needed | Source of truth |
|---|---|---|
| LinkedIn | keywords + location | `Settings.linkedin_keywords` + `Settings.linkedin_location` (NEW — see below) |
| Workday | tenant slugs | `Settings.workday_companies: list[str]` (`models/settings.py:77-80`, exists) |
| Greenhouse | company slugs | `Settings.greenhouse_companies` (env-only, `config.py:41`); cron reads via `app_settings.greenhouse_companies` |
| Lever | company slugs | `Settings.lever_companies` (env-only, `config.py:42`); cron reads via `app_settings.lever_companies` |
| Ashby | company slugs | `Settings.ashby_companies` (env-only, `config.py:43`); cron reads via `app_settings.ashby_companies` |
| Indeed | keywords + location | `Settings.indeed_keywords` + `Settings.indeed_location` (NEW — see below) |

**Current asymmetry surface.** Plan 33 added `workday_companies` as a per-user DB-backed field (because Workday tenants are user-specific watchlists), but `greenhouse_companies` / `lever_companies` / `ashby_companies` as env-only (because ATS company-lists are operator-tier curation, not per-user). This asymmetry held under "scrapers run via test fixtures" — `0.2.0.07` test suites stuff `ScrapeQuery.company_filter` directly. The cron firing makes the asymmetry visible: LinkedIn + Indeed have NO `keywords` / `location` source today; the test fixtures pass them directly.

| Option | A — Add `Settings.{linkedin,indeed}_{keywords,location}` per-user DB-backed (recommended for plan 35; closes the asymmetry by making input always per-user) | B — Add `LINKEDIN_KEYWORDS` / `LINKEDIN_LOCATION` / `INDEED_KEYWORDS` / `INDEED_LOCATION` env-var slots (4 new slots) | C — Hard-code `ScrapeQuery()` with empty keywords, let scrapers default to "site:everything" |
| --- | --- | --- | --- |
| Capability | Per-user keyword + location tunable via Settings UI; matches LinkedIn's UX expectation ("which roles do you want notified about"). | Operator sets instance-wide search terms via env; same for all users. | Scrapers search broadly; user filters via Discover UI keyword filter. |
| Cost | Alembic 0007 adds 4 nullable columns (TEXT). Settings UI form-handler `update_sources` accepts 4 new optional kwargs. `_compose_query` reads 4 fields. | 4 new env vars + 4 validators + `.env.example` rows + README rows + SCRAPER_SITES.md update. | Zero schema, zero env. LinkedIn `_LIST_BASE` query degenerates to `?keywords=&location=&start=0&f_TPR=r604800` — likely returns the "all jobs" feed which is unbounded. Hits `query.max_listings=200` cap quickly. |
| Risk | LOW — pattern matches `Settings.workday_companies`; same migration shape; ~10 LOC alembic. | MEDIUM — env-only doesn't scale to multi-user (cloud tier). | HIGH — unbounded query against LinkedIn looks like a bot; risks IP block. Indeed similar. |
| Maintenance | New per-user field. Add to UI form. | New per-instance fields. Documented. | None — but unworkable. |
| Lock-in | None — fields can move to JSONB blob later if many search-filters proliferate. | Medium — env-only entrenches single-tenant. | None — but pattern doesn't work. |

**Recommendation: A — `Settings.{linkedin,indeed}_{keywords,location}` per-user DB-backed.** Three reasons:

1. **Symmetry with `workday_companies`.** Already per-user DB-backed for the same input-shape reason (operator wants per-user job-watching scope). Extending the same pattern to LinkedIn + Indeed keeps the model coherent. **A future cleanup row (filed as `0.2.0.13a` or similar) can fold the ATS company lists into Settings too** — but that's not in scope here; env-based ATS lists per `0.2.0.07` (PR #102 deviation) stay.

2. **Multi-user readiness.** Cloud-tier user A wants senior SWE / NYC; user B wants ML engineer / SF; user C wants product / remote. Per-user DB fields scale.

3. **The Settings UI form for source-configuration is on the `0.2.0.11` plan's deliverables list.** Adding 4 nullable columns now in 0.2.0.10's migration lets 0.2.0.11's UI work form-bind without a migration round-trip.

**Trade-off accepted.** Alembic 0007 ships in this plan. ~30 LOC migration; ~6 LOC SQLModel field additions; ~12 LOC `update_sources` mutator extension; ~10 LOC `_compose_query` reader; ~6 tests. Worth the simplicity gain.

**Locked decision:** **A** — Alembic 0007 adds `linkedin_keywords: list[str] | None`, `linkedin_location: str | None`, `indeed_keywords: list[str] | None`, `indeed_location: str | None`. Helper `_compose_query(source: JobSource, settings: Settings) -> ScrapeQuery` reads from these + `workday_companies` for the source-keyed dispatch.

**ATS company lists (`greenhouse_companies` / `lever_companies` / `ashby_companies`) stay env-only as plan 33 (0.2.0.07) shipped.** The cron resolves these via `config.settings` (the env-loaded `pydantic-settings` singleton) and passes them as `ScrapeQuery.company_filter`. Asymmetry note: until a future cleanup row promotes the env ATS lists to per-user DB-backed, multi-user cloud tier users SHARE the same ATS company lists. Acceptable for single-tenant today + the cleanup row (deferred to `0.2.0.13` or `0.2.5.X`) closes it before multi-user matters.

### D.5 — Failure handling: APScheduler retries vs JobScrapeRun status vs Discord alerting

Three layers of failure handling exist. Plan 35 has to decide which layer triggers what.

| Failure | Where caught | Action |
| --- | --- | --- |
| Scraper-fatal (auth invalid, site fully down) | `scraper.scrape()` raises → `scraper_service.run_scraper` catches at top level | `JobScrapeRun.status = FAILED` (or PARTIAL); `errors[]` includes `kind=fatal msg=...`; `log.exception(...)`; **does NOT raise out of `run_scraper`**. Cron continues to next user. |
| Per-listing tier-1 (rate-limited, parse-failure) | `scraper.scrape()` catches per-listing → appends to `self._errors` | `JobScrapeRun.status = PARTIAL` if some listings yielded; `errors[]` includes per-listing details. Cron continues. |
| `asyncio.CancelledError` (scheduler time-budget elapsed) | `scraper_service.run_scraper` catches separately | `JobScrapeRun.status = TIMED_OUT`; re-raises so APScheduler sees the cancellation. Cron job marked as crashed; next firing retries per misfire_grace_time. |
| Infrastructure-level (DB unreachable, scheduler thread died) | APScheduler core | `misfire_grace_time=300` reschedules within 5 min if scheduler comes back. Persistent failures stop the cron after 3 misses. |
| Consecutive-fail backoff per source | NEW — added in this plan via `_should_skip_consecutive_failures` | Read last N JobScrapeRun rows for `(user_id, source)` ordered DESC LIMIT 3. If all 3 are FAILED, skip this firing; log INFO with the count. Reset on first SUCCESS / PARTIAL. **Threshold = 3.** Per-source-per-user. |
| Critical operator alert | `notifications.notify_admin_error(...)` from cron body when consecutive failures hit threshold | Discord notification when consecutive-fail threshold trips. Honors `Settings.notify_on_errors=True` per `services/notifications.py:345-363`. |

| Option | A — Use APScheduler retries + JobScrapeRun history + auto-skip after 3 consecutive failures + Discord alert (recommended) | B — APScheduler retries only; let JobScrapeRun history accumulate fail rows without auto-skip | C — Cron job pauses itself after N consecutive failures via `scheduler.pause_job(<id>)` |
| --- | --- | --- | --- |
| Capability | Operator gets a one-time alert when LinkedIn starts failing; cron stops wasting credits on a fail-loop; auto-resume on first SUCCESS without operator intervention. | Cron runs every 30min forever, accumulating FAILED rows. Operator notices via Discover UI "no new jobs in 24h" feeling. | Cron stops; operator must manually resume via `POST /api/v1/scheduler/jobs/{name}/resume`. |
| Cost | ~30 LOC helper (read last 3 JobScrapeRun rows; gate on all-FAILED). One Discord webhook call per threshold-trip. | Zero. | Pause/resume API exists per `BACKEND.md § D.8`. ~10 LOC. |
| Risk | LOW — failure-state recovery is automatic (first SUCCESS unblocks). | MEDIUM — operator-blind failure mode; LinkedIn outage = silent. | MEDIUM — operator must manually intervene to resume; self-hoster on vacation = no scrapes for days. |
| Maintenance | One helper. One alert. | None. | One pause action. One resume action. Two operator surfaces. |
| Lock-in | None. | None. | Medium — once jobs auto-pause, the UI must surface "this job is paused, click to resume" — adds Settings UI work to 0.2.0.11. |

**Recommendation: A — auto-skip after 3 consecutive failures + Discord alert.** Three reasons:

1. **Self-hoster ergonomics.** A flaky source (LinkedIn returns 403 for an IP range; Workday tenant slug typo) shouldn't cost operator credits or look-like-it-still-works. Three consecutive FAILED rows is a clear signal something's wrong; one Discord alert tells the operator + skips future firings; first SUCCESS auto-resumes. No manual intervention needed in the happy-recovery case.

2. **Cost protection.** Each LLM-extraction is a paid call. A scraper that keeps hitting tier-1 errors but yields listings = wasted LLM credits on garbage extractions. Auto-skip on consecutive-FAILED breaks that loop.

3. **Discoverable failure mode.** The Discord alert ("LinkedIn scraping has failed 3x consecutively — auto-skipping until next manual trigger or first success") is a one-time push notification, not a recurring spam. Operator opens Settings · Sources (`0.2.0.11` UI work) to see the JobScrapeRun history per source and the auto-skipped status.

**Trade-off accepted.** The helper adds one DB query per firing (read 3 rows). At single-user-single-source = 1 query / 30 min = negligible.

**Locked decision:** **A** — auto-skip via 3-consecutive-FAILED check, single Discord alert on trip, auto-resume on first SUCCESS.

### D.6 — APScheduler trigger tuning: jitter + misfire_grace_time + max_instances

Tuning knobs for the 6 cron registrations:

- **`max_instances=1`**: prevents concurrent same-source firings. Existing pattern (`scheduler/jobs.py:145`). KEEP.
- **`coalesce=True`**: if scheduler missed N firings (process down), only fires once on resume instead of N times. Existing pattern. KEEP.
- **`misfire_grace_time=300`**: 5 min grace before scheduler gives up on a missed firing. Reasonable default for 30-90 min cadences. KEEP (matches APScheduler 3.x default-ish).
- **`jitter=30`**: NEW — random ±30s on each firing so the 6 scrapers don't all fire exactly on the minute, smearing CPU + memory + outbound HTTP. `CronTrigger(... jitter=30)`. **Adds jitter to all 6.**
- **`replace_existing=True`**: idempotent registration. Existing pattern. KEEP.

| Option | A — Add `jitter=30` on all 6 cron registrations (recommended) | B — No jitter; let crons fire on minute-boundaries |
| --- | --- | --- |

| Risk | LOW — jitter is an APScheduler standard knob. | MEDIUM — 6 simultaneous Chromium browsers under Crawl4AI = peak memory burst; one Postgres pool peak; one outbound HTTP burst flagged as bot. |

**Recommendation: A — add `jitter=30`.**

### D.8 — File layout + helper boundaries

`src/scheduler/scraping.py` is the new file. Contents:

```python
"""Phase 2 scraping crons — one job per JobSource in scraper.sites:scrapers.

Per docs/design/SCHEDULER.md § C (graduated from plan 35 § D.X). Each job
iterates Settings rows for users who have not disabled the source, resolves
their LLM provider for AI enrichment, composes a ScrapeQuery per source,
invokes scraper_service.run_scraper, and lets the per-listing tier-1 +
scraper-fatal tier-2 error handling persist results into JobScrapeRun.

Consecutive-failure auto-skip (D.5): if the last 3 JobScrapeRun rows for
(user_id, source) are all FAILED, skip the firing and emit one Discord
admin alert. Auto-resume on first SUCCESS.
"""

from __future__ import annotations

import logging
from apscheduler.schedulers.asyncio import AsyncIOScheduler
from apscheduler.triggers.cron import CronTrigger
from sqlmodel import select

from db.session import async_session
from llm import get_provider as llm_get_provider
from llm.base import LLMProviderError
from models import JobScrapeRun, JobScrapeStatus, JobSource, Settings
from scraper.crawl4ai_client import Crawl4AIClient
from scraper.sites import scrapers as scraper_registry
from scraper.types import ScrapeQuery
from services.notifications import notify_admin_error
from services.scraper_service import run_scraper

log = logging.getLogger(__name__)

# Per-source defaults sourced from BACKEND.md § I.1. Treated as the
# "operator left Settings.source_schedules empty" fallback.
_DEFAULT_SCHEDULES: dict[str, str] = {
    JobSource.LINKEDIN.value: "*/30 * * * *",     # every 30min
    JobSource.WORKDAY.value: "0 * * * *",         # every 60min
    JobSource.GREENHOUSE.value: "0 * * * *",
    JobSource.LEVER.value: "0 * * * *",
    JobSource.ASHBY.value: "0 * * * *",
    JobSource.INDEED.value: "0 */90 * * *",       # ~every 90min (cron approximation)
}

_CONSECUTIVE_FAIL_THRESHOLD = 3


def _resolve_cron(source: JobSource, settings: Settings) -> str:
    """Per-user cron expression with BACKEND.md fallback."""
    return settings.source_schedules.get(source.value, _DEFAULT_SCHEDULES[source.value])


def _compose_query(source: JobSource, settings: Settings) -> ScrapeQuery:
    """Build a per-source ScrapeQuery from Settings + env-loaded config."""
    from config import settings as app_settings
    if source is JobSource.WORKDAY:
        return ScrapeQuery(company_filter=list(settings.workday_companies or []))
    if source is JobSource.GREENHOUSE:
        return ScrapeQuery(company_filter=list(app_settings.greenhouse_companies or []))
    if source is JobSource.LEVER:
        return ScrapeQuery(company_filter=list(app_settings.lever_companies or []))
    if source is JobSource.ASHBY:
        return ScrapeQuery(company_filter=list(app_settings.ashby_companies or []))
    if source is JobSource.LINKEDIN:
        return ScrapeQuery(
            keywords=list(settings.linkedin_keywords or []),
            location=settings.linkedin_location,
        )
    if source is JobSource.INDEED:
        return ScrapeQuery(
            keywords=list(settings.indeed_keywords or []),
            location=settings.indeed_location,
        )
    return ScrapeQuery()


async def _should_skip_consecutive_failures(session, *, user_id: int, source: JobSource) -> bool:
    stmt = (
        select(JobScrapeRun)
        .where(JobScrapeRun.user_id == user_id, JobScrapeRun.source == source)
        .order_by(JobScrapeRun.started_at.desc())
        .limit(_CONSECUTIVE_FAIL_THRESHOLD)
    )
    rows = (await session.exec(stmt)).all()
    if len(rows) < _CONSECUTIVE_FAIL_THRESHOLD:
        return False
    return all(r.status == JobScrapeStatus.FAILED for r in rows)


async def _scrape_one_user(session, *, settings: Settings, source: JobSource) -> None:
    if settings.sources_enabled.get(source.value, True) is False:
        return
    if await _should_skip_consecutive_failures(session, user_id=settings.user_id, source=source):
        log.info(
            "skipping scraping.%s for user=%s — 3 consecutive FAILED",
            source.value, settings.user_id,
        )
        # One-time admin alert per threshold trip (idempotent via JobScrapeRun history).
        await notify_admin_error(
            settings=settings,
            message=f"Scraping for {source.value} has failed 3x consecutively — auto-skipping until first SUCCESS.",
        )
        return
    try:
        provider = await llm_get_provider(session=session, user_id=settings.user_id)
    except LLMProviderError as exc:
        log.warning(
            "LLM provider unavailable user=%s source=%s: %s",
            settings.user_id, source.value, exc,
        )
        provider = None
    scraper_cls = scraper_registry[source.value]
    client = Crawl4AIClient(
        rate_limit_per_minute=scraper_cls.rate_limit_per_minute,
        random_delay_seconds=scraper_cls.random_delay_seconds,
    )
    scraper = scraper_cls(
        client=client,
        session=session,
        user_id=settings.user_id,
        provider=provider,
    )
    try:
        await run_scraper(
            session,
            scraper=scraper,
            user_id=settings.user_id,
            query=_compose_query(source, settings),
            triggered_by="cron",
        )
    except Exception as exc:  # noqa: BLE001 — per-user isolation
        log.exception(
            "scraping.%s failed for user=%s: %s",
            source.value, settings.user_id, exc,
        )


async def _scrape_source(source: JobSource) -> None:
    """Job body for `scraping.<source>`. One firing → iterate all enabled users."""
    async with async_session() as session:
        rows = (await session.exec(select(Settings))).all()
        for s in rows:
            await _scrape_one_user(session, settings=s, source=source)
        await session.commit()


def register_scraping_jobs(scheduler: AsyncIOScheduler) -> None:
    """Register one cron per JobSource present in scraper.sites:scrapers.

    Cron expression comes from the FIRST active user's Settings.source_schedules
    (single-user Phase 2 simplification — multi-user reschedule on per-user
    cron change deferred to 0.2.0.13).
    """
    for source_value, _scraper_cls in scraper_registry.items():
        source = JobSource(source_value)
        cron_str = _DEFAULT_SCHEDULES[source_value]  # see § D.X for refresh strategy
        scheduler.add_job(
            _scrape_source,
            CronTrigger.from_crontab(cron_str, timezone="UTC"),
            kwargs={"source": source},
            id=f"scraping.{source_value}",
            name=f"scraping.{source_value}",
            replace_existing=True,
            max_instances=1,
            coalesce=True,
            jitter=30,
            misfire_grace_time=300,
        )
```

### D.10 — n8n interaction (or lack thereof)

`0.2.0.14` (legacy 2.10) migrates n8n DataTable + Google Sheet → PostgreSQL. The scheduler does NOT interact with n8n. Both run in parallel during the migration window per `BACKEND.md § J.5`:

1. n8n Main Workflow stays enabled (`Lw1uK5APIhIeUeem` per BACKEND.md § J.5) and continues firing scrapes via the legacy RSShub + n8n DataTable path.
2. Naavik APScheduler crons fire scrapes via the native `0.2.0.06`–`0.2.0.09` pipeline.
3. Both writers land in the SAME PostgreSQL `job` table (n8n via direct INSERT, Naavik via `upsert_job`).
4. **Dedup catches the overlap.** Naavik's tier-3 fuzzy dedup (plan 34) catches `(company, role)` collisions even when sources differ. Existing rows from n8n carry `source=N8N_LEGACY` (the JobSource enum value reserved by plan 27); Naavik scrapers carry `source=LINKEDIN` / `WORKDAY` / etc. Cross-source fuzzy dedup makes the new row land with `duplicate_of_id` set to the n8n row. Discover UI surfaces one of them (the canonical, oldest) and the duplicate stays queryable.
5. After 1 week of clean Naavik runs (per BACKEND.md § J.5 line 629), operator disables n8n Main Workflow + the `0.2.0.14` migration script consolidates historic rows.

**No code in plan 35 references n8n.** The interaction is via the shared DB table; the dedup layer handles correctness.
