# 34 · `0.2.0.09` — Job dedup (tier-3 fuzzy across sources)

## Goal

Ship `src/services/dedup.py` — the missing **tier-3 fuzzy** layer of the 3-tier waterfall locked in `JOB_MODEL.md § G`. Tier-1 (`(user_id, source, external_id)` partial-unique) and tier-2 (`(user_id, url)` partial-unique) already structurally prevent same-source double-writes (plan 27). What ships in plan 34 catches the **cross-source cross-posting** case that the 6 site scrapers from `0.2.0.07` make physically possible: the same Stripe Senior Software Engineer role appears on LinkedIn + Greenhouse + Lever simultaneously, every scraper writes its `Job` row, and without tier-3 the Discover UI shows three near-identical cards. The new module exposes `find_duplicate(session, *, user_id, company, role, source) -> Job | None` which is called inline from `job_service.upsert_job` AFTER the tier-1 miss + BEFORE the INSERT, plus the schema addition `Job.duplicate_of_id: int | None` (FK → `Job.id`, on-delete SET NULL) that records the relationship. Alembic 0006 adds the column, the `pg_trgm` extension, and one new GIN trigram index on `lower(company)`. Engineer wires `list_jobs` + Discover filters to skip `duplicate_of_id IS NOT NULL` rows by default so duplicates remain queryable but invisible.

This plan is `Type: design`. On approval, the locked contract graduates into `docs/design/JOB_DEDUP.md` — the canonical reference scraper_service + Discover UI + the future `dedup_recent_jobs` cron all cite. The plan file then archives.

## Why now

Four forces, ordered by force:

1. **`0.2.0.07` per-site scrapers shipped and now produce cross-source duplicates by design.** Plan 33 (PR #102) landed 6 ScraperBase subclasses; every scraper emits `(source=<board>, external_id=<board-stable-id>)` distinct per source. A Stripe role on LinkedIn (`linkedin_job_id=4082391738`) and the same role on Greenhouse (`greenhouse_internal_id=4502890008`) hit tier-1 with **disjoint** `(source, external_id)` triples, then hit tier-2 with **disjoint** URLs (`linkedin.com/jobs/view/...` vs `boards.greenhouse.io/stripe/jobs/...`), and both INSERT. With no tier-3 in place every cross-posted role lands twice or thrice — and the Discover UI (`0.2.0.11`) sees three swipe-cards for one opportunity. The tier-3 work was deferred from plan 27 § G specifically to land here, after extraction (`0.2.0.08`) populates `company` + `role` reliably from JD bodies.

2. **`0.2.0.08` AI extraction made the comparison fields reliable.** Plan 30 (PR #106) landed `services/job_extractor.enrich_raw_job` which OVERWRITES the scraper's best-guess `company_name` + `position_title` with authoritative reads from the JD body. Without extraction first, `company` could be "Stripe, Inc." on one board and "Stripe" on another and "Stripe (YC W11)" on a third — fuzzy matchable, but only after the listing-card noise gets stripped. Now post-extraction, the fields are LLM-normalized and the fuzzy comparison is on clean strings. Sequencing locks: `0.2.0.05 → 0.2.0.06 → 0.2.0.07 → 0.2.0.08 → 0.2.0.09`.

3. **`JOB_MODEL.md § G` already locked the architecture; this plan executes it.** Quote: *"Fuzzy title + company. Levenshtein on `(company.lower() strip)` + `(role.lower() strip)` — deferred to `0.2.0.09`. Will live in `services/dedup.py` (new module). Cross-board cross-posting … is handled by tier 3 — two `Job` rows with different `source` values can both be live at the same time; `0.2.0.09` merges them when fuzzy match scores high."* `BACKEND.md § J.3` line 472 also reserves `jobs.dedup` as an hourly cron name. Plan 34 fills in the **how** (pg_trgm + rapidfuzz hybrid, `duplicate_of_id` FK, inline-in-upsert wedge point) — the **what** is locked.

4. **`job_service.upsert_job` already promised this.** Source comment at `src/services/job_service.py:194`: *"Field-level merge (e.g. diffing description + skills against the new payload) is deferred to `0.2.0.09` dedup work."* Engineers reading the codebase expect tier-3 to land in this plan's PR. Delaying further means scrapers run in the wild producing visible duplicate cards — a paper-cut Discover UX will rage about.

ROADMAP cross-references: `ROADMAP.md:230` row `0.2.0.09`; `ROADMAP.md:228` row `0.2.0.08` (EXECUTED, unblocks this); `ROADMAP.md:224` row `0.2.0.07` (EXECUTED, scrapers produce the cross-source duplicates).

### D.1 — Where does dedup run?

The crux call. Three placements.

| Option | A — Inline in `upsert_job` pre-INSERT (recommended) | B — Post-insert daily cron sweeps duplicates | C — Hybrid: tier-1 inline + tier-3 in cron |
| --- | --- | --- | --- |
| Capability | Tier-3 fires synchronously on every `upsert_job`. Cross-source duplicate is detected at INSERT time; new row lands with `duplicate_of_id` already set; Discover UI never shows it. | Both rows land live; cron pass (`every 60min` per `BACKEND.md § J.3` line 472) sets `duplicate_of_id` on the newer; Discover UI shows duplicate briefly until next sweep. | Tier-1 stays structural (partial-unique); tier-3 deferred to cron. Inserts stay fast. |
| Cost | One extra SELECT per upsert (~5ms with pg_trgm GIN narrowing to ~5-20 candidates + rapidfuzz on each). ~80 LOC service + 30 LOC `upsert_job` integration. | ~120 LOC cron + scrape_service hook + duplicate row visible up to 60min. | Cron infrastructure work duplicated. ~150 LOC. |
| Risk | LOW — synchronous path, deterministic, easy to test. Worst case is fuzzy false-positive (Stripe X vs Stripe Y both senior SWE → false-merge); mitigated by tuning threshold + 1-line manual unmerge via `restore_job`-shaped helper. | MEDIUM — UI shows duplicates briefly; user could swipe-action one then have it re-collapse. Confusing UX. | LOW — but cron infrastructure isn't free; APScheduler hooks land in `0.2.0.10`. |
| Maintenance | One write path. Add new sources → fuzzy still works. | Two write paths (insert + cron) drift over time. | Same dual-path problem as B for the tier-3 leg. |
| Lock-in | None — `dedup_recent_jobs` cron can ALSO call `find_duplicate` later for historical cleanup; both consumers welcome. | Cron-only locks us into batch-eventual-consistency UX. | Soft lock on cron-as-tier-3-owner. |

**Recommendation: A — inline in `upsert_job`.** Three reasons:

1. **Single write path.** `upsert_job` is already the load-bearing dedup helper (tier-1 + tier-2 partial-unique constraints fire here). Tier-3 belongs in the same lexical scope. No "is this Job a tier-3 duplicate?" mystery for future readers.

2. **Discover UX needs synchronous correctness.** When a scraper run finishes and the user opens Discover, they see N cards. If one of the N is a tier-3 duplicate of another, the user swipes both, the second one is wasted action. The 5ms cost per `upsert_job` is amortized over the LLM extraction (1-3s per Job in `0.2.0.08`) — totally negligible.

3. **Cron-based dedup is still cheap to add later.** `services/dedup.py` exposes `find_duplicate(session, *, user_id, company, role, source) -> Job | None` as the primitive. `dedup_recent_jobs(session, *, user_id, hours=24)` is an optional 20-LOC wrapper that scans `Job WHERE found_at > now() - interval N hours AND duplicate_of_id IS NULL` and runs the same primitive. `0.2.0.10` scheduler can register it if and only if drift is observed.

**Trade-off accepted.** Option A's 5ms cost is on the synchronous scraper path. Profiled against a 200-listing LinkedIn scrape, total dedup overhead is ~1 second (200 × 5ms) — within the existing scrape budget (per-scraper 30-listing-per-minute rate limit per `ScraperBase.rate_limit_per_minute`). No anti-pattern.

**Locked decision (zoom-through):** **A** — inline in `upsert_job` pre-INSERT.

### D.2 — How does the candidate filter work?

A naive `SELECT * FROM job WHERE user_id=X` then `rapidfuzz` in Python on every row is O(N) per upsert. At 10k jobs that's 10k × ~50us per `token_set_ratio` = 500ms per upsert — unacceptable. We need a narrower pre-filter.

| Option | A — Full table scan + rapidfuzz | B — pg_trgm GIN + rapidfuzz precision (recommended) | C — Deterministic hash of canonical strings |
| --- | --- | --- | --- |
| Capability | Compare every Job's `company` + `role` against incoming. | pg_trgm `%` operator narrows to candidates whose `lower(company)` is similar (default trigram threshold 0.3); rapidfuzz then scores precisely on `(company, role)` joint similarity. | sha256 of `lower(company.strip()) || "|" || lower(role.strip())` — exact equality check on a hashed column. |
| Cost | O(N) per upsert. At 10k jobs: ~500ms per upsert. Linear with growth. | O(log N) GIN lookup + ~10-20 rapidfuzz calls. ~5ms per upsert at 10k jobs; degrades sublinearly. | O(1) B-tree lookup. ~1ms. |
| Risk | High — scales badly past 1k jobs. | LOW — pg_trgm is battle-tested; GIN index update overhead is fast (~50us per insert). | HIGH — misses every near-duplicate ("Stripe, Inc." vs "Stripe" sha256-differ). Defeats the purpose of fuzzy match. |
| Maintenance | None | One Postgres extension + one GIN index. | None per se, but caller has to compute the canonical hash everywhere consistently. |
| Lock-in | None | pg_trgm is contrib, available everywhere we deploy. | Hash-key drift — change canonicalization → must rehash everything. |

**Recommendation: B — pg_trgm GIN + rapidfuzz precision.**

**Pattern (locked):**

```python
# services/dedup.py
async def find_duplicate(
    session: AsyncSession,
    *,
    user_id: int,
    company: str,
    role: str,
    source: JobSource,
    excluded_job_id: int | None = None,
) -> Job | None:
    """Find a tier-3 fuzzy match for the (company, role) pair.

    Returns the existing Job row if found, None otherwise. Caller wires
    `excluded_job_id` to skip self-match on re-runs.

    Algorithm:
    1. pg_trgm GIN-indexed `%` filter on `lower(Job.company)` against
       `lower(company)` → narrow N rows to ~5-20 candidates.
    2. For each candidate, compute `rapidfuzz.fuzz.token_set_ratio` on
       `(company, role)` joint similarity. Score = 0.6 * company + 0.4 * role.
    3. Return first candidate with score >= 88.0 (0-100 scale). Tie-break:
       oldest `found_at` wins (we merge INTO the original).
    """
    norm_company = company.strip().lower()
    norm_role = role.strip().lower()
    if not norm_company or not norm_role:
        return None

    # Same-source dedup is the tier-1 partial-unique's job, not ours.
    # Tier-3 is explicitly cross-source.
    stmt = (
        select(Job)
        .where(
            Job.user_id == user_id,
            Job.deleted_at.is_(None),
            Job.duplicate_of_id.is_(None),  # don't chain duplicates
            Job.source != source,
            text("lower(job.company) % :norm_company"),
        )
        .params(norm_company=norm_company)
        .order_by(Job.found_at.asc())
        .limit(20)
    )
    if excluded_job_id is not None:
        stmt = stmt.where(Job.id != excluded_job_id)

    candidates = (await session.exec(stmt)).all()

    best: tuple[float, Job] | None = None
    for c in candidates:
        cs = fuzz.token_set_ratio(norm_company, c.company.strip().lower())
        rs = fuzz.token_set_ratio(norm_role, c.role.strip().lower())
        score = 0.6 * cs + 0.4 * rs
        if score >= 88.0 and (best is None or score > best[0]):
            best = (score, c)

    return best[1] if best else None
```

**Trade-off accepted.** rapidfuzz adds a runtime dep (~600 KB compiled wheel). Worth it — the alternative is hand-rolling Levenshtein in Python (~10x slower, much more bug surface). rapidfuzz is AGPL-friendly (MIT) and ships nixpkgs.

**Locked decision (zoom-through):** **B** — pg_trgm GIN as candidate filter + rapidfuzz `token_set_ratio` as precision scorer. Threshold **88.0** on weighted joint score (0.6 company + 0.4 role). Threshold tuned to be conservative — false-positive (false-merge) is worse than false-negative (occasional duplicate card), because the former hides a real opportunity from Discover.

### D.3 — How is the duplicate relationship stored?

| Option | A — `duplicate_of_id: int \| None FK Job.id` on the NEW row, keep both rows (recommended) | B — Merge metadata into original; soft-delete new | C — `JobAlias` table (source, external_id, job_id) |
| --- | --- | --- | --- |
| Capability | Both `Job` rows exist; UI filters `WHERE duplicate_of_id IS NULL`; future "show all sources" diagnostic UI can join. | One row, augmented; cleaner UI list; deleted row gone. | Highly normalized; supports M:N (theoretical "this Stripe role is on 5 boards"). |
| Cost | One nullable FK col + 1 index. ~10 LOC migration. Easy to reverse (clear FK). | Soft-delete + raw_meta merge logic (`sources_seen[]`, `urls_seen[]`); destroys per-source `external_id` for the duplicate. | New table + 2 FKs + denormalized join in every Job query. ~80 LOC. |
| Risk | LOW — additive; no information loss. | MEDIUM — soft-delete in tier-3 collides with the operator's "this Job was archived" semantics (`archive_job`). Two unrelated reasons to flip `deleted_at`. | LOW per se, but high cost-per-benefit at MVP. |
| Maintenance | One column, one index. | Two reasons for `deleted_at` to be set (user-archive vs dedup). | New table to migrate, query, test. |
| Lock-in | None — `duplicate_of_id` can later be removed if we decide on B. | Hard lock — once merged, you can't un-merge without raw_meta archaeology. | Soft lock — `JobAlias` becomes a permanent surface. |

**Recommendation: A — `duplicate_of_id` FK on the new row, both rows survive.**

**Filter semantics (locked):**

- `list_jobs(...)` default: `WHERE duplicate_of_id IS NULL` (duplicates hidden).
- `list_jobs(... include_duplicates=True)`: returns everything (diagnostic mode for the future Scrapes operator panel).
- Discover UI route reads `list_jobs(...)` default — duplicates never reach swipe-cards.
- `archive_job(job_id)` independently sets `deleted_at`; orthogonal to dedup state.
- On `archive_job(original)` where N rows have `duplicate_of_id == original.id`: the FK SET NULL clears the duplicate links so the formerly-shadowed Jobs surface back into Discover. Behavioral note documented in `JOB_DEDUP.md § E`.

**Trade-off accepted.** The duplicate row carries its own `external_id` + `url` — diagnostic info is preserved. Storage cost ~1 KB per duplicate row is negligible.

**Locked decision (zoom-through):** **A** — `duplicate_of_id` FK; both rows live; default filter hides duplicates.

```python
"""Add pg_trgm extension + Job.duplicate_of_id FK + GIN trigram index on lower(job.company).

Plan 34 / 0.2.0.09 — tier-3 fuzzy dedup.
"""

from alembic import op
import sqlalchemy as sa

revision = "0006"
down_revision = "0005"

def upgrade() -> None:
    op.execute("CREATE EXTENSION IF NOT EXISTS pg_trgm")
    op.add_column(
        "job",
        sa.Column("duplicate_of_id", sa.Integer(), nullable=True),
    )
    op.create_foreign_key(
        "fk_job_duplicate_of_id",
        "job", "job",
        ["duplicate_of_id"], ["id"],
        ondelete="SET NULL",
    )
    op.create_index(
        "ix_job_duplicate_of_id",
        "job", ["duplicate_of_id"],
    )
    # GIN trigram index on lower(company) for cross-source fuzzy lookup.
    op.execute(
        "CREATE INDEX ix_job_company_trgm ON job "
        "USING GIN (lower(company) gin_trgm_ops)"
    )

def downgrade() -> None:
    op.drop_index("ix_job_company_trgm", table_name="job")
    op.drop_index("ix_job_duplicate_of_id", table_name="job")
    op.drop_constraint("fk_job_duplicate_of_id", "job", type_="foreignkey")
    op.drop_column("job", "duplicate_of_id")
    # pg_trgm extension is not dropped (other tables may grow trgm indexes).
```

## Deviations from plan

- **What:** `tests/test_scraper_service.py` + `tests/test_job_service.py` `_FakeSession` gained a `bind.dialect.name = "sqlite"` attribute. **Why:** `dedup.find_duplicate` reads `session.bind.dialect.name` to switch between the pg_trgm `%` operator (production) and a sqlite LIKE fallback (in-memory tests). **Impact:** test substrate only — no production behavior change.
- **What:** `migrations/versions/0006_job_dedup.py` wraps `op.create_foreign_key("fk_job_duplicate_of_id", ...)` inside `if is_postgres:`. **Why:** sqlite cannot `ALTER TABLE ADD CONSTRAINT` (same caveat plan 27 hit on `Job.last_scrape_run_id` FK). **Impact:** production Postgres still gets the FK + `ON DELETE SET NULL`; sqlite test substrate gets the column + btree index without the FK — matches plan 27 pattern.
- **What:** `services/dedup.py::find_duplicate` has a sqlite LIKE-fallback candidate filter alongside the Postgres pg_trgm `%` filter. **Why:** the test substrate runs sqlite (`_FakeSession` declares dialect=sqlite); the production code path runs pg_trgm. The fallback uses `lower(job.company) LIKE :like_company` with the first 8 chars of the normalized incoming company as a coarse narrowing filter. **Impact:** identical semantics from caller's perspective; rapidfuzz scoring runs on both code paths.
- **What:** Scraper service tests need a second queued `_exec_all` per cold-cache upsert. **Why:** the tier-3 dedup wedge issues an additional `session.exec` after a tier-1 miss. The plan's § D.7 sketch made this explicit; the test queue was previously sized 1-per-yield. **Impact:** `tests/test_scraper_service.py::_setup_session_for_sample` + the two partial-test helpers queue `_exec_all_empty()` after each `_exec_one(None)` for cold-cache paths.
- **What:** New base dependency `rapidfuzz>=3.10.0,<4` added to `pyproject.toml`. **Why:** plan-spec'd, just noting actual lockfile state. **Impact:** `uv.lock` regenerated; `rapidfuzz==3.14.5` resolved (nixpkgs ships `python312Packages.rapidfuzz`).
