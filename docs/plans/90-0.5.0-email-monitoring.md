# 90 · 0.5.0 — Email Monitoring foundation

## Goal

Scaffold the foundation that lets Naavik watch a user's inbox, persist
incoming application-related email per Application, classify each message
(INTERVIEW_REQUEST / REJECTION / OFFER / ASSESSMENT / FOLLOW_UP), surface
high-priority signals on Discord + Telegram + the in-app toast queue, and
seed the AI draft-response surface. Closes ROADMAP rows
`0.5.0.01-06`. Plans 91 (LinkedIn outreach `0.5.0.09-15`) and 92 (interview
scheduling + prep `0.5.0.07-08`) follow this one and explicitly depend on
its EmailAccount + EmailMessage + AppEventKind surface.

## Why

ROADMAP § 0.5.0 deliverable: "Email inbox monitored → job statuses
auto-updated. Recruiter/employee contacts tracked → AI-assisted outreach
→ referral requests sent at optimal timing." The status-update arm is the
foundation — outreach (plan 91) reads the same EmailMessage signals to
score recipient engagement; interview scheduling (plan 92) reads
`AppEventKind.EMAIL_STATUS_SUGGESTED` payloads to seed Calendly handoff.
Building outreach or interview before the email substrate is rebar before
foundation.

Two adjacent constraints frame the design:

1. **Vault is sunset** (plan 26 / `0.2.0.01`, 2026-05-19). The
   BACKEND.md § L.1 sketch that names `vault.set(scope="integrations",
   key="gmail.refresh_token", ...)` is OBSOLETE — Naavik no longer has
   that surface. Per-user inbox credentials must land somewhere new, and
   "where" is the most contested decision in this plan (Q2).
2. **Owner has no LLM configured** (0.7.0.48 / plan 89 inherited the
   "no-LLM graceful degrade" pattern from extraction). The connection +
   storage + poller must be fully functional + testable without an LLM —
   classification falls back to "OTHER + unclassified_reason" cleanly, the
   way scorer's `judge_skipped_reason="no_provider_configured"` does
   (plan 65 § H.4).

### A. Option matrices

#### A.1 — Connection method (Q1)

| Option | Capability | Setup cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **A.1.a IMAP only (rec.)** | Provider-agnostic (Gmail/Outlook/Yahoo/Fastmail/Fastmail/Hey/iCloud/self-hosted Postfix) | LOW — user pastes app-password into a Settings field | App-password setup is friction-heavy on Gmail (requires 2FA + "App passwords" UI dive); but it's a one-time step | LOW — single sync codepath | None |
| A.1.b Gmail API only | Push webhooks (Pub/Sub), rich metadata, scope-limited tokens | HIGH — Naavik would have to register an OAuth Client App + ship the client_id/secret OR force every self-hoster to register their own Google Cloud project | High setup friction; Gmail-only | HIGH — Google SDK churn, scope migrations | Google |
| A.1.c Both | Maximum flexibility | VERY HIGH — 2 codepaths + 2 test matrices | Highest engineer-hours cost | VERY HIGH | Mixed |

**Recommendation: A.1.a — IMAP only for the foundation.** Reasons:

- Provider-agnostic matches Naavik's "self-hosted first" posture. Gmail
  API forces self-hosters to set up a Google Cloud project just to read
  their own email; IMAP doesn't.
- Same code works for the Cloud tier ($15/mo) — bring-your-own-inbox is
  the symmetric promise.
- Self-hoster onboarding is "paste app-password into Settings" — same
  ergonomic shape as Discord webhook + Telegram bot today.
- `aioimaplib` (or equivalent async IMAP client) is ~600 LOC of vendor
  surface to wrap; engineer ships in Wave 2.

**Accepted trade-off:** no real-time push. 10min polling cadence (A.6
locks). For a foundation that classifies application emails (not chat),
10min latency is acceptable.

**Follow-up scope** (not in this plan): `0.5.0.01.1` — Gmail API + Gmail
push webhooks when sub-minute classification matters. Filed after this
plan ships; depends on Naavik Cloud OAuth-app registration.

#### A.2 — Per-user credential storage (Q2 — the crux)

This is the most owner-controversial decision in the plan. Vault sunset
(AGENTS.md § Key Conventions § CLI) forbids re-introducing the
AES-256-GCM file-blob pattern. But Naavik must store SOME secret material
per user (IMAP app-password) to authenticate inbox sync.

| Option | Capability | Cost | Risk | Maintenance | Lock-in | Sunset-compliance |
|---|---|---|---|---|---|---|
| **A.2.a Fernet column-level encryption (rec.)** | Multi-user; rotatable via SECRET_KEY change; encrypted at rest in DB | LOW — ~80 LOC helper module (`cryptography.fernet.Fernet`); no new dep | If attacker has SECRET_KEY they have everything (acknowledged plan 26 retrospective: vault had the same flaw) | MEDIUM — key rotation needs a re-encrypt cron | None | **Acceptable** — column-level encryption, not vault revival. No `.enc` file, no audit-log, no Argon2id/PBKDF2 CLI, no `~/.naavik/key.bin`. Mirrors Postgres `pgcrypto` pattern. Doc note: "Trust posture = trust the DB column + SECRET_KEY; same as JWT signing." |
| A.2.b Plaintext JSONB column | Multi-user; trivial | LOWEST | DB backups leak passwords; `pg_dump` output is a credential exfil vector | LOWEST | None | **Acceptable but worse posture.** Honest "we trust the DB the way we trust Profile data + Settings JSONB" stance — defensible if owner picks. |
| A.2.c Env-only single-account (`IMAP_HOST`/`IMAP_USERNAME`/`IMAP_PASSWORD`) | Single-user only | LOWEST | Blocks multi-user (Cloud tier roadmap) | LOWEST | None | **Compliant** — matches Discord/Telegram env-var pattern exactly. |
| A.2.d Vault revival | (would unify with other secrets) | HIGH | Sunset violation — FORBIDDEN | n/a | n/a | **FORBIDDEN** by AGENTS.md § Key Conventions § CLI. Listed for "why not." |

**Recommendation: A.2.a — Fernet column-level encryption.** Plan-quality
case:

- The vault deletion (plan 26) was theater because (a) the master key was
  derived from `SECRET_KEY` — same env var JWT signing reads, so attacker
  with `SECRET_KEY` already owns JWTs + vault, (b) the encrypted file
  added complexity without raising the trust floor, and (c) the audit log
  + Argon2id ceremony added attack surface (privileged file writes) that
  filesystem perms `chmod 0600 .env` already cover.
- Fernet column-level encryption sidesteps each of those flaws: it's
  per-row encryption inside the existing DB row; no separate file; no
  audit log to write; no CLI subcommand; trust posture identical to
  Postgres `pgcrypto` (which `pg_dump` similarly carries plaintext under
  the same SECRET_KEY trust posture).
- Multi-user is on the roadmap (Naavik Cloud tier). Env-only A.2.c
  blocks that; A.2.b is fine but reduces the blast-radius shield by one
  layer if the DB leaks without `SECRET_KEY`.

**Concrete code shape** (engineer scaffolds):

```python
# src/services/email_credentials.py
from __future__ import annotations
import base64
import hashlib
from cryptography.fernet import Fernet, InvalidToken
from config import settings as app_settings

def _fernet() -> Fernet:
    # Derive a stable 32-byte key from SECRET_KEY via SHA-256.
    # Same SECRET_KEY trust posture as JWT signing (plan 26 retrospective).
    digest = hashlib.sha256(app_settings.secret_key.encode("utf-8")).digest()
    return Fernet(base64.urlsafe_b64encode(digest))

def encrypt_password(plaintext: str) -> bytes:
    return _fernet().encrypt(plaintext.encode("utf-8"))

def decrypt_password(token: bytes) -> str:
    try:
        return _fernet().decrypt(token).decode("utf-8")
    except InvalidToken as exc:
        raise CredentialDecryptError(...) from exc
```

`EmailAccount` model carries `imap_password_encrypted: bytes` (LargeBinary
column). Decryption only happens inside the IMAP-sync transaction; the
plaintext never returns from any service-layer accessor.

**Hard rule the engineer enforces:** the decrypted plaintext password is
NEVER logged, NEVER returned from any HTTP endpoint, NEVER stored on the
`EmailAccount` Pydantic Read schema. New lint test
`tests/test_no_email_password_leak.py` (regex sweep over routes + log
calls) guards regression.

**Owner pivot path:** if owner judges A.2.a as vault theater (legitimate
read), pivot to A.2.b plaintext-JSONB by (a) removing `email_credentials.py`,
(b) changing `imap_password_encrypted: bytes` to
`imap_password: str` on the model, (c) dropping the encrypt/decrypt calls
in `email_sync.py`. ~10 LOC delta; engineer scaffolds A.2.a but the
revert is mechanical.

#### A.3 — Email message storage shape (Q3)

`EmailThread.messages` is currently a JSONB list. The substrate
inventory (item 1) flagged "Phase 2+ may promote to a separate
`EmailMessage` table." This is that decision point.

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A.3.a Extend `EmailThread.messages` JSONB (status quo) | One table; aligns with current Discover-card SCREEN_DATA shape | LOWEST | JSONB grows unbounded per thread; per-message classification has no index; queries like "all INTERVIEW_REQUEST messages for user" require JSONB scan | HIGH once threads > 50 messages | None |
| A.3.b New `EmailMessage` table — FULL body persisted | Proper relational shape; per-message indices on `(thread_id, classification, received_at)`; classification first-class | MEDIUM — alembic + model + ~6 service-layer query rewrites | DB grows fast (50 recruiter messages × 30KB body = 1.5MB per thread × N threads); body is plaintext-sensitive (job applicant identity + interview times in raw form) | MEDIUM | None |
| **A.3.c New `EmailMessage` table — metadata + 200-char snippet only (rec.)** | Privacy-first; small DB; classification first-class | MEDIUM — same as A.3.b minus body column | Classification accuracy: subject + sender + 200-char snippet is usually enough; the existing prompt § A.6 truncates body to 4000 chars anyway. Re-classification on demand requires re-fetch from IMAP | MEDIUM | None |

**Recommendation: A.3.c — `EmailMessage` table, metadata + snippet only.**
Reasons:

- Privacy posture: `pg_dump` of a Naavik DB leaks Profile + Settings +
  Application notes today. Adding full inbox bodies multiplies leak
  blast-radius for negligible classification accuracy gain.
- Owner-controlled escalation: add `Settings.email_store_full_bodies:
  bool = False` (filed as `0.5.0.05a` follow-up, not in this plan) for
  users who want full-body archives. Default off.
- Re-classification on demand: IMAP is the source of truth for the body.
  Naavik refetches by `message_id_external` if a model upgrade wants
  re-classification.

**`EmailMessage` schema** (engineer reuses verbatim — Q5 affirms):

```python
# src/models/email_message.py
class EmailMessage(SQLModel, table=True):
    __tablename__ = "email_message"
    __table_args__ = (
        UniqueConstraint("thread_id", "message_id_external",
                         name="uq_email_message_external"),
        Index("ix_email_message_thread_received", "thread_id", "received_at"),
        Index("ix_email_message_user_class",
              "user_id", "classification", "received_at"),
    )

    id: int | None = Field(default=None, primary_key=True)
    user_id: int = Field(foreign_key="user.id", index=True)
    thread_id: int = Field(foreign_key="email_thread.id", index=True)
    application_id: int | None = Field(default=None,
                                       foreign_key="application.id", index=True)

    provider: str                                  # "imap" | "gmail" | "outlook"
    message_id_external: str                       # RFC 5322 Message-ID
    sender_email: str
    sender_name: str | None = None
    subject: str
    snippet: str = Field(max_length=240)           # 200-char preview; 240 cap absorbs UTF-8 multibyte
    received_at: datetime

    classification: EmailClassification | None = None
    auto_classified: bool = Field(default=True)
    classification_model: str | None = None
    classification_at: datetime | None = None
    unclassified_reason: UnclassifiedReason | None = None
    urgency: str | None = None                     # "high"|"medium"|"low" from prompt

    suggested_status: ApplicationStatus | None = None
    suggested_at: datetime | None = None
    suggestion_dismissed_at: datetime | None = None
    suggestion_applied_at: datetime | None = None

    created_at: datetime = ...
    updated_at: datetime = ...
```

migrate. The new `EmailMessage` rows are authoritative going forward;

```python
# src/services/email_classifier.py (sketch)
from llm.prompts.classify_email import classify_email as classify_prompt
from llm import get_provider, LLMProviderError
from services.llm_tracker import tracked_call

async def classify_unprocessed(session, *, limit: int = 50) -> int:
    unprocessed = (await session.exec(
        select(EmailMessage).where(EmailMessage.classification.is_(None)).limit(limit)
    )).all()
    classified = 0
    for msg in unprocessed:
        user_settings = await _get_user_settings(session, msg.user_id)
        try:
            provider = get_provider(user_settings)
        except LLMProviderError as exc:
            if exc.kind == "auth_required":
                msg.classification = EmailClassification.OTHER
                msg.unclassified_reason = UnclassifiedReason.NO_PROVIDER_CONFIGURED
                msg.auto_classified = False
                msg.classification_at = datetime.now(UTC)
                session.add(msg)
                continue
            raise
        try:
            result = await tracked_call(
                session=session, user_id=msg.user_id,
                provider=provider, method="structured",
                prompt_name="classify_email",
                sender=msg.sender_email, subject=msg.subject,
                body=msg.snippet,  # body is the 200-char snippet — prompt truncates anyway
            )
        except Exception as exc:
            msg.unclassified_reason = UnclassifiedReason.LLM_FAILED
            msg.classification_at = datetime.now(UTC)
            session.add(msg)
            continue
        msg.classification = EmailClassification(result.classification)
        msg.urgency = result.urgency
        msg.classification_model = provider.model_name
        msg.classification_at = datetime.now(UTC)
        # Trigger downstream: emit EMAIL_RECEIVED AppEvent + priority notification + status suggestion.
        await _post_classify_dispatch(session, msg)
        classified += 1
    return classified
```

#### A.5 — Auto-status mapping — auto-update vs human-confirm (Q5)

THE DESTRUCTIVE-ACTION DECISION. A misclassified REJECTION email auto-
flipping an Application to CLOSED is unrecoverable at the audit level
(the original status is gone unless we read AppEvent history).

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A.5.a Auto-update on every confident classification | Hands-free | LOW | High — misclassification → destructive + irreversible (AppEvent log preserves history but UI status flips) | LOW | High — operator support cost for "why did my application close?" |
| **A.5.b Human-confirm via in-app suggestion banner (rec.)** | Safe; mirrors hacker-approved sponsorship-gate pattern (plan 76 — owner explicitly opts in to destructive flips) | MEDIUM — banner UI per pending suggestion; new `AppEvent(EMAIL_STATUS_SUGGESTED)` kind | Some friction; user must dismiss/confirm | MEDIUM | None — promote to A.5.c via toggle later |
| A.5.c Hybrid — auto OFFER + INTERVIEW_REQUEST (positive); human-confirm REJECTION + ASSESSMENT (irreversible) | Best balance | MEDIUM | Some auto-flips still surprising | MEDIUM | None |

**Recommendation: A.5.b — human-confirm-all for the foundation.**
Concrete shape:

1. Classifier persists `EmailMessage.classification`.
2. Classifier calls `email_status_mapper.suggest_status(application,
   classification) → SuggestedTransition | None`.
3. If non-None, persists `EmailMessage.suggested_status` + emits
   `AppEvent(kind=EMAIL_STATUS_SUGGESTED, payload={current, suggested,
   reason, message_id})`.
4. UI surfaces "Suggested action" banner on Application detail +
   Tracking row; click "Apply" calls
   `POST /api/v1/applications/{id}/apply-email-suggestion/{message_id}` →
   service invokes `update_status(... trigger=AUTO_FROM_EMAIL)` →
   persists `EmailMessage.suggestion_applied_at`.
5. Click "Dismiss" persists `suggestion_dismissed_at`; AppEvent log
   carries the dismissal as a payload field.

**Mapping table** (engineer hardcodes; owner verifies on review):

| EmailClassification | Suggested ApplicationStatus | Closed reason | When to skip |
|---|---|---|---|
| INTERVIEW_REQUEST | RECRUITER_SCREEN (if currently APPLIED) → ONSITE_LOOP (if currently RECRUITER_SCREEN) | — | Skip if already at or beyond suggested |
| ASSESSMENT | RECRUITER_SCREEN (informational; same as INTERVIEW_REQUEST) | — | Skip if classification.urgency=="low" |
| OFFER | OFFER | — | Skip if currently OFFER or CLOSED |
| REJECTION | CLOSED | `rejected_by_them` | Skip if currently CLOSED or OFFER |
| FOLLOW_UP | (no suggestion — informational) | — | Always skip |
| OTHER | (no suggestion) | — | Always skip |

**Owner pivot path** (Settings-level toggle, filed as `0.5.0.03a`): add
`Settings.email_auto_apply_status_changes: bool = False`; when True,
high-confidence positive classifications (OFFER + INTERVIEW_REQUEST)
auto-flip without banner. REJECTION + ASSESSMENT remain human-confirm
even with the toggle on (irreversible-side stays gated).

**Account-ban risk** (per BACKEND.md § L.2 framing — emails are
fundamentally less hostile than LinkedIn-DM scraping; IMAP is a
legitimate protocol with a documented contract; no anti-scraping defense
in normal email providers). Mitigations the foundation respects:

- Per-account sync uses ONE connection (no parallel IMAP across same
  inbox).
- Sync window scoped to "since last_sync_at" — never full inbox refetch.
- Failure backoff: 3rd consecutive auth failure → mark
  `EmailAccount.status=AUTH_REQUIRED`; cron skips; UI surfaces "Reconnect
  IMAP" card.
- Gmail's specific 15-IMAP-connections/day cap is well under our 10min
  cadence (= 144 connections/day from one account), so we will hit it on
  Gmail. Q6 follow-up: register IDLE-mode (single long-lived connection)
  in `0.5.0.01.2` to dodge the cap. Mitigated for foundation by
  documenting in RUNBOOK "if you see Gmail IMAP rate-limit, set
  EMAIL_SYNC_INTERVAL_MINUTES=15 in env."

The Fernet column-level encryption (§ A.2.a) is distinct in:

- Encrypted data lives INSIDE a Postgres row (not a separate file).
- Key derivation is a single SHA-256 of `SECRET_KEY` (no salt/iterations
  ceremony; SECRET_KEY itself carries the entropy via the
  `_enforce_secret_key` validator in `config.py:113`).
- No audit log. No CLI surface. No file permissions to manage. No key
  rotation script.
- `pgcrypto` would do the same thing server-side; we choose app-side
  because (a) the consumers are already in Python, (b) sqlite parity
  tests don't have `pgcrypto`.
