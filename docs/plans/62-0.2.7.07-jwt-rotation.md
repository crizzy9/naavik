# 62 · Multi-tenant JWT signing-key rotation (ROADMAP 0.2.7.07)

> **Design plan.** Body graduates to `docs/design/JWT_ROTATION.md` on approval. This file becomes the plan archive.

## A. Goal + Context

**Goal.** Ship the design that lets the cloud-tier Naavik deployment ($15/mo, multi-tenant — AGENTS.md § Project) rotate per-tenant JWT signing keys without forcing every signed-in user to re-login, and that isolates one tenant's key compromise from every other tenant's session corpus.

**Why now.** Naavik shipped Phase 1 with a single `SECRET_KEY` env var consumed by `services/auth.py:issue_jwt` + `verify_jwt` (HS256, `app_settings.secret_key`; src/services/auth.py:39, 133, 147). That's correct for self-hosted single-tenant — one operator owns the env, one key signs everything, key rotation = restart with new env. It's wrong for multi-tenant cloud because:

- One env var can't carry N keys.
- One key signing everyone's JWTs makes a key-leak a corpus-wide compromise.
- Atomic-swap rotation drops in-flight sessions — terrible UX for paying users.
- Compliance (SOC 2, ISO 27001 — table stakes for a paid cloud tier) requires documented key-rotation cadence + per-tenant blast-radius isolation.

The denylist shipped in plan 50 (0.2.1.04) handles "revoke one user's tokens"; rotation handles "rotate one tenant's signing key without invalidating live sessions."

**Why "Phase 2+" not "now."** ROADMAP row 0.2.7.07:322 explicitly tags this as Phase 2+ multi-tenant cloud feature; self-hosted single-key stays. The single-tenant code path must still work after this design lands — degradation is a hard requirement (D9 below).

**Cross-refs.**
- `AGENTS.md § Tech Stack` — "FastAPI JWT (forms — email + password) — OIDC for self-hosted is Phase 2+." This plan is the LOCAL JWT signer's key management; OIDC (`0.8.0.01`) is the external IdP track — different feature, different plan.
- `AGENTS.md § Key Conventions § CLI` — vault is sunset (DELETED via plan 26 / 0.2.0.01). Encrypted-at-rest local secret storage is FORBIDDEN. Signing keys live in a database table (postgres at-rest encryption is the operator's deployment-config choice) OR in env (single-tenant self-host path).
- `src/services/auth.py:39` — `JWT_ALGORITHM = "HS256"` (today's signer constant; this plan adds RS256).
- `src/models/revoked_jwt.py` — denylist substrate from plan 50; this plan does NOT touch the denylist (orthogonal).
- ROADMAP row 0.2.1.05 — completed; "JWT key rotation CLI" was descoped per plan 26 (CLI sunset).

## B. Proposal (file-by-file)

### B.1. New SQLModel + migration

**File:** `src/models/tenant_signing_key.py` (new — ~70 LOC)

```python
"""Per-tenant JWT signing key. One row per active+grace+retired key per tenant."""

class TenantSigningKeyStatus(str, Enum):
    ACTIVE = "ACTIVE"        # signs new tokens
    GRACE = "GRACE"          # verifies only; rotated out within grace window
    RETIRED = "RETIRED"      # archive only — does not verify

class TenantSigningKey(SQLModel, table=True):
    __tablename__ = "tenant_signing_key"
    id: int | None = Field(default=None, primary_key=True)
    tenant_id: int = Field(foreign_key="tenant.id", nullable=False, index=True)
    kid: str = Field(nullable=False, index=True, unique=True)  # 8-byte URL-safe base64; goes in JWT header
    algorithm: SigningAlgorithm = Field(sa_column=Column(Enum(SigningAlgorithm), nullable=False))
    status: TenantSigningKeyStatus = Field(sa_column=Column(Enum(TenantSigningKeyStatus), nullable=False, default=TenantSigningKeyStatus.ACTIVE))
    public_key_pem: str = Field(nullable=False)               # PEM-encoded; safe to expose
    private_key_pem: str = Field(nullable=False)              # PEM-encoded; postgres at-rest is the host's job
    created_at: datetime = Field(default_factory=lambda: datetime.now(UTC))
    rotated_at: datetime | None = Field(default=None)         # set when status → GRACE
    retired_at: datetime | None = Field(default=None)         # set when status → RETIRED
```

**Migration:** `migrations/versions/0011_tenant_signing_key.py` — additive; creates `tenant_signing_key` table + 2 postgres ENUMs (`tenantsigningkeystatus`, `signingalgorithm`).

**Tenant table.** `Tenant` is assumed to exist by the time this ships — currently Naavik is single-tenant (`User.id` IS the tenant for all practical purposes). The plan lands a stub `Tenant` model alongside this work OR coordinates with the multi-tenancy plan (0.8.0.NN, separate track). For Phase 2+ scope this plan ASSUMES `Tenant` exists; if not, the migration adds a one-row stub (`Tenant.id=1, name='self-hosted'`) and `TenantSigningKey.tenant_id` always equals 1 on self-hosted deployments. **OQ.7** captures this.

### B.2. Signer / verifier rewrite

**File:** `src/services/auth.py` — rewrite `issue_jwt` + `verify_jwt`; add 3 helpers.

```python
# Signer
async def issue_jwt(session: AsyncSession, *, user_id: int, tenant_id: int, keep_signed_in: bool = False) -> str:
    active = await get_active_signing_key(session, tenant_id=tenant_id)
    if active is None:
        raise RuntimeError("no active signing key for tenant — rotation in progress?")
    header = {"kid": active.kid, "alg": active.algorithm.value}
    payload = {
        "sub": str(user_id),
        "tid": str(tenant_id),          # NEW: tenant id for verifier routing
        "jti": secrets.token_urlsafe(16),
        "iat": int(now.timestamp()),
        "exp": int((now + ttl).timestamp()),
    }
    if active.algorithm == SigningAlgorithm.RS256:
        return jwt.encode(payload, active.private_key_pem, algorithm="RS256", headers=header)
    elif active.algorithm == SigningAlgorithm.HS256:
        return jwt.encode(payload, active.private_key_pem, algorithm="HS256", headers=header)

# Verifier
async def verify_jwt(session: AsyncSession, token: str) -> tuple[int, int, str, datetime] | None:
    # 1. Parse header w/o verifying signature to get kid.
    try:
        unverified_header = jwt.get_unverified_header(token)
    except jwt.InvalidTokenError:
        return None
    kid = unverified_header.get("kid")
    if not kid:
        return None
    # 2. Lookup key by kid; reject if status == RETIRED.
    key = await get_signing_key_by_kid(session, kid=kid)
    if key is None or key.status == TenantSigningKeyStatus.RETIRED:
        return None
    # 3. Verify with the key's public material + the key's declared algorithm.
    try:
        decoded = jwt.decode(
            token,
            key.public_key_pem if key.algorithm == SigningAlgorithm.RS256 else key.private_key_pem,
            algorithms=[key.algorithm.value],
        )
    except (jwt.InvalidTokenError, ValueError):
        return None
    # 4. Existing claims extraction; return (user_id, tenant_id, jti, expires_at).
```

**Helpers:**

```python

async def get_signing_key_by_kid(session, *, kid) -> TenantSigningKey | None

```

### B.3. Rotation service

**File:** `src/services/signing_key_rotation.py` (new — ~150 LOC)

```python
async def rotate_signing_key(
    session: AsyncSession,
    *,
    tenant_id: int,
    grace_window_days: int = 7,
    actor: str,  # "scheduler:cron" | "ui:user@email" — for audit
) -> TenantSigningKey:
    """Generate a new keypair, mark old ACTIVE → GRACE with rotated_at = now,
    insert new ACTIVE row. Atomic in one transaction.

    Postcondition: tenant has exactly one ACTIVE key. May have 0..N GRACE keys.
    """

async def expire_grace_keys(session: AsyncSession, *, now: datetime | None = None) -> int:
    """Find GRACE keys whose rotated_at + grace_window_days < now. Mark RETIRED.
    Returns count expired. Idempotent — safe to run every scheduler tick.
    """

async def ensure_active_key(session: AsyncSession, *, tenant_id: int) -> TenantSigningKey:
    """If tenant has no ACTIVE key (deployment race or migration), generate one.
    Safety net — should never fire in normal operation, but guards against
    lockout if the rotation transaction rolls back partway."""
```

## C. Option matrices (10 design decisions)

### C.1. Key storage location (D1)

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **DB-per-tenant table (RECOMMENDED)** | Native DB transaction semantics for rotation; works on every deploy target (Docker, Nix, cloud) | Zero new infra; postgres at-rest encryption is operator config (already a self-host requirement for `users.password_hash`) | Compromised postgres = all keys leaked. Mitigated by postgres at-rest encryption + filesystem perms (same trust model as `users.password_hash` already relies on) | One table, one migration; no external dep | None — keys live in our DB |
| KMS-backed (AWS KMS / GCP KMS / HashiCorp Vault) | Industry-standard key isolation; key material never touches Naavik memory beyond the unwrap | New env var `KMS_KEY_ID`; cloud-vendor SDK dep (boto3, google-cloud-kms); test infra needs a KMS mock | KMS outage = signer down (mitigated by short-lived envelope keys) | Operator must configure KMS; another moving part | Lock-in to one cloud vendor's KMS (or self-host HashiCorp Vault) |
| Env-per-tenant | Trivial implementation | Doesn't scale beyond ~5 tenants (env var per tenant = unworkable) | Rotation = restart = downtime per tenant | None | None |

**Recommendation: DB-per-tenant.** Self-host parity (no new infra); transactional rotation; postgres at-rest is already a host responsibility for password hashes. KMS becomes an optional cloud-tier add-on later (envelope encryption — encrypt `private_key_pem` with a KMS data key; the column stays the same, just stores ciphertext + KMS ref).

### C.2. Key algorithm (D2)

| Option | Token size | Signer-verifier split? | CPU cost (sign/verify) | Lib support |
|---|---|---|---|---|
| HS256 (current) | smallest | NO — symmetric; signer-leak = verifier-leak | ~5µs / ~5µs | universal |
| **RS256 (RECOMMENDED)** | +200 bytes (2048-bit) | YES — public verifier; private signer | ~1.5ms / ~50µs | universal (pyjwt + cryptography ship; already deps) |
| EdDSA (Ed25519) | +50 bytes vs HS256 | YES | ~50µs / ~150µs | pyjwt requires `cryptography` ≥ 36 (already pinned ≥ 41); broadly supported |

**Recommendation: RS256.** Asymmetric is required for the future Naavik-API + Naavik-Worker split (workers verify; only the API signs). EdDSA is faster + smaller but adoption is uneven for JWT verifiers (e.g., legacy SDKs); RS256 is the universal default. Token-size delta (~200B) is negligible vs the existing JWT payload (~500B). Cost: 1.5ms/sign on login (not hot path).

### C.3. Rotation cadence (D3)

| Option | Operator load | Security strength | Compliance fit |
|---|---|---|---|
| Manual-only | low (operator clicks when paranoid) | weak (operators forget) | weak (auditors want documented cadence) |
| Fixed schedule (90d) | zero (cron-driven) | strong (predictable rotation) | strong (SOC 2 maps directly) |
| Usage-based (every N issuances) | medium (must instrument counters) | medium (rotation rate varies w/ load) | medium (auditors want time-bound) |
| **Hybrid: 90d default + on-demand UI button (RECOMMENDED)** | zero default; one click on incident | strong | strong |

**Recommendation: Hybrid 90-day + on-demand.** Default `Settings.jwt_rotation_days = 90` is configurable per-tenant; emergency rotations fire via the Settings UI button. APScheduler job runs daily, checks all tenants, rotates anyone whose ACTIVE key is older than `jwt_rotation_days`.

### C.4. Grace-period strategy (D4)

| Option | UX disruption | Attack surface during grace |
|---|---|---|
| Atomic swap (no grace) | severe — every signed-in user re-logins on rotation | none — old key invalidated instantly |
| **Dual-key window (7d default, RECOMMENDED)** | zero — grace key verifies old tokens; new tokens carry new kid | new tokens carry new kid; old tokens carry old kid; grace key kept verifiable for 7d then RETIRED |
| Token-version-tied | medium — forces re-login on next token refresh | depends on TTL |

**Recommendation: Dual-key window, 7-day default.** Industry-standard. JWT TTL is 24h default / 30d "keep signed in"; 7d grace covers 24h tokens easily, plus the 30d ones get re-issued during normal use within the grace window. `Settings.jwt_grace_window_days = 7` configurable 1-30.

**Edge case:** if rotation cadence (90d) is shorter than the max JWT TTL (30d), all "keep signed in" tokens survive at most 2 rotations before forced re-login at refresh. Acceptable; document in JWT_ROTATION.md § H.

### C.5. Key identifier — `kid` claim (D5)

| Option | Token size | Verifier complexity | Info leak |
|---|---|---|---|
| **Required `kid` (RECOMMENDED)** | +12 bytes for 8-byte b64 kid | O(1) lookup by kid index | kid is PUBLIC by spec (JWT header is unencrypted); reveals key-id only, which is fine |
| Try-all-active-keys | zero | O(N) verify attempts per token; N = #(ACTIVE + GRACE); 2-3x verify cost worst-case | none |
| `kid` optional, fallback to try-all | smallest tokens for legacy clients | verifier must handle both paths | partial |

**Recommendation: Required kid.** Token-size delta is in the noise. Verifier complexity drops O(N) → O(1). `kid` is PUBLIC by JWS spec — it's an identifier, not a secret. Forged-kid attacks are rejected at the key lookup step (kid → key.tenant_id; if claim's `tid` ≠ key.tenant_id, reject).

### C.6. JWKS endpoint exposure (D6)

| Option | Use case | Surface |
|---|---|---|
| **Private only — no JWKS endpoint (RECOMMENDED FOR v1)** | Internal verifier only (Naavik API + Naavik Worker share DB) | zero new HTTP routes |
| Expose `/.well-known/jwks.json` per tenant | External services verify Naavik-issued JWTs (n8n, custom integrations) | new tenant-scoped public route; cache header tuning |

**Recommendation: Private-only for v1.** External verifier need is hypothetical until n8n/portfolio integrations actually want to verify Naavik JWTs (none today; n8n consumes events, doesn't verify our JWTs). Adding JWKS later is additive (~50 LOC + one route). Don't over-engineer. The DESIGN.md graduates with a "JWKS endpoint reserved — add when external verifier need surfaces" stub.

### C.7. Per-tenant vs deployment-wide isolation (D7)

| Option | Blast radius | Operator complexity |
|---|---|---|
| **Per-tenant keypair (RECOMMENDED)** | one tenant compromised = one tenant rebuilt | rotation per tenant; same code path covers self-host (1 tenant) and cloud (N) |
| Shared deployment-wide | one key leak = entire deployment | simpler — one rotation event |
| KMS-managed per-tenant key-ID | per-tenant blast isolation + KMS-grade audit | more infra |

**Recommendation: Per-tenant keypair.** Required for cloud-tier blast-radius isolation. Self-hosted single-tenant uses the same code path with one row in `tenant_signing_key` — no perf overhead, identical semantics.

### C.8. Old-key destruction policy (D8)

| Option | Forensics | Compliance |
|---|---|---|
| Immediate-after-grace | none | matches "keys not retained beyond use" guidance |
| **Archived RETIRED (read-only audit; RECOMMENDED)** | full — investigators can prove which key signed a disputed token | matches SOC 2 "key history" guidance |
| Soft-deleted on operator request | partial | medium |

**Recommendation: Archived RETIRED rows persist.** `status=RETIRED` rows stay in the table forever (until operator runs a manual purge). Disk cost is trivial (~2KB per RSA-2048 key). Forensics value during incident response is high — proving "this JWT was signed by key X which was active during window Y" requires the row.

### C.9. Self-hosted single-tenant degradation (D9)

| Option | Code complexity | Self-host perf overhead |
|---|---|---|
| **Multi-tenant path also serves single-tenant (RECOMMENDED)** | low — single code path | one extra DB roundtrip per JWT issue + verify (~1ms) |
| Separate single-key fast-path (env-only) | medium — two code paths | none |

**Recommendation: Same code path.** One row in `tenant_signing_key` for the self-hosted instance, `tenant_id=1`. The DB roundtrip is ~0.5ms over the existing 1-2ms JWT verify; negligible. Two code paths = drift bait + double the test surface. **Fallback contingency:** if `tenant_signing_key` is empty (fresh install before first request), `ensure_active_key` bootstrap-creates one on demand (idempotent; safe under concurrent first-requests).

### C.10. Rotation trigger mechanism (D10)

| Option | Discoverability | Audit trail | CLI sunset violation? |
|---|---|---|---|
| **APScheduler cron + Settings UI button (RECOMMENDED)** | UI button + scheduler log | full — `actor` column in audit log records `"scheduler:cron"` vs `"ui:user@email"` | NO |
| Operator CLI subcommand (`naavik rotate-jwt-key`) | low for new operators | full | YES — CLI sunset (0.2.0.02) |
| Webhook (POST /admin/rotate) | external | partial | NO but exposes internals |

**Recommendation: APScheduler cron + Settings UI button.** CLI sunset forbids the `naavik rotate-jwt-key` subcommand path. Settings UI button is operator-facing + discoverable. APScheduler cron handles the cadence-driven case.

## E. Test plan

### E.1. Unit
- `kid` header injection on every issue
- Lookup by kid returns correct key
- Algorithm mismatch (token says HS256, key is RS256) → reject
- Empty/null kid header → reject
- `tid` claim mismatch with key's tenant_id → reject (forged-kid attack)
- Grace-key token decoded successfully
- Retired-key token rejected with same error as forged-kid (no info leak)

### E.2. Integration
- Rotate-while-tokens-in-flight: issue 5 tokens, rotate, verify all 5 still decode within grace window
- Expire-grace-during-active-session: 5 tokens issued with old key, advance clock past grace, verify all 5 rejected at next request
- Self-host single-tenant: zero-rows in `tenant_signing_key` → first request bootstraps one ACTIVE key via `ensure_active_key`
- APScheduler fires `rotate_signing_keys_job` on schedule; verify rotation occurred

### E.3. Security
- Forged-kid attack: tamper JWT header to point at another tenant's kid; reject due to `tid` claim mismatch
- Replay of RETIRED key: token signed by RETIRED key (history) rejected
- Lockout safety net: simulate transaction rollback during rotation; `ensure_active_key` recovers
- Tenant isolation: tenant A's user cannot rotate tenant B's key via UI (IDOR)

## F. Risk + mitigation

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| **Lockout — all keys RETIRED, no ACTIVE** | LOW | CRITICAL (no JWT can be issued; entire tenant locked out) | `ensure_active_key` safety net invoked on every `issue_jwt` path; auto-bootstraps if 0 ACTIVE. Plus: alembic migration is constraint-protected — refuse to retire the last ACTIVE row of a tenant (CHECK constraint `at least one ACTIVE per tenant`) |
| **Race on rotation — two operators click "Rotate now" simultaneously** | LOW | MEDIUM (two new keys created; one becomes orphan) | Rotation transaction takes a SELECT ... FOR UPDATE on the active row before insert. Second clicker gets a no-op + "already rotating" message |
| **Grace window expires while tokens active** | MEDIUM | LOW (affected users re-login) | Document in README + show next-rotation timestamp in Settings UI |
| **RS256 keygen cost on first-request boot** | LOW | LOW (cold start +500ms) | Bootstrap happens once per tenant per deployment; warm path is O(1) DB read |
| **APScheduler doesn't fire** | LOW | LOW (rotation skipped one day; backfill on next tick) | Existing APScheduler observability (`docs/RUNBOOK.md`) catches missed-fires; daily idempotency means missed ticks self-heal |
| **postgres at-rest unencrypted** | MEDIUM | HIGH (signing keys leak) | Already a Phase 1 invariant for password hashes; document in JWT_ROTATION.md § "Operator responsibilities" |
| **JWT_ROTATION.md drift vs auth.py** | MEDIUM | MEDIUM | Design doc graduation (Type: design) makes JWT_ROTATION.md canonical; PR template requires it to be updated alongside auth.py changes |
| **Single-tenant Naavik deployment overhead** | LOW | LOW | One row in `tenant_signing_key`; +0.5ms per JWT verify (negligible) |

## G. Surface-impact summary

- **New DB table:** `tenant_signing_key` (one row per active+grace+retired key per tenant; per-tenant blast isolation)
