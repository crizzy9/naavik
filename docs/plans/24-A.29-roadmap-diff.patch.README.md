## What this patch does

Rewrites `ROADMAP.md` from the legacy two-level phase scheme (`A.29` / `PC.6a` / `2.12` / `DEF-05`) to the new 4-level semver task-ID schema (`MAJOR.MINOR.PATCH.POSITION`) per `docs/design/PHASE_NUMBERING.md` § 1.

Every existing ROADMAP row keeps its `Notes` column content (with a legacy-ID parenthetical added for greppability); the **section headers** and **`#` column** are what changes. This is a RENAME pass, not a content rewrite.

Specifically:

- **`### Phase 0` + `### Phase 1` + `### Pre-Phase-2 paper cuts` + `### Phase A`** → ONE collapsed `### 0.1.0` section (the historical bundle per D.6 REV-3 single-fold).
- **`### Phase 2`** → `### 0.2.0` (with sub-task renumber per D.10; vault + Job models marked HIGH).
- **`Phase 1 deferred items` table (DEF-01..DEF-25 + JWT-denylist)** → six thematic patch-release sections `### 0.2.1` (security) / `### 0.2.2` (UI) / `### 0.2.3` (ATS-scraper) / `### 0.2.4` (tracking) / `### 0.2.5` (observability) / `### 0.2.6` (tooling + paper-cuts) per D.9.
- **`### Phase 2.5: Agent-system follow-ups`** → `### 0.7.0` (separate agent-system follow-up release per architect Decision B; preserves the existing user-locked separation from product Phase 6).
- **`### Phase 3`, `### Phase 4`, `### Phase 5`, `### Phase 6`** → `### 0.3.0`, `### 0.4.0`, `### 0.5.0`, `### 0.6.0` (1:1 rename per D.2).
- **A.30 (#72)** → standalone `### 0.1.1` release (Python rewrite of legacy bash).
- **A.31 (#74)** → fold into `0.1.1` as second sub-task (CHANGELOG markdown sanitization; same Python package as A.30, smaller scope, same release-cycle).
- **A.28a (#64)** → fold into `0.2.6.NN` (tooling/paper-cut theme match).
- **`## Priority Queue` section** at top of ROADMAP → REPLACED with a one-paragraph pointer to the derived view `.claude/naavik-ops task list 0.2.0` per D.13 (the canonical "what should I work on" surface is now release-version-derived).
- **`## Agent System (mirror conventions)`** mapping table at bottom → updated for the new release-version Milestones and removes the legacy `Phase A` / `Pre-Phase-2 paper cuts` / `Phase 1.x deferred` / `Phase 2.5` rows.

**Outcome:** `### 0.7.0` holds the 12 deferred Phase 2.5 items (A.9, A.10, A.18, A.19, A.20, A.21, A.22, A.23, A.24, A.25, A.26, A.27). A.28a moves to `### 0.2.6` per theme match.

## Phase 1 collapse granularity rationale (architect Decision: deliverable-level)

Per D.1 Option B, Phase 1's 5 Waves with ~80 sub-tasks must collapse. Three sub-options:

| Option | 0.1.0 position count | Pros | Cons |
|---|---|---|---|
| Per-Wave (5 positions) | ~36 | Tightest | Loses major-deliverable specificity (auth, vault, services indistinguishable from screens within one Wave 4 slot) |
| **Per-deliverable (14 positions)** (LOCKED) | ~48 | Preserves "this position covers the 20-entity SQLModel substrate; that position covers Typst PDF generation"; future readers can grep | Slightly more slots to manage; still well under 99-cap |
| Per-sub-task (~80 positions) | >99 | Maximum forensic detail | Blows the 2-digit position cap |

**Outcome:** Phase 1 gets 14 deliverable-level positions (`0.1.0.10` – `0.1.0.23`); sub-task detail (e.g. "11 page templates", "20 SQLModel entities") survives in Notes column prose per D.1 Option B contract.

## Rollback contract

If `step_7_rewrite_roadmap()` fails mid-apply:

1. `git diff ROADMAP.md` shows partial application (probably clean — `git apply` is all-or-nothing at the file level).
2. `git checkout HEAD -- ROADMAP.md` restores authoritative state.
3. Re-run `python .claude/migrations/A.29-phase-renumber.py --apply` — idempotent per script header; redirects-map check skips already-migrated GitHub state from earlier successful steps; step 7 retries.

If the patch needs to be REGENERATED (e.g. ROADMAP drifts before Wave 5 runs):

1. Re-run architect dispatch with this README + the migration script + the current ROADMAP.md state.
2. Architect re-produces the diff against the new HEAD.
3. Patch supersedes; archived at `docs/plans/archive/24-A.29-roadmap-diff.patch` post-Wave-5.
