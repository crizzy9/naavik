## Proposal

Three items shipped in one PR on `feat/0.2.5-observability-batched-closeout`. Each item must independently pass `uv run ruff check . && uv run pytest -x`. Each closes a filed ROADMAP row via the BOOKKEEPING mark-done. Engineer drives the work; architect + hacker review in parallel.

### Item 1 — Submission-result observability dashboard (0.2.5.02, ROADMAP `0.2.5.02`)

**Rationale.** Operator needs to see "ATS X has been failing with kind=CAPTCHA on board=GREENHOUSE 14 times this week" at a glance. The data already exists in `Application.submission_artifacts["last_failure"]` JSONB (shape: `{kind, message, captured_at}`, written by `application_service._record_failure` at `src/services/application_service.py:354`). Today it's only surfaced inline on the Failed-DRAFT row in the tracking page. The closeout adds an aggregated dashboard at Settings · Submissions sub-tab.

**Files.**

- `src/services/application_service.py` — new `async def aggregate_submission_failures(session, user_id, *, since_days: int = 30) -> list[dict]`. Single `SELECT` over `Application` (soft-delete-aware via `deleted_at IS NULL` filter) returning rows shaped `{board: str, failure_kind: str, count: int, latest_at: datetime}`. Source data: JSONB path-extract `submission_artifacts->'last_failure'->>'kind'`. `GROUP BY board, failure_kind`. Order: `count DESC`. Postgres-native `jsonb_extract_path_text` via `sqlalchemy.func` — no raw SQL. Empty result for users with zero failed DRAFTs.
- `src/ui/routes/settings.py` — register new tab key `"submissions"` in `_TAB_TEMPLATES` mapping to `pages/_settings_submissions.html`. Extend `_ctx_for_tab` to call `aggregate_submission_failures` when `tab == "submissions"` and inject `submission_failures: list[dict]` into ctx. Settings page tab strip auto-renders new tab via existing pattern (see existing `_TAB_TEMPLATES` enumeration).
- `src/ui/templates/pages/_settings_submissions.html` — new partial. DaisyUI table: columns `BOARD / FAILURE KIND / COUNT / LATEST AT`. Chip-style severity coloring by `failure_kind` (CAPTCHA = amber, AUTH_REQUIRED = rose, RATE_LIMITED = slate, others = neutral). Empty state: card with `inbox` Lucide icon + "No submission failures recorded yet."
- `src/ui/templates/pages/settings.html` — add `submissions` to tab-strip enumeration (mirror the existing tab loop; static label "SUBMISSIONS").
- (No new env var, no migration, no CLI extension.)

**LOC.** ~50 LOC service helper (sqlalchemy `func.jsonb_extract_path_text`) + ~60 LOC template + ~15 LOC route wiring. **Tests** (~50 LOC): empty state (user with no failed DRAFTs returns `[]`); populated state (3 boards × 2 kinds → 6 aggregate rows, count + latest_at correct); per-user IDOR (User A's failures don't leak to User B's aggregate).

### Item 2 — Daily LLM cost-cap dashboard widget (0.2.5.03, ROADMAP `0.2.5.03`)

**Rationale.** Wave 6 will ship cap enforcement (cron flip from eager → lazy on cap-trigger). This item ships the visible progress UI as Settings · LLM Provider tab polish. Today the cap field (`Settings.daily_llm_cost_cap_usd`) exists in the DB but is invisible to operators — they discover it only in `.env.example`. The widget surfaces it next to the existing THIS MONTH / AVG / RATE LIMIT cost cards.

**Files.**

- `src/services/llm_tracker.py` — new `async def today_cost_usd(session, user_id) -> float`. Single `SELECT COALESCE(SUM(cost_usd), 0.0) FROM api_usage WHERE user_id = :u AND occurred_at >= :midnight_utc`. `midnight_utc` computed as `datetime.now(UTC).replace(hour=0, minute=0, second=0, microsecond=0)`. Returns `0.0` for users with no calls today.
- `src/ui/routes/settings.py` — `_ctx_for_tab` extends ctx with `today_cost_usd: float` and `cost_cap_usd: float | None` (passthrough from `settings.daily_llm_cost_cap_usd`) on the `llm-provider` tab path only (skip the query for other tabs — N+1 dodge).
- `src/ui/templates/pages/_settings_llm.html` — new card-row after the existing 3-cost-card grid (lines 103–119). DaisyUI progress bar via `<progress class="progress progress-primary">` with `value=today_cost_usd` `max=cost_cap_usd`. Pct label, "$X.XX of $Y.YY today" subtext, "resets at midnight UTC" hint. Cap unset (`cost_cap_usd is None`) → render "No daily cap set" placeholder card linking to `.env.example` comment ("Set `DAILY_LLM_COST_CAP_USD` in .env"). Over-cap state (`today_cost_usd >= cost_cap_usd`) → swap progress color to `progress-error` + amber `triangle-alert` Lucide icon + "Cap exceeded — Wave 6 will throttle new LLM calls when enforcement ships."
- (No new env var — `daily_llm_cost_cap_usd` already config-loaded via `.env`. No migration. No CLI extension.)

**LOC.** ~25 LOC service helper + ~30 LOC template addition + ~10 LOC route wiring. **Tests** (~30 LOC): cap unset → widget renders placeholder card; cap set + zero spend → 0% bar; cap set + partial spend → correct pct; over-cap state → progress-error color + warning text; midnight UTC boundary (sum excludes yesterday's calls).

### Item 3 — Scraper-run history UI page (0.2.5.04, ROADMAP `0.2.5.04`)

**Rationale.** `JobScrapeRun` model (shipped 0.2.0.05) has been silently accumulating rows for every scheduled scrape since 0.2.0.10 wired the scheduler. No UI surface today. Operators debugging "why is LinkedIn returning zero jobs" have to grep logs or open a psql session. The closeout adds a recent-runs table to Settings · Sources sub-tab (fold-in — same tab being extended by 0.2.0.16 first-run walkthrough; engineer scopes the merge as additive partial).

**Files.**

- `src/services/job_service.py` — new `async def list_recent_scrape_runs(session, user_id, *, limit: int = 50) -> list[JobScrapeRun]`. Single `SELECT FROM job_scrape_run WHERE user_id = :u ORDER BY started_at DESC LIMIT :limit`. SQLModel `select(JobScrapeRun)` per `count_jobs_by_source` pattern at line 359. Returns `list[JobScrapeRun]` — caller projects via `JobScrapeRunRead.model_validate` to avoid `raw_meta` JSONB exposure (defense-in-depth, same pattern as PR #146 item 3 / 0.2.0.11c).
- `src/ui/routes/settings.py` — `_ctx_for_tab` extends ctx with `recent_scrape_runs: list[JobScrapeRunRead]` (projected) on the `sources` tab path only. Pass through to template.
- `src/ui/templates/pages/_settings_sources.html` — APPEND new `<section>` after the existing "Workday companies" section. DaisyUI table: columns `SOURCE / STATUS / STARTED / DURATION / LISTINGS / NEW / ERRORS`. Status chip-colored via existing JobScrapeStatus enum (SUCCESS = emerald, PARTIAL = amber, FAILED = rose, TIMED_OUT = rose, RUNNING = sky). Duration formatted via `{{ run.duration_ms or '—' }}ms`; errors as truncated `errors[0] | truncate(60)` with `... +N more` suffix if `errors | length > 1`. Empty state: "No scraper runs yet — runs appear here when the scheduler fires."
- (No new env var, no migration, no CLI extension. Tab key already registered.)

**LOC.** ~40 LOC service helper + ~50 LOC template section + ~10 LOC route wiring. **Tests** (~50 LOC): empty state; populated with mixed statuses (5 runs spanning all 5 status enum values + 2 sources); per-user IDOR (User A's runs don't leak); LIMIT clause caps at 50 even when 60 rows exist; `raw_meta` not in projection output.
