# 25 · `0.1.1` — Legacy bash → Python rewrite + mutating task subcommands + CHANGELOG sanitization

## Goal

Replace the two legacy bash dispatchers — `scripts/gh-project.sh` (1469 LOC, 21 subcommands, sole writer of `.claude/github-issue-map.json` + GitHub Project state) and `scripts/agent-memory.sh` (843 LOC, 12 subcommands, sole writer of `.claude/memory/*.jsonl`) — with native Python implementations under `.claude/naavik_ops/gh.py` + `.claude/naavik_ops/memory.py`. Land native impls of the 5 mutating `task` subcommands stubbed in A.29 (`insert` / `defer` / `prioritize` / `move` / `renumber`). Roll `scripts/roadmap_parser.py` into `.claude/naavik_ops/lib/roadmap.py`. Fold in two paper cuts: 1-line `.gitignore` add of `.claude/worktrees/` (PR #75 hacker LOW finding) and CHANGELOG.md markdown-escape hardening in `lib/changelog.py:62` (PR #73 hacker LOW Finding 3). Ship as the `0.1.1` patch release post-merge.

## Why

`0.1.0` (A.29 Wave 5) shipped the `.claude/naavik-ops` dispatcher + 4-level semver schema but the `gh` and `memory` subcommand groups are currently subprocess wrappers around the legacy bash scripts (`gh.py:55-67` `_shim`, `memory.py:42-50` `_shim`). The transition was intentional — let A.29 land schema + dispatcher contract first, defer the rewrite to a separate patch release so review surface stayed bounded. That patch is `0.1.1`.

Three pressures force the work now:

1. **Single-writer rule is brittle under bash.** Both scripts hold the sole-writer contract for state files (`AGENTS.md § GitHub state — single writer rule`). The map cache's idempotency, the JSONL atomic append, and the flock-serialized writes are all bash patterns that Python implementations express more clearly (typed errors, dataclasses, pytest assertions). Every future contributor reads bash through subprocess shims first; readability tax compounds.
2. **Mutating task ops are blocked on the rewrite.** A.29 Deviation 1 stubbed `insert` / `defer` / `prioritize` / `move` / `renumber` because they need atomic 3-store mutations (ROADMAP rewrite + Issue title rewrite + map cache write) that are clean in Python and ugly in bash-driving-Python. Until those land, the 4-level schema is read-only for day-to-day shuffling — the user's stated reason for filing A.30 immediately after A.29 was "move-around testing happens AFTER A.30 ships" (memory `A.29-then-A.30-immediate-sequencing`).
3. **One latent security finding has a deadline.** Hacker Finding 3 from PR #73 review flagged `lib/changelog.py:62` `ReleaseEntry.text` as unsanitized — markdown chars in commit-message bodies render directly into released `CHANGELOG.md`. Not exploitable today (Wave 5 closed-Issue ingestion stubs the entries). When A.30 wires real commit ingestion, the latent bug becomes live. Must land in the same release that wires ingestion.

`0.1.1` is the right vehicle because (a) it's a contract change with a security follow-up that already has an Issue (`#74`), (b) bundling lets us delete `scripts/gh-project.sh` + `scripts/agent-memory.sh` + `scripts/roadmap_parser.py` in one wave instead of three (less drift between ROADMAP rows tracking three patch-releases), and (c) the deviations from plan 24 explicitly named A.30 as the home for the 5 mutating subcommands + bash deletion + dual-Bash-grant cleanup. ROADMAP § 0.1.1 rows are already filed at `0.1.1.01` (A.30) and `0.1.1.02` (A.31); this plan implements both.

The shipping invariant after this plan executes: `scripts/` is empty except for `scripts/README.md` documenting the `.claude/naavik_ops/` (agent-system tooling) vs `scripts/` (project-wide user-runnable, post-0.1.1 unused) split. The dispatcher writes Python natively to all state stores. The single-writer rule survives unchanged — only the implementation language flips.

## Proposal

The rewrite is sequenced as **5 waves** (1 less than the brief's suggested 8 — collapsing W5+W6 + W7 into single waves where deliverables compose cleanly). Each wave lands as a sequenced commit on a single branch `feat/0.1.1.01-bash-to-python`. PR opens at end of W5. Wave 6 (release ceremony) is post-merge.

The plan body uses **D-numbered design decisions** that compose into wave deliverables (matching plan 24's convention so reviewers cross-refer cleanly). § Build sequence at end resolves D-IDs into actual wave order. § Risk + mitigation rolls up cross-wave hazards.

### Cross-cutting context

**Sole-writer invariant.** After this plan executes, `.claude/naavik-ops gh ...` is the only path to `.claude/github-issue-map.json` + GitHub Project state, AND `.claude/naavik-ops memory ...` is the only path to `.claude/memory/*.jsonl`. ### D.1 — Cutover strategy: hard cutover within `0.1.1` (sole writer flip mid-branch)

**Option matrix.**

| Option | A — Dual-write transition (keep bash scripts; Python and bash both write) | B — Hard cutover within the same release (bash deleted at end of W3) | C — Two patch releases (`0.1.1` ports gh + memory only; `0.1.2` deletes bash + adds mutating ops) |

### D.5 — CHANGELOG.md markdown sanitization (A.31, Issue #74): Wave 1 (before the rewrite touches `lib/changelog.py`)

**Option matrix.**

| Option | A — Wave 1 (sanitize at `ReleaseEntry` construction time; safe for ALL writers) | B — Wave 4 (sanitize at `render_release` time; only impacts rendered output) | C — Skip; defer to `0.1.2` | D — Strip-newlines + leading `#` only (minimal: handle header smuggling, ignore link injection) |
|---|---|---|---|---|

| Lock-in | None | None | none | None |

**Recommendation: A.** Sanitize at `ReleaseEntry.text` construction in `lib/changelog.py`. Escape CommonMark special chars per [CommonMark spec § escape characters](https://spec.commonmark.org/0.15/) (`\`, `` ` ``, `*`, `_`, `{`, `}`, `[`, `]`, `(`, `)`, `#`, `+`, `-`, `.`, `!`, `|`, `>`, `<`). Strip embedded newlines (commit-msg bodies can contain them; CHANGELOG bullets must be single-line). Reject inputs containing `\r` (Windows line endings).

Land in Wave 1, BEFORE any closed-Issue-ingestion code in Wave 4 — that ordering is non-negotiable per ROADMAP row `0.1.1.02` ("Must land BEFORE A.30 Wave 5 ingests real commit data"). The wave numbering means the sanitization is on `main` (via merged `0.1.0`) → branched → patched in W1 → still in the working tree when W4 lands ingestion. No window of exploitability ever exists.

**Implementation sketch** (Wave 1 deliverable):

```python
# .claude/naavik_ops/lib/changelog.py — patched in Wave 1

_MD_ESCAPABLE = re.compile(r'([\\`*_{}\[\]()#+\-.!|<>])')

def _sanitize_changelog_text(text: str) -> str:
    """Escape CommonMark special chars + collapse whitespace.

    Per A.31 (Issue #74). Defends CHANGELOG.md from markdown injection in
    commit-msg bodies sourced from PR squash titles + auto-classified entries.
    """
    if "\r" in text:
        raise ValueError("CHANGELOG entry contains CR; refuse")
    # collapse internal newlines + multiple whitespace to a single space
    collapsed = re.sub(r"\s+", " ", text).strip()
    # escape markdown specials
    return _MD_ESCAPABLE.sub(r"\\\1", collapsed)


@dataclass
class ReleaseEntry:
    text: str
    commit_sha: str | None = None

    def __post_init__(self) -> None:
        self.text = _sanitize_changelog_text(self.text)
```

Tests in `tests/test_naavik_ops/test_changelog.py` add 4 cases: leading `#` escaped, `[evil](url)` escaped, embedded newline collapsed, `\r` rejected with `ValueError`.

### D.6 — Native impls of the 5 mutating task subcommands (`insert` / `defer` / `prioritize` / `move` / `renumber`)

Per A.29 Deviation 1 + plan 24 § D.11.2 contract.

Each subcommand is a 3-store atomic operation:

1. **ROADMAP edit** — read `ROADMAP.md`, parse the release-version's table per `lib/roadmap.py`, mutate row positions/titles/priorities, write `ROADMAP.md.tmp`, `os.replace`.
2. **GitHub Issue rewrite** — for each shifted Issue, call `gh.cmd_update_issue_title()` (NEW helper in `gh.py`) which composes `gh issue edit <N> --title "[<new-id>] <title>"` via subprocess + writes new title back to the map cache.
3. **Map cache update** — `.claude/github-issue-map.json:issues` key rewrite (old-ID → new-ID for shifted rows) + `redirects` key add for the old IDs.

**Atomicity model** (per plan 24 § D.11.3 + D.11.2 invariant): write `ROADMAP.md.tmp` + `.claude/github-issue-map.json.tmp` first; only after ALL GitHub `issue edit` calls succeed do we `os.replace` both files. On any failure, delete the `.tmp` files + log + restore previous state. The flock at `~/.naavik/naavik-ops.lock` serializes concurrent invocations (already implemented in `lib/flock.py`).

**Subcommand specs** (file-by-file).

#### `cmd_insert(rest)` — `.claude/naavik_ops/task.py:cmd_insert`

```
naavik-ops task insert <version>.<pos> "<title>" [--effort E] [--priority HIGH|MEDIUM|LOW]
```

Steps:

1. Parse args + validate (`version` 3-level, `pos` `01..99`, title quoted-safe, `--priority` rejected if 4-level position is on a patch release).
2. Acquire flock at `~/.naavik/naavik-ops.lock`.
3. `lib/roadmap.parse_release_section(version)` → list of `{position, status, title, priority, notes}` rows.
4. If `<pos>` is occupied by a `[x]` (frozen done-row) → exit 1 with diagnostic + suggest `<pos+1>`.
5. Compute shift map: every row with `position >= <pos>` AND status != `[x]` gets `position += 1`. Build rename pairs `[(old_id, new_id) for each shifted row]`.
6. Compute new row: `task_id = f"{version}.{pos:02d}"`, status `[ ]`, title, priority, notes empty.
7. **Pre-flight failure check** — for each `new_id` in the rename pairs + the new insert ID, ensure no conflict in the existing map cache.
8. Write `ROADMAP.md.tmp` with shifted+inserted rows.
9. For each `(old_id, new_id)` in rename pairs: call `gh.update_issue_title(map[old_id], f"[{new_id}] {title}")` + update `.claude/github-issue-map.json:issues` + add `redirects[old_id] = new_id`. Buffer in `.claude/github-issue-map.json.tmp`.
10. Call `gh.create_issue(task_id, title, priority=..., effort=..., milestone=version)` to create the new Issue. Stores into `map.tmp`.
11. `os.replace` both tmp files → real paths.
12. Release flock.
13. Print summary: `inserted: <task_id> (Issue #N); shifted: 0.2.0.06→0.2.0.07, 0.2.0.07→0.2.0.08, …`

Idempotency: re-running `insert 0.2.0.05 "Same title"` when `0.2.0.05` already has that title → no-op (detect via reading map cache first; compare titles via the gh API).

Failure modes:
- Shell metachar in title → reject in step 1.
- Step 9 partial — one Issue rewrites then API rate-limits → rollback by re-running the failed GitHub `issue edit` calls with the OLD titles, then delete both `.tmp` files. Worst case (atomicity bug) leaves a small drift; `naavik-ops task check` detects it on next invocation.
- Flock contention → block (default flock semantics); 30-second timeout before bailing.

LOC estimate: ~150 LOC including the helpers.

#### `cmd_defer(rest)` — `.claude/naavik_ops/task.py:cmd_defer`

```
naavik-ops task defer <task-id> [--by N=1 | --to <new-pos>]
```

Steps:

1. Parse args. `--by N` shifts the task by N positions (positive = down/later; negative = up/sooner). `--to <new-pos>` moves to absolute position. Exactly one must be specified.
2. Reject if `<task-id>` is `[x]`.
3. Reject if target position is occupied by an `[x]` row (frozen).
4. Compute the inverse shift set: rows in `[task.position, new_pos]` (or `[new_pos, task.position]` if moving up) shift by ±1.
5. Same atomic 3-store mutation as `insert`.

Idempotency: defer when already at target position → no-op.

LOC estimate: ~80 LOC (mostly reusing `insert`'s shift helpers).

#### `cmd_prioritize(rest)` — `.claude/naavik_ops/task.py:cmd_prioritize`

```
naavik-ops task prioritize <task-id> [--to-priority HIGH|MEDIUM|LOW|unset]
```

**Simpler than `insert` / `defer`** — only mutates Priority field, no position shift, no Issue title rewrite. Touches:

1. ROADMAP: edit the row's Priority column.
2. GitHub Project: call `gh.set_priority(map[task_id], priority)` (via `gh-project.sh set-priority` subprocess shim during W2, native after W2 completes).
3. Map cache: `priorities[task_id] = priority` (new sub-key, populated by A.29 migration's PHASE_A_HISTORICAL_MAP; this command extends it).

No ROADMAP-rewrite of any other row. No Issue title rewrite. Flock still acquired (consistency).

LOC estimate: ~50 LOC.

#### `cmd_move(rest)` — `.claude/naavik_ops/task.py:cmd_move`

```
naavik-ops task move <task-id> <new-version>.<new-pos>
```

**Highest-risk operation** per plan 24 § D.11.2. Two releases mutated atomically.

Steps:

1. Parse + validate. Source `<task-id>` 4-level; destination `<new-version>.<new-pos>` 4-level. Cross-release-priority preservation: if both source and dest are task-level, priority preserved; if dest is a patch (3-level), reject (3-level move-target is invalid).
2. Reject if source is `[x]` (frozen).
3. Reject if dest position is occupied by `[x]`.
4. Compute TWO shift maps: source release's rows `> task.position` shift up by 1; dest release's rows `>= new_pos` shift down by 1.
5. Atomic 3-store write — but ROADMAP needs both release sections rewritten (which is why this is highest-risk). Write `ROADMAP.md.tmp` covering both sections.
6. GitHub: rewrite all shifted Issue titles in both releases + rewrite the moving Issue's title + update its `milestone` from `<old-version>` to `<new-version>`.
7. Map cache: rewrite affected `issues` keys + add `redirects` entries for old IDs.

Failure mode: dest release's rollback succeeds but source's fails → orphan ID. Mitigation: write `ROADMAP.md.tmp` covering BOTH source + dest releases atomically in one `os.replace`; rollback if any single Issue rewrite fails.

LOC estimate: ~180 LOC including the source-vs-dest shift computation.

#### `cmd_renumber(rest)` — `.claude/naavik_ops/task.py:cmd_renumber`

```
naavik-ops task renumber <version>
```

Compact active gaps within a release. Done rows (status `[x]`) unchanged; active rows (`[ ]`/`[~]`) compact toward the low end.

Example: `0.2.0.01 [x], 0.2.0.02 [x], 0.2.0.04 [~], 0.2.0.06 [ ]` → `0.2.0.01 [x], 0.2.0.02 [x], 0.2.0.03 [~], 0.2.0.04 [ ]`.

Steps:

1. Parse `<version>`.
2. Read release rows. Sort by current position.
3. For each active row, compute its target position (next-free after the last `[x]`).
4. Build rename pairs. Apply atomic 3-store mutation as `insert`.

LOC estimate: ~100 LOC.

**Shared helpers** (factored out of the 5 subcommands; new in `.claude/naavik_ops/task.py`):

- `_compute_shift_map(release_rows, insert_pos, direction)` — returns `[(old_id, new_id), ...]`.
- `_apply_atomic_3store(roadmap_diff, issue_renames, map_diff)` — the shared atomic-write helper. Flock + tmp + replace.
- `_validate_rename_pair(old_id, new_id, existing_map)` — pre-flight conflict check.
- `_update_redirects(old_id, new_id, map_dict)` — append to `redirects` sub-key.
