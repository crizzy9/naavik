# 76 · 0.4.0.08 — Sponsorship-gate enforcement at submission

## Goal

Block submission of any Application whose linked Job requires US
citizenship or a green card when the calling user's Profile says
they need sponsorship. Belt-and-suspenders defense on top of the
scorer's score-time visa filter — protects against race conditions
where Job.score was computed before Profile.visa_sponsorship_needed
was set, OR where the scorer was bypassed entirely (manual
applications with a real job_id).

## Why

AGENTS.md § Owner Profile (Shyam Padia, H1B + i-140 pending) requires
"score 0 for jobs requiring US citizenship, Green Card, or no
sponsorship." The scorer's visa filter (`scorer/visa.py:35-67`)
honors this at score time. The submission path does NOT independently
re-check.

Three concrete failure scenarios identified in `docs/design/research/0.4.0-AUDIT.md § D`:

1. Race — Job scored before Profile.visa_sponsorship_needed was set;
   Job.score is non-zero; right-swipe queues; cron submits.
2. Manual — `create_manual` Application bypasses scoring; operator
   might submit to a no-sponsorship Job by error.
3. Stale — Scraper didn't extract visa_restrictions on first pass;
   LLM extraction filled it later; Job.score reflects null pre-extract.

Without this gate, an H1B operator could auto-submit to a
US-citizen-only job. Violates Owner Profile rule. This is the
foundation plan in the 0.4.0 sequence — Plans 77-82 all assume
`validate_submittable` enforces the gate.

## Proposal

Single-commit, single-file logic change with new tests. No DB
migration, no new env var, no new CLI command, no new UI surface.

### D.1 Service-layer change

`src/services/application_service.py` — extend `validate_submittable`
(~line 279). Pseudocode:

```python
async def validate_submittable(session: AsyncSession, application: Application) -> None:
    # existing checks: docs_state, screener answers...

    # NEW: sponsorship-gate belt-and-suspenders
    if application.job_id is not None:
        from services.scorer.visa import needs_visa_zero_out

        profile = (
            await session.exec(
                select(Profile).where(Profile.user_id == application.user_id)
            )
        ).one_or_none()
        job = (
            await session.exec(select(Job).where(Job.id == application.job_id))
        ).one_or_none()

        if profile is not None and job is not None and needs_visa_zero_out(profile, job):
            raise ValidationError(
                "Job requires sponsorship Naavik can't provide. "
                "Submission blocked. Update Profile.visa_sponsorship_needed "
                "if you have a valid work authorization for this role.",
                code="visa_incompatible",
            )
```

Key choices:

- **Reuses `scorer.visa.needs_visa_zero_out`** — same predicate as
  the scorer. Zero new visa logic; one source of truth for the rule.
- **Gates only when `application.job_id IS NOT NULL`** — manual
  entries with no Job context bypass. Operator's intent is explicit
  there.
- **Reads Profile + Job inline** — application_service doesn't carry
  Profile cache; cost is one extra SELECT per submission, acceptable
  for a safety check.
- **Uses lazy import** to avoid `services.scorer` ↔ `application_service`
  circular dep risk.

### D.2 ValidationError code surface

`ValidationError(code="visa_incompatible")` is a new error code. The
following downstream paths need to handle it gracefully:

- `submit_draft` (line ~422) — already wraps `validate_submittable`
  in a try/except that surfaces as HTTP 409 with `code` in body.
  No change needed.
- `process_auto_apply_queue` (line ~718) — catches `ValidationError`,
  logs, skips. Already handles unknown codes.
- HTMX submit route at `/_fragments/apply/submit-now/<id>` — should
  render the friendly message text. Existing 409 handler suffices.

### D.3 No new tests for visa.needs_visa_zero_out

That logic shipped with plan 65 / 0.3.0 and is already covered. New
tests cover the integration point only.

### Risk + mitigation

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Profile.visa_sponsorship_needed is None on legacy profiles → `needs_visa_zero_out` returns False (correct), no false-positive blocks | LOW | LOW | Already handled by `scorer/visa.py:44-45` early-return |
| Cron loops on a visa-blocked DRAFT (revert SAVED but stays SAVED forever) | LOW | LOW | Behavior is identical to existing failure modes — operator manually re-queues after fixing profile |
| Sponsorship check on every submit adds ~10ms latency (two extra SELECTs) | LOW | LOW | Acceptable; ATS submission itself is 500ms+ |
| `update_status(APPLIED)` (manual stage override) bypasses the gate | NONE | NONE | Intentional — operator deliberately flips status; not auto-pipeline |
