# 73 · 0.3.2.03 · Score history time-series view

## Goal

Surface per-role-family scoring trends so the user can see e.g. "Your ML role match average trended up 12% this month — backend held steady at 0.78." Two surfaces:
- **Profile** — sparkline strip showing 30-day rolling avg of scores per top-3 role families
- **`/scores`** — dedicated route w/ full breakdown (per-role-family × per-30-day-window grid)

`Type: design` because this introduces a new route + potentially a new data entity. Mockups + DATA_MODEL.md graduation expected.

## Why

ROADMAP row 0.3.2.03 (legacy ID 3.6):
> Score history time-series view (sparkline on Profile + dedicated `/scores` route showing per-role-family trends)

Source data: `Job.match_breakdown.scored_at` (plan 65 schema; 18-key JSONB) carries the timestamp every score was written. Aggregating across jobs by role-family (derived from `Job.role`) + 30-day windows yields the trend data.

Why now: 0.3.0 scoring substrate (plan 65) populated `Job.match_breakdown` w/ schema_version=1 for every job scored. Two-week observation window has 100+ scoring runs accumulated; visualizing the data tells the user whether their profile-tuning + bullet edits are actually moving the needle.

This is the LOWEST priority sub-plan in master plan 68 (LOW priority on ROADMAP). Lands LAST in the 0.3.2 sweep — independent of 72/74 but depends on plan 69 for service-layer access.

## Proposal

### Option matrix (Q3 from master plan 68) — data layer

| Option | Approach | Cost | Pros | Cons |
| --- | --- | --- | --- | --- |
| **A. New `ScoreSnapshot` table** | Append-only per (Job, scored_at) tuple, indexed by `(user_id, scored_at)` | New table + alembic migration + write trigger in scorer | Easy per-window queries; can capture full match_breakdown shape | Heavy writes (every scoring run = 1 row); long-term storage cost |
| **B. Aggregation cron** | Daily 03:30 UTC cron rolls up `Job.match_breakdown` history → writes daily aggregates to `score_snapshot_daily` materialized view (or table) | New cron + view + 1 service fn | Lighter (1 row per role-family per day, not per-job per-scoring-run); historical breakdown survives Job soft-delete | Queries need view refresh OR computed-at-read; lag of up-to-24h |
| **C. On-demand query over Job.match_breakdown** | Each `/scores` page render queries Job table + parses match_breakdown JSONB on the fly | None — pure query | No new tables; always up-to-date | Heavy query w/ JSONB scanning + role-family classification on each page load |

**Architect recommendation: Option B (aggregation cron).** Sparkline on Profile is a "good enough current state"; up-to-24h lag is fine. Heavy queries on every Profile page load (Option C) are wasteful. Option A adds DB write load to every scoring run for a feature that's a Phase-6-tier polish.

**Owner picks before plan execution** — Master plan Q3 surfaces this.

### File-by-file edits (post-designer pick)

Assuming Option B (aggregation cron):

1. **`alembic/versions/00XX_score_snapshot_daily.py`** — NEW migration creates `score_snapshot_daily` table:
   ```sql
   CREATE TABLE score_snapshot_daily (
     id SERIAL PRIMARY KEY,
     user_id INTEGER NOT NULL REFERENCES "user"(id),
     window_date DATE NOT NULL,
     role_family VARCHAR(64) NOT NULL,
     scored_count INTEGER NOT NULL,
     score_mean DOUBLE PRECISION NOT NULL,
     score_p50 DOUBLE PRECISION,
     score_p90 DOUBLE PRECISION,
     created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
     UNIQUE (user_id, window_date, role_family)
   );
   CREATE INDEX ix_score_snapshot_daily_user_date ON score_snapshot_daily (user_id, window_date DESC);
   ```
2. **NEW `src/models/score_snapshot.py`** — SQLModel for the table. PK + Pydantic schema.
3. **NEW `src/services/score_history_service.py`** (~150 LOC):
   - `roll_up_daily(session, user_id, target_date)` — reads `Job.match_breakdown` where `scored_at` within `target_date`; classifies `Job.role` to role-family (heuristic: ML / backend / frontend / data-eng / devops / platform / other); groups by family; computes mean/p50/p90 of overall score; upserts to `score_snapshot_daily`.
   - `get_sparkline_data(session, user_id, days=30, top_families=3)` — returns top-3 role families by `scored_count` over last 30d + their daily mean series for sparkline rendering. List of dicts `{family, daily_scores: [...30 floats]}`.
   - `get_full_grid(session, user_id, days=90, families=None)` — returns full grid (per-family × per-day) for the `/scores` route.
4. **NEW `src/scheduler/jobs.py:score_history_rollup`** APScheduler cron — daily 03:30 UTC (post-scoring cron at 03:00 per plan 65 § T10).
5. **`src/scheduler/__init__.py`** — register the cron + add to allowlist per plan 27 § C.5 func-ref allowlist pattern.
6. **NEW `src/ui/routes/scores.py`** — `GET /scores` page handler. Renders `pages/scores.html`. Auth-gated via `require_authed_session`. Uses `score_history_service.get_full_grid` + `score_history_service.get_sparkline_data`.
7. **NEW `src/ui/templates/pages/scores.html`** — full-page layout. Top: 30-day sparkline strip per top-3 family. Body: heatmap grid (per-day × per-family). Header: time-range selector (30 / 60 / 90 days).

### Risk + mitigation

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| Role-family classifier (`Job.role` → ML/backend/frontend/data-eng/...) is heuristic and inaccurate | HIGH | LOW (visual polish, not core function) | Heuristic keyword-match (`"machine learning" → ml`, `"backend" → backend`, etc.); fallback `other` bucket. Engineer can refine post-ship if owner reports misclassification. |
| Daily cron causes contention w/ scoring cron at 03:00 UTC | LOW | LOW | Schedule rollup at 03:30 UTC (30min gap after scoring cron); rollup is read-mostly + INSERT-on-conflict idempotent |
| `score_snapshot_daily` table grows unbounded | LOW | LOW | Per-(user, family, day) = ~7-10 rows/day × ~365 days = ~3K rows/year. Negligible. |
| Sparkline rendering bloats Profile page weight | LOW | LOW | Pure SVG, no JS, ~3 sparklines × ~30 points each = ~5KB total |
| Plan 69 (route+ctx rewire) hasn't shipped yet → profile_ctx has both `sd.*` calls + needs sparkline_data injection | HIGH | MEDIUM | Build sequence enforces plan 69 lands first. If plan 73 dispatches before 69, engineer files deviation + defers profile sparkline to follow-up |
| Empty state — new user with 0 score history | LOW | LOW | Template guards `{% if sparkline_data %}`; renders empty-state card pointing to /discover |
| `/scores` route adds to sidebar — overlaps w/ existing nav | LOW | LOW | Place under Profile in sidebar; pattern is "Profile → Edit → Scores" sub-nav |
| `ScoreSnapshotDaily` adds 24th entity to DATA_MODEL.md — graduation gap | LOW | LOW | Plan body specifies the graduation in same PR |
