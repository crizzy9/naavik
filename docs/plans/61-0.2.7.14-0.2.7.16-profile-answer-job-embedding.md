# 61 · 0.2.7.14 + 0.2.7.16 — `ProfileAnswer` reuse cache + `JobEmbedding` semantic match

## Goal

Ship the two pgvector-adjacent DATA_MODEL.md extensions in one combined design plan. **`ProfileAnswer`** (row `0.2.7.14`) — a per-user reuse cache keyed by deterministic question fingerprint that offers the user's last answer to a substantially-equivalent screener question as a starting point on a future application (never auto-submits). **`JobEmbedding`** (row `0.2.7.16`) — a sibling table of dense vector embeddings keyed by `job_id`, materialized in a nightly APScheduler batch (with optional sync trigger), enabling cosine-similarity semantic match for the Phase 3 scorer and Phase 6 "similar jobs" surface. Both ship behind `Settings` toggles defaulting OFF so a self-hoster can run the migration without forcing an embedding-provider choice on day one.

## Why

ROADMAP rows `0.2.7.14` (line 327) + `0.2.7.16` (line 329) are the last two `Type: design` rows in `0.2.7` (the deferred-from-`0.2.x` catch-all). They share more substrate than their separate ROADMAP cells suggest:

1. Both extend `docs/design/DATA_MODEL.md` — `ProfileAnswer` graduates § J (the Phase 2+ reuse-cache stub, line 1287); `JobEmbedding` graduates § H + § G (the Phase 6 explicit stub, line 1244).
2. Both leverage the pgvector extension already enabled in `migrations/versions/0001_initial.py:40` (Decision § N.8 in DATA_MODEL.md). Splitting plans would double-author the pgvector index strategy, dimensionality decision, and provider-abstraction surface.
3. `ProfileAnswer` ships an **optional** semantic fingerprinting upgrade path that uses the same embedding pipeline as `JobEmbedding` (deferred to follow-up `0.8.0`; the v1 fingerprint is exact-normalized, no embeddings).
4. Both must wrap any LLM/embedding call via `services/llm_tracker.tracked_call` (per `engineer-llm-tracker-wrap` skill body + BACKEND.md § M.4) so the existing `ApiUsage` cost surface picks them up.

This is also the first Naavik feature that asks the user to pick an **embedding** provider distinct from their completion provider — Anthropic does not offer embeddings, so an Anthropic-completion user must additionally configure OpenAI OR Ollama for embeddings. That's an operator decision worth surfacing once in a combined plan rather than dropping it twice in sequential plans.

## Proposal

The build splits into three commits, all behind feature flags so the migration ships safely without forcing the operator to configure an embedding provider on day one. Detail follows; the option matrices in § C lock the design decisions.

# src/models/profile_answer.py
from datetime import datetime
from sqlalchemy import Column, DateTime, Index, UniqueConstraint
from sqlmodel import Field, SQLModel

from ._common import utcnow


class ProfileAnswer(SQLModel, table=True):
    """Per-user reuse cache for screener-question answers.

    Key: `(user_id, question_fingerprint)`. Fingerprint algorithm = exact-
    normalized (lowercase + strip punctuation + collapse-whitespace +
    remove company tokens from a curated blocklist + Porter-stem) per
    decision D6. Engineer migration path to semantic fingerprint
    (cosine-sim cluster) deferred to 0.8.0 follow-up.

    Privacy: per-user only. Never cross-user (decision D8).

    Phase 2+ entity (DATA_MODEL.md § J line 1287 → graduates here).
    """

    __tablename__ = "profile_answer"
    __table_args__ = (
        UniqueConstraint("user_id", "question_fingerprint",
                         name="uq_profile_answer_user_fingerprint"),
        Index("ix_profile_answer_user_last_used",
              "user_id", "last_used_at"),
    )

    id: int | None = Field(default=None, primary_key=True)
    user_id: int = Field(foreign_key="user.id", index=True)

    question_fingerprint: str = Field(index=True, max_length=256)
    # The most-recent canonical question text (the source row); not part of key.
    question_text_sample: str = Field(max_length=1024)
    answer: str = Field(max_length=8192)

    # Provenance — the ApplicationScreenerAnswer row whose answer was canonicalized.
    source_screener_answer_id: int = Field(
        foreign_key="application_screener_answer.id",
    )

    # Stats — drive promotion/decay in 0.8.0+.
    times_offered: int = Field(default=0)        # bumped on every reuse prompt
    times_accepted: int = Field(default=0)       # bumped when user accepts the suggested draft
    last_used_at: datetime = Field(
        default_factory=utcnow,
        sa_column=Column(DateTime(timezone=True), nullable=False),
    )

    created_at: datetime = Field(
        default_factory=utcnow,
        sa_column=Column(DateTime(timezone=True), nullable=False),
    )
    updated_at: datetime = Field(
        default_factory=utcnow,
        sa_column=Column(DateTime(timezone=True), nullable=False),
    )

# src/models/job_embedding.py
from datetime import datetime
from pgvector.sqlalchemy import Vector
from sqlalchemy import Column, DateTime, Index
from sqlmodel import Field, SQLModel

from ._common import utcnow

# Provider-agnostic dimension. Stores native 768-d nomic (Ollama default)
# OR Matryoshka-truncated 768-d OpenAI text-embedding-3-small. Locks dim
# at column-creation; cross-provider stable. See decision D2.
EMBEDDING_DIM = 768


class JobEmbedding(SQLModel, table=True):
    """Sibling table — one row per Job (1:1 keyed by job_id).

    Phase 6+ entity (DATA_MODEL.md § H line 1261 → graduates here).
    Materialized in nightly APScheduler batch + on-demand from
    `scraper_service` on new-job arrival when
    `Settings.semantic_match_enabled = True`. Default OFF (decision D3).

    Dimensionality changes require DROP + CREATE TABLE (decision D4).
    """

    __tablename__ = "job_embedding"

    job_id: int = Field(
        primary_key=True, foreign_key="job.id",
        # No ondelete=CASCADE here — Job uses soft delete (deleted_at);
        # archive_job leaves embedding row as historical. delete_orphans
        # happens via nightly batch's missing-job sweep.
    )
    user_id: int = Field(foreign_key="user.id", index=True)

    # The actual embedding. 768-d covers nomic native + truncated OpenAI.
    # `Vector(768)` enforced at column level; pgvector-python casts list[float]
    # to vector on insert.
    embedding: list[float] = Field(
        sa_column=Column(Vector(EMBEDDING_DIM), nullable=False),
    )

    # Provenance — which provider/model wrote this row. Used by the batch
    # to skip rows that already match the current provider+model.
    model: str = Field(max_length=128)       # e.g. "openai/text-embedding-3-small@768" or "ollama/nomic-embed-text"
    dim: int = Field(default=EMBEDDING_DIM)  # always EMBEDDING_DIM today; recorded for future migrations

    # Content fingerprint — SHA-1 of (title || description). Detects when a
    # Job's text changed and the embedding needs refresh. Cheap idempotency.
    content_hash: str = Field(max_length=64, index=True)

    created_at: datetime = Field(
        default_factory=utcnow,
        sa_column=Column(DateTime(timezone=True), nullable=False),
    )
    updated_at: datetime = Field(
        default_factory=utcnow,
        sa_column=Column(DateTime(timezone=True), nullable=False),
    )
```

**Index** (alembic 0013 § B.6): `CREATE INDEX ix_job_embedding_embedding_cosine ON job_embedding USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 200);` per decision D5 + the web-research-confirmed defaults for sub-100K-row datasets.

# Signatures only.

class EmbeddingProvider(ABC):
    """Subset of LLMProvider — embed-only. Concrete impls in
    src/llm/openai_embed.py + src/llm/ollama_embed.py. Anthropic NOT
    implemented (Anthropic does not offer embeddings — decision D1).

    Why a separate ABC + not extension of LLMProvider: completion +
    embedding are different SDK methods + different cost models. Keeping
    the surface tight prevents accidental misuse (e.g. calling `complete()`
    on an embedding-only provider).
    """

    @abstractmethod
    async def embed(self, text: str) -> list[float]: ...

    @property
    @abstractmethod
    def model_name(self) -> str: ...

    @property
    @abstractmethod
    def provider_id(self) -> str: ...

    @property
    @abstractmethod
    def dimension(self) -> int: ...


async def get_embedding_provider(settings: Settings) -> EmbeddingProvider | None:
    """Resolve per-user embedding provider from Settings.embedding_provider.
    Returns None when not configured (Settings.embedding_provider is None
    OR Settings.semantic_match_enabled is False). Caller treats None as
    'feature disabled' — no-op. Defaults: ollama if OLLAMA_BASE_URL is set;
    openai if OPENAI_API_KEY is set + ollama is not; else None."""

async def embed_job(
    session: AsyncSession, *, job: Job, settings: Settings,
) -> JobEmbedding | None:
    """Compute embedding for `Job.title || Job.description`, persist a
    JobEmbedding row (upsert on job_id). All LLM calls wrapped via
    llm_tracker.tracked_call(prompt_name='embed_job'). Skips when
    content_hash matches the existing row's hash + model also matches.
    Returns None when provider unconfigured."""

async def search_similar(
    session: AsyncSession, *, user_id: int, query_embedding: list[float],
    threshold: float = 0.65, limit: int = 20,
) -> list[tuple[int, float]]:
    """Cosine-similarity search over the user's JobEmbedding rows. Returns
    [(job_id, similarity)] for similarity >= threshold, sorted DESC by sim.
    Uses pgvector cosine distance operator (`<=>`). NEVER cross-user
    (filters WHERE user_id = :user_id; decision D8)."""

async def delete_orphan_embeddings(session: AsyncSession) -> int:
    """Nightly-batch helper. DELETE FROM job_embedding WHERE job_id NOT IN
    (SELECT id FROM job WHERE deleted_at IS NULL). Returns row count.
    Idempotent + handles the soft-delete + restore cycle (a restored Job
    re-acquires an embedding on next batch tick)."""
```

## C — Option matrices (10 design decisions)

### Decision D1 — Embedding provider strategy

| Option | Capability | Cost (10K embeds) | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: User-configured (openai OR ollama, exclusive) | Both viable | OpenAI ~$0.0004; Ollama free + 5W laptop CPU | Operator picks; no fallback | Single code path | Per-user; switchable |
| B: Dual-provider with OpenAI fallback to Ollama on rate-limit | Auto-resilience | OpenAI ~$0.0004; Ollama free fallback | Dimension consistency hard (1536 vs 768); rate-limit detection brittle | Two code paths + composite-dimension reconciliation | Hard |
| C: Force Ollama-only (local-first ideology) | One path | Free | Self-host only — cloud users blocked | Minimal | Cloud-tier-hostile |

**Recommendation: A**, with locked output dimension = 768 (OpenAI via Matryoshka truncation; Ollama nomic native). Reuses existing per-user `LLMProvider` mental model. Dual-provider defers but the dimension-reconciliation problem is real-as-designed and not worth solving for v1.

### Decision D2 — Embedding dimensionality

| Option | Capability | Cost (storage @ 50K jobs) | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: 1536d (OpenAI native) | Highest fidelity (MTEB 62.3) | ~307 MB | Ollama users can't match (nomic max 768) — provider-incompatible | Hard | OpenAI-only path |
| B: 768d (Matryoshka truncate OpenAI; Ollama nomic native) | MTEB 62.39 (nomic) vs 62.3 (1536d openai) — comparable | ~153 MB | None | Trivial | None |
| C: 384d (truncate both) | MTEB ~60.5 — meaningfully worse on short text | ~77 MB | Quality regression for ~20% storage savings | Trivial | None |

**Recommendation: B**. 768d is the dim-floor that both providers natively support. MTEB scores are within noise. The 20% storage saving from 384d isn't worth the recall regression on screener-style short text. Locked to 768d in `EMBEDDING_DIM` constant.

### Decision D3 — JobEmbedding materialization timing

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: Synchronous on `job_service.upsert_job` | Real-time; immediate "similar jobs" | Scraper p50 + 200ms (OpenAI) or 80ms (Ollama local) | Bombs scraper latency budget; LLM outage halts scrape | Single hook | Couples scraper to LLM |
| B: APScheduler nightly batch + optional sync trigger gated by `semantic_match_sync_on_upsert` toggle | Bounded latency; cron + opt-in real-time | Free (off-peak); cap-respecting | Up to 24h cold-cache for new jobs | Cron job + service layer | Loose coupling |
| C: On-demand at first search | Lazy | Zero upfront; up-front latency on first search | First-search hang; multi-job batch trip-trip-trip | Search path | Couples search to LLM |
| D: Event-driven via `AppEvent` | Reactive | Same as B but more bookkeeping | AppEvent semantics drift (it's pipeline-history, not infrastructure-events) | Two write surfaces | High |

**Recommendation: B**. Batch is the predictable cost shape. Optional sync trigger handles the "I just added a job manually and want similar-jobs immediately" UX without bombing the scraper's p50. Cron at 02:00 UTC + 03:00 UTC orphan sweep. Default cap = `daily_llm_cost_cap_usd` (already exists).

### Decision D4 — JobEmbedding row strategy

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: Sibling table `job_embedding(job_id PK FK)` | Schema-evolution-friendly (DROP+CREATE on dim change) | One JOIN at search | Join cost ~1ms (HNSW index does the bulk; the join is the trivial part) | Two tables | None |
| B: Inline column `Job.embedding: vector(N)` | One table; no JOIN | Migration on dim change rewrites all Job rows (large table) | High — every dim change needs a `ALTER TABLE ... ADD COLUMN ... DROP COLUMN` dance | Single table | High |

**Recommendation: A**. Dimensionality change is anticipated (OpenAI model rev, Ollama new embedder). Sibling table makes the change a `DROP TABLE job_embedding; CREATE TABLE job_embedding; nightly batch fills it`. Inline column would re-write `Job` (the busiest table in the system).

### Decision D5 — pgvector index type

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: HNSW with `m=16, ef_construction=200` | Best recall; no train step; online inserts | Build ~minutes per 10K rows; memory ~256MB during build | Memory floor matters on tiny VPS | One index; well-documented defaults | None |
| B: IVFFlat with `lists=N/1000` | Fastest build; lower memory | Recall drop; needs re-build on data growth past `lists`; train step on populated table | Re-tune required as table grows | Tunable; needs operator to re-INDEX | Per-dataset |

**Recommendation: A**. Web research confirms HNSW is the safer default for sub-100K-row indexes — better recall, no train step, handles online writes (which is exactly what the nightly batch produces). IVFFlat wins only at >1M rows w/ static data, which is multi-user-cloud-tier territory + a future phase.

### Decision D6 — ProfileAnswer fingerprint algorithm

| Option | Capability | Cost per lookup | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: Exact-normalized (lowercase + strip-punct + remove-company + stem + SHA-1) | Deterministic; reproducible across hosts | Zero (CPU only) | Misses "Tell us about a time you failed" vs "Tell us about a failure" | Pure function; testable | None |
| B: Semantic via embedding cluster (cosine-sim threshold on question embedding) | Captures paraphrase | One embed call per new question + nearest-neighbor search | LLM cost on every new screener question; provider must be configured | Couples to embedding pipeline | High |
| C: LLM-canonicalize (one LLM call per new question → canonical form → SHA-1) | Best semantic dedup | ~$0.001/question (Claude Haiku) | Defeats the cost-saving point of reuse cache | Coupled to LLM; non-deterministic outputs | High |

**Recommendation: A**. v1 ships with acknowledged precision loss; the alternative (B/C) defeats the purpose because the LLM cost equals the cost of just re-drafting. The 0.8.0 follow-up upgrades to semantic fingerprinting once `JobEmbedding` proves the embedding pipeline is operationally sound + cost-bounded.

### Decision D7 — ProfileAnswer reuse UX

| Option | Capability | Risk | Cost | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: Silent autofill | Fastest UX | **NON-STARTER — user-data + AI-output that auto-submits without confirmation = trust break** | Zero | None | None |
| B: Prompt-with-diff inline (suggested vs blank/current) | User explicitly accepts; provenance visible | Low | One extra render | Existing screener-row partial | None |
| C: Banner "we have a suggestion — click to load" | Two clicks (load + accept) | Friction | Minimal | None | None |

**Recommendation: B**. Matches existing screener-review gate (`reviewed_at IS NOT NULL` is the existing submit-blocker). Provenance chip ("Suggested from prior application at <company>") preserves audit trail. **Option A is forbidden by policy** — no AI-generated content auto-submits without explicit user confirmation.

### Decision D8 — ProfileAnswer scope across multi-tenant

| Option | Capability | Risk | Cost | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: Per-`user_id` only | Privacy by default | Reuse only within own corpus | None | Trivial | None |
| B: Opt-in shared corpus | Cross-pollination of answers | **Privacy nightmare — salary expectations, identity question wording, prior-company names leak across tenants** | Opt-in flow + cross-user index | Hard | High |
| C: Per-org (Phase 2+ org tenancy) | Useful at enterprise scale | Requires org model (not in roadmap) | Complex | Org-aware index | Defers |

**Recommendation: A**. Privacy non-negotiable. `search_similar` enforces `WHERE user_id = :user_id` at the service layer. Hacker-test (`tests/test_embedding_idor.py` + `tests/test_profile_answer_idor.py`) confirms.

### Decision D9 — Embedding similarity threshold for "match"

| Option | Capability | Risk | Cost | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: Fixed cosine threshold 0.65 + configurable via `Settings.semantic_match_threshold` | Operator-tunable; sensible default | Threshold poorly matches small/large corpora | None | One Setting field | None |
| B: Relative top-N (always take top 20) | Always returns results | Returns noise on small corpora; no signal-quality gate | Slightly cheaper search | Trivial | None |
| C: System-fixed 0.65 (no override) | Predictable | Operator can't tune | None | Minimal | High |

**Recommendation: A**. 0.65 is a reasonable cosine-sim floor per the nomic-embed-text + openai text-embedding-3-small documentation (both target >=0.5 as "semantically related"; 0.65 picks the meaningfully-relevant zone without over-tightening to >=0.8 territory which would miss paraphrase). Configurable so a user with sparse data can loosen.

### Decision D10 — Migration sequencing

| Option | Capability | Risk | Cost | Maintenance | Lock-in |
|---|---|---|---|---|---|
| A: One alembic file (0012) covering both tables | One revision to remember | Rollback of one feature requires rollback of both | Slightly cheaper to author | Slightly easier to read | High |
| B: Two alembic files (0012 ProfileAnswer, 0013 JobEmbedding) | Independent rollback of either feature | Two revisions to track | Trivial | One file per concern | None |

**Recommendation: B**. Rollback granularity matters: if `JobEmbedding` causes a self-hoster trouble (e.g. pgvector version mismatch, HNSW memory floor), they can `alembic downgrade 0012` without losing `ProfileAnswer`. Both ship in the same PR; alembic resolves order automatically.
