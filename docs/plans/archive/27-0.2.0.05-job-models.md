# 27 · `0.2.0.05` — SQLModel Job hardening + StatusHistory (scrape lifecycle)

## Goal

Harden `src/models/job.py` (which already exists from plan 10 Wave 4 as the MVP placeholder) into the production schema that all 9 downstream scraper sub-tasks (`0.2.0.06`–`0.2.0.14`) hard-depend on, and ship the **`Job` scrape-lifecycle observability table** (`JobScrapeRun` + per-job FK `Job.last_scrape_run_id`) that the user's dispatch prompt refers to as "StatusHistory." Job's pipeline-level status (DRAFT → APPLIED → … → CLOSED) already lives on `Application.status` + is audited row-by-row by `AppEvent` + `StatusChangePayload`; that machinery is unchanged. The missing surface is **scrape-side**: each time a scraper touches a job listing, a row needs to land so the dedup logic (`0.2.0.09`), rate-limiter (`0.2.0.13`), and operator-facing scrape diagnostics (`0.2.5.02`, future) have something to read. Ship `migrations/versions/0005_job_hardening.py` (additive — adds 6 columns to `Job`, drops 1 ENUM value migration, indexes 2 new constraints; creates the new `job_scrape_run` table), a tightened `JobSource` enum, a tightened `visa_restrictions` ENUM (string today; enum-promoted here), Pydantic API schemas in `src/models/job.py` (alongside the SQLModel), and the seed expansion in `src/db/sample_data.py` so `0.2.0.06`+ has realistic fixtures.

This plan is `Type: design`. On approval, the locked contract graduates into `docs/design/JOB_MODEL.md` — the canonical reference scrapers + AI extraction + dedup + scoring all read from. The plan file then archives.

## Why now

Five forces, ordered by force:

1. **HIGH priority — gates the whole 0.2.0 scraper chain.** ROADMAP `:218` flags `0.2.0.05` HIGH because `0.2.0.06`–`0.2.0.14` cannot proceed without locked Job + scrape-side observability semantics. Crawl4AI (`0.2.0.06`) writes via service-layer; site scrapers (`0.2.0.07`) need `external_id` semantics + visa enum locked before they can emit `RawJob` instances; dedup (`0.2.0.09`) needs `UNIQUE(user_id, source, external_id)` constraint to lean on (URL fuzzy match is the fallback, not the primary). Without this plan, every downstream scraper plan blocks or ships against guesses that re-converge into a costly schema drift later.

2. **Vault deprecation just cleared the Settings layer (plan 26 EXECUTED 2026-05-19).** Settings rows + `services/env_secrets.py` are now env-clean. Scraper-related Settings fields the new `JobSource` enum implies (`workday_companies`, `sources_enabled`, `source_schedules`, `notify_threshold` — see `BACKEND.md § L`) land onto an env-clean surface without form-PUT vault drag. Sequencing locks tight: `0.2.0.01` deleted vault, `0.2.0.05` hardens models, `0.2.0.06` starts coding scrapers.

3. **The current `Job` model is an MVP placeholder.** Plan 10 § C.4 deferred "Phase 2 scrapers" to `0.2.0`; the Job row that exists today (`src/models/job.py`) is enough for the Discover screen mockups to render fixtures but is structurally missing the four production-scraper hooks: (a) **`external_id`** for source-specific identifier so two LinkedIn scrape runs converge to one Job row, (b) **production `(source, external_id)` UNIQUE constraint** so dedup `0.2.0.09` is structurally guaranteed (today's `url` per-user partial-unique covers the happy path but breaks when LinkedIn URLs change canonical form between job-list and job-detail pages), (c) **`visa_restrictions` as a typed ENUM** (today a free-form string read by `services/scorer.py:_BLOCKING_RESTRICTIONS` — the scorer hardcodes `{"us_citizen_only", "green_card_required"}` which is fragile to scraper drift), and (d) **scrape-lifecycle observability** so operators can see "LinkedIn scraper ran 30 min ago, fetched 47 listings, 3 new, 0 errors" in the UI (Settings · Deployment or a future Scrapes tab).

4. **n8n migration (`0.2.0.14`) needs the schema ready before the import script can run.** `services/legacy_import.py` (Phase 2 BACKEND § J.5 deliverable) reads CSV → creates `Job` + `Application` rows. CSV columns from the n8n DataTable (`hfvivTlQThpPytkl` per `AGENTS.md § External Integrations § n8n`) include `source`, `url`, `company`, `title`, `posted_at`, `description`, `score`, `decision`, `applied_at`. Mapping `source` cell values onto a typed `JobSource` enum requires the enum to exist; mapping `decision` onto `Job.queue_state` requires the existing enum unchanged; the n8n DataTable's `external_url` / `internal_id` columns map onto the **new** `Job.external_id`. The import script can't land cleanly until `0.2.0.05` ships.

5. **`AppEvent` covers application-side history, NOT scrape-side history.** The user dispatch prompt's "StatusHistory" framing collides with terminology already on the floor: `AppEvent.kind=STATUS_CHANGE` + `StatusChangePayload` (`src/models/app_event_payloads.py:24`) is the canonical row-per-status-transition surface for `Application.status`. Building a parallel "StatusHistory" table for Job would either (a) duplicate that surface — the dedup/lint/visibility implications would be miserable, or (b) confuse the meaning of "status" (Job has `queue_state`, Application has `status`; both legitimate; both audited). The clean break is: **scrape-side observability is its own table** (`JobScrapeRun`, one row per scraper invocation), and **Job ↔ Application status changes** stay on `AppEvent` (unchanged). Plan 27 explicitly does NOT add a third status concept.

### D.1 — Scope framing: harden existing `Job` vs net-new model

The user's dispatch prompt described `0.2.0.05` as "create the Job model." Reality (`src/models/job.py` 113 LOC, present since plan 10 Wave 4) is that Job already exists. Two framings of the actual scope:

**Option matrix.**

| Option | A — Harden existing `Job` + add `JobScrapeRun` table (recommended) | B — Net-new `Job_v2` table + migration data over + drop `Job` |
| --- | --- | --- |
| Capability | Additive only: 6 new columns + 1 enum-promote of `visa_restrictions` + 1 new table. Zero data loss. Sample data + seed pass after additive migration. | Clean slate; can rename / restructure fields aggressively. |
| Cost | ~80 LOC across `src/models/job.py` + 1 migration file + ~30 LOC service additions + ~40 LOC seed expansion + ~120 LOC tests + doc graduation. | ~400 LOC: full model rewrite + data-copy migration + dual-read interim + ATSCredential.FK rewire (Job FKs across `Application.job_id`, `Contact warm_intro_contact_id` — see § E below) + months-long deprecation window |
| Risk | LOW — additive migrations are safe; the existing Discover UI keeps reading Job; no consumer breaks. | HIGH — every consumer of Job rewires: `src/api/*`, `src/ui/discover_ctx.py`, `src/services/application_service.py:get_or_create_draft`, `src/services/scorer.py`, `src/db/sample_data.py`. Migration window is multi-PR. |
| Maintenance | None — single existing entity grows. | High — dual model + dual write path during migration. |
| Lock-in | None | Sets a precedent ("we redo models when scope grows") that doesn't compose with future plans. |

**Recommendation: A.** The existing `Job` already covers the visible-to-user fields (`company`, `role`, `location`, `salary_min/max`, `description`, `tags`, `queue_state`, `score`, `match_breakdown`, `raw_meta`) that the Discover mockups + fixtures lean on. What's missing is **scraper plumbing** (external_id, scrape_run linkage, visa enum) — a clean additive extension. Option B's blast radius is unjustified for a model whose Phase 1 shape was, in fact, correct for the user-visible surface; only the integration plumbing is short.

**Trade-off accepted.** Some scraper-author convenience would have wanted a renamed `Job.title` (currently `Job.role`); we don't rename. Engineers writing scrapers map `RawJob.title` (per `BACKEND.md § J.1`) onto `Job.role` at the service-layer boundary in `services/scraper_service.py`. Documented in graduation doc + the build-sequence W2 note.

**Rationale recorded for `memory`:** decision-id `0.2.0.05-scope-framing`, verdict `A`, captured at plan approval via `.claude/naavik-ops memory record-decision`.

### D.2 — Where does scrape-side history live?

The user's dispatch prompt described the second model as "StatusHistory" with a state machine matching Application's pipeline. As § Why now point 5 above explains, that table would collide with `AppEvent + StatusChangePayload` which already does application-side audit. The real missing surface is **scrape-side observability**: who scraped what, when, how many results came back, what failed. Three options.

**Option matrix.**

| Option | A — Promote scrape-side events into `AppEvent` (add `JOB_SCRAPED` / `SCRAPE_RUN_COMPLETED` / `SCRAPE_RUN_FAILED` kinds) | B — New `JobScrapeRun` table — one row per scraper-invocation, plus `Job.last_scrape_run_id` FK (recommended) | C — New `job_scrape_history` (per-job, append-only) — one row per scrape-touch of a specific Job |
| --- | --- | --- | --- |
| Capability | Unified event log. UI can show "all events for app X" in one stream. | Discrete per-run row carries metrics (`requests_made`, `listings_returned`, `new_jobs`, `errors[]`, `duration_ms`). UI Scrapes panel reads this. | Captures every touch of a specific Job (e.g., "LinkedIn rescraped 3 times this week"); useful for "this job description changed" detection. |
| Cost | ~30 LOC (just enum entries + payload classes) | ~80 LOC: new SQLModel + Alembic + 2 indexes + service helpers | ~120 LOC: full new entity + per-Job FK + cron writers |
| Risk | MEDIUM — `AppEvent.application_id` is required-ish (model says `int \| None` with nullable=True at line 25); a scrape-side event with no application_id would emit rows that the Application-detail timeline UI silently filters out, but the rows persist on the user-events stream. Workable, but conceptually muddy: AppEvent is "events on an Application" not "events in the system." | LOW — disjoint scope. Easy to test. Aligns with operator mental model ("scrapes are a system-level concern, not per-application"). | LOW operationally — purely additive. BUT scope creep: users don't care about per-Job scrape history at MVP; only operators do, and operators care about per-run aggregates, not per-Job-per-touch. |
| Maintenance | Future readers expect AppEvent to be about Applications | Conventional layered split; aligns with `services/scraper_service.py` ownership | Higher — every scraper run multiplies row count linearly with listings × runs |
| Lock-in | Soft — refactoring later is painful because consumers `WHERE kind IN ('JOB_SCRAPED', ...)` everywhere | None — `JobScrapeRun` is a stand-alone observability surface | Higher — schema decision sticky |

**Recommendation: B — `JobScrapeRun` table.** Scrape-side observability is a system concern, not an Application concern. The clean conceptual split:

- `AppEvent` — events on an Application (status change, docs generated, email received, …). Owned by `services/application_service.py`. Already done.
- **`JobScrapeRun`** — one row per scraper-invocation. Owned by `services/scraper_service.py` (lands in `0.2.0.06`). Carries `(source, started_at, finished_at, status, requests_made, listings_returned, new_jobs, updated_jobs, errors, duration_ms, run_id)`. Aggregates the "what happened this run" story.
- `Job.last_scrape_run_id` — optional FK to `JobScrapeRun` so a UI ("this job last refreshed 2h ago via LinkedIn") can join one row.

This composes with `0.2.0.13` rate-limiting (which reads `JobScrapeRun.requests_made` to compute per-source budget consumption) and `0.2.5.02` (DEF-16, scrape failure-kind aggregates dashboard) without needing a redesign.

**Trade-off accepted.** Option A's "unified event log" appeal is real but illusory; scrape runs aren't a stream of `Application` events. Option C's per-Job-per-touch granularity is genuinely useful for "JD-changed since last scrape" detection — but that's a JD-diff feature (post-0.6.0 LLM job), not a Phase 2 scraper need. Plan 27 ships Option B; Option C remains available as a Phase 6+ addition (deferred to `0.2.5.NN` backlog when the failure-kind aggregates dashboard ships).

**Rationale recorded for `memory`:** decision-id `0.2.0.05-scrape-history`, verdict `B`, captured at plan approval.

#### `JobScrapeRun` schema sketch (commit W1 + W2 deliverable)

```python
# src/models/job_scrape_run.py — new file

from __future__ import annotations
from datetime import datetime

from sqlalchemy import CheckConstraint, Column, DateTime, Index
from sqlalchemy.dialects.postgresql import ARRAY, JSONB
from sqlmodel import Field, SQLModel

from ._common import utcnow
from .enums import JobScrapeStatus, JobSource


class JobScrapeRun(SQLModel, table=True):
    __tablename__ = "job_scrape_run"
    __table_args__ = (
        CheckConstraint(
            "finished_at IS NULL OR finished_at >= started_at",
            name="ck_job_scrape_run_finish_after_start",
        ),
        CheckConstraint(
            "requests_made >= 0 AND listings_returned >= 0 AND new_jobs >= 0 AND updated_jobs >= 0",
            name="ck_job_scrape_run_counters_nonneg",
        ),
        Index("ix_job_scrape_run_source_started", "source", "started_at"),
        Index("ix_job_scrape_run_user_status_started", "user_id", "status", "started_at"),
    )

    id: int | None = Field(default=None, primary_key=True)
    user_id: int = Field(foreign_key="user.id", index=True)

    source: JobSource              # which scraper ran
    status: JobScrapeStatus        # RUNNING | SUCCESS | PARTIAL | FAILED | TIMED_OUT
    triggered_by: str              # "cron" | "manual" | "test"   (free-form; not an enum)

    started_at: datetime = Field(
        default_factory=utcnow,
        sa_column=Column(DateTime(timezone=True), nullable=False, index=True),
    )
    finished_at: datetime | None = Field(
        default=None,
        sa_column=Column(DateTime(timezone=True), nullable=True),
    )

    requests_made: int = Field(default=0)        # # HTTP / Crawl4AI requests fired
    listings_returned: int = Field(default=0)    # # RawJob rows yielded
    new_jobs: int = Field(default=0)             # # new Job rows persisted
    updated_jobs: int = Field(default=0)         # # existing Jobs touched (description refresh)

    errors: list[str] = Field(
        default_factory=list,
        sa_column=Column(ARRAY(sa.String()), nullable=False, server_default="{}"),
    )
    # Each entry: "stage=<list_jobs|fetch_detail|persist> url=<...> kind=<rate_limit|captcha|timeout|parse_failure|other> msg=<...>"
    # Plain strings (not JSONB) — operator-grep-able in logs/admin views. Bounded by anti-detection budget; typically 0-5 per run.

    duration_ms: int | None = None               # finished_at - started_at, computed on finalize
    raw_meta: dict = Field(
        default_factory=dict,
        sa_column=Column(JSONB, nullable=False, server_default="{}"),
    )
    # raw_meta: scraper-specific (e.g. {"rsshub_endpoint": "...", "rate_limit_hits": 0, "user_agent_pool_idx": 3})

    created_at: datetime = Field(
        default_factory=utcnow,
        sa_column=Column(DateTime(timezone=True), nullable=False),
    )
```

### D.3 — `Job.external_id` + dedup constraint shape

Today `Job` dedup is on `(user_id, url) WHERE deleted_at IS NULL` (partial unique per-user — see `src/models/job.py:33-38`). This works when URLs are canonical, but LinkedIn / Workday / Indeed all have multiple URL forms for the same listing (job-list page vs job-detail page vs share-link vs internal-tracker-redirect). The production dedup spec (BACKEND § J.3 step 2.c, "Dedup (URL match + fuzzy title/company via edit-distance)") wants:

1. **Exact match first** via `(source, external_id)` — fast structural dedup using each board's stable identifier.
2. **URL match second** — current path.
3. **Fuzzy title/company third** — Levenshtein on `(company.lower() strip)` + `(role.lower() strip)`; the `0.2.0.09` work.

Plan 27 ships the **first two** structurally. Fuzzy is `0.2.0.09`.

**Option matrix for `Job.external_id`:**

| Option | A — `external_id: str` required + UNIQUE(`user_id`, `source`, `external_id`) WHERE `deleted_at IS NULL` (recommended) | B — `external_id: str \| None` optional + UNIQUE only when present | C — Multi-key JSONB `Job.identifiers: {"linkedin_job_id": "...", "greenhouse_internal_id": "..."}` |
| --- | --- | --- | --- |
| Capability | One identifier per source; structural exact-match dedup is bulletproof | Allows MANUAL source jobs (user-added) without forcing a fake ID | Captures multiple boards advertising the same job (e.g. LinkedIn cross-posts a Greenhouse job) |
| Cost | ~20 LOC + 1 index + back-fill story for existing rows | ~25 LOC + tricker constraint logic | ~50 LOC + JSONB GIN index + service-layer key normalization |
| Risk | MANUAL source needs a synthetic ID — easy: `f"manual-{uuid7()}"`. Backfill of existing fixtures: deterministic from URL hash | If a real scraper forgets to set `external_id`, dedup silently disables for that source — failure mode harder to spot in code review | Cross-board dedup is "future cool feature" not Phase 2 need; YAGNI |
| Maintenance | Standard. UNIQUE constraint enforced by Postgres. | Some defensive coding around None checks in dedup hot path | High — every scraper plus dedup logic must normalize keys |
| Lock-in | None | None | Moderate — schema lock |

**Recommendation: A — required `external_id` + UNIQUE(`user_id`, `source`, `external_id`) WHERE `deleted_at IS NULL`.** MANUAL source uses `external_id = f"manual-{uuid7()}"` generated at row-insert time in `services/job_service.py:create_manual_job(...)`. N8N_LEGACY uses `external_id = legacy_row["internal_id"]` from the CSV. Existing fixtures get backfilled deterministically from URL via `hashlib.sha1(url).hexdigest()[:12]` so the alembic up migration succeeds against any live DB.

**Indices added to `Job` (commit W1 deliverable, replacing/augmenting current set):**

- KEEP `ix_job_user_url_unique_alive` — fallback URL dedup; supports "+ Add by URL" without scraper round-trip.
- ADD `ix_job_user_source_external_id_unique_alive` — UNIQUE(`user_id`, `source`, `external_id`) WHERE `deleted_at IS NULL`. This is the **primary** dedup constraint.
- KEEP `ix_job_user_queue`, `ix_job_score_desc`, `ix_job_found_at_desc`, `ix_job_tags_gin` (all current).

**Trade-off accepted.** Option C's cross-board cross-posting is a real phenomenon (a Stripe job appearing on LinkedIn + Greenhouse simultaneously), but the dedup story handles it via fuzzy match (`0.2.0.09` work). Plan 27's `(source, external_id)` UNIQUE is per-source — two source-different `Job` rows for the same conceptual job are allowed; `0.2.0.09` merges them when fuzzy match scores high.

### D.4 — `JobSource` enum: extend vs overload `ApplicationBoard`

Today `Job.source` is `JobSource ∈ {AUTOMATED, MANUAL}` and `Job.board` is `ApplicationBoard ∈ {GREENHOUSE, WORKDAY, LEVER, ASHBY, LINKEDIN, INDEED, COMPANY_DIRECT, MANUAL}` (per `src/models/enums.py:61` + `:134`). The split made sense when "scrape-source vs ATS-board" were distinguishable. Production scrapers force the question: do we extend `JobSource` to enumerate per-source, or keep using `ApplicationBoard`?

**Option matrix.**

| Option | A — Extend `JobSource` to enumerate per-source (recommended); deprecate AUTOMATED catch-all | B — Keep `JobSource ∈ {AUTOMATED, MANUAL}`; rely on `ApplicationBoard` for per-source identity | C — Add a third enum `ScraperKey` (LINKEDIN_GUEST_API, LINKEDIN_RSSHUB, WORKDAY_PLAYWRIGHT, …) explicitly distinct from board |
| --- | --- | --- | --- |
| Capability | Single source-of-truth; one query "give me all LINKEDIN-source jobs" against `Job.source`; `JobScrapeRun.source` aligns | Forces queries to do `WHERE Job.source = AUTOMATED AND Job.board = LINKEDIN` | Captures "two scraper strategies for one board" (e.g. LinkedIn via RSShub vs LinkedIn via guest API) |
| Cost | ~5 LOC enum changes + careful migration of existing rows (`AUTOMATED` → infer per `board`) | None | ~30 LOC plus introduces a new field on Job + JobScrapeRun |
| Risk | Migration of existing rows must succeed against any populated DB; fixtures fan out from "all AUTOMATED" to per-board | Awkward dedup queries; `0.2.0.09` author writes `source=AUTOMATED AND board=X` patterns everywhere | YAGNI for Phase 2 — RSShub vs guest API is a scraper-internal detail, captured in `JobScrapeRun.raw_meta` already |
| Maintenance | Standard. Single enum to keep aligned with scraper modules | Two-axis logic permeates downstream code | Three enums to keep coherent |
| Lock-in | None — additive migration | Moderate — every new scraper grows the two-axis query patterns | None |

**Recommendation: A.** New `JobSource` enum values (final spec):

**Migration shape (commit W1 in `0005_job_hardening.py`):**

```sql
-- Postgres ENUM type alter: add new values, drop old.
-- ENUM additions are safe; removing AUTOMATED needs a data-migration pass.

ALTER TYPE "jobsource" ADD VALUE IF NOT EXISTS 'workday';
ALTER TYPE "jobsource" ADD VALUE IF NOT EXISTS 'greenhouse';

```

**Migration safety note.** This re-mapping reads `board::text::jobsource`. The text values match because `ApplicationBoard.GREENHOUSE = "greenhouse"` etc. align byte-for-byte with the new `JobSource.GREENHOUSE = "greenhouse"`. If any AUTOMATED row has a `board` value that wasn't in the new JobSource set (e.g. LINKEDIN_LEGACY, …), the migration fails loud — that's the intended safety. Tested in W1 round-trip.

**Trade-off accepted.** The dangling `'automated'` enum value is mildly ugly. Postgres `ALTER TYPE … DROP VALUE` is intentionally not supported (a 12-year-open feature request) — the canonical workaround is a multi-step migration that creates a new enum type + recasts every column. Plan 27 defers that to a follow-up ROADMAP row (`0.2.5.NN-cleanup-dangling-enum-value`) — purely cosmetic, no functional impact.

### D.5 — `visa_restrictions` string → typed enum

Today `Job.visa_restrictions` is `str | None` and `services/scorer.py:_BLOCKING_RESTRICTIONS = frozenset({"us_citizen_only", "green_card_required"})` hardcodes the two strings the visa filter looks for. This is fragile: AI extraction (`0.2.0.08`) writes whatever the LLM produces; one prompt churn and the filter silently misses everything. Production scrapers need typed values.

**Option matrix.**

| Option | A — Promote to typed `VisaRestriction` enum (recommended) | B — Keep string but add a `tests/test_visa_restrictions_vocabulary.py` lint covering the LLM extraction prompt | C — Move to JSONB `Job.visa_meta: {requirement: str, source_text: str}` |
| --- | --- | --- | --- |
| Capability | Postgres-enforced vocabulary; scorer pattern-match against enum cases | LLM-output validation only; DB happily stores anything | Captures "the LLM said: 'open to OPT/CPT but no H1B for senior roles'" + a normalized requirement |
| Cost | ~10 LOC enum + ~5 LOC migration data backfill + ~10 LOC scorer rewrite | ~30 LOC test surface + extraction prompt schema | ~50 LOC plus updates to scorer + UI + filter |
| Risk | LLM extraction must produce enum-valid output; structured-output schemas via Pydantic catch this (extract_job uses `provider.structured(...)` per `extract_job.py:39`) | LLM drift surfaces only at runtime | Schema bloat for Phase 2; cross-stale "free-text + structured" surface |
| Maintenance | Standard | Higher — every prompt change risks vocab drift | Highest — JSONB key churn |
| Lock-in | None | None | Moderate |

**Recommendation: A.** Final enum:

```python
class VisaRestriction(StrEnum):
    US_CITIZEN_ONLY = "us_citizen_only"
    GREEN_CARD_REQUIRED = "green_card_required"
    SPONSORSHIP_AVAILABLE = "sponsorship_available"
    NOT_MENTIONED = "not_mentioned"          # AI extraction default when JD doesn't say
```

Four values per ROADMAP owner profile + SCREENS.md `Discover` filter intent. Plan 27 explicitly does NOT introduce 5-value granularity ("uncertain_but_likely" / "uncertain_but_unlikely") — too subtle for the LLM to extract reliably; the visa filter doesn't need that resolution (it filters or it doesn't); SCREENS.md `Discover` filter toggle is a single "visa-friendly only" boolean. Plan 27 ships the 4-value form. If LLM ergonomics ask for finer granularity later, that's a `0.3.X` scoring-pipeline plan.

**Backfill for existing rows (commit W1 in migration):**

-- Two-step ALTER TABLE: column type change with USING expression.
ALTER TABLE job ADD COLUMN visa_restrictions_new visarestriction;

UPDATE job SET visa_restrictions_new = CASE
  WHEN visa_restrictions IS NULL THEN 'not_mentioned'::visarestriction
  WHEN lower(trim(visa_restrictions)) = 'us_citizen_only' THEN 'us_citizen_only'::visarestriction
  WHEN lower(trim(visa_restrictions)) = 'green_card_required' THEN 'green_card_required'::visarestriction

  ELSE 'not_mentioned'::visarestriction
END;

```python
async def upsert_job(...) -> tuple[Job, bool]:
    existing = (
        await session.exec(
            select(Job).where(
                Job.user_id == user_id,
                Job.source == source,
                Job.external_id == external_id,
                Job.deleted_at.is_(None),
            )
        )
    ).one_or_none()

    if existing is None:
        job = Job(user_id=user_id, source=source, external_id=external_id, **_normalize(raw))
        if scrape_run_id is not None:
            job.last_scrape_run_id = scrape_run_id
        session.add(job)
        await session.flush()
        return job, True

    # Existing — refresh extraction metadata, merge raw_meta, bump last_scrape_run_id.
    existing.description_extracted_at = datetime.now(UTC)
    existing.raw_meta = {**existing.raw_meta, **(raw.get("raw_meta") or {})}
    if scrape_run_id is not None:
        existing.last_scrape_run_id = scrape_run_id
    # Field-level merge intentionally minimal in plan 27 — full diff/refresh
    # logic ships in 0.2.0.09.
    session.add(existing)
    await session.flush()
    return existing, False
```

### D.11 — Cross-cutting: timestamps, soft-delete, multi-tenant readiness, UUID vs int

- **Audit columns.** Every new entity (`JobScrapeRun`) carries `created_at`/`updated_at` per `DATA_MODEL.md § C` convention. No SQLModel mixin exists in the codebase today — fields are inline per-entity. Plan 27 inlines per `Job` precedent (lines 101-112 of `src/models/job.py`).
- **Soft-delete.** `JobScrapeRun` does NOT get `deleted_at`. Scrape-run rows are operator audit data — never soft-deleted; pruned via a cron at scale (Phase 6+). `Job` keeps existing `deleted_at` soft-delete.
- **Multi-tenant.** Every new table + column carries `user_id` FK + index. `Job.user_id` already exists; new `JobScrapeRun.user_id` mirrors. Cron loops in scraper service iterate `for user in users:` from day one (`ARCHITECTURE.md § 7` says single-user MVP but model is multi-tenant-ready). Plan 27 keeps this property.
- **UUID vs int PK.** Existing convention is `int = Field(primary_key=True)` (per `DATA_MODEL.md § C` convention). Plan 27 keeps this. UUID is post-0.6.0 work if multi-region / multi-tenant cloud tier ever needs distributed-ID sharding.
