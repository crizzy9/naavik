### Item 1 — Restore Lucide via CDN with self-hosted fallback (0.2.2.02 / DEF-19)

**Rationale.** Plan 09a Issue 1 (2026-05-02) switched from `https://unpkg.com/[email protected]/dist/umd/lucide.min.js` to self-hosted `/static/lucide.min.js` to fix "icons don't render" after an unpkg flake. Self-host works but adds ~30 KB to the static bundle and forces every fork to vendor a JS dep. Production should serve from a CDN; the 09a archive log noted the candidate fallback chain (`unpkg → jsdelivr → self-hosted`). Switch to jsDelivr as primary (multi-CDN-backed, has been stable for the htmx/Sortable lines we already use) with the existing `/static/lucide.min.js` retained as `onerror` fallback. Keep the local file in `src/ui/static/` — it's our break-glass.

Pin the version (`0.469.0` matches the vendored `lucide.min.js` shipped in plan 09a per the file's version comment — engineer must `grep` the local file's version banner pre-edit and pin to that exact tag). ### Item 2 — Mobile sidebar toggle reliability after navigation (0.2.2.03 / DEF-20)

**Rationale.** Plan 09a Issue 2 added `data-sidebar-toggle` event delegation on `document.body` (`base.js:209–227`) and the IDEMPOTENT GUARD (`base.js:13–22`) that prevents the IIFE from re-attaching listeners on `hx-boost="true"` script re-execution. User report: still "kind of wonky" after navigating away. Read of `base.js` shows the toggle handler IS already delegated on `document.body.click` so it survives DOM swaps in principle. Likely remaining failure: when `hx-boost` swaps the `<main>` content, `document.body.dataset.sidebarOpen` is preserved (correct) but `aria-expanded` on the two `[data-sidebar-toggle]` buttons may NOT be re-synced if the buttons themselves were swapped in via OOB. The hamburger lives OUTSIDE the swapped region (in `sidebar.html` which lives in `<aside>`) so it doesn't get swapped. The IN-DRAWER close button is also in `<aside>`, also not swapped. So the swap surface is innocent. Real bug suspect: `syncSidebarAria()` (`base.js:203–208`) is called only inside the click handler at lines 213 + 218 + 224 — never on `htmx:afterSwap`. If a navigation closes the drawer client-side then a back-button restore re-opens it without firing the click handler, ARIA state drifts. Fix: call `syncSidebarAria()` once on `DOMContentLoaded` AND on `htmx:afterSwap` so the on-disk attribute always matches the `data-sidebar-open` body attribute.

**Files.**

- `src/ui/static/base.js:226` — after the existing `document.body.addEventListener('click', ...)` block (closing `})` at line 227), add four lines:

  ```javascript
  // 09a follow-up — sync ARIA on initial paint + after every HTMX swap so the
  // hamburger / in-drawer button stay correct even when navigation runs without
  // a click event firing (back-button restore, history pop, hx-boost).
  if (document.readyState !== 'loading') {
    syncSidebarAria();
  } else {
    document.addEventListener('DOMContentLoaded', syncSidebarAria);
  }
  document.body.addEventListener('htmx:afterSwap', syncSidebarAria);
  ```

  Placement is AFTER the click handler block so `syncSidebarAria` is in scope. ESLint not in repo; manual code review covers ordering.

**LOC.** ~8 LOC JS diff. **Tests.** Extend `tests/test_mobile_sidebar.py` with one new test `test_base_js_syncs_aria_on_swap`: assert `base.js` body contains both `'htmx:afterSwap'` AND `'syncSidebarAria'` in the new block (regex / substring match — TestClient pulls `/static/base.js` text). Confirms the new wiring landed without exercising the browser. Live drawer-toggle behavior is exercised manually per the no-Playwright-on-NixOS convention.

### Item 3 — Discover card max-w cap on ultra-wide screens (0.2.2.04 / DEF-21)

**Rationale.** Plan 09a Issue 8 dropped the `max-w-7xl` page cap on Discover so the swipe card could stretch (the swipe card itself is `max-w-[460px] lg:max-w-none` per `components/swipe_card.html:24`). On 1440px desktops this is fine. On 4K monitors (2560×1440 typical, 3840×2160 occasionally) the card edges spread >1500px apart and the content feels sparse. Add a `2xl:max-w-[1400px]` cap to the Discover page wrapper. Tailwind's `2xl` breakpoint is `>= 1536px`, so 1440×900 monitors stay unaffected (full-width as today); 1536px+ monitors clamp to 1400px max with auto margins.

**Files.**

- `src/ui/templates/pages/discover.html:8` — change `<div class="px-6 lg:px-8 py-6 lg:py-8 flex flex-col gap-5">` to `<div class="px-6 lg:px-8 py-6 lg:py-8 flex flex-col gap-5 2xl:max-w-[1400px] 2xl:mx-auto">`. Update the comment at lines 5–7 to read "Discover uses the full viewport width on lg+ (no max-w-7xl cap) but clamps to 1400px on 2xl+ (>=1536px) so the swipe card doesn't sprawl on 4K monitors. Other pages keep their max-w-7xl wrapper."
- (No other files — `_discover_queue.html` is a fragment swapped into `#discover-main` which lives INSIDE the wrapper, so it inherits the clamp.)

**LOC.** ~3 LOC template diff (class string extension + comment refresh). **Tests.** `tests/test_discover_max_w_cap.py` — new TestClient file. 2 assertions: (a) `GET /discover` body contains the string `2xl:max-w-[1400px]`; (b) `GET /discover` body contains `2xl:mx-auto` (so the clamp is horizontally centered, not left-aligned). Width-actual rendering is browser behavior (not unit-testable); the template-string assertion confirms the contract.
