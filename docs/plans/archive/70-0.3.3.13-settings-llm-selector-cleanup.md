# 70 · 0.3.3.13 · Settings · LLM dual-selector cleanup

## Goal

Settings · LLM Provider tab currently renders TWO provider-selection surfaces — neither functional per owner local QA. Delete the "Active provider" radio-card section (vestige from pre-vault era) + simplify provider switching to a single canonical surface (model dropdown w/ env-presence indicators). Per owner directive verbatim: *"the active provider one should go and the api key one should stay."* Single PR + ~50 LOC; template surgery + ctx field cleanup + 1 test. Independent of plan 69 (data flow); parallel-shippable.

## Why

Owner local QA report (verbatim): **"Settings · LLM has two provider selectors, neither works."**

Confirmed via `src/ui/templates/pages/_settings_llm.html` audit:

- **Section 1 (lines 28-49):** "Active provider" header → grid of 3 `provider_card.html` partials (Anthropic / OpenAI / Ollama) rendered as radio cards w/ HTMX `hx-trigger="change"` on radio input. Each card binds `provider` form field + on change fires `hx-get="/_fragments/settings/llm/model-options?provider={{ p.id }}"` to re-render the model dropdown.
- **Section 2 (lines 51-133):** "API key (configured via environment)" header → grid of 3 env-presence indicator cards using `env_indicators[p.id]` (read from `env_secrets.env_indicators_for_llm_tab()`). NOT a form input — purely informational.

The dual surface is a vestige of plan 26 (vault deprecation, 2026-05-19): pre-vault, "Active provider" radio + "API key input" pair was the canonical surface. Plan 26 deleted the API-key INPUT but left the radio surface AND added the new env-presence card grid below it. Result: two selectors visible; owner is right to call this confusing.

Per owner directive, the "Active provider" radio cards GO. The env-presence indicators STAY.

Why neither works today (root cause):
1. The "Active provider" radio cards mutate `settings.llm_provider` in DB via `PUT /api/v1/settings/llm` — verified per `src/api/settings.py:75-167`. The handler accepts `application/x-www-form-urlencoded` (lines 93-96), reads `llm_provider`, casts to `LLMProviderEnum`, persists. **This SHOULD work for the form-submit path.** Owner saying "neither works" likely means:
   - On click, the radio card visually selects but the form-submit button is far below — owner may not realize they need to click "Save changes" (the radio change fires only model-dropdown refresh, not the persist).
   - OR: the submit button is gated by Depends(require_authed_session) returning 401 (overlaps with bug 7).
   - OR: Session 401 cascade — verify against plan 71.
2. The env-presence cards SHOULDN'T be interactive at all — they're status-only. Owner may have tried clicking them expecting interaction.

Either way: deleting the radio section unblocks owner's mental model. The env-presence cards become the canonical "you have these configured" surface.

## Proposal

### Option matrix (Q1 from master plan 68)

How do users switch active provider after the radio cards are deleted?

| Option | UX | Backend change | Pros | Cons |
| --- | --- | --- | --- | --- |
| **A. Implicit by env-presence** | None — `services.env_secrets.env_indicators_for_llm_tab()` returns `{anthropic: True, openai: False, ollama: False}`; backend picks first `True` in priority order (Anthropic > OpenAI > Ollama) | `settings_service.update_llm()` drops `provider` arg; `Settings.llm_provider` becomes deprecated read-only column populated from env-resolution helper | Single source of truth (env); matches post-vault "trust env" model; least UI clutter; user can't accidentally set provider w/o API key | If user wants OpenAI but Anthropic key is also set, they need to clear ANTHROPIC_API_KEY in .env (no UI override) |
| **B. Hidden form-field toggle** | Tiny `<select>` next to the model dropdown ("Provider: Anthropic ▼"); selectable only if env-indicator True | Keep `Settings.llm_provider` writable; PUT /settings/llm still accepts `llm_provider` form field | Lets user explicitly switch to a non-default configured provider; still one UI element instead of three | Adds back a "selector" exactly what owner asked to remove (might violate directive) |
| **C. Read-only "Current: Anthropic" label** | Single label `<p>` showing the active provider; no UI to change | Like Option A — backend computes from env | Cleanest visually; explicit about what's active | Same con as A — to change, edit `.env` + restart |

**Architect recommendation: Option A.** Cleanest match to owner directive + matches plan 26's post-vault "env-only" model. Settings UI shows what's configured + which one is active (implicit). To switch, operator edits `.env` and restarts (or unsets the higher-priority key).

**Owner picks before plan execution** — Master plan Q1 surfaces this.

### File-by-file edits (Option A assumed; revise on owner pick)

1. **`src/ui/templates/pages/_settings_llm.html`** — DELETE lines 28-49 (the "Active provider" `<section>` containing the 3 `provider_card.html` includes). Replace with NOTHING (env-presence grid below already covers the visual surface). Keep the `<form>` wrapper since the model dropdown + cost cards + semantic-match toggle ALL still need to POST.
2. **`src/ui/templates/pages/_settings_llm.html`** — REMOVE the `provider_id` jinja context reference from the model-dropdown section (line 97-99). Add a small "Active provider: **{{ active_provider_label }}**" label above the model dropdown, sourced from the new ctx field.
3. **`src/ui/routes/settings.py:_ctx_for_tab`** — `provider_id` field stays (it's still used to filter `_LLM_MODEL_OPTIONS` for the model dropdown). Add `active_provider_label: str` field computed from `env_secrets.env_indicators_for_llm_tab()` w/ priority resolution.
4. **`src/services/env_secrets.py`** — Add `resolve_active_llm_provider() -> LLMProvider` helper. Priority: Anthropic > OpenAI > Ollama; returns first present, defaults to `LLMProvider.ANTHROPIC` if none configured (matches current `Settings.llm_provider` default per `models/settings.py`).
5. **`src/services/settings_service.py:update_llm`** — Mark the `provider` arg as **soft-deprecated**: if a caller passes `provider`, log a warning + persist anyway (back-compat for existing tests). Plan body emphasizes that the UI no longer surfaces provider mutation; future plan removes the arg fully.
6. **`src/api/settings.py:put_llm`** — Inspect form payload for `llm_provider` field. If present, log warning ("Active provider is now resolved from env-presence; ignoring") and don't override the DB column. Or: silently accept + persist (back-compat). Engineer picks the safer of the two; recommend log-warning-but-persist for one release, then full removal.
7. **`src/ui/templates/components/provider_card.html`** — KEEP file but mark deprecated in docstring. May still be used by `pages/settings.html` in a different context. Verify via `grep -rn "provider_card.html" src/ui/templates/`.
8. **`tests/test_settings_llm_dual_selector_removed.py`** — NEW. 3 tests:
   - GET `/settings/llm-provider` does NOT render an `<input type="radio" name="provider">` element
   - GET `/settings/llm-provider` renders the env-presence grid (3 indicator cards)
   - GET `/settings/llm-provider` renders an "Active provider: <name>" label
9. **`tests/test_env_secrets.py`** — add 4 tests for `resolve_active_llm_provider()`: Anthropic-only env → ANTHROPIC; OpenAI-only → OPENAI; Ollama only → OLLAMA; none → ANTHROPIC (default).
