# 37 · 0.2.0.12 Discord + Telegram notifications for new jobs

## Goal

Wire the `0.2.0.10` per-source scrape crons into outbound Discord + Telegram channels so the operator gets one notification per `JobScrapeRun` summarizing the new jobs that just landed (source, count, top N titles with deep links to `/jobs/{id}`). Reuses the existing `services/notifications.py` substrate (Discord webhook, Telegram bot, in-app toast, per-event toggle) shipped in Wave 6; this plan adds the `EVENT_SCRAPE_RUN_NEW_JOBS` event + the integration point in `scraper_service.run_scraper`. Net effect: the operator's Discord/Telegram pings during the day, like the n8n flow did, but the trigger is naavik-native and the dispatch lives next to the scraper lifecycle that produced the row.

## Why

`ROADMAP.md` row `0.2.0.12` (Issue #17, milestone `0.2.0`) is the last of the four scraper-surface rows (`0.2.0.10` cron + `0.2.0.11` UI + this one + `0.2.0.13` rate-limit) that turns Phase 2 into "the scraper actually pings the user when something new happens" — the explicit n8n parity bar called out in the row title ("Port from n8n"). The n8n flow pinged Discord on every high-scoring job; that gating was scoring-conditional, but scoring is Phase 3 (`0.3.0.02`), so the row-as-written would silently no-op for the next ~10 plans of runway. The pivot in this plan is to make the trigger **scrape-run-completion-based**, not **per-job-score-based**: every completed `JobScrapeRun` with `new_jobs > 0` dispatches one summary message, regardless of `Job.score`. When scoring lands at `0.3.0.02`, the existing per-job `notify_new_high_score` path becomes the second tier (high-score-only inline notification) — they coexist; this plan ships the first tier.

`services/notifications.py` already carries the Discord embed builder, Telegram outbound `sendMessage` wrapper, per-event toggle helper (`_is_event_enabled`), and rate-limit-tolerant `httpx.AsyncClient` posts — all six event constants from the Wave-6 build are already wired. Plan 26 (`0.2.0.01`) moved Discord webhook + Telegram bot token from the vault to env vars consumed by `pydantic-settings` (`DISCORD_WEBHOOK_URL`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`); `_discord_url()` + `_telegram_token()` + `_telegram_chat_id()` already read those. The hard work was done in Wave 6; this plan **does NOT extend** the secret surface — it adds one event constant + one new event-emitter + one call site.

ROADMAP rank is implicit (no Priority cell as of 2026-05-19); shipping it consolidates the 0.2.0 milestone before `0.2.0.13` (rate-limit) lands. Per BACKEND.md § M.5 + § H.3 cross-service flow, "scrape → upsert → notify" is the canonical seam; this plan implements that seam at the **post-scrape** boundary rather than the per-upsert boundary, for the rate-limit-friendliness reasons argued in § D.1 below.

### B · Decision matrix — six locked choices

#### D.1 Trigger point — per-upsert vs post-scrape vs daily-digest

Per CONTEXT key decision 1. Three options:

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| (a) Inline per-`upsert_job` after successful insert | Highest fidelity; per-job ping | Each cron firing produces N msgs (up to LinkedIn `_DEFAULT_CRON_SCHEDULES["linkedin"] = */30` × ~50 listings = 100 msgs/hour just from LinkedIn); Discord global webhook = 30 msgs/min → trivial to hit 429 | Blocks scrape on network I/O; couples scraper success to webhook availability; user gets notification spam | High — every upsert path needs the notify hook | Couples notify to upsert |
| **(b) Post-scrape, in `scraper_service.run_scraper` after lifecycle finalize (chosen)** | One msg per JobScrapeRun = max 6 sources × ~6 firings/hour × 1 user = ~36 msgs/hour (well under 30/min); batched summary embed reads better than per-job spam | Slight delay (up to one cron interval) between job persistence + ping | Lower fidelity — user sees "5 new from LinkedIn" not "this specific LinkedIn job appeared 12s ago"; lifecycle bug → no notification (mitigated: finalize is in `finally:`) | Low — one call site in one service | None — additive |
| (c) Cron-driven daily digest (separate APScheduler job at e.g. 09:00) | Lowest noise; matches `admin.weekly_summary` § I.1 pattern | Highest latency — user could miss a high-priority job for 23h | New cron + counter table or recompute over `JobScrapeRun` history | Two notify pathways drift (digest vs urgent) | Couples future high-score path to digest cadence |

**Pick (b).** Rationale: the per-run summary is the cleanest fit to the existing `JobScrapeRun` lifecycle — the row already carries `new_jobs` + `listings_returned` + `status` + `duration_ms`, and the lifecycle's `finally:` block guarantees finalization-before-notify ordering. It dodges Discord's 30/min webhook rate limit by collapsing N upserts → 1 message. Option (a) is the n8n parity option but n8n's flow was the only thing in the pipeline; here, the cron triggers 6 sources every interval — the math escalates fast. Option (c) is a Phase 6 polish target (`admin.weekly_summary` already in BACKEND.md § I.1) that consumes the same `JobScrapeRun` data this plan persists; we'll layer it later without rework.

**Important second-tier behavior.** When scoring ships at `0.3.0.02`, the existing `notify_new_high_score(settings, job)` helper becomes the high-fidelity layer — it fires per-job, gated on `score >= settings.notify_threshold` (default 0.80). Two layers coexist: the per-run summary in this plan (every run, low-fidelity, source/count/links) + the per-high-score-job ping (gate-and-go, high-fidelity, sponsorship-flagged, individual). No conflict — different events, different toggles, different cadence.

#### D.2 Filter criteria — "new jobs only" semantics + duplicates

Per CONTEXT key decision 2 + 6. Options:

| Filter | Choice | Why |
|---|---|---|
| `created` flag on `upsert_job` result | YES — only count rows where `created=True` | Updates of existing rows aren't "new jobs"; spam reduction |
| `Job.duplicate_of_id is None` | YES — top-jobs listing excludes flagged duplicates from the link list (count includes them) | Counter says "5 new" but the user-facing link list shows only the 3 non-dup; duplicates are still useful in the diagnostic UI per `0.2.0.11` `include_duplicates` toggle, but spammy in Discord |
| `Job.score >= settings.notify_threshold` | NO for this event | Pre-`0.3.0`, score is always 0.0; gating would mean zero notifications. **This event is intentionally score-blind.** When scoring lands, the per-job `notify_new_high_score` (different event) handles the score-gated path |
| `Job.archived == False` | YES — soft-deleted rows excluded | Standard |
| Per-source enable/disable | YES — gated by `settings.sources_enabled.get(source.value, True)` | Same as cron skip logic; if the cron is enabled, notifications are too. A future granular "scrape but don't ping for source X" toggle is a Settings · Notifications follow-up (`0.2.5.NN` candidate) — not in scope here |

Net effect: a LinkedIn firing that yields 12 RawJobs, of which 5 are net-new + 2 are flagged as duplicates of existing Workday rows, produces ONE Discord message: title "5 new jobs from LinkedIn", description listing 3 deep links (the non-dup new rows) + a footer "2 cross-source duplicates merged".

#### D.3 Channels — Discord vs Telegram vs both

Per CONTEXT key decision 3. Options:

| Option | Choice | Why |
|---|---|---|
| (a) Send to Discord if configured | YES | Webhook URL is env-loaded; presence-of-URL = enabled; no UI gating |
| (b) Send to Telegram if configured | YES | Bot token + chat ID env-loaded; presence-of-both = enabled |
| (c) `asyncio.gather` over both (fan-out) | YES | Matches the existing `notify_new_high_score` + `notify_application_submitted` pattern in `notifications.py:272-314`; `return_exceptions=True` so one channel's 429 doesn't break the other |
| (d) Per-channel enable flag in Settings (e.g. `notify_via_discord: bool`) | NO | YAGNI; the env-var presence-check already serves as the on/off switch. If the operator wants to disable Discord, they unset `DISCORD_WEBHOOK_URL`. **Per-EVENT toggles** are the right granularity; per-CHANNEL toggles add UI surface without operational benefit |

**Pick (a) + (b) + (c).** Rationale: the existing helpers `send_discord` + `send_telegram` already silent-no-op when the env vars are unset (`_discord_url()` returns None → return False; same for Telegram). Wrapping them in `asyncio.gather(...)` with `return_exceptions=True` matches the established pattern. The in-app toast (third gather arm) lights the SSE `#toast-region` so the user gets the notification even on a tab that's open — consistency with the rest of the notification system.

#### D.4 Rate limiting

Per CONTEXT key decision 4. Discord webhook = 30 msgs/min global; Telegram bot = 30 msgs/sec to same chat. The per-scrape-run approach naturally throttles:

- LinkedIn cron `*/30 * * * *` = 2 firings/hour × 1 user = 2 msgs/hour/source
- Workday/Greenhouse/Lever/Ashby = `0 * * * *` = 1 firing/hour each = 4 msgs/hour
- Indeed = `IntervalTrigger(minutes=90)` = ~0.67 firings/hour
- Total: ~6.67 msgs/hour/user — three orders of magnitude under Discord's 30/min ceiling

**No additional rate-limit work needed for the single-user self-host case.** If multi-tenant cloud ever lights up (Phase 2+ post-CLI sunset), we revisit — but at that point we batch-by-tenant or sharded webhooks. Captured as a forward ref, not a current concern.

`httpx.AsyncClient(timeout=10.0)` (already the default in `notifications.py`) caps a single misbehaving webhook target. The Discord 429 response is logged but not retried — the next scrape firing will dispatch fresh; transient outages self-heal.

#### D.5 Message format — per-job card vs summary embed

Per CONTEXT key decision 5. Options:

| Option | Choice | Why |
|---|---|---|
| (a) One Discord message per job (n8n-style) | NO | See § D.1 rate-limit math + § D.4 |
| **(b) Summary embed per scrape run with top-5 inline (chosen)** | YES | Discord embed supports a description block + fields; top-5 keeps the embed under Discord's 6000-char total + 4096-char description-only limits |
| (c) Plain text bullet list | NO | Embeds render better in Discord clients and are filterable by colour-coding (cyan for new-jobs event matches the existing `EVENT_NEW_HIGH_SCORE` cyan in `_embed_for_event` line 99) |

**Pick (b).** Format sketch:

```
Discord embed:
  title:        "🆕 5 new jobs from LinkedIn"
  description:  "• Senior SWE — Stripe — sf.gov: <link>"
                "• Staff Engineer — Anthropic: <link>"
                "• ML Platform Lead — Anthropic: <link>"
                "• Senior Backend — Discord: <link>"
                "• ... +1 more"
  color:        5793266 (cyan, matches EVENT_NEW_HIGH_SCORE convention)
  fields:
    - "Run"       :  "linkedin · 12 listings · 5 new · 7 updated · 1.4s"
    - "Threshold" :  "score gate disabled until 0.3.0"
  footer:        "naavik · <ISO timestamp>"

Telegram (Markdown):
  📌 *5 new jobs from LinkedIn*
  • Senior SWE @ Stripe — <link>
  • Staff Engineer @ Anthropic — <link>
  • ... +3 more
  _Run: 12 listings · 5 new · 7 updated · 1.4s_
```

Top-5 cap is intentional: more than 5 in one message starts feeling like spam; if a single firing returns 50 new jobs, the operator wants the count + a CTA to `/jobs?source=linkedin&order=found_at_desc` — that link is in the embed footer. (Plan 36 doesn't ship the order-by querystring, so for MVP the link goes to `/discover?source=linkedin`; a follow-up adds an `order_by=found_at` query — filed in OQ.3.)

#### D.6 `Settings` columns — do we need new ones?

Per CONTEXT key decision 7. Existing relevant columns on `Settings`:

| Column | Used for | Reuse here? |
|---|---|---|
| `notify_threshold: float = 0.80` | Score gate for `notify_new_high_score` | NO — this event is score-blind per § D.2 |
| `notify_on_errors: bool = True` | Critical admin error → Discord | NO — different event |
| `notifications_enabled: dict` (JSONB) | Per-event-type toggle dict | YES — new key `"scrape_run_new_jobs": true/false` (default true) |
| `sources_enabled: dict` (JSONB) | Per-source cron enable | YES — read-only; if source disabled, we never enter the scrape codepath, so notify is naturally gated |

**No new `Settings` column.** The dict-typed `notifications_enabled` is exactly the right shape (Wave 6 made it freeform JSONB precisely so we can add event types without migration churn). Operator opt-out path: PUT `/api/v1/settings/notifications` with `{"notifications_enabled": {"scrape_run_new_jobs": false}}` — already routed by `settings_service.upsert_settings_notifications`. UI checkbox added in `_settings_notifications.html`.

#### D.7 Failure handling

Per CONTEXT key decision 8. Modes:

| Failure | Behavior |
|---|---|
| `DISCORD_WEBHOOK_URL` unset | `_discord_url()` returns None; `send_discord` returns False silently; no log noise |
| `TELEGRAM_BOT_TOKEN` unset OR `TELEGRAM_CHAT_ID` unset | `send_telegram` returns False silently; no log noise |
| Discord webhook 429 (rate-limit) | Existing `send_discord` logs `warning("discord webhook failed: %d ...")` + returns False; **no retry** (next scrape firing will dispatch a fresh summary) |
| Discord webhook 5xx | Same as 429; logged + abandoned |
| `httpx.RequestError` (network) | Existing `send_discord` catches + logs; returns False |
| Telegram returns non-2xx | Same pattern as Discord |
| `notify_scrape_run_summary` itself raises | `run_scraper`'s post-finalize block catches via `try/except Exception` + logs `log.warning("scrape-run notify failed: %s", exc)` — **never block the scrape lifecycle on notification failure**. The JobScrapeRun row is already persisted before the notify dispatch. |
| `list_new_jobs_from_run` query fails | Caught alongside the above; notify is best-effort |

This matches the established pattern in `application_service.py:471` (`log.warning("notify_application_submitted failed: %s", exc)`) — notifications are best-effort, scraping is load-bearing.

## Open questions

The defaults in this proposal are the architect's recommendation. User can override before approval.

- [ ] **OQ.1 — trigger point**: post-scrape (option b) selected per § D.1. Confirm not per-upsert (a) or daily digest (c)? **Default: b**.
- [ ] **OQ.2 — score-blind**: confirm the event is intentionally score-blind for the entire 0.2.x window (until 0.3.0.02 lands). The user receives summary notifications regardless of job quality. Acceptable? **Default: yes — n8n parity bar + scoring isn't shipped yet**.
- [ ] **OQ.3 — top-N count**: top-5 chosen for embed-size + readability. Should it be 3? 10? Configurable via `Settings.notifications_top_n_per_run`? **Default: 5 hardcoded — config-creep guard; revisit if user reports it's too few/many in practice**.
- [ ] **OQ.4 — toast channel**: should the in-app toast (third gather arm in `notify_scrape_run_summary`) fire even when no user is logged in (i.e., toast queue accumulates while no SSE subscriber reads it)? Existing `push_toast` uses `_TOAST_QUEUE: asyncio.Queue(maxsize=128)` which silently drops on overflow — fine for our cadence (~6.67 msgs/hour). **Default: keep the toast call; the queue's drop-on-overflow already handles the no-subscriber case**.
- [ ] **OQ.5 — duplicate handling in top-5 list**: should `Job.duplicate_of_id IS NOT NULL` rows count toward `new_jobs` (yes, per `upsert_job`'s `created=True` semantic) but be excluded from the top-5 link list (yes — they're not useful as deep links)? **Default: yes to both — count includes dups; top-5 excludes them. § D.2.**
