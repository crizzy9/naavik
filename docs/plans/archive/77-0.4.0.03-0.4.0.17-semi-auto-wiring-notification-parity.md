# 77 · 0.4.0.03 + 0.4.0.17 — Semi-auto wiring + notification parity

## Goal

Connect the apply-preview HTMX two-step (shipped in plan 75 / 0.3.3.08
but not wired to the UI entry-point) AND give manual review-and-apply
submissions the same Discord/Telegram notification echo that auto-apply
already gets. Closes ROADMAP rows 0.4.0.03 refinement + 0.4.0.17 +
0.3.3.08a (the deferred wiring follow-up filed in PR #170 architect
review).

## Why

Two gaps in the semi-auto submission UX:

**Gap M1 (`0.3.3.08a`):** `discover_action_bar.html:20-25` still points
the "Review & apply" CTA at the OLD workspace fragment
(`/_fragments/discover/expanded/{job_id}`), not the new preview card
shipped in plan 75. The two-step UX is server-side-only dead code from
a user's POV. ~10 LOC + manual QA.

**Gap M2 (`0.4.0.17`):** Auto-apply cron calls
`notifications.notify_application_submitted` per submitted Application
(`scheduler/jobs.py:46-52`). Manual review-and-apply submissions (`POST
/api/v1/applications/{id}/submit`) do NOT — the `notify_fn` parameter
is optional and not threaded from the HTTP route. Inconsistent operator
experience: auto-submitted gets Discord echo; manually-submitted
doesn't.

Closes 3 ROADMAP rows + 1 prior follow-up in one ~80 LOC PR.

## Proposal

Single PR; 2 commits (commit 1: M1 wiring + tests; commit 2: M2
notification parity + tests).

### D.1 Commit 1 — apply-preview wiring (M1 / 0.3.3.08a)

**Change A:** `src/ui/templates/components/discover_action_bar.html`
(lines ~20-25): point "Review & apply" button at
`/_fragments/apply/preview/<application_id>` instead of the workspace
fragment.

```html
<!-- BEFORE -->
<button hx-get="/_fragments/discover/expanded/{{ job_id }}"
        hx-target="..." ...>Review & apply</button>

<!-- AFTER -->
<button hx-get="/_fragments/apply/preview/{{ application.id }}"
        hx-target="#apply-preview-slot"
        hx-swap="innerHTML" ...>Review & apply</button>
```

**Change B:** Add an `#apply-preview-slot` mount point in the Discover
right-rail card OR Up-next card area. Concrete: extend
`up_next_card.html` to render `<div id="apply-preview-slot"></div>`
after the existing CTA chip when `state in ('saved', 'queued')`.

**Change C:** Verify HX-Trigger pathway works end-to-end. The existing
plan 75 routes (`apply/preview`, `apply/confirm`, `apply/cancel-preview`)
already emit `HX-Trigger: appliesBundleGenerationStart` on confirm. Add
a small JS hook in `base.js` to play the toast + redirect on
`appliesBundleGenerationComplete` (plan 75 documents the event but
doesn't wire the toast).

**Tests:**

- Test 1: GET `/discover/{job_id}` returns HTML containing
  `hx-get="/_fragments/apply/preview/`.
- Test 2: Click-through sim — POST `/_fragments/apply/confirm/<id>`
  returns expected partial.
- Test 3: Playwright manual QA — capture screenshot before + after to
  verify the slot mounts the preview card visually.

### D.2 Commit 2 — notification parity (M2 / 0.4.0.17)

**Change A:** `src/services/application_service.submit_draft` — add a
NEW helper `_default_notify_fn(session, settings)` that returns the
wired callable (mirrors `scheduler/jobs.py:46-52`'s pattern):

```python
async def _default_notify_fn(session, settings):
    from services.notifications import notify_application_submitted
    async def _notify(application):
        await notify_application_submitted(settings=settings, application=application)
    return _notify
```

**Change B:** `submit_draft(...)` accepts `notify_fn=None`. When
`None`, look up `Settings` per `application.user_id` and call
`_default_notify_fn` automatically.

**Change C:** Existing auto-apply cron caller passes `notify_fn`
explicitly (unchanged). New behavior only triggers for HTTP-driven
submit (from `/_fragments/apply/confirm/<id>` → `submit_draft`).

**Tests:**

- Test 1: HTTP submit-draft path calls notify_fn when settings have
  Discord webhook configured (mock `_send_discord_application_submitted`,
  assert called once).
- Test 2: HTTP submit-draft path skips notify when Settings None or
  no channels configured (no-op; no exception).
- Test 3: Existing auto-apply cron path unchanged (regression).

### D.3 Apply-preview confirm route — `submit_draft` call site

Verify (in PR review) that
`POST /_fragments/apply/confirm/{application_id}` ends up calling
`submit_draft` from `discover.py:719-770`. If it dispatches to
`bundle_generator.generate_bundle` only (i.e. generates docs but
doesn't submit), the wiring is incomplete and we add a follow-up
submission action to the confirm route. Inspect-and-decide during
implementation.

## Deviations from plan

- **added new route /_fragments/apply/preview/by-job/{job_id}...** — what: added new route /_fragments/apply/preview/by-job/{job_id} instead of changing hx-get to /_fragments/apply/preview/<application_id>. why: discover_action_bar.html receives job_id (not application_id) — the by-job variant get_or_creates the DRAFT and renders the same partial; keeps existing application-id route untouched + matches the get_or_create_draft pattern used by /_fragments/discover/expanded/. impact: new route surface — documented in plan archive; discover_action_bar.html now points at /_fragments/apply/preview/by-job/{job_id} (single caller); follow-up plans wanting a job-id apply-preview entry should reuse this route. surface: none.
- **did NOT add a base.js toast** — what: did NOT add a base.js toast handler for HX-Trigger appliesBundleGenerationComplete (plan § D.1 Change C). why: existing confirm route emits HX-Trigger bundle-generated (per plan 75 / 0.3.3.08) and bundle generation lives behind a separate handoff to the existing /api/v1/applications/{id}/generate-bundle route — wiring the toast was speculative since the trigger payload + downstream listener semantics belong to plan 75 contract, not this wiring PR. impact: toast on bundle-completed remains a follow-up; user gets HTMX swap into apply-preview-slot which is the canonical confirmation surface; if observed UX needs the toast, file as 0.4.0.03b follow-up. surface: none.
- **_default_notify_fn signature is (settings) not (session** — what: _default_notify_fn signature is (settings) not (session, settings). why: helper does not need the session — Settings is already loaded inline at line 462 of submit_draft and passed in; dropping session keeps the helper testable + matches the closure-only role. impact: callers reuse submit_draft contract unchanged; explicit notify_fn passers (auto-apply cron) untouched; helper exported on services.application_service so future callers can wrap explicitly if needed. surface: cron schedule.
- **did not modify any existing tests** — what: did not modify any existing tests when default-notify-fn shipped. why: existing tests that pass no notify_fn ALSO have exec_queue Settings → None which short-circuits the default helper to None; the new helper only fires when Settings is populated, which the 3 new tests exercise explicitly; existing 26 submit_draft + auto-apply tests pass unchanged. impact: zero regression on baseline 29 application_service tests; 3 new tests cover the default-helper happy/skip/override matrix; total 32. surface: none.
