# 42 · 0.2.0.04 PC.6b — Onboarding bypass on `/api/v1/profile/from-extraction`

## Goal

Close the hacker MEDIUM finding from PR #69 by gating `POST /api/v1/profile/from-extraction` with a no-existing-user precondition so a flagged operator can no longer downgrade their real-JWT cookie to the `naavik_session=fake-1` fake-session value. Also fold in 3 LOW non-blocking notes from the same review (~5 LOC + 1 test assertion strengthening). Single security fix; ships as `feat/0.2.0.04-onboarding-bypass` PR; CONTRACT_CHANGE per `docs/PLAYBOOK.md § H` (touches `src/**` + `tests/**`).

## Why

PR #69 (plan 23 / PC.6a) shipped the `require_authed_session` wrapper across 41 mutation routes — every authed surface now redirects flagged users (`must_change_password=True`) to `/auth/change-password`. Engineer correctly skipped 2 onboarding routes (auth.py:145, 223) because gating them with the wrapper would 401 every fresh signup at the upload step (no cookie yet). Hacker's MEDIUM probe found the residual exposure: `post_profile_from_extraction` is the endpoint that **sets** `naavik_session=FAKE_SESSION_VALUE`, and a flagged operator (or confused-deputy via XSS / shared browser / leftover session) who POSTs to it after login will have their real-JWT cookie REPLACED with the fake-session value. Every `require_authed_session`-gated route then takes the fake-session None pass-through branch and the must-change-password redirect never fires. Single-user MVP exposure is acceptable today (plan 23 § Deviations from plan #1), but the row MUST ship before any multi-user expansion or before `0.2.0.07`+ scrapers start writing per-user-bound jobs against a wrong-user JWT.

## Proposal

### Files modified

- **`src/ui/routes/auth.py:223-238`** (`post_profile_from_extraction`): swap signature from `request: Request` to `request: Request, session: AsyncSession = Depends(get_session)`. Add early count probe via the same `select(func.count()).select_from(User)` + `.one()` unwrap pattern used at `_compute_signup_disabled:54-65` (this file) and `post_signup:196-203` (`src/api/auth.py`). If `existing_count > 0`, return `Response(status_code=409, content=...)` HTML error card (HTMX-swappable into `#onboarding-step-content`) saying "Account already exists. Sign in instead." with a link back to `/login`. Only fall through to the existing fake-session cookie write when `existing_count == 0` (fresh-install bootstrap path).
- **`tests/test_auth.py:1217`** (LOW Note #1 fold-in): add a 1-line guard comment above the `monkeypatch.setattr(auth_svc, "verify_jwt", ...)` line: `# NOTE: wrapper imports verify_jwt by bare name at services/auth.py:338; if verify_jwt moves to a sibling module, switch this monkeypatch to the wrapper's own import path or this test silently no-ops.`
- **`tests/test_auth_gate.py:184-237`** (LOW Note #2 fold-in): in `test_fake_session_caller_unaffected_across_groups`, after the existing `assert r.status_code not in gate_codes` sweep, pin ONE representative route to a positive assertion: `assert positive_route_response.status_code in {200, 204, 422}` to catch a future regression that converts an existing route into a 500 (silent pass through the negative-only sweep).
- **`src/services/auth.py:307-308`** (LOW Note #3 fold-in): extend the existing search-replace note in the `require_authed_session` docstring with one line about the return-type tightening at retirement: `# At retirement, also tighten _user: User | None -> User on dependent handlers because require_password_complete returns User, not User | None.`
- **`tests/test_auth_gate.py`** (new tests; see § Test plan): 4 new cases for the no-user-precondition fix.

### Behavior contract

`POST /api/v1/profile/from-extraction` is now a single-shot fresh-install endpoint. Resolution:

1. Count `User` rows.
2. If count > 0 → return 409 + `_onboarding_already_exists_card` HTML fragment with HX-Redirect: `/login`. **Do NOT set the fake-session cookie.**
3. If count == 0 → existing behavior: 204 + `HX-Redirect: /` + `naavik_session=fake-1` cookie set.

This preserves the fresh-install onboarding flow (Wave 6 will rewrite this when real auth lands per `services/profile_service.commit_extraction`) while closing the demotion-attack surface for any post-bootstrap user.
