# 74 · 0.3.2.04 · Calibration + cost-cap fallback indicator banner

## Goal

Extend the existing `_llm_cost_cap_widget.html` (Settings · LLM tab; plan 54 / 0.2.5.03) with a prominent fallback indicator: when LLM judge is paused due to cost-cap exhaustion OR no LLM provider is configured, render an amber banner explaining the degraded mode + linking to recovery action. Per 0.3.0 OQ-5 lock: "silent fallback + banner on Settings · LLM tab." This plan ships the banner.

`Type: execution` — simple widget extension; no new design contract.

## Why

Plan 65 (0.3.0 scoring substrate) shipped graceful fallback when LLM judge can't run:
- Cost-cap exhausted mid-day → `JobScore.judge_skipped=True`, `JobScore.judge_skipped_reason="cost_cap_exhausted"`
- No LLM provider configured → `JobScore.judge_skipped=True`, `judge_skipped_reason="no_provider_configured"`

Composite layers 1-3 (tag + semantic) still return a score; UI renders it normally — but user doesn't know the LLM judge was skipped. Owner directive at OQ-5 lock (per ROADMAP § 0.3.0): "silent fallback + banner on Settings · LLM tab" — the banner part was filed as 0.3.2.04 and never shipped.

This plan delivers it.

### Risk + mitigation

| Risk | Likelihood | Impact | Mitigation |
| --- | --- | --- | --- |
| `Job.match_breakdown.judge_skipped` is a JSONB key — query cost over many jobs | LOW | LOW | Query is `WHERE user_id=X AND scored_at >= today_midnight_utc AND match_breakdown @> '{"judge_skipped": true}'` — GIN-indexable; or filter in Python after fetching today's `Job` rows (small N). |
| Banner display blocks the actually-useful cost-cap progress bar | LOW | LOW | Banner rendered BELOW progress bar; doesn't replace it |
| User dismisses banner — no persistent UI signal | LOW | LOW | No dismiss action — banner stays visible while `judge_skipped_count_today > 0`. Resets at UTC midnight w/ new scoring run. |
| Banner false-positive when judge_skipped is set for unrelated reasons (network error, provider 5xx) | LOW | LOW | Banner copy lists the SPECIFIC reason ("cost_cap_exhausted" / "no_provider_configured"); other transient errors don't trigger banner (their `judge_skipped_reason` won't match the user-relevant set). |
| Plan 65's `JobScore` schema vs Plan 73's `ScoreSnapshotDaily` — banner queries Job.match_breakdown but score history queries ScoreSnapshotDaily | LOW | LOW | Independent surfaces. Banner uses real-time `Job.match_breakdown`; sparkline uses cron-rolled aggregates. |
