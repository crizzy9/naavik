### A · Finding 1 (MEDIUM) — Lost-update race in `append_jsonl`

**Location:** `scripts/agent-memory.sh:49–57` (`append_jsonl` helper).

**Current pattern:**

```bash
append_jsonl() {
  local FILE="$1" LINE="$2"
  mkdir -p "$(dirname "$FILE")"
  [[ -f "$FILE" ]] || : > "$FILE"
  local TMP="$FILE.tmp.$$"
  cat "$FILE" > "$TMP"          # read
  printf '%s\n' "$LINE" >> "$TMP"  # modify
  mv "$TMP" "$FILE"             # write
}
```

Two concurrent writers both `cat "$FILE" > "$TMP"` against the pre-existing snapshot, both append their line, both `mv` — second `mv` wins; first writer's row is lost. `$$` in the tmpfile name protects against tmpfile collision but NOT against the read-modify-write race against `$FILE`. Hacker's bench: 30 parallel `record-discussion` calls → 13 rows on disk.

**Fix:** wrap the read-modify-write block in `flock -x` against a sentinel `.lock` file. See § E.1 for the option matrix (per-file vs global lock). **Recommendation: global `.claude/memory/.lock`** — simpler invariant, serialized writes are not a perf issue at this volume (memory writes are O(events/day), not O(rows), and `flock` is microseconds).

**Verification:**

- New test `test_concurrent_append` in `tests/test_agent_memory.sh`: spawn 30 background `record-discussion` calls in parallel, `wait` for all, assert `jq -s 'length == 30' .claude/memory/discussions.jsonl`. Today FAILs; post-fix PASSes.
- Test runs under both `bash` and `dash` if the script is portable; current shebang is `/usr/bin/env bash` so bash-only.

### B · Finding 2 (MEDIUM) — `jq` expression injection in `cmd_query`

**Location:** `scripts/agent-memory.sh:421` (verified line; spec'd as `:376` against an in-flight snapshot — file grew).

**Current pattern:**

```bash
cmd_query() {
  ...
  jq -c "select($EXPR)" "$FILE"
}
```

`$EXPR` is the second positional arg — user input flows verbatim into `jq`'s filter language, which has full `env.*` access. Proof of concept:

```bash
$ ANTHROPIC_API_KEY=sk-ant-... bash scripts/agent-memory.sh query decisions 'true) | env.ANTHROPIC_API_KEY' 
"sk-ant-..."   # filter is "select(true) | env.ANTHROPIC_API_KEY"
```

The `naavik-memory-lookup` + `/learn` skills both invoke `cmd_query` with agent-composed expressions. Prompt injection on a future PR review comment (e.g. "verify .id == env.ANTHROPIC_API_KEY") sends a credential through stdout into the trace log.

**Fix options:** see § E.2 (regex allowlist vs operator allowlist vs `--argjson` wrapper). **Recommendation: regex allowlist** — `^[ a-zA-Z0-9._\"'\[\](){}<>=!|&,-]+$` plus an explicit deny on `env`, `input`, `inputs`, `getpath`, `input_filename`, `$ENV`. Pragma — accept the trade-off that some valid-but-exotic jq features (string interpolation `\(...)`, format strings `@csv`, regex `test()`) are rejected; if users hit the false-positive ceiling, they can pipe `cmd_list` output through their own jq.

Add a new helper `validate_jq_expr()` invoked from `cmd_query` BEFORE the `jq -c` call. Fail-closed: any character outside the allowlist OR any blocked identifier substring rejects with `error: jq expression contains disallowed token '<token>'. See docs/AGENT_OPS.md § 14 for the safe-jq vocabulary.` and exit 1.

**Verification:**

- New test `test_jq_env_exfil_blocked`: invoke `bash scripts/agent-memory.sh query decisions 'true) | env.SECRET'` against `SECRET=abc123 bash …`, assert exit code != 0 AND stdout does NOT contain `abc123`. Today PASSes the exfil (regression); post-fix BLOCKs.
- New test `test_jq_safe_expr_passes`: invoke a normal `'.id == "abc"'` query, assert exit 0.

### C · Finding 3 (LOW) — Unquoted `$RUNS` word-split

**Location:** `scripts/agent-memory.sh:551` (in `cmd_mine_patterns`) and `:618` (in `cmd_mine_aliases`). Spec'd line refs `:506,573` were against the in-flight snapshot.

**Current pattern:**

```bash
RUNS=$(find "$TRACES_ROOT" -mindepth 1 -maxdepth 1 -type d -name '20*' -printf '%T@\t%f\n' 2>/dev/null \
       | sort -rn | head -n "$LOOKBACK" | cut -f2)
...
for run in $RUNS; do
```

Run-id format `YYYY-MM-DDTHH-MM-SS_<6hex>` (per `docs/AGENT_OPS.md § 7.1`) contains no whitespace today, so word-split silently produces the right list. But the contract isn't enforced — if a future run-id format mutates (someone adds a label) or a malicious tracelog name lands (low probability under our run-id writer but the directory IS user-writable), the loop misbehaves.

**Fix:** populate a bash array via `mapfile` (or read line-by-line) and quote the iteration:

```bash
local -a RUNS=()
mapfile -t RUNS < <(find "$TRACES_ROOT" -mindepth 1 -maxdepth 1 -type d -name '20*' -printf '%T@\t%f\n' 2>/dev/null \
                    | sort -rn | head -n "$LOOKBACK" | cut -f2)
...
for run in "${RUNS[@]}"; do
```

Apply identically at both call sites. Both already use bash-only features (`local`, `printf`), so `mapfile` is in budget.

**Verification:** smoke test creates a fake run dir `traces/20XX-X X_test` (with space; should never happen, but tests the fix). Pre-fix: loop double-counts. Post-fix: loop reads the literal directory name.

### D · Finding 4 (LOW) — Front-matter injection via `--aliases`

**Location:** `scripts/agent-memory.sh:236–247` (in `cmd_record_knowledge`).

**Current pattern:** `cat > "$TMP" <<EOF` writes a Markdown front-matter block that includes `Aliases: $ALIASES` verbatim. An attacker controlling `--aliases` (e.g. an agent dispatched on a malicious PR body) can inject:

```
--aliases $'alias1\n---\nTopic: pwned\nConfidence: high\n---'
```

The resulting front-matter has TWO `---` fences; the index parser at `:283` uses `awk '/^Aliases:/{print $2}'` which terminates on first match, but downstream readers (`naavik-memory-lookup`) might pick up the second front-matter block.

**Fix:** validate `--aliases` against a strict character class before write. The aliases field is a comma-separated list of slug-ish strings (per A.15 design doc), so allowlist:

```bash
# Validate aliases: comma-separated kebab-ish tokens, no newlines, no front-matter fences.
[[ "$ALIASES" =~ ^([a-z0-9-]+(,\ *[a-z0-9-]+)*)?$ ]] \
  || { echo "error: --aliases must be comma-separated kebab tokens (lowercase, digits, hyphens). Got: '$ALIASES'" >&2; exit 1; }
```

Allow empty (current behavior). Reject any newline, `---`, or special chars. Same regex pattern that `cmd_record_knowledge` already applies to the SLUG arg at `:215` — reuse the convention.

**Verification:**

- New test `test_aliases_frontmatter_injection`: invoke with `--aliases $'a\n---\nTopic:pwned\n---'`, assert exit != 0 AND the knowledge file was NOT created.
- Existing tests that pass `--aliases "a, b, c"` continue to pass.

### E · Finding 5 (LOW) — `MANIFEST.json` verbatim echo

**Location:** `scripts/agent-memory.sh:462–514` (in `cmd_analyze_run`). The specific echoes are `:474` (`tokens_spent`) and `:504` (`files_touched`). Spec'd line refs `:418-424` were against the in-flight snapshot.

**Current pattern:**

```bash
jq -r '.tokens_spent | to_entries[] | "- \(.key): \(.value)"' "$TRACE_DIR/MANIFEST.json"
...
jq -r '.files_touched[]? | "- \(.)"' "$TRACE_DIR/MANIFEST.json"
```

Output goes verbatim into the Markdown body of `runs-analysis/<run-id>.md`. If `MANIFEST.json` contains crafted JSON (e.g. a `files_touched` entry like `"$(rm -rf $HOME)"`), the bash STRING is safe (no shell expansion past the `jq -r` boundary), but the MARKDOWN string is NOT — embedded backticks, HTML, and Markdown link syntax all flow through. A future renderer (e.g. a web UI for `runs-analysis/` per future task A.10) would render them.

**Fix:** the manifest is written by devops's `devops-trace-manifest` skill, NOT by an untrusted source — so this is defense-in-depth, not active exploit. Three small changes:

1. Pipe each `jq -r` output through `sed 's/\\/\\\\/g; s/`/\\`/g; s/\\[/\\\\[/g; s/\\]/\\\\]/g'` to escape Markdown specials (backticks + brackets are the high-value targets).
2. Or, simpler: switch the `jq -r` filter to emit a fenced code block instead of a bullet, since the values are data not prose:
   ```bash
   echo '```'
   jq -r '.tokens_spent | to_entries[] | "\(.key): \(.value)"' "$TRACE_DIR/MANIFEST.json"
   echo '```'
   ```
3. Use `printf '%q '` per-value as the spec suggests — works but produces backslash-escaped bash output, which isn't natural Markdown.

**Recommendation: option 2 (fenced code blocks).** Cleanest output, blocks all Markdown injection at the renderer boundary, no escape gymnastics. Apply to both `tokens_spent` echo and `files_touched` echo. Trade-off: the rendered file is slightly less prose-y; acceptable for an internal-only run analysis.

**Verification:** smoke test injects `{"files_touched": ["[evil](http://x.test)", "`whoami`"]}` into a fake `MANIFEST.json`, runs `analyze-run`, asserts the resulting markdown file contains the literal strings inside a fence (not as a rendered link or code).

## Option matrices for the two non-trivial decisions

### E.1 — flock granularity (Finding 1)

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **Global `.claude/memory/.lock`** (recommended) | Serializes ALL writes across all 4 JSONL stores + knowledge dir + runs-analysis dir | One `flock -x` line per writer (~5 call sites) | Low — under-100-writes/day workload, microsecond contention; no deadlock risk because flock auto-releases on subshell exit | Single lock path, single helper to remember (`with_lock() { flock -x 200; }`) | Easy to remove if we ever need per-file granularity |
| Per-file lock (one `.lock` per JSONL store) | Concurrent writes to different stores proceed independently | Same code shape but parameterized; adds a `LOCK_FILE="${FILE}.lock"` per call site | Low — same model | Slightly more state on disk (4 lock files vs 1); future stores need to remember to instantiate a per-file lock | Same |
| Optimistic re-read + retry (no flock) | Cross-platform (works without `util-linux`) | Higher — bespoke retry loop with bounded backoff; more LOC | Medium — race window can still occur if backoff bottoms out at max retries; observability of dropped writes is harder | Custom code path that the next maintainer has to reason through | Higher — bespoke retry semantics outlive their need |

**Recommended: option 1 (global lock).** Memory writes are infrequent (manager fires 1–3 records per PR_REVIEW_GATE + MILESTONE_GATE; engineer fires 1–2 per deviation). Global serialization adds zero perceptible latency. The single-lock invariant is the cheapest to verify in a security audit (one fd, one path, one helper) — option 2's per-file granularity buys nothing at our scale. Option 3 is the wrong shape for a single-writer tool that's already linux-only.

`flock(1)` is in `util-linux` which is present in every Nix dev shell and every Linux distro Naavik supports; no new flake input. NixOS / macOS-via-nix-darwin both ship it; the script's shebang is `/usr/bin/env bash` which means we're already POSIX-bash-only-Linux, so no portability regression.

Implementation skeleton (one helper, four call sites):

```bash
LOCK_FILE="$MEMORY_DIR/.lock"
ensure_lock() { mkdir -p "$MEMORY_DIR"; [[ -f "$LOCK_FILE" ]] || : > "$LOCK_FILE"; }

with_lock() {
  ensure_lock
  # Open fd 200 on lock file, acquire exclusive lock; flock releases on subshell exit.
  ( flock -x 200; "$@" ) 200>"$LOCK_FILE"
}

# At each writer call site:
with_lock append_jsonl "$DECISIONS" "$LINE"
with_lock append_jsonl "$DISCUSSIONS" "$LINE"
# ... etc for LESSONS, PATTERNS, knowledge writer, runs-analysis writer
```

`with_lock` is non-recursive; `cmd_record_knowledge` calls `cmd_update_index` AFTER its own write completes, so each acquires/releases serially. No reentrancy needed.

### E.2 — jq sandbox mechanism (Finding 2)

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **Regex character allowlist + blocked-identifier deny-list** (recommended) | Blocks `env`, `$ENV`, `input`, `getpath` etc. without parsing jq; simple to audit | ~15 LOC helper; one new test | Low (false-positive risk on exotic-but-safe filters like `@csv` is acceptable) | One regex, one list, easy to extend | None — replaceable with a fancier parser later |
| Operator allowlist (parse the expression and reject anything not in `{., ==, !=, <, >, <=, >=, and, or, not, length, type, in, has, select, ., [...]}`) | Stricter — semantically validates the AST | ~80 LOC of jq-grammar parsing in bash (or via `jq` itself with `-n` mode) | Higher — re-implementing a parser is the AST-parser version of writing your own crypto | Brittle; jq grammar evolves | Higher |
| `jq --argjson` template (rewrite cmd_query to take `--field <name> --op <eq|ne|gt> --value <val>` and assemble the filter internally) | Strongest — user never authors jq | Highest — breaks the existing `/memory query` UX (agents have to use a constrained DSL); needs `/memory query` skill rewrite | Lowest residual risk | Highest — every new query shape needs a new arg | Highest — agents pivot away from raw jq forever |

**Recommended: option 1 (regex allowlist).** Cheap, auditable, retrofittable — and we keep the existing `/memory query` UX that the 4 memory-aware skills (`naavik-memory-lookup` etc.) depend on. The deny-list closure is the key insight: `jq`'s privileged surface is small and well-named (`env`, `$ENV`, `input`, `inputs`, `input_filename`, `getpath`, `path`, `paths`, `setpath`, `delpaths`) — match those as substrings; the residual exploitable surface is "filters that read the JSONL itself," which is exactly what `cmd_query` is supposed to do.

Implementation:

```bash
validate_jq_expr() {
  local EXPR="$1"
  # Char allowlist — letters, digits, common jq punctuation + space.
  if [[ ! "$EXPR" =~ ^[\ a-zA-Z0-9_.\"\'\[\](){}<>=!|\&,:?-]+$ ]]; then
    echo "error: jq expression contains disallowed character. Allowed: [a-zA-Z0-9_.\"'\[](){}<>=!|&,:?-]" >&2
    return 1
  fi
  # Identifier deny-list — substring match, no word-boundary games.
  local BAD
  for BAD in env '$ENV' input inputs input_filename getpath path paths setpath delpaths debug stderr; do
    if [[ "$EXPR" == *"$BAD"* ]]; then
      echo "error: jq expression contains disallowed identifier '$BAD'. See docs/AGENT_OPS.md § 14." >&2
      return 1
    fi
  done
  return 0
}

# In cmd_query, before invoking jq:
validate_jq_expr "$EXPR" || exit 1
jq -c "select($EXPR)" "$FILE"
```

Trade-off accepted: `paths` substring match also rejects `pattern_id` (substring `path` doesn't match `pattern_id` since `path` is a full identifier in the deny-list — the implementation must use word-boundary regex, not raw substring, OR escape the deny-list to `\bpath\b`). **Engineer note: implement the identifier deny-list with `[[ "$EXPR" =~ (^|[^a-zA-Z0-9_])${BAD}([^a-zA-Z0-9_]|$) ]]` (word-boundary match) to avoid false-positives like `pattern_id` being rejected for substring `path`.** Validated against `.id == "pattern__halt"` (must pass) and `.path == "x"` (must reject — exotic but the surface is too dangerous to allow).
