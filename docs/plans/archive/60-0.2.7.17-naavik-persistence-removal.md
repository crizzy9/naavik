# 57 · 0.2.7.17 · `NAAVIK_PERSISTENCE` env-var full removal

## Goal

Delete the `NAAVIK_PERSISTENCE` env var and the dual memory-vs-DB branch in `src/db/sample_data.py`. After this PR every page handler, fragment endpoint, JSON stub, and SSE stream reads exclusively from Postgres via the service layer (`src/services/*`). `src/db/sample_data.py` survives — its sole consumers post-merge are `src/db/seed.py` (production seeding) and the pytest fixture suite (in-memory unit tests that bypass DB entirely). The env var disappears from `flake.nix`, `nix/devshell.nix`, `.env.example`, `README.md`, `docs/RUNBOOK.md`, `docs/ARCHITECTURE.md`, and `tests/test_persistence_swap.py` is replaced by service-layer parity tests. A new regression lint (`tests/test_no_sample_data_imports_in_routes.py`) ensures no future route reaches for `from db import sample_data`.

## Why

Plan 10 Wave 4 + Wave 5 partially migrated the canonical read accessors to honor `NAAVIK_PERSISTENCE=db` (18 of the 41 accessors in `src/db/sample_data.py:6481-7178` already query Postgres when the env is set; the rest fall back to in-memory fixture lists). Plan 10b set the env var as orchestrator + `nix develop` default. The env var was supposed to disappear in a "follow-up cleanup once the swap is verified" (per `docs/plans/archive/10-backend-impl.md:287` + `:602`). That cleanup never landed. Today the situation is:

- The orchestrator + `nix develop` already export `db`, so production-shape pages read from Postgres.
- Bare `uv run fastapi dev` (without orchestrator) defaults to `memory` — operators following bare commands silently see stale fixtures.
- The 23 still-memory-only accessors include every mutation shim (`_create_draft`, `_set_job_queue_state`, `_append_outreach_message`, `_append_manual_application`, `_append_scraped_job`, `_apply_status_override`, `_apply_failure_to_draft`, `_record_screener_answer`), every KPI computation (`kpi_active_applications`, `kpi_response_rate_90d`, `kpi_onsite_rate_90d`, `kpi_offer_rate_90d`, `pipeline_strip_counts`, `priority_actions`), the email thread surface (`get_email_threads`, `get_email_thread`, `email_threads_for_application`, `email_signal_feed`), Outreach (`get_contacts`, `contacts_for_company`, `contacts_for_application`, `outreach_messages_for_*`), and screener / generated-document / app-event reads. These appear in the Overview, Tracking, Outreach, and Discover · review surfaces — so every "real-data" interaction silently writes to in-memory lists that vanish on server restart.

Cleanup is overdue. The env-var-gated dual-path doubles the surface area of every accessor + makes mode-bisection bugs hard to reason about (e.g. plan 10b deviation: `Settings.allow_multiple_users` scalar-select workaround in `src/api/auth.py`). Plan 10c deviation explicitly called out this row (`docs/plans/archive/10c-first-time-setup.md:421` — "Should be folded into the wider Wave-4 cleanup tracked in ROADMAP § Phase 1 deferred backlog (B6: full `NAAVIK_PERSISTENCE` env-var removal + sqlmodel-vs-sqlalchemy unification)"). `ROADMAP.md:330` (0.2.7.17 / legacy DEF-23) is the canonical row.

This plan is intentionally scoped narrowly. The **fake-session retirement track** (transitional `_user: User | None = Depends(require_authed_session)` + hardcoded `user_id=1` per `db/sample_data.py:USER.id == 1`) is a separate multi-PR refactor flagged in 0.2.7.01, 0.2.7.02, 0.2.7.03, and 0.2.7.23. Routes that today pass `user_id=1` keep doing so after this plan ships — but the call now resolves through `services/*` against Postgres instead of branching on `_is_db_mode()`. Fake-session retirement is its own work.
