### Owner's 6 follow-up items

1. **Password min-length 12 → 8 chars.** "more standard for selfhosted apps." Single-line constant flip in `src/services/auth.py` + banner copy in `login.html`.

2. **Remove `is_admin` differentiation.** "Whats the point of having an admin we need to strip that behavior. What is an admin and what is not an admin in an application like this?" Right answer for this app: **there are no admin-only operations** (every user owns their own data; no cross-tenant admin actions; no admin-gated routes). The `is_admin` flag is a vestige of plan 10b's single-user gate. Keep column for schema compat; flip default to True; drop column drop migration to `0.7.0.49` follow-up. Owner's specific case ("my account isn't admin because there are stale users") is fixed via wipe (`rm -rf .naavik/db` + restart); the broader fix removes the concept entirely.

3. **Resume upload broken end-to-end.** Two root causes:
   - `src/ui/templates/components/dropzone.html` form has `hx-post` but NO `hx-trigger` for file-change. File selection fires `change` event on `<input>`, but the form never submits. Fix: add `hx-trigger="change from:#dropzone-input"` to the form so file selection triggers the POST.
   - `src/ui/routes/auth.py:post_extraction_upload` is a STUB that returns hardcoded "Shyam Padia" data via SSE. Owner wants real parsing (NO LLM — "we dont have an LLM connected yet"). Fix: rewrite endpoint to actually receive the `UploadFile`, save to `data_dir/uploads/<user_id>/<utc-ts>.pdf`, extract text via `pdfplumber` (NEW dep), return a confirmation partial showing extracted-character count + a "Continue to your profile" button → `/profile/edit`. Collapse onboarding from 3 steps (upload + extracting + review) to 1 step (upload → redirect to profile edit). Steps 2 + 3 were stub-only with hardcoded data.

4. **Skip on resume → /login instead of /overview.** Same root cause as item 5 (Secure cookie). After fix #5, the `<a href="/">Skip</a>` link in `_onboarding_step_upload.html` will properly land on `/` (overview). One template review: change link to `/profile/edit` instead of `/`, since the user hasn't filled their profile yet — better UX.

5. **Login loop (root cause).** `src/main.py:71` instantiates `FastAPI()` WITHOUT `debug=app_settings.debug`. So `request.app.debug` is always False. `_set_session_cookies` derives `secure = not request.app.debug if hasattr(request.app, "debug") else True` → always `Secure=True` cookies in dev. Browser on `http://localhost:8000` won't send Secure cookies → `require_authed_session` 307s every request to `/login`. **Fix: `FastAPI(debug=app_settings.debug, ...)`.** Single-line wire-up.

6. **ERD diagram.** Owner wants a visual data model in mermaid / excalidraw "that i can easily view using the architect so i can suggest changes because the current data model doesnt seem right to me". Architect dispatches to generate `docs/design/ERD.md` with a `mermaid erDiagram` covering every SQLModel + relationships. Mermaid renders inline in GitHub markdown — owner can review directly in the PR diff. Architect should also flag any data-model concerns inline (sub-section "Open questions / observations" at bottom of ERD doc).

### Wave 2 design decisions

| Decision | Choice | Rationale |
|---|---|---|
| `is_admin` field — drop column or deprecate? | Deprecate (flip default True; keep column) | Schema-compat for upgraders; column drop is `0.7.0.49` follow-up; this PR stays UI-fix-shaped |

## Goal

Remove the entire signup-disabled / single-user MVP gating concept across template, route, API, model, sample data, tests, and docs. **Multi-user signup is the default**: first user becomes admin (existing behavior preserved); subsequent users sign up as regular users (`is_admin=False`) without any gate. No 403 on second signup. No amber banner. No `_compute_signup_disabled` helper. No `allow_multiple_users` enforcement.

## Why this scope (owner directive 2026-05-24)

> "Lets remove the whole signup disabled logic please. its not right we will not be restricting users to a single user instance. i think this is causing more churn than needed. we need to properly go through all the code to remove this properly."

Three patches around `signup_disabled` (plan 10c, 0.7.0.45, 0.7.0.47) confirm the gate's design assumption doesn't fit the deployment model. Each patch creates a new edge case for the next one to chase. The clean cut is to remove the gate entirely.

**The 0.7.0.47 patch attempt** (PR #211, closed) was a UI workaround that left the underlying gate intact — banner still rendered, 403 message still mentioned "single-user MVP," operators with stale users still saw confusing UX. Owner verified this was insufficient.

## Design decision

| Option | Chosen | Rationale |
|---|---|---|
| **A** — Remove gating entirely; first user is admin, subsequent users are regular | ✅ | Owner directive; matches standard self-hosted patterns (Gitea, Nextcloud, Vaultwarden); eliminates 3+ patches of churn |
| B — Keep gate but flip `allow_multiple_users` default to True | ✗ | Toggle remains a footgun; tests still churn around it; operators with `False` legacy rows still hit the gate |
| C — Add new `Settings.allow_signups` admin toggle (default True) for future close-down | ✗ | Just renames the problem; can be filed as future `0.7.0.50` follow-up when an operator actually needs it |

Selected: **Option A**. The deferred follow-ups (column drop migration + future admin-toggle-to-close-signups) are filed as `0.7.0.49` + `0.7.0.50` respectively.
