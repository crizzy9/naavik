# 58 · 0.2.7.06 — Paired UI editors (rate-limit JSONB + LinkedIn/Indeed keywords)

## Goal

Replace the read-only `<details data-source-configure>` popovers on the Settings · Sources panel with writable forms. Two coupled editors ship together: (1) a per-source rate-limit form exposing `rpm` / `delay_lo` / `delay_hi` as numeric inputs bound to `Settings.scraper_rate_limits[<source>]`, and (2) per-source LinkedIn / Indeed keyword + location forms bound to `Settings.linkedin_keywords` / `Settings.linkedin_location` / `Settings.indeed_keywords` / `Settings.indeed_location`. Both editors POST via HTMX into `PUT /api/v1/settings/sources` — the existing endpoint that already accepts these payloads. No new route. No new env var. No new on-disk artifact. Net new surface = two writable form partials + form-rendering ctx in the route + 10+ tests.

## Why

ROADMAP row `0.2.7.06` (line 321, LOW priority, filed 2026-05-20 by plan 49 OQ.3 lock). Aggregates the two deferred follow-ups from plan 49 / `0.2.0.16`: rate-limit JSONB editor (originally tagged `0.2.5.05`) + LinkedIn/Indeed keywords editor (originally tagged `0.2.5.06`). Both were collapsed into `0.2.7.06` when the 0.2.5 milestone closed out (ROADMAP line 30). Plan 49 § A locked the design direction — read-only popovers ship now, writable editors land in a follow-up. SOURCES_UI.md § H names this row twice as the canonical follow-up. Substrate is already in place: `Settings.scraper_rate_limits` (JSONB column shipped 0.2.0.13, validated via `RateLimitConfig`), `Settings.linkedin_keywords` / `linkedin_location` / `indeed_keywords` / `indeed_location` (shipped 0.2.0.10), `PUT /api/v1/settings/sources` endpoint (already accepts every kwarg per `tests/test_api_settings_sources.py::test_put_sources_passes_all_kwargs_to_service`). The substrate landed before the UI surface; this plan closes the gap.

## Proposal

### A · Panel-location decision (option matrix)

The dispatch explicitly forks: dedicated routes (`/settings/rate-limits` + `/settings/keywords`) vs. fold into the existing Sources tab. Three viable surfaces:

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **A — Two dedicated routes** (`/settings/rate-limits`, `/settings/keywords`) as new Settings sub-tabs | Two top-level Settings tabs; full-page editors | +2 routes, +2 `_TAB_TEMPLATES` entries, +2 tab-nav buttons in `pages/settings.html`, ~280 LOC src | MED — Settings tab nav balloons from 7 → 9; operators hunting for "rate limits" must learn a new tab. SCREENS.md § 11 needs a third rewrite in two weeks. | Each new editor adds a tab; pattern doesn't compose | High — once a tab, hard to fold back without breaking deep-links |
| **B — Deep sub-routes under `/settings/sources/{rate-limits,keywords}`** | Sources Configure popover links to dedicated mini-page; mini-page POSTs back to `PUT /api/v1/settings/sources` | +2 routes, +2 fragment templates, +0 tab entries, ~250 LOC src | LOW — Sources tab stays as-is; the popover's "Configure →" link becomes a real navigation target rather than degrading to inline content. Two HTMX swaps. | Each new editor is one sub-route under `/settings/sources/` — extensible | Medium |
| **C — Inline writable form replacing popover content** (recommended) | Popover body IS the form; HTMX swap on submit re-renders just the popover content | +0 routes, +2 partials replacing popover branches in `_source_row.html`, ~200 LOC src | LOW — composes perfectly with shipped plan 49 substrate; popover already has `<details>`-styled real estate. Operator clicks "Configure", form appears in same row, saves in-place. Matches SOURCES_UI.md § H phrasing ("replaces the read-only `<details>` popover"). | One row per source self-contained; future per-source axes (rotation policy, undetected-adapter toggle) drop into same popover | Lowest — no route/nav surface added |

**Recommendation: Option C (inline form within popover).** Three reasons:

1. **SOURCES_UI.md § H lock-in.** The graduated design doc explicitly stages this row as "replaces the read-only `<details>` popover." Option C is the literal interpretation; Options A and B add a new route surface that wasn't in the contract.
2. **LOC budget.** Dispatch caps src at ~250 LOC + ~150 LOC tests. Option C lands well under (~200 src + ~150 tests). Options A and B push close to or over.
3. **Cognitive surface.** The Sources tab already shows configured/last-run/rate-limit/configure for each source. The writable editor reuses that mental model — the operator stays on one page, clicks Configure, edits, saves. Options A / B fragment the model across two clicks and two routes.

Trade-off acknowledged: a `<details>` popover hosting a multi-input form is visually busy. Mitigation — the form lives in the same `border + bg-slate-950/60` box the existing popover uses; engineer cribs the LLM-tab form styling for vertical input stack (label + input + helper text). Operators who need to mass-edit rate limits can still POST `PUT /api/v1/settings/sources` directly (the API endpoint stays canonical).

(Plan 49 § A's recommendation of A2 — separate panel — was the right call **when shipping plan 49 alone**: at that time, the rate-limit editor was a separate row in a future milestone. Now that we're shipping the editors against the already-built popover infrastructure, the inline path is cheaper and the deep-link target was always-degrade per OQ.2. This isn't a contradiction; it's the same decision tree resolved with new substrate in hand.)

#### B.2 NEW `src/ui/templates/components/_rate_limit_editor.html` — rate-limit form partial (~70 LOC)

```jinja2
{#
  _rate_limit_editor.html — per-source rate-limit form (rpm + delay_lo + delay_hi).

  Args:
    view : dict with keys `source` (str), `rate_limit` ({rpm, delay_lo, delay_hi}).

  Plan 58 / 0.2.7.06. HTMX form posts to PUT /api/v1/settings/sources;
  server validates via RateLimitConfig (rpm ∈ [0.1, 600]; delay ∈ [0, 600];
  delay_lo ≤ delay_hi). The CSRF token is injected by the
  plan-45 Jinja context-processor (`csrf_token` in template globals).
#}
{% set v = view %}
<form data-rate-limit-form="{{ v.source }}"
      hx-put="/api/v1/settings/sources"
      hx-headers='{"X-CSRF-Token": "{{ csrf_token }}"}'
      hx-vals='js:{scraper_rate_limits: rateLimitJson_{{ v.source | replace("-","_") }}()}'
      hx-target="closest [data-source-editor]"
      hx-swap="outerHTML"
      class="mt-2 flex flex-col gap-2 text-xs">
  <h4 class="text-[10px] uppercase tracking-wide text-slate-500">Rate limit</h4>
  <div class="grid grid-cols-3 gap-2">
    <label class="flex flex-col gap-1">
      <span class="text-[10px] text-slate-400">rpm</span>
      <input type="number" step="0.1" min="0.1" max="600"
             name="{{ v.source }}_rpm"
             value="{{ '%.2f' | format(v.rate_limit.rpm) }}"
             required
             class="w-full px-2 py-1 rounded bg-slate-900 border border-slate-800 text-slate-100 font-mono text-xs" />
    </label>
    <label class="flex flex-col gap-1">
      <span class="text-[10px] text-slate-400">delay lo (s)</span>
      <input type="number" step="0.1" min="0" max="600"
             name="{{ v.source }}_lo"
             value="{{ '%.1f' | format(v.rate_limit.delay_lo) }}"
             required
             class="w-full px-2 py-1 rounded bg-slate-900 border border-slate-800 text-slate-100 font-mono text-xs" />
    </label>
    <label class="flex flex-col gap-1">
      <span class="text-[10px] text-slate-400">delay hi (s)</span>
      <input type="number" step="0.1" min="0" max="600"
             name="{{ v.source }}_hi"
             value="{{ '%.1f' | format(v.rate_limit.delay_hi) }}"
             required
             class="w-full px-2 py-1 rounded bg-slate-900 border border-slate-800 text-slate-100 font-mono text-xs" />
    </label>
  </div>
  <p class="text-[10px] text-slate-500">
    rpm ∈ [0.1, 600]; delay ∈ [0, 600]s; lo ≤ hi.
  </p>
  <div class="flex items-center gap-2">
    <button type="submit"
            class="px-2.5 py-1 rounded bg-indigo-500 hover:bg-indigo-400 text-white text-xs font-medium">
      Save
    </button>
    <span data-rate-limit-save-status="{{ v.source }}" class="text-[10px] text-slate-500"></span>
  </div>
</form>
```

**Wiring note for HTMX `hx-vals`.** The nested-dict shape `{"scraper_rate_limits": {"<source>": {"rpm": x, "delay_lo": y, "delay_hi": z}}}` can't be expressed in flat form-encoding. The engineer has two options: (1) ship a tiny per-form JS helper `rateLimitJson_<source>()` that reads the three inputs and returns the nested JSON (recommended — keeps a single PUT endpoint); (2) extend `PUT /api/v1/settings/sources` to accept flat `linkedin_rpm` / `linkedin_lo` / `linkedin_hi` form fields and assemble server-side. **Engineer-judgment** — option (1) is HTMX-idiomatic and minimal-code; option (2) avoids JS entirely but adds 20 LOC of server-side flat-field unpacking. Both are acceptable; document the choice in the deviation log.

#### B.4 `src/api/settings.py` — extend `put_sources` form-handling

Currently the route accepts JSON only (`Annotated[dict[str, Any] | None, Body()]`). HTMX submits `application/x-www-form-urlencoded`. Three changes:

1. **Accept form bodies** — borrow the `_is_form_request(request)` helper from `put_llm` (already in same file). When form-encoded, parse via `await request.form()`.
2. **Flat-field → nested-dict unpacking** (only if engineer picks B.2 option (2); skip if option (1) — HTMX submits the JSON via `hx-vals`).
3. **Comma-split keywords** — `linkedin_keywords` / `indeed_keywords` arrive from the form as comma-separated strings; split on `,`, strip whitespace, drop empties before calling `update_sources`.
4. **CSRF gate** — add `_csrf: None = Depends(require_csrf)` (already imported pattern; `api.scheduler` and `ui.routes.discover` use this exact line). State-changing endpoint per AGENTS.md § Frontend (HTMX form submission).
5. **HTMX response shape** — when `_is_form_request(request)`, re-render the entire Sources panel partial via `_ctx_for_tab` + `templates.TemplateResponse(request, "pages/_settings_sources.html", ctx)` so the panel reflects the saved state without a full page reload. JSON consumers (existing tests + machine callers) keep the JSON response. Mirrors `put_llm` HTMX/JSON branch.

LOC delta: ~+30 LOC in `put_sources` + 1 new import (`require_csrf` already imported elsewhere; add to `src/api/settings.py`).
