# 81 · 0.4.0.07 + 10 + 12 + 16 — Application detail polish + postmortem UI + timeline view + analytics dashboard

## Goal

Four UI improvements shipped together (`docs/design/research/0.4.0-AUDIT.md
§ G` clusters them under one plan because they all touch
`_application_detail.html` + share state):

- **0.4.0.10:** Postmortem UI on Application detail — HTMX modal
  overlay (locked Option D per audit memo § F).
- **0.4.0.12:** Application timeline view — full AppEvent history
  toggle on the slide-over.
- **0.4.0.16:** Application detail polish — editable notes inline,
  Discover-review jump link for DRAFTs, compact score chip.
- **0.4.0.07 refinement:** Application analytics dashboard — 4 KPIs
  (Response Rate · 90d, Onsite Rate · 90d, Offer Rate · 90d,
  Funnel · 90d) + 3 breakdowns (by company, by role-family, by tag)
  rendered with uplot (locked Option A per audit memo § E).

## Why

The slide-over is the operator's primary lens on a single application
post-submit. Today it's read-only and missing 3 of the 4 affordances
Tracking should offer (postmortem details, edit notes, regenerate
bundle hint for DRAFTs). Combined with the analytics dashboard, this
plan completes the operator's "see what happened, do something about
it" surface.

The 4 KPIs are specified in DATA_MODEL.md § F (Response/Onsite/Offer
Rate + Funnel · 90d). Substrate already shipped (AppEvent history is
populated; `Application.applied_at` is set). What's missing is the
service-layer KPI derivation + the rendered surface.

```python
"""Application KPI derivations per DATA_MODEL.md § F.

All KPIs scoped to (user_id, time_window). Time window defaults to
90 days. Computed from AppEvent history + Application.applied_at.

Pure-aggregation; no LLM, no scraper, no notification. Idempotent.
"""

from __future__ import annotations

from dataclasses import dataclass
from datetime import UTC, datetime, timedelta

from sqlalchemy import func
from sqlmodel import select
from sqlmodel.ext.asyncio.session import AsyncSession

from models import AppEvent, AppEventKind, Application, ApplicationStatus


@dataclass(slots=True)
class FunnelCounts:
    applied: int
    recruiter: int
    onsite: int
    offer: int


@dataclass(slots=True)
class ApplicationKpis:
    window_days: int
    applied_in_window: int
    response_rate: float   # ratio with ≥ RECRUITER_SCREEN at any point
    onsite_rate: float     # ratio with ≥ ONSITE_LOOP at any point
    offer_rate: float      # ratio with ≥ OFFER at any point
    funnel: FunnelCounts


async def compute_kpis(
    session: AsyncSession,
    *,
    user_id: int,
    window_days: int = 90,
) -> ApplicationKpis:
    """Compute 4 KPIs for user_id over the past window_days."""
    threshold = datetime.now(UTC) - timedelta(days=window_days)
    applied_stmt = (
        select(Application.id, Application.status)
        .where(
            Application.user_id == user_id,
            Application.applied_at >= threshold,
            Application.deleted_at.is_(None),
            Application.status != ApplicationStatus.DRAFT,
        )
    )
    rows = (await session.exec(applied_stmt)).all()
    total = len(rows)

    if total == 0:
        return ApplicationKpis(window_days=window_days, applied_in_window=0,
                               response_rate=0.0, onsite_rate=0.0, offer_rate=0.0,
                               funnel=FunnelCounts(0, 0, 0, 0))

    # For each application, scan AppEvent history for the max status reached.
    # (Backwards transitions handled per DATA_MODEL.md: max-reached, not current.)
    ids = [r[0] for r in rows]
    events_stmt = (
        select(AppEvent.application_id, AppEvent.payload)
        .where(
            AppEvent.application_id.in_(ids),
            AppEvent.kind == AppEventKind.STATUS_CHANGE,
        )
    )
    events = (await session.exec(events_stmt)).all()

    # Status → ordinal for max-reached
    STATUS_ORDINAL = {
        "APPLIED": 1, "RECRUITER_SCREEN": 2, "ONSITE_LOOP": 3, "OFFER": 4, "CLOSED": 0,
    }
    per_app_max: dict[int, int] = {}
    for app_id, payload in events:
        to = (payload or {}).get("to")
        if to in STATUS_ORDINAL:
            per_app_max[app_id] = max(per_app_max.get(app_id, 0), STATUS_ORDINAL[to])

    # Funnel counts: how many reached each stage at any point.
    funnel = FunnelCounts(
        applied=sum(1 for v in per_app_max.values() if v >= 1),
        recruiter=sum(1 for v in per_app_max.values() if v >= 2),
        onsite=sum(1 for v in per_app_max.values() if v >= 3),
        offer=sum(1 for v in per_app_max.values() if v >= 4),
    )

    # Rates
    return ApplicationKpis(
        window_days=window_days,
        applied_in_window=total,
        response_rate=funnel.recruiter / total,
        onsite_rate=funnel.onsite / total,
        offer_rate=funnel.offer / total,
        funnel=funnel,
    )
```

### Risk + mitigation

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Postmortem modal requires markdown filter | LOW | LOW | Jinja `markdown` filter already in `templates_setup.py` (used by plan 52) |
| Analytics KPI computation slow on 500+ row history | LOW | LOW | Single-pass over AppEvent + Application rows; <100ms on 1k rows |
| Lossy AppEvent history (some past cycles missed emitting STATUS_CHANGE) → false-low rates | MED | LOW | Add `analytics_data_warning` banner when total < 5 events; document per AUDIT.md § J risk #3 |

| uplot bar chart for funnel doesn't auto-scale on small N | LOW | LOW | Use uplot's `range` config; document in plan |
