# 59 · 0.2.7.12 — Auto-apply immediate dispatch on right-swipe

## Goal

Add `Settings.auto_apply_immediate_dispatch: bool = false` toggle that, when enabled, fires the auto-apply queue cron NOW (via APScheduler one-off `DateTrigger`) the moment a user right-swipes a job in Discover. Reduces user-perception latency from "up to 5 minutes" (cron tick `IntervalTrigger(minutes=5)`) to "~1-2 seconds" (APScheduler dispatch overhead) while preserving the existing retry semantics, daily cap enforcement, and per-source isolation that `process_auto_apply_queue` already provides.

## Why

ROADMAP row `0.2.7.12` (line 325) filed 2026-05-01, deferred from 0.2.4.05. Right-swipe in Discover currently flips `Job.queue_state → QUEUED_FOR_AUTO_APPLY` and creates a DRAFT (`src/ui/routes/discover.py:126-135`); the `applications.auto_apply` cron (`src/scheduler/jobs.py:36-62`, `IntervalTrigger(minutes=5)`) eventually picks it up. The 5-minute worst-case wait is fine for batch background apply but feels broken when a user just decisively right-swiped a high-score role and the apply button "does nothing visible". The latency contract changes from "submission happens sometime in the next 5 minutes" to "submission happens immediately, with the same downstream retry/error pipeline".

Self-host first principles: default OFF preserves today's behavior; operators opt in via Settings UI. No new cron, no new background worker, no new env var. Reuses every piece of the existing infrastructure — `process_auto_apply_queue` for the actual submission logic, `scheduler.get_scheduler()` for the dispatch handle, the `FUNC_REF_ALLOWLIST` entry for `scheduler.jobs:auto_apply` (plan 48 / 0.2.0.10b already added).

## Design decision — dispatch mechanism (locked)

| Option | What | Latency | Retry semantics | New surface | Verdict |
|---|---|---|---|---|---|
| A — Synchronous submit in route handler | Route awaits ATS dispatch before HTTP response | ~1-30s (ATS-bound) | None — request crash drops submission | ATS call in route layer | rejected — blocks the HTMX response on slow ATS; user sees apparent UI hang; ATS 503 directly hits UX |
| B — FastAPI `BackgroundTasks` after response | Schedule submit after the HTMX response returns | ~100ms-30s (ATS-bound) | None — process restart loses queued task | New BackgroundTask call site | rejected — loses every retry/cap guarantee `process_auto_apply_queue` already enforces; orphans on process kill |
| C — In-memory asyncio.Queue + worker task in lifespan | New worker awaits queue; route enqueues | <100ms enqueue | None — queue evaporates on restart | New lifespan worker + queue | rejected — net-new runtime surface for a problem APScheduler already solves; restart loses items |
| **D — APScheduler one-off `add_job(DateTrigger=now)`** | **Reuse `scheduler.get_scheduler()` to schedule `scheduler.jobs:auto_apply` with `DateTrigger(run_date=datetime.now(UTC))`** | **~1-2s end-to-end** | **Preserved — same `process_auto_apply_queue` body that the 5-min cron uses, including `submit_draft` + daily cap + `_record_failure`** | **None** | **CHOSEN** |

**Why D wins.** The exact pattern is already battle-tested in production at `src/api/scheduler.py:135-145` (plan 47 / 0.2.0.10a `/jobs/{id}/run` endpoint): `scheduler.add_job(job.func, DateTrigger(run_date=now), id=f"{job_id}-manual-{uuid4()[:8]}", max_instances=1, coalesce=True, replace_existing=False)`. The transient job auto-removes itself after firing. `scheduler.jobs:auto_apply` is already in `FUNC_REF_ALLOWLIST` (`src/scheduler/json_jobstore.py:50`) per plan 48, so the JSON jobstore accepts the transient row without allowlist edits. The 5-min cron and the manual fire share the same `func` reference, just different transient ids — APScheduler treats them as separate registrations, so the original cron's `next_run_time` is untouched.

**Locked secondary decisions:**

- **No per-application-id targeting.** The one-off fires `scheduler.jobs:auto_apply` (zero-arg), which calls `process_auto_apply_queue` over the FULL `QUEUED_FOR_AUTO_APPLY` queue for ALL users. Mirrors what plan 47 / `/jobs/{id}/run` does. Per-row scoping would require a NEW allowlist function (`auto_apply_for_application(application_id)`) — net-new code path, net-new test surface, net-new failure mode. The queue body is already idempotent + per-row safe; firing it whole when one row was just enqueued submits that row plus any other rows already-queued, which is the operator's intent ("flush the queue NOW").
- **No `add_job` failure surfacing in the HTTP response.** If `scheduler.get_scheduler()` is None (lifespan boot failed) or `add_job` raises, the route logs at WARN and returns the normal next-card response. The right-swipe still flipped queue_state + created the DRAFT — the 5-min cron will catch it on next tick. Best-effort dispatch matches the `notify_fn` failure-handling pattern in `submit_draft:507`.
- **Toggle scope.** The new setting governs ONLY the dispatch-now decision. Existing `Settings.auto_apply_enabled` is still the master switch — if `auto_apply_enabled=False`, neither cron nor immediate dispatch submits anything (the queue body returns early at `process_auto_apply_queue:669`). `auto_apply_immediate_dispatch=True` with `auto_apply_enabled=False` is harmless (fires queue, queue self-skips per-row).

### D.4 — `src/ui/routes/discover.py` — fire one-off after right-swipe (~25 LOC diff)

Edit `post_auto_submit` at `src/ui/routes/discover.py:121-135`. Read the user's Settings; if `auto_apply_immediate_dispatch=True`, schedule the transient job. Best-effort — failures logged + swallowed:

```python
@router.post(
    "/api/v1/applications/{job_id}/auto-submit",
    response_class=HTMLResponse,
    name="discover_auto_submit",
)
async def post_auto_submit(
    request: Request,
    job_id: int,
    session: AsyncSession = Depends(get_session),
    user: User | None = Depends(require_authed_session),
    _csrf: None = Depends(require_csrf),
):
    """Right-swipe — flip Job → QUEUED_FOR_AUTO_APPLY + create DRAFT.

    Plan 59 / 0.2.7.12: when `Settings.auto_apply_immediate_dispatch=True`,
    additionally schedule a one-off `scheduler.jobs:auto_apply` via
    `APScheduler DateTrigger(now)`. Mirrors `src/api/scheduler.py:135-145`
    (plan 47 / 0.2.0.10a `/jobs/{id}/run` pattern). Best-effort — any
    failure logs at WARN and falls through to the 5-min cron tick.
    """
    await sd._set_job_queue_state(job_id, JobQueueState.QUEUED_FOR_AUTO_APPLY)
    await sd._create_draft(1, job_id)
    user_id = _effective_user_id(user)
    if user_id is not None:
        await _maybe_dispatch_auto_apply_now(session, user_id=user_id)
    return await _next_card_response(request)


async def _maybe_dispatch_auto_apply_now(
    session: AsyncSession, *, user_id: int
) -> None:
    """Schedule a transient `scheduler.jobs:auto_apply` one-off when the
    user's Settings.auto_apply_immediate_dispatch is True.

    Best-effort: caller MUST NOT propagate exceptions. The 5-min cron is
    the fallback path for every failure mode here (scheduler not running,
    Settings row missing, add_job raises).
    """
    try:
        from datetime import UTC, datetime
        from uuid import uuid4
        from apscheduler.triggers.date import DateTrigger
        from scheduler import get_scheduler
        from services import settings_service
        from scheduler.jobs import auto_apply as auto_apply_func

        s = await settings_service.get_or_create(session, user_id)
        if not s.auto_apply_immediate_dispatch:
            return
        scheduler = get_scheduler()
        if scheduler is None or not scheduler.running:
            log.info(
                "auto_apply_immediate_dispatch=True but scheduler not running; "
                "5-min cron will pick up queue"
            )
            return
        now = datetime.now(UTC)
        manual_id = f"applications.auto_apply-immediate-{uuid4().hex[:8]}"
        scheduler.add_job(
            auto_apply_func,
            DateTrigger(run_date=now),
            id=manual_id,
            name=manual_id,
            args=[],
            kwargs={},
            max_instances=1,
            coalesce=True,
            replace_existing=False,
        )
        log.info("scheduled immediate auto_apply manual_id=%s", manual_id)
    except Exception as exc:  # noqa: BLE001 — best-effort
        log.warning("immediate auto_apply dispatch failed: %s", exc)
```
