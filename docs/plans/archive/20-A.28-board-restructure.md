### A · Wave 1 — Add `Backlog` to the Project v2 Status field

The `Status` field on Project #4 (`PVTSSF_lAHOAISVS84BX5RPzhTC84Y` per `.claude/github-project.json:8`) currently has 3 single-select options: `Todo` / `In Progress` / `Done`. GitHub Projects v2 supports up to ~10 single-select options per field; adding `Backlog` is one GraphQL mutation against `updateProjectV2Field`.

#### A.1 — Decision: how does the `Backlog` option get added?

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| Manual one-off `gh api graphql` mutation, then re-run `scripts/gh-project.sh init` to refresh the cache | Direct + auditable in the PR body; cache reseed is the existing idempotent path | Smallest — one mutation + one `init` re-run | Low — `init` is idempotent + tested; the only risk is forgetting to re-run it (caught by smoke test in § F) | The mutation lives in the plan + the migration runbook; doesn't grow `gh-project.sh` for a one-time op | None — `Backlog` survives in the field schema regardless of how it was added |
| Extend `scripts/gh-project.sh init` to auto-add `Backlog` if missing (like the Priority + Effort auto-create blocks at `scripts/gh-project.sh:184-220`) | One-line fork bootstrap (every new clone gets Backlog automatically) | Higher — adds branching to `init`; init now does more than "read existing"; harder to argue init is purely a cache-prime | Medium — if a fork has a non-standard Status field (Backlog already exists with different ID, or different option order), the auto-add could collide | Future authors mistake init for "reseed the project schema" — drift from intent | Low |
| **Add a new `add-status <option-name>` subcommand to `scripts/gh-project.sh`; document running it as part of the migration runbook** | Reusable: future status additions (e.g. `Blocked` someday) use the same path; init stays read-only | Slightly higher than option 1 — ~40 LOC new function + smoke test | Low — explicit user invocation; idempotent (skip if option exists) | The subcommand exists alongside `set-status`/`set-priority`/`set-effort`; mental model is "field-options writers" | None |

**Recommendation: option 3 (`add-status` subcommand).** Reusable for future status additions (the user has hinted at `Blocked` semantics in agent prompts — `next-unblocked` already skips items labelled `blocked`, so a future `Blocked` status is plausible). Keeps `init` cache-only (clear separation between "discover schema" and "mutate schema"). Trade-off accepted: ~40 LOC of new function for a feature used twice in a year. Option 1 is fine if engineer pushes back on scope; option 2 is the trap because it muddles `init`'s role.

  ```bash
  # add-status <option-name> [--color GREEN|RED|...]
  cmd_add_status() {
    require_gh; load_cache
    local NAME="${1:?usage: add-status <option-name> [--color COLOR]}"
    local COLOR="GRAY"
    shift
    while [[ $# -gt 0 ]]; do
      case "$1" in --color) COLOR="$2"; shift 2 ;; *) echo "unknown arg: $1" >&2; exit 1 ;; esac
    done
    # Idempotency: re-read live options, skip if NAME exists.
    local EXISTING
    EXISTING="$(gh api graphql -f query='
      query($p:ID!) { node(id:$p) { ... on ProjectV2 {
        field(name:"Status") { ... on ProjectV2SingleSelectField { options { name id } } }
      }}}' -F p="$PROJECT_ID" | jq -r --arg n "$NAME" '.data.node.field.options[] | select(.name == $n) | .id')"
    if [[ -n "$EXISTING" ]]; then
      echo "status option '$NAME' already exists (id=$EXISTING)"
    else
      gh api graphql -f query='
        mutation($f:ID!, $n:String!, $c:ProjectV2SingleSelectFieldOptionColor!) {
          updateProjectV2Field(input:{
            fieldId:$f,
            singleSelectOptions:[{name:$n, color:$c, description:"Deferred — not in current cycle"}]
          }) { projectV2Field { ... on ProjectV2SingleSelectField { id options { id name } } } }
        }' -F f="$STATUS_FIELD_ID" -F n="$NAME" -F c="$COLOR" >/dev/null
      echo "added status option: $NAME (color=$COLOR)"
    fi
    # Reseed cache by re-running init's option-resolution block.
    echo "→ run 'scripts/gh-project.sh init' to refresh .claude/github-project.json"
  }
  ```

#### B.3 — `next-unblocked` (the contested semantics)

| Option | Capability | Cost | Risk | Maintenance | Lock-in |

**Subcommand spec:**

```bash
# scripts/gh-project.sh backlog-by-epic [--top N]
#
# Reads Project items where Status=Backlog, groups by parent epic (via sub-issue link),
# orders epics by their Priority field (CRITICAL > HIGH > MEDIUM > LOW > unset),
# returns JSON to stdout. Default --top 5 = top 5 items per epic.
#
# Output shape:
# [
#   {
#     "epic_issue": 18,
#     "epic_title": "[Epic] Phase 2.5",
#     "epic_priority": "MEDIUM",
#     "items": [
#       {"issue": 4, "title": "[A.9] Cap retention on traces/", "priority": "LOW"},
#       {"issue": 5, "title": "[A.10] Visual run dashboard", "priority": "LOW"},
#       ...
#     ]
#   },
#   ...
# ]
#
# Implementation sketch:
# 1. GraphQL query Project items, filter Status=Backlog (~150 items max).
# 2. For each item, resolve parent epic via sub-issue link (already cached in .claude/github-issue-map.json under "subissues" or via gh api graphql sub_issues field).
# 3. Group items by parent epic; epics without parent group under "_unparented".
# 4. Sort epics: epic_priority enum sort (CRITICAL=4, HIGH=3, MEDIUM=2, LOW=1, null=0).
# 5. Within each epic group, items are unprioritized — preserve insertion order from GraphQL (which is creation order).
# 6. Truncate each items[] to TOP entries; add "total_items" if truncated.
# 7. Emit JSON via jq.
```
