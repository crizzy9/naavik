# 36 · 0.2.0.11 HTMX UI — job list with filters + job detail view

## Goal

Wire the live `Job` table (now populated hourly by the `0.2.0.10` APScheduler crons) into the existing `/discover` swipe-queue UI by replacing the `db.sample_data` in-memory shim with `services.job_service.list_jobs`, add a five-axis HTMX filter toolbar over the queue, and ship a new dedicated `/jobs/{job_id}` read-only Job-detail route distinct from the existing `/discover/{job_id}` application-workspace route. Net effect: the user can finally see, filter, and inspect the jobs that scrapers + extraction + dedup have been quietly persisting since `0.2.0.07`–`0.2.0.10` merged.

## Why

`ROADMAP.md` row `0.2.0.11` (Issue #16, milestone `0.2.0`) is the last in-milestone product surface unblocked by `0.2.0.07`–`0.2.0.10`. Today the Discover swipe queue runs against `db.sample_data` (in-process Python lists seeded at boot), so the scrapers' real output is invisible — operators can confirm via `psql` that rows landed in `job` + `job_scrape_run`, but the only UI surface is the seeded sample data. `services.job_service.list_jobs` was authored explicitly for this task (plan 27 § D.9 docstring cites "Phase 2.0.11 Discover UI surfaces persisted Jobs"); `JobFilter` already encodes the 11-field filter contract; `0.2.0.09` already populates `duplicate_of_id` so the filter just needs to expose `include_duplicates`. The pivot is small, but it's the moment Phase 2 work becomes user-visible. Adjacent need: when a scrape lands a Job whose `score == 0.0` (pre-0.3.0 scoring), the swipe card's score-circle is meaningless — users need a non-Discover surface to actually look at the row. Hence the new `/jobs/{job_id}` detail page, which reads the Job in isolation and renders all fields scraped/extracted, leaving the application-workspace surface (`/discover/{job_id}`) for the Phase 1 generate-bundle flow.

ROADMAP rank for this row is implicit (no Priority cell as of 2026-05-19); shipping it now consolidates the 0.2.0 milestone before `0.2.0.12` (notifications) lands, and it transitively unblocks the deferred Phase 2.5 surfaces (`0.2.0.10a` scheduler endpoints, `0.2.0.13` per-source rate-limit tuning) that want a real Sources UI panel to live next to.

### B · Decision matrix — five locked choices

#### D.1 Job-detail route — new `/jobs/{job_id}` vs HTMX-swap into Discover right rail

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **(a) New `/jobs/{job_id}` page (chosen)** | Full read-only job view; link-shareable; distinct surface from application-workspace | +1 route, +1 template, +1 ctx builder, +1 sidebar nav slot? | Two surfaces for one Job (`/discover/{id}` = bundle workspace; `/jobs/{id}` = read-only) — risk of user confusion | Each surface owns one concern; low | None — additive |
| (b) HTMX swap into Discover right-rail drawer | No new route; fits existing IA | Right rail already crowded (Up next + Stuck + Saved + Tip cards per SCREENS § 7) | Card-stack + drawer + popover all compete for focus | Right rail becomes a multi-purpose surface; high | Couples Job detail to Discover lifecycle (browser back from drawer is fiddly) |

**Pick (a).** Rationale: `/discover/{id}` is firmly the "tailor + apply" workspace per SCREENS.md § 8 — overloading it for "just look at the raw job" would muddy that contract. `/jobs/{id}` is a clean read surface that links cleanly from the swipe card's "ℹ More info" affordance (added this plan as a tiny `<a>` link in `swipe_card.html`) and from any future Tracking-list "view source job" deep link. The "two surfaces" risk is real but small: the left-rail nav contains no `/jobs` entry (Discover stays the entry point); `/jobs/{id}` is a destination, not a list.

**No `/jobs` list route ships this plan.** The Discover queue IS the job list — Tinder-style swipe = filtered list with one big card at a time. Adding a dense list view duplicates the surface. The deferred `job_card.html` partial is scaffolded for a future Phase 2.5 row that wants a "table view" toggle on Discover; this plan leaves it placeholder-only.

#### D.2 Filter UI — chip-row toolbar vs sidebar drawer vs full-page reload

| Option | Capability | Cost | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **(a) Sticky chip-row toolbar w/ `<details>` popovers (chosen)** | Inline; doesn't displace card-stack; 5 chips fit horizontally on lg+; collapses to 2-row wrap on md | One new component + macro | `<details>` keyboard semantics need explicit `aria-expanded` wiring | Low — `<details>` is browser-native | None |
| (b) Sidebar drawer (right rail) | Familiar | Right rail is already used by Up next / Stuck / Saved / Tip cards on Discover (SCREENS § 7) | Eats real estate; mobile = full-screen drawer | Two competing right-rail layouts (filter mode vs default mode) | Moderate |
| (c) Full-page reload via `<form GET>` | Trivial | Loses HTMX-fluid swap; queue re-renders w/ flash; breaks keyboard navigation | Page jumps on every filter change — UX regression vs sample-data behavior | Lowest | None |

**Pick (a).** Rationale: HTMX-first per AGENTS.md § Frontend; `<details>` popover is one-line native HTML and matches DaisyUI's collapse pattern; doesn't conflict with the right-rail; works on mobile (popovers stack as bottom-sheet-likes). The Discover heading area is currently a single row of three buttons (Saved · Filters · Add by URL); the toolbar inserts BELOW that row so it never collides w/ the action buttons.

#### D.3 Filter axes for MVP — which of `JobFilter`'s 11 fields to surface

| Axis | Surface? | Why |
|---|---|---|
| `source` (9 values) | YES — chip w/ multi-select-friendly popover (single-select for MVP; multi-select is a follow-up) | Most operationally relevant — "show me only LinkedIn jobs", "exclude Indeed noise" |
| `remote_only` (bool) | YES — toggle chip (indigo when on) | Highest signal-to-cost ratio; one bit |
| `visa` (4 values) | YES — chip | Visa-restriction = score-zero hard filter per AGENTS.md § Owner Profile |
| `seniority` (7 values) | YES — chip | Sr/Staff/Principal filtering is what the user does daily |
| `score_min` (0.0–1.0) | YES — chip w/ slider in popover (default 0.0) | Pre-scoring jobs all = 0.0; until 0.3.0 ships, slider stays at 0.0 (visible-but-mostly-noop); explicit "show all (incl. unscored)" toggle handles the 0.0 case |
| `include_duplicates` | YES — toggle chip; default off | Operator-mode escape hatch; needed for diagnostic UX once tier-3 dedup starts flagging real cross-source duplicates |
| `company` | NO — text-search-only via separate search input; deferred to plan 36a if needed | Too freeform for a chip; substring matching needs separate UX |
| `board` | NO — overlaps w/ `source` for MVP | Defer |
| `queue_state` | NO — handled by the existing Saved/Skipped/Up-next sidebar already | Defer |
| `score_max` | NO — slider can become range-slider when scoring lands | Defer to 0.3.0 |
| `tag` | NO — tag chips need a different UX (multi-select w/ AND/OR) | Defer to 0.3.0 (tags become first-class then) |
| `posted_within_days` | NO — needs design (preset chips: 24h / 7d / 30d) | Defer |

**6 active filter chips for MVP** (source, remote_only, visa, seniority, score_min, include_duplicates). Each maps 1:1 to a `JobFilter` field. URL contract: `/discover?source=LINKEDIN&remote_only=1&visa=NONE&seniority=SENIOR&score_min=0.5&include_duplicates=0` (querystring is the source of truth; browser back/forward works naturally).

#### D.4 Filter round-trip — full-page swap vs `#discover-main` fragment swap

| Option | UX | Cost | HTMX idiom |
|---|---|---|---|
| **(a) `hx-get="/_fragments/discover/queue?..." hx-target="#discover-main" hx-push-url="true"`** | Card-stack swaps in place; URL updates; back-button works | One new fragment handler (or generalize the existing `fragment_queue`) | Canonical |
| (b) Full GET to `/discover?...` | Page reloads; keyboard handlers re-register | Trivial | Anti-pattern |

**Pick (a).** `hx-push-url="true"` keeps the URL bar in sync so a refresh restores the filter state; the existing `/_fragments/discover/queue` endpoint takes no filters today — generalize it to accept the same querystring as `/discover`. Cost: ~10 LOC in `fragment_queue`.

#### D.5 Pagination — offset+limit vs cursor vs scroll-to-load

At scale (cron firing hourly across 6 sources, plan 35 ships 5–25 listings per source per fire), a single user could be looking at 100–500+ jobs after a week. The current swipe queue's "next card" advances on action — pagination doesn't apply to one-card-at-a-time. But the bottom-of-rail "Up next" listing (`up_next_card.html`) and the future job-list view DO need it.

| Option | Capability | Cost | Risk | Maintenance |
|---|---|---|---|---|
| **(a) Offset+limit (chosen)** | Simple, works w/ `list_jobs(page=, page_size=)` (already accepts these) | None — already supported | Skipped/inserted rows can shift the offset window | Low |
| (b) Cursor (`found_at < :cursor`) | Stable under inserts | New ORDER BY tiebreaker + extra param plumbing | Tier-3 dedup can reshuffle order | Higher |
| (c) `hx-trigger="revealed"` infinite scroll | Modern UX | Needs scroll-anchor + de-dup logic on swap | Loses keyboard nav semantics | High |

**Pick (a).** The swipe queue itself doesn't paginate (it advances one card at a time via `/_fragments/discover/next-card`). The "Up next" rail uses `list_jobs(page=0, page_size=4)`. The Saved-jobs list at `/discover?filter=saved` (already a URL state per `discover.html:17`) gets `page_size=50` w/ a "Load more" button hx-getting `page=1`. Cursor pagination defers to Phase 4 (Tracking) where ordering is more sensitive.

## Deviations from plan

- **Regression lint pivoted from forbid-imports to forbid-removal-of-`job_service.list_jobs`.** Plan § A surface inventory called for extending `tests/test_no_legacy_jobsource_imports.py` to forbid `db.sample_data` *imports* from `src/ui/routes/discover.py`. Reality: `discover.py` still legitimately uses `sd.` for the skip/save/saved/skipped/by-url/auto-submit flows that aren't migrated this PR, so an outright import ban would break the file. The lint instead asserts `services.job_service.list_jobs` is called from `src/ui/discover_ctx.py` (which is the umbilical the plan actually cut). When a future row migrates the remaining sample-data callers, the lint can tighten to a full import ban. **Impact:** none on this PR; documented inline in the test header so the next author understands the staging.
- **`_effective_user_id(fake-session)` returns `None` in Discover, `1` in Jobs.** Plan implied a single resolution rule. Reality differs because Discover has a `db.sample_data` fallback inside `build_discover_ctx` — returning `None` signals "skip the live `list_jobs` pivot and use sample data," which preserves the existing memory-mode test surface (`test_pages.py`, `test_discover_redesign.py`) bit-for-bit. `/jobs/{id}` has no fallback path — a single-Job read needs a real user_id, so it maps fake-session to the seeded owner (`USER.id == 1`). Both rules are documented in the routes' helper docstrings. **Impact:** plan 2.11 (CLI sunset) retires the fake-session stub; at that point both helpers collapse to `user.id` straight.
- **Empty-DB UX uses the existing `build_discover_ctx` fallback, not an alembic data migration.** Plan § E.1 mitigation proposed appending 5 demo Jobs via an alembic data migration when the live table is empty + `debug` + `SELF_HOSTED`. Reality: the shadow-data fallback already provides the same dev UX — when live `list_jobs(...)` returns `[]`, `build_discover_ctx` filters the sample-data shadow queue through the same `JobFilter` and renders it. Adding a data migration would risk shipping demo rows into self-hoster prod DBs when `NAAVIK_DEBUG` accidentally flips on. **Impact:** simpler diff (no migration to author/audit); identical end-user behavior.
- **Filter toolbar visible by default; "Filters · N" button toggles its `hidden` class.** Plan § D.2 picked the chip-row toolbar but didn't specify whether it was visible-by-default or collapsed. I made it visible-by-default with a `Filters · N` button on the header that toggles `classList.hidden` via inline JS. Rationale: scanning the active chips at a glance is more valuable than an extra click. **Impact:** ~2-line onclick handler in `discover.html`; `data-filter-toolbar-toggle` attribute on the button for any future analytics hook.
- **`_filter_hidden_inputs.html` partial added (not in plan § A surface inventory).** Each per-chip `<form>` in the toolbar needs to mirror the *other* filter axes as hidden inputs so a single-axis change doesn't lose sibling state when the form submits. Extracted into a shared include. **Impact:** one extra partial under `components/`. Behavior change vs naive single-form: filter state is preserved across chip clicks.
- **`job_card.html` placeholder NOT scaffolded.** Plan § A row called it out as "scaffolded but not shipped this plan — see § D.2." Reality: an empty scaffolded file with no callers is dead code that fails the engineer comment policy. Deferred entirely until whatever future row actually adds a "table view" toggle on Discover. **Impact:** none on this PR; future row authors check § A / § D.2 of plan 36 for the proposed structure.
- **`/api/v1/jobs/{job_id}` moved + tightened to require auth + IDOR boundary.** Plan § A row called for the *move* (cohesion); my implementation also added `Depends(require_authed_session)` + the `_job_or_404` user-id boundary that the old handler in `discover.py` didn't have. The old handler returned any Job to any caller (or no caller at all). The new one enforces 401 on no-cookie + 404 cross-user. **Impact:** `tests/test_stub_endpoints.py::test_jobs_get_by_id` updated to monkeypatch `job_service.get_job` (no longer hits sample-data shim). API consumers that previously called the endpoint without a session cookie now get 401 — this matches the security review path the same plan applies to `archive_job`/`restore_job` (0.7.0.15 fold-in).
- **`/_fragments/jobs/{job_id}` chrome-less variant added on top of the plan's surface.** Forward-compat for plan 0.2.0.12+ that may want to deep-link a Job preview into a drawer (Tracking-list "view source job" link).
