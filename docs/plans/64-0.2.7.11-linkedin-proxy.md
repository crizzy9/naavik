# 64 · `0.2.7.11` — LinkedIn proxy support

## Goal

Add the missing fourth anti-detection layer to the `Crawl4AIClient` → `LinkedInScraper` stack: a per-source HTTP / HTTPS / SOCKS5 proxy plumbed in via Crawl4AI 0.8.6's `CrawlerRunConfig.proxy_config`, configured via a single env var (`LINKEDIN_PROXY_URL`) that the operator points at any residential or datacenter proxy provider, with credentials carried in URL Basic-auth form and routed through the existing `safe_url` redaction guard so they never land in `JobScrapeRun.errors[]` or logs. Telemetry adds three keys to `JobScrapeRun.raw_meta` — `proxy.host` (redacted hostname only), `proxy.used` (bool), `proxy.bytes_estimated` (best-effort upper bound) — so operators know when scrapes ran over the proxy and (roughly) how much bandwidth they cost. Defaults: proxy applies only to LinkedIn this plan; **proxy failure is loud-fail, not degrade-to-direct** (silent fall-through to direct connections is what gets LinkedIn accounts banned); session stickiness is **per-`Crawl4AIClient` instance** (the scheduler constructs a fresh client per firing, which gives natural ~5-minute-window stickiness without a separate state machine). On approval the plan content graduates into a new `docs/design/LINKEDIN_PROXY.md`; `SCRAPER_BASE.md § G.11` becomes a one-line forward pointer. Out of scope: generic per-source proxy infrastructure (filed as Open Question OQ.5 — recommended LinkedIn-only first; multi-source generalization is a follow-up); IP-classifier validation that the operator's chosen proxy is actually residential (footgun by design — we don't gate the operator); proxy-pool rotation strategies beyond what Crawl4AI ships (`RoundRobinProxyStrategy`) — reserved for the multi-source generalization.

## Why now

Four forces, ordered by load:

1. **Plan 38 / `0.2.0.13` (rate limit + anti-detection) explicitly reserved this slot.** `docs/design/SCRAPER_BASE.md § G.11` shipped with the words: *"Out of scope for `0.2.0.13`. Deferred to `0.2.3.03` (Phase 6+) per ROADMAP. When that row lands, a new `Settings.scraper_proxy_url` field + `Crawl4AIClient(proxy_config=...)` plumbing extends this section."* The ROADMAP row was subsequently moved from `0.2.3.03` → `0.2.7.11` during the 0.2.x consolidation (ROADMAP `0.2.3` deliverable line: *"0.2.3.03 moved to 0.2.7.11"*). The substrate (`Settings.scraper_rate_limits` JSONB pattern + `RateLimitConfig` resolver) is the template this plan copies; the wiring (`Crawl4AIClient.fetch_html` + `stream_many` already construct `BrowserConfig` + `CrawlerRunConfig` per request) has the exact slot ready.

2. **LinkedIn's 0.4 rpm rate limit is the tightest we ship and proxies are the only way to scale it.** Plan 38 shipped `LinkedInScraper.rate_limit_per_minute = 0.4` (~24 requests / hour). At 24/hr, a typical operator targeting 5 keyword sets in one location is at the rate-limit ceiling within the first scrape sweep. Multi-proxy rotation lifts that ceiling by N (number of proxies). This plan ships the single-proxy wiring; the rotation strategy is reserved for the multi-source follow-up but the resolver shape this plan adopts allows operators to point at a provider's "sticky session" URL that already gives them up to N IPs.

3. **`docs/design/research/LINKEDIN_SCRAPING.md` § 6 explicitly identifies proxy as a substrate prerequisite for any realistic LinkedIn scraping deployment.** The 214-line option matrix that locked in plan 33's "Option B — direct guest API + Crawl4AI stealth" path was conditional on layered defenses. Stealth (G.5) + UA rotation (G.4) + rate limit (G.2/G.3) all shipped in plans 29 + 38. Proxy is the last layer the research doc names; without it, the `crypticsoul.dev` operator's residential IP becomes a single point of failure — one CAPTCHA round or 24-hour rate-limit cooldown and the entire `discover` pipeline stops feeding LinkedIn.

4. **Crawl4AI 0.8.6 (the version we already pin) ships native `ProxyConfig` + per-request `CrawlerRunConfig.proxy_config` and the surface area this plan touches is unchanged from where plan 38 left it.** Per [Crawl4AI 0.8 proxy docs](https://docs.crawl4ai.com/advanced/proxy-security/), `proxy_config` is a `ProxyConfig | list[ProxyConfig] | None` field on `CrawlerRunConfig` (the per-request config we already build in `Crawl4AIClient.__init__` at `crawl4ai_client.py:108-111`). The legacy `BrowserConfig.proxy` argument is deprecated. `ProxyConfig.from_string("http://user:pass@host:port")` accepts the env-var shape operators are familiar with. Total wiring delta: ~30 LOC across one file (`crawl4ai_client.py`) + one new helper module (`scraper/proxy.py`) + one env-var resolver (`config.py` adds one field) + one `LinkedInScraper.__init__` constructor-side override.

ROADMAP cross-references: `ROADMAP.md` row `0.2.7.11` (line 324); `ROADMAP.md` row `0.2.3` deliverable line ("0.2.3.03 moved to 0.2.7.11"); `ROADMAP.md` row `0.5.0.12` (LinkedIn outreach automation — references `docs/design/research/LINKEDIN_SCRAPING.md § 5` and explicitly names this plan's substrate as the proxy-side foundation).

### D.1 — Session stickiness strategy

LinkedIn fingerprints sessions across requests (cookie continuity, TLS-fingerprint stability, IP geo-stickiness). Rotating IPs per request triggers "suspicious activity" challenges within ~5-10 requests. The standard residential-proxy provider offering is a **"sticky session"** URL that holds the same exit IP for N minutes (Bright Data: 1-30min via `session-id-XYZ` URL param; Smartproxy: similar via username suffix `user-session-XYZ`; IPRoyal: 1h sticky via username pattern). The question is how Naavik composes its own session window on top.

**Option matrix.**

| Option | A — Sticky-per-`Crawl4AIClient`-instance (recommended) | B — Rotating per-request (no stickiness control on Naavik side; rely on provider) | C — Explicit window state machine (rotate every 30min via `time.monotonic()` checkpoint) |
| --- | --- | --- | --- |
| Capability | Scheduler constructs a fresh `Crawl4AIClient` per `_scrape_one_user` firing (`scheduler/scraping.py:158`). One client instance = one scrape sweep = one sticky session naturally. LinkedIn's fingerprint sees one IP per sweep. | All requests funnel into a provider rotation pool; each request gets whichever IP the provider hands out. Highest IP diversity but LinkedIn fingerprints the rapid IP changes. | Naavik tracks `(start_time, current_proxy)` per session; rotates the URL when wall-clock exceeds 30min. |
| Cost — code | Zero state machine. `Crawl4AIClient.__init__` accepts `proxy_config: ProxyConfig \| None` and uses it for the instance lifetime. ~5 LOC delta in client. | Pass `proxy_rotation_strategy=RoundRobinProxyStrategy(...)` to `CrawlerRunConfig`. ~10 LOC + need to construct N `ProxyConfig`s. | New `ProxySessionManager` class. ~80 LOC + a thread-safe state store + tests for the rotation edge cases. |
| Risk — LinkedIn ban | LOW — one IP per sweep (~5min window in default cron schedule = under any provider's sticky cap). | HIGH — rapid IP cycling is the textbook bot signal LinkedIn catches. | MEDIUM — window correctness is fragile under scheduler-overlap conditions; two cron firings in the same 30-min window must coordinate. |
| Risk — provider misuse | LOW — operator points the env-var URL at the provider's "sticky session" endpoint per their docs. If they point it at the rotating endpoint, B-shape behavior, but that's the operator's choice. | LOW — explicit. | HIGH — Naavik's window can fight the provider's window. |
| Cost — operator config | One env-var: `LINKEDIN_PROXY_URL=http://user:pass@gate.smartproxy.com:7000` (or whatever the provider's sticky-session URL is). | Multiple proxy URLs comma-separated in env-var; ParseError surface is larger. | Same as A + an opaque rotation policy operators have to reason about. |
| Per-sweep IP diversity | LOW (1 IP/sweep) | HIGH | MEDIUM |
| Lock-in | None — `ProxyConfig` is a Crawl4AI 0.8.6 boundary type, can shape-shift via a wrapper. | Some — `RoundRobinProxyStrategy` ties us to Crawl4AI's rotation impl. | High — Naavik now owns the rotation contract; if Crawl4AI ships a better one in 0.9, we eat the migration. |

**Recommendation: A — sticky-per-`Crawl4AIClient`-instance, no explicit window state machine.**

**Reason 1: the scheduler already gives us natural stickiness for free.** `scheduler/scraping.py:_scrape_one_user` constructs a fresh `Crawl4AIClient` per cron firing (post-plan-38, every firing also gets a fresh UA from the rotation pool). LinkedIn cron schedule is conservative (every ~5min in a busy operator's setup; every 30min in default). One sweep = one client instance = one sticky session aligns with how every residential-proxy provider's sticky URL works (Bright Data 1-30min, Smartproxy session-based). No code on our side; we ride the scheduler's existing per-firing isolation.

**Reason 2: rotating-per-request is what gets the account banned.** The 214-line LinkedIn research doc and every public scraping post-mortem (Crawlee, JobSpy, etc.) flag rapid IP cycling as the most obvious bot signal. Even with stealth + UA rotation, jumping IPs mid-session reads as "different physical human typing in a different city on the same LinkedIn session" — LinkedIn handles that with an immediate challenge.

**Reason 3: explicit window state is over-engineered for v1.** Operators who want >24/hr throughput from LinkedIn buy more proxies + run more cron firings, not longer-running scrapes. The 30min-window state machine is interesting for the future "long-running session" case (e.g. Phase 5 outreach with persistent cookies); it doesn't earn its complexity in v1 anonymous-scrape.

**Trade-off accepted.** Operators who need IP-rotation within a sweep don't get it from this plan — they configure the provider's rotation URL and accept higher ban risk, OR they wait for the multi-source generalization to ship native rotation. Documented in `LINKEDIN_PROXY.md § Stickiness behavior`.

**Locked decision (subject to OQ.1): A** — sticky-per-`Crawl4AIClient`-instance.

### D.2 — Provider integration: agnostic vs provider-specific

The three serious residential proxy providers (Bright Data, Smartproxy/Decodo, IPRoyal) all expose a standard HTTP `CONNECT`-method proxy endpoint. They differ in auth shape (Bright Data uses customer ID + zone in URL: `brd-customer-{id}-zone-{zone}:{password}@brd.superproxy.io:33335`; Smartproxy uses username + suffix tags: `user-USERNAME-session-XYZ:password@gate.smartproxy.com:7000`; IPRoyal uses `username:password@geo.iproyal.com:12321`). All three accept the standard `http://user:pass@host:port` URL form.

**Option matrix.**

| Option | A — Provider-agnostic via `ProxyConfig.from_string("http://user:pass@host:port")` (recommended) | B — Provider-specific adapters (one class per Bright Data / Smartproxy / IPRoyal with their API token) | C — Hybrid: standard URL + an optional `LINKEDIN_PROXY_PROVIDER=bright_data` hint for telemetry only |
| --- | --- | --- | --- |
| Capability | Operator points env-var at provider's standard URL. Works for any HTTP / HTTPS / SOCKS5 proxy. | Per-provider sticky-session APIs, geo-targeting via provider's API, automatic rotation via provider's API. | Standard URL works; provider hint surfaces in `JobScrapeRun.raw_meta` for cost analysis. |
| Cost — code | Single helper `scraper/proxy.py:resolve_proxy_config()`. ~30 LOC + Pydantic v2 validator. | 3 × ~80 LOC adapters + 3 API tokens in env (`BRIGHTDATA_API_TOKEN`, etc.) + adapter factory. | ~40 LOC (standard URL + 5-LOC switch for the hint). |
| Risk — vendor lock-in | NONE — Naavik never speaks provider-specific API. Switch providers = update env-var. | HIGH — every provider migration is a code change. | Same as A; hint is non-load-bearing. |
| Risk — provider features | LOW — operators can use ANY provider feature exposed via URL params (session, country, sticky-time). Operator embeds those in the URL the env-var holds. | LOW — every feature surfaced explicitly via Naavik's adapter. | Same as A. |
| Operator UX | Excellent — copy/paste URL from provider's dashboard. | Worse — operator picks adapter + finds their API token + plugs that in. | Same as A + optional dropdown. |
| Maintenance | NONE per provider — they own URL stability. | OWN bug surface — every provider API change is a Naavik PR. | Same as A. |
| Telemetry granularity | Coarse — Naavik sees host only via `safe_proxy_host`. | Fine — per-provider request counts. | Medium — hint label, no API call. |
| Multi-provider | Operator runs N sweeps with N different URLs (env-var-per-sweep is a follow-up; v1 is single URL). | Native via adapter factory. | Same as A. |

**Recommendation: A — provider-agnostic via `ProxyConfig.from_string`.**

**Reason 1: lock-in is the bigger long-term cost.** Naavik's entire LLM provider abstraction (`src/llm/{base,anthropic,openai,ollama}.py`) follows the same "abstract over the standard" principle — we don't bake Anthropic-specific features into our code path; the user picks their provider. Same shape here. Bright Data costs ~$15/GB; if Smartproxy ships at $9/GB tomorrow, operators should be able to switch via one env-var edit, not a Naavik release.

**Reason 2: provider-specific features fit in the URL.** Every meaningful feature (sticky session, country pin, sub-account split) is a URL-side capability the provider exposes; operators copy/paste the URL from their dashboard and we never touch their config. The Bright Data customer-zone customer URL `brd-customer-{id}-zone-{zone}:{password}@brd.superproxy.io:33335` works as-is.

**Reason 3: maintenance is zero per provider.** Providers own their URL backward-compatibility; we own nothing. If Bright Data ships a new region domain, that's a one-character env-var edit on the operator side.

**Trade-off accepted.** Per-provider cost-tracking (Bright Data reports bytes/$ via API; that data doesn't reach Naavik). Mitigated by D.9's `JobScrapeRun.raw_meta["proxy"]["bytes_estimated"]` upper-bound which gives operators a request-time view; granular dashboards stay on the provider's side.

**Locked decision (subject to OQ.2): A** — provider-agnostic.

### D.3 — Proxy storage locus: env, DB, or extension of `scraper_rate_limits`

The proxy URL is a secret (it carries Basic-auth credentials). Three places it could live: env-only (`LINKEDIN_PROXY_URL`); per-user Settings column (multi-tenant cloud-shaped); nested into the existing `Settings.scraper_rate_limits` JSONB (which is per-source).

**Option matrix.**

| Option | A — Env-only `LINKEDIN_PROXY_URL` (recommended for v1) | B — Per-user `Settings.scraper_proxy_url: str` DB column | C — Nest into `Settings.scraper_rate_limits["linkedin"]["proxy_url"]` |
| --- | --- | --- | --- |
| Capability | Single-tenant. One proxy URL per Naavik instance. | Per-user. Each user configures their own proxy via Settings UI. | Per-user + per-source. Multi-source from the start. |
| Cost — code | New `config.py` field + new `scraper/proxy.py` resolver. ~40 LOC. Env-presence indicator via `env_secrets.py` extension. | Alembic migration to add column. `settings_service` mutator. Settings UI write-with-encryption-or-not decision (we've sunset vault — see Risk row). ~120 LOC. | Extend `RateLimitConfig` Pydantic model with optional `proxy_url` field. Same vault concern as B. ~60 LOC. |
| Risk — secret-handling | LOW — env-var pattern is identical to every other secret since plan 26. `chmod 0600 .env` is the defense. | HIGH — DB-stored proxy URL with Basic-auth creds is **exactly** the kind of secret the vault used to protect. We deleted the vault in plan 26 BECAUSE that protection was theater. Re-introducing DB-stored credentials reopens the surface. | Same as B. |
| Risk — multi-tenant | n/a — single-tenant target. | LOW — DB-per-user is the right shape for multi-tenant cloud. | LOW — same. |
| Risk — sunset compliance | LOW — env-only is the established post-plan-26 pattern. | RED — DB-stored credentials directly contradict the post-vault stance unless we re-build the encrypted-at-rest layer the vault provided. That's the work plan 26 deleted. | RED — same as B. |
| Operator UX | One env-var. | UI input form for the URL. | Same as B + a sub-form within Sources panel. |
| Composition | Env var resolved at startup. Settings UI shows env-presence indicator only (matches LLM API key pattern). | Settings UI shows the value (or masked value) which means the user can READ it back via UI = secret-in-DB problem. | Same as B. |

**Recommendation: A — env-only `LINKEDIN_PROXY_URL` for v1.**

**Reason 1: matches the post-vault posture.** Plan 26 deleted the encrypted vault precisely because it was security theater (the vault key was derived from `SECRET_KEY`, the same env var; an attacker with `SECRET_KEY` could decrypt both). The post-plan-26 contract is "secrets live in env; filesystem perms are the defense" (`AGENTS.md § Key Conventions § CLI`, codified 2026-05-10). DB-stored proxy credentials would re-open the surface plan 26 closed.

**Reason 2: single-tenant is the v1 target.** Multi-tenant cloud lands as 0.8.0+ — that's where per-user proxy config matters (one user's residential proxy contract, another's datacenter proxy). v1 is one operator running their own instance. Per-user DB column is YAGNI now; we file the multi-tenant generalization as a deferred row (§ § H).

**Reason 3: env-only is the lowest-risk landing path.** No migration, no UI write surface, no audit-log decision, no encrypted-at-rest re-introduction.

**Trade-off accepted.** Multi-tenant cloud operators have to wait for the storage upgrade (filed as `0.8.0.NN` follow-up — see § H). Settings UI surfaces a read-only env-presence indicator (matching the LLM API key pattern from plan 26).

**Locked decision (subject to OQ.3): A** — env-only `LINKEDIN_PROXY_URL`.

### D.4 — Residential vs datacenter: validate or trust the operator

LinkedIn's bot detection treats datacenter IPs (AWS, Google Cloud, etc.) with higher suspicion than residential IPs. Operators choosing the wrong proxy type silently amputates the anti-detection benefit.

**Option matrix.**

| Option | A — Operator picks; no validation (recommended) | B — Validate at config time (curl through proxy → IP-classifier API like ipinfo.io → reject if datacenter) | C — Add a warning indicator in Settings UI when configured proxy resolves to a known datacenter range |
| --- | --- | --- | --- |
| Capability | Operator points env-var at any proxy. Naavik trusts the operator. | Naavik rejects datacenter proxies at boot with a hard error. | Soft warning surface. |
| Cost — code | 0 LOC. | New ipinfo.io API integration (or maxmind GeoLite). New env-var for the classifier API token. ~80 LOC + a runtime fetch on boot. | Same as B but warning instead of error. ~80 LOC. |
| Risk — operator footgun | HIGH — operator chooses datacenter unwittingly + gets account banned. | LOW — Naavik refuses to start with a wrong-type proxy. | MEDIUM — warning is hideable. |
| Risk — false-positive | n/a | HIGH — IP-classifier API can mislabel residential proxies as datacenter (especially "residential-rotating" pools that share datacenter front-ends). | Same as B. |
| Risk — vendor dependency | NONE | HIGH — Naavik now requires an IP-classifier API key. That's another env-var, another billing-relationship, another point of failure. | Same as B. |
| Risk — outbound traffic at boot | NONE | HIGH — Naavik phones home to ipinfo.io on every restart. Self-hosted privacy posture suffers. | Same as B. |
| Maintenance | NONE | OWN the IP-classifier integration | Same as B. |

**Recommendation: A — operator picks; no validation; document loudly.**

**Reason 1: self-hosted privacy contract.** Naavik does NOT phone home in any other code path. Adding an outbound-on-boot dependency for the residential-vs-datacenter check breaks that contract.

**Reason 2: false-positive risk is high.** Residential-rotating pools from major providers often share datacenter-IP front-ends; IP-classifier APIs flag them as datacenter even when the exit-IP is residential. Naavik would reject a perfectly good proxy URL.

**Reason 3: the operator footgun is loud enough.** `LINKEDIN_PROXY_URL` in `.env.example` carries a comment block warning that datacenter IPs are LinkedIn-suspicious; the design doc says the same. Operators who ignore documentation will hit pain — but they'll know what to do (switch provider).

**Trade-off accepted.** Operators can configure a datacenter proxy and silently degrade their LinkedIn anti-detection posture. Mitigated by the `.env.example` comment block + `LINKEDIN_PROXY.md § Provider selection`.

**Locked decision (no OQ — defaults align with sunset / privacy posture): A** — no validation.

### D.5 — Geo-targeting

LinkedIn associates account history with a country; sustained IP-from-different-country reads as account compromise. Most residential providers expose geo-pinning via URL params (Bright Data: `country-us` in the username; Smartproxy: `-country-us` suffix).

**Option matrix.**

| Option | A — Operator embeds geo in URL; Naavik passes through (recommended) | B — Optional `LINKEDIN_PROXY_COUNTRY=us` env-var; Naavik composes the URL | C — Auto-infer geo from `Settings.linkedin_location` |
| --- | --- | --- | --- |
| Capability | Operator pastes the provider's URL that already has geo embedded. | Naavik composes the URL from base + country. | Auto-pinning to user's location. |
| Cost — code | 0 LOC. | New env-var + URL-template-substitution logic. ~50 LOC. | ~80 LOC + geocode-to-country mapper. |
| Risk — provider-specific URL shape | NONE | HIGH — every provider has a different geo-pin shape (`country-us` vs `-country-us` vs `geo-us`). Naavik would need provider-specific templates. | Same as B. |
| Risk — misalignment | NONE — operator owns the geo policy. | LOW — Naavik enforces a single country. | LOW — Naavik picks; could be wrong on remote-from-anywhere users. |
| Lock-in | NONE | per-provider | per-provider |

**Recommendation: A — operator owns geo via URL.**

**Reason 1: provider-specific URL templates are exactly what option D.2 ruled out.** We chose provider-agnostic; adding provider-specific geo shaping immediately re-introduces lock-in.

**Reason 2: operators with a LinkedIn account already know their account's country.** It's not Naavik's call.

**Locked decision (no OQ — falls out of D.2): A** — geo via operator's URL.

### D.6 — Failover behavior: fail loud or degrade to direct?

Critical decision. If `LINKEDIN_PROXY_URL` is set but the proxy is dead (provider outage, expired credit, blocked port), what should the scraper do?

**Option matrix.**

| Option | A — Fail loudly: log + mark JobScrapeRun status=FAILED (recommended) | B — Degrade to direct connection silently | C — Fall back to a "secondary proxy URL" env-var; fail loudly only if both die |
| --- | --- | --- | --- |
| Capability | Cron firing fails visibly; operator notified via existing scrape-run-summary Discord webhook + admin-alert mechanism (plan 35 `consecutive_scrape_failures`). | Scrapes still produce data; the operator never knows the proxy was bypassed. | Two URLs; primary + fallback. |
| Risk — account ban | LOW — proxy outage = no LinkedIn requests = no ban risk. | CRITICAL — silent fall-through to operator's residential IP is what gets the LinkedIn account banned. The whole reason proxy exists is to hide the residential IP. | LOW — both proxies have to die; very unlikely. |
| Risk — observability | LOW — `JobScrapeRun.errors[]` carries the error; admin alert fires. | CRITICAL — operator only finds out when their LinkedIn account gets the suspicious-activity email. | LOW — same as A. |
| Risk — code surface | LOW — passthrough error. | LOW — explicit try-except → set `proxy_config=None`. | MEDIUM — two URLs to manage. |
| Operator UX | Loud error in the Discover panel "View scrape run" detail. | Silent. | Slightly more env-var config. |

**Recommendation: A — fail loudly. Never degrade to direct.**

**Reason 1: this is the rule that exists to prevent account bans.** Every production-quality scraper post-mortem (n8n's original setup, Crawlee public discussions, JobSpy's docs) names "silent direct-IP fallback" as the #1 way to lose a LinkedIn account. The proxy is configured BECAUSE the residential IP is exposed; bypassing the proxy is exactly the thing the operator paid the proxy provider to prevent.

**Reason 2: failure is observable.** Plan 35 already shipped `consecutive_scrape_failures` counter + Discord admin alert on 3 consecutive FAILEDs. A bad proxy that produces 3 FAILED runs in a row fires the admin alert — operator notices within one hour.

**Reason 3: degrade-to-direct is a footgun that operators will not understand until too late.** "Why did Naavik silently bypass my expensive residential proxy?" is not a conversation we want to have after an account ban.

**Trade-off accepted.** Cron firings during a proxy outage produce zero data (instead of degraded data via residential IP). Operators MUST keep proxy credit topped up. Documented in `LINKEDIN_PROXY.md § Failure handling`.

**Locked decision (subject to OQ.4): A** — fail loud.

| Risk — operator UX | LOW — narrow env-var. | LOW — explicit per-source picker. | MEDIUM — operator can't proxy LinkedIn without also proxying Greenhouse (or vice versa). |
| Cost — provider bytes | LOW — only LinkedIn traffic over proxy. | MEDIUM — operator's monthly proxy bytes go through every source. | HIGH — every source over proxy = $$ per GB. |
| Future-flexibility | HIGH — generalization is a follow-up plan that consolidates the LinkedIn-specific helper into the per-source `scraper_proxies` table. | LOW — built once; refactor expensive. | LOW — locks all sources together. |

### D.8 — Proxy authentication carrying: URL Basic-auth vs separate env-vars vs cookie/token

Proxy credentials need to ride with the request to the proxy. Three shapes.

**Option matrix.**

| Option | A — Basic-auth in URL: `http://user:pass@host:port` (recommended) | B — Separate env-vars: `LINKEDIN_PROXY_URL` + `LINKEDIN_PROXY_USERNAME` + `LINKEDIN_PROXY_PASSWORD` | C — Provider API token via `LINKEDIN_PROXY_API_TOKEN` |
| --- | --- | --- | --- |
| Capability | Single URL carries everything. `ProxyConfig.from_string` natively supports this. | Separate fields. Explicit. | API-token shape (rare; provider-specific). |
| Cost — code | 0 LOC parsing — `ProxyConfig.from_string` does it. | ~30 LOC parsing + Pydantic field-level validation. | ~80 LOC adapter per provider. |
| Risk — URL secret-leakage | HIGH if not redacted — `safe_url()` already strips query/fragment but the userinfo segment (`user:pass@`) is in the AUTHORITY, not query. We need an explicit `safe_proxy_host(url)` helper that strips userinfo BEFORE any log line, JobScrapeRun.errors line, or telemetry line is composed. | LOW — secrets never enter the URL string, so URL-shape redactors don't need to special-case. | MEDIUM — token in env is fine; if it accidentally ends up in a log, single field is easier to redact than three. |
| Risk — copy/paste UX | LOW — operators paste the URL from provider dashboard verbatim. | MEDIUM — three fields = three copy/paste operations + a chance to miss one. | LOW — single field. |
| Risk — operator confusion | LOW — URL-with-userinfo is standard. | MEDIUM — three env-vars for one concept. | LOW. |
| Provider compatibility | Universal — every provider documents this URL form. | Universal | Per-provider |

**Recommendation: A — Basic-auth in URL, WITH explicit `safe_proxy_host` redaction guard.**

**Reason 1: provider dashboards print this exact format.** Bright Data, Smartproxy, IPRoyal all expose copy/paste-able URLs of the `http://user:pass@host:port` shape. Anything other than passing this verbatim creates friction.

**Reason 2: `ProxyConfig.from_string` handles it natively.** No parsing on our side; Crawl4AI 0.8.6 already supports `http://user:pass@host:port` per the public docs.

**Reason 3: redaction is the real concern, and it's tractable.** Our existing `safe_url(url)` (in `scraper/redaction.py`) preserves scheme + host + path but strips query/fragment — it does NOT strip the userinfo segment. We need a sibling `safe_proxy_host(url)` that returns `<host>:<port>` only (zeroing scheme + userinfo + path). One helper, ~10 LOC, ~5 tests covering Basic-auth-in-URL and bare-URL cases. Every log-emitting site in this plan (Crawl4AIClient logs, scraper_service errors, scheduler logs) routes proxy URLs through `safe_proxy_host` before logging.

**Trade-off accepted.** The redaction guard adds one helper + careful audit of every site that might log a proxy URL. Mitigated by a lint guard test (`tests/test_no_proxy_url_in_logs.py`) that grep-checks for `LINKEDIN_PROXY_URL` shape strings in log output of every scraper test.

**Locked decision (no OQ — falls out of D.2 + D.3): A** — Basic-auth in URL + redaction guard.

### D.9 — Cost surfacing: track bytes per source

Residential proxies are billed per-GB. Operators want to know whether LinkedIn scraping is costing them $5/month or $50/month.

**Option matrix.**

| Option | A — Track per-scrape proxy bytes in `JobScrapeRun.raw_meta["proxy"]` (recommended) | B — New `ProxyUsage` table for fine-grained billing | C — Don't track; operators monitor cost on the provider's dashboard |
| --- | --- | --- | --- |
| Capability | Best-effort upper bound (request size + response HTML size summed per scrape). One JSON sub-key per run. | Time-series per-byte data. Cost dashboards. | Operator owns it. |
| Cost — code | ~20 LOC: instrument `Crawl4AIClient.fetch_html` + `stream_many` to track response.html length sum on a counter; service layer reads counter into `raw_meta`. | New SQLModel + alembic migration + service-layer mutator + UI page. ~250 LOC + alembic 0012. | 0 LOC. |
| Risk — accuracy | LOW (upper bound) — response HTML length ≠ bytes-over-wire (compression), but it's a useful proxy that operators can multiply by an empirical ratio. | High — bytes-over-wire would require lower-level instrumentation. Crawl4AI doesn't expose that. | n/a |
| Risk — schema bloat | LOW — single sub-key in existing JSONB. | HIGH — new table = new migration = new operational surface. | n/a |
| Operator UX | One number per scrape run in the existing "View scrape run" detail. | Dedicated dashboard. | Provider's dashboard. |

**Recommendation: A — `JobScrapeRun.raw_meta["proxy"]` sub-key, no new table.**

**Reason 1: convention parity with plan 38.** Plan 38 added `JobScrapeRun.raw_meta["rate_limit"]` + `["adapter_used"]` in the same shape. Adding `["proxy"]` follows the established pattern.

**Reason 2: upper bound is enough.** Operators don't need byte-perfect accounting from Naavik (the provider has that); they need a "did this scrape cost ~50KB or ~5MB" sanity check.

**Reason 3: no schema change, no migration risk.**

**Shape.**

```json
{
  "rate_limit": { "hits": 0, "backoff_total_s": 0.0, "ua": "Mozilla/5.0 ..." },
  "adapter_used": "stealth",
  "proxy": {
    "used": true,
    "host": "gate.smartproxy.com:7000",
    "bytes_estimated": 487293,
    "request_count": 24
  }
}
```

Sub-fields: `used` (bool — was the proxy on for this run?); `host` (string — `safe_proxy_host(url)` output; empty when `used=false`); `bytes_estimated` (int — upper bound on response HTML lengths summed across the run); `request_count` (int — number of HTTP requests issued through the proxy).

**Locked decision (subject to OQ.6): A** — `JobScrapeRun.raw_meta["proxy"]` sub-key.

### D.11 — Anti-detection layer composition

This plan ships the fourth layer on top of stealth + UA rotation + rate limit. Operators ask whether each layer earns its keep or whether we could simplify.
