# 68 · 0.3.2 UI remediation master — owner-reported regression sweep + UI polish

## Goal

Master plan gating the full sweep of 8 owner-reported regressions (Discover broken, Profile broken, Save doesn't persist, stub data still reaching UI, Login doesn't work, Settings · LLM dual selector, 401 errors when saving, Overview pipeline-live broken) PLUS the 4 deferred 0.3.2 UI polish rows. Six sub-plans (`69`–`74`) ship the actual work; this doc locks the order, the root-cause analysis, the designer subdispatch contract, and the post-mortem of why these regressions cleared PR_REVIEW_GATEs. **No code in this plan** — the sub-plans carry execution scope.

## Why this slipped

8 regressions in local QA after 7 PRs in 2 sessions (PRs #162–#168) cleared parallel-reviewer gates. That's a process miss, not bad luck. The candid causes:

### Root cause 1 — Plan 60 descoped commit 2 silently

`docs/plans/archive/60-0.2.7.17-naavik-persistence-removal.md` shipped the env-var removal + service-layer foundation. But its `## Deviations from plan` section (line 215-219) explicitly records:

> **commit 2 = no route rewire** — what: commit 2 = no route rewire; sample_data accessors collapse to pure-memory in commit 3. why: routes currently read sd.\* (memory). Adding Depends(get_session) breaks the test surrogate (asyncpg connection attempt). Full route+ctx rewire requires either (a) live DB available in tests OR (b) dependency_overrides in 14 test files. Scope exceeds single dispatch.

`tests/test_no_sample_data_imports_in_routes.py:_KNOWN_LEGACY_OFFENDERS` (13 entries) documents the offenders. **The follow-up was filed as `0.2.7.17a`, then moved to `0.8.0.38` (low priority) per user "defer rest of 0.2.x not done → 0.8.0" directive on 2026-05-21.**

Operationally, that means: after plan 60 shipped, the 8 routes (`discover/profile/overview/outreach/tracking/email/fragments/settings`) + 5 ctx-builders still call `sd._set_job_queue_state`, `sd._create_draft`, `sd._append_outreach_message`, `sd._append_manual_application`, `sd._append_scraped_job`, `sd._apply_status_override`, `sd._apply_failure_to_draft`, `sd._record_screener_answer` — all of which mutate **in-memory module-level lists** (`SAVED_JOBS`, `OUTREACH_MESSAGES`, etc. in `src/db/sample_data.py`). The lists reset on every worker restart. Every save the user makes "works" (no error returned) and then evaporates on reload — exactly matching the owner report "Save doesn't persist."

KPIs/pipeline strip/email signals also read from these in-memory accessors, so "Overview pipeline live broken" is the same root cause: `sd.pipeline_strip_counts()` reads `APPLICATIONS` (the in-memory list), not the DB; if a user creates an Application via the real API path (`POST /api/v1/applications/...`), it lands in the DB but not in `APPLICATIONS`, so the Overview never reflects it.

**Why the parallel reviewer missed it**: architect on PR #161 reviewed plan-adherence + design-coherence + sunset-guard. The plan's own deviations section called the descope out clearly. **Architect approved BECAUSE the descope was openly documented** — there's no policy rule that says "deviations descoping the bulk of a plan must REQUEST_CHANGES." That's the gap.

**Process fix proposal A (`0.7.0.NN` — file separately)**: extend `naavik-ops plan archive` to refuse archive when an engineer-deviation marks ≥ 30% of original Build sequence as "descoped to follow-up" UNLESS the follow-up ROADMAP row is filed AND in the current cycle's release version (not Backlog / 0.8.0). Right now the descope → 0.8.0 move is just doc edits; nothing forces a follow-up to actually land.

**Process fix proposal B (`0.7.0.NN` — file separately)**: extend `architect-plan-quality-bar` skill with a 12th check: "did the plan deliver every Build sequence item, OR did each descoped item get a follow-up plan filed in the CURRENT release version?" Make this an architect REVIEWED block, not approval-with-notes.

### Root cause 2 — Manual QA gate skipped the surface-level smoke

`engineer-manual-qa-gate` skill exists. Per `docs/AGENT_OPS.md § 14` it requires per-surface verification through the actual user surface — not just unit tests passing. For PRs #161, #166, #167, #168, the engineer ran `uv run pytest -x` (1641 tests passing), then ran route-level + service-level tests, and hand-back said "ready for PR."

**No engineer dispatch in the 7-PR sweep actually loaded `/discover`, `/profile`, `/overview`, `/settings/llm-provider` in a browser, performed a save action, refreshed the page, and verified persistence.** That's the gate that would have caught all 4 of Bugs 1/2/3/4/8.

**Process fix proposal C (`0.7.0.NN`)**: enforce `engineer-manual-qa-gate` via a Playwright capture gate at the engineer-deviations.log: every plan execution must append a `[ts] QA_GATE surface=<...> outcome=pass evidence=<screenshot-path>` line for each user-facing surface affected. Manager / architect verifies the line at hand-back; absence blocks PR open. This is more onerous than today's "Playwright optional" stance — but a brief screenshot trip across the affected pages catches every "save doesn't persist" / "page broken" regression class.

### Root cause 3 — Auth flow + first-run UX never got its own end-to-end test pass

Plan 10c (first-time-setup ergonomics) shipped `~/.naavik/dev-credentials` artifact under tight env conditions (`NAAVIK_DEBUG=1` AND `NAAVIK_DEV_PASSWORD` unset AND `SELF_HOSTED` mode). Plan 18 (PC.6) shipped password-change enforcement. Plan 26 (vault deprecation) removed the vault. Plan 42 (PC.6b onboarding bypass) closed the fake-session-on-onboarding hijack. Plan 62 (JWT rotation) added rotation keys.

**At no point did anyone run a fresh `nix run .#dev`, get the dev-credentials artifact, log in, make a save, log out, log back in, and verify the save persists.** Each of the above plans tested its OWN incremental change in isolation. The full first-run UX is a composition no single plan owned.

Owner running `uv run fastapi dev` from outside `nix run .#dev`: the `NAAVIK_DEBUG` env var isn't set (it's exported only by `flake.nix:devEnv` per plan 10c). So `~/.naavik/dev-credentials` is never written, the seeded user has an unguessable password, and the operator hits 401 the moment they try to save. The signup form is also hidden (because `signup_disabled` evaluates True — there's already a seeded User).

**Process fix proposal D (`0.7.0.NN`)**: every release-version cut (0.3.X → 0.4.0, etc.) requires a "fresh-install smoke" devops dispatch. The dispatch boots a clean `rm -rf .naavik && nix run .#dev`, performs a Playwright login + edit + save + reload sequence, captures screenshots, attaches to the release MILESTONE_GATE. Without that smoke, MILESTONE_GATE doesn't close.

## Open questions

- [ ] **Q1 (plan 70):** When the "Active provider" radio cards are deleted, how do users switch providers? **Three options:**
  1. **Implicit by env-presence** — engine picks first configured provider in priority order Anthropic > OpenAI > Ollama. User changes `.env` and restarts.
  2. **Hidden form-field toggle** — keep the provider field in `Settings.llm_provider`, drive selection from a small `<select>` next to the model dropdown (less visual real-estate than 3 radio cards).
  3. **Read-only "Current: Anthropic" label** — show which provider is active, no UI to change; require `.env` edit + restart.
  *Owner directive verbatim: "the active provider one should go and the api key one should stay." Each option satisfies "active provider goes." Architect recommends Option 1 (implicit by env-presence) — least UI clutter, matches the post-vault "trust env" model from plan 26. **Owner picks before plan 70 execution.**

- [ ] **Q2 (plan 71):** First-run UX — should we add a "fresh-start diagnostic" surface that detects when `NAAVIK_DEBUG` is unset + no User exists + no dev-credentials file + and prints a one-screen guidance? Options:
  1. **README + RUNBOOK update only** — operator reads docs to recover.
  2. **HTML page at `/setup-help`** — detects the broken-first-run state on `GET /` and serves a guidance page.
  3. **Onboarding-first redirect** — when no User exists, always redirect `/` → `/onboarding` (today's behavior is signup form on `/login`, which is similar but less obvious).
  *Architect recommends Option 1 + Option 3 (already partially there). **Owner picks before plan 71 execution.**

- [ ] **Q3 (plan 73):** `ScoreSnapshot` data model — new table vs aggregation cron output? Options:
  1. **New `ScoreSnapshot` table** — append-only per (Job, scored_at) tuple, indexed by (user_id, scored_at). Heavy writes.
  2. **Aggregation cron** — daily 03:30 UTC cron computes role-family aggregates from `Job.match_breakdown` history, writes to a `score_snapshot_daily` materialized view. Lighter.
  *Architect recommends Option 2 (aggregation cron) — `Job.match_breakdown.scored_at` already exists per `DATA_MODEL.md § C`; cron just rolls up. **Owner picks before plan 73 execution.**
