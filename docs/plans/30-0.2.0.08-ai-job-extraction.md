# 30 · `0.2.0.08` — AI job extraction (HTML → `RawJob`-shaped fields)

## Goal

Ship `src/services/job_extractor.py` — the LLM-backed service that takes a scraper-emitted `RawJob` (which carries `description_html` + optionally `description_text`), runs the HTML through a stripped-down extraction prompt, validates structured output against the canonical `RawJob` schema, and returns an **enriched `RawJob`** with the authoritative `description_text` / `tags` / `skills_required` / `*_hint` enum reads filled. The service is invoked from per-site scrapers (queued `0.2.0.07`) and from `+ Add by URL` (Phase 6 `generic.py`); it wraps every LLM call through `services/llm_tracker.tracked_call(...)` so `ApiUsage` rows persist for the daily cost cap, deletes the duplicate `ExtractedJob` Pydantic schema in `src/llm/prompts/extract_job.py` (which today drifts from the canonical `RawJob` shape and lacks the tracker wrap), and ships HTML-fixture-only tests so no real Chromium / no real LLM provider is required to run the suite.

This plan is `Type: design`. On approval, the locked extraction contract graduates into `docs/design/JOB_EXTRACTION.md` — the canonical reference for what fields the LLM is authoritative on, what fields it overwrites, and what fields stay scraper-owned. The plan file then archives.

## Why now

Five forces, ordered by force:

1. **`0.2.0.07` per-site scrapers cannot persist usable Jobs without extraction.** Every site scraper (LinkedIn, Workday, Greenhouse, Lever, Ashby, Indeed) emits `RawJob` with `description_html` filled and the visible Job fields (`company_name` / `position_title` / `location_raw` / `salary_raw` / `*_hint` trio) populated from listing-card HTML. The structured Job fields the **scorer** (`services/scorer.py`) reads — `description` (plain text), `skills_required[]`, `criteria[]`, `tags[]`, `visa_restrictions`, `remote_policy`, `seniority_level` — are populated only by AI extraction. Without `0.2.0.08`, `0.2.0.07` ships Jobs that match the dedup constraint but score `0.0` on every row (no `skills_required` overlap → match_breakdown empty), and the visa filter has nothing to read. The two plans block tightly: `0.2.0.07` calls into `0.2.0.08`.

2. **The `extract_job.py` skeleton in `src/llm/prompts/` is structurally wrong and bypasses the tracker.** Plan 10 Wave 4 shipped `src/llm/prompts/extract_job.py:1-50` as a placeholder: an `ExtractedJob` Pydantic model with **11 fields** (mismatched against `RawJob`'s 17), no service wrapper, and a direct `await provider.structured(...)` call that the `engineer-llm-tracker-wrap` skill explicitly forbids — line 49 bypasses `services/llm_tracker.tracked_call(...)` so the ApiUsage row never lands. That's a daily-cost-cap blind spot the moment any scraper runs. The pre-existing skeleton needs to be replaced, not extended.

3. **`RawJob` graduated to `docs/design/SCRAPER_BASE.md § D` as the canonical scraper-emit DTO.** That doc explicitly mandates `*_hint` semantics: "scraper's best guess; AI may override; AI extraction (`0.2.0.08`) overwrites with the authoritative read from the JD body" (`SCRAPER_BASE.md:114` + `:124`). The extraction service is the only writer of those authoritative reads. Keeping a parallel `ExtractedJob` schema means every future field-add lives in two places — exactly the kind of drift `RawJob extra="forbid"` was designed to prevent.

4. **The cost cap depends on tracker wrapping.** `services/llm_tracker.tracked_call` is what writes `ApiUsage(input_tokens, output_tokens, cost_usd, latency_ms)` so Settings · LLM Provider's "THIS MONTH" / "AVG / GENERATION" / "RATE LIMIT" cards aggregate spend (`BACKEND.md § M.4`). The existing resume-extraction service (`src/services/extraction.py:151`) is the convention to follow — every LLM call there flows through `llm_tracker.tracked_call(... session=, user_id=, provider=, method="structured", prompt_name="extract_resume", prompt=..., schema=...)`. Plan 30 lifts the same pattern across the job-extraction boundary so `0.2.0.07`'s six scrapers + `0.2.0.10`'s cron-driven scraping all bill correctly.

5. **HTML preprocessing pays for itself within one scraper run.** LinkedIn / Workday / Greenhouse job detail pages routinely return 80-120 KB of HTML; the existing 30k-character cap in `extract_job.py:48` truncates ~20-30% of long JDs. Pre-stripping `<script>` / `<style>` / `<nav>` / `<footer>` / SVG / image tags via BeautifulSoup (already a transitive dep through Crawl4AI per `uv.lock:346`) drops 60-80% of bytes for negligible CPU; the truncation cap then almost never trips, so the LLM sees the complete JD body and `skills_required` extraction stops missing the bottom-of-page "Required:" sections.

ROADMAP cross-references: `ROADMAP.md:224` row `0.2.0.08`; `ROADMAP.md:218` row `0.2.0.05` (Job model, EXECUTED); `ROADMAP.md:222` row `0.2.0.06` (Crawl4AI substrate, EXECUTED); `ROADMAP.md:223` row `0.2.0.07` (per-site scrapers, queued — depends on this plan).

### D.1 — Schema consolidation: where does the LLM-output shape live?

The crux design call. The existing `src/llm/prompts/extract_job.py` ships an `ExtractedJob(BaseModel)` with 11 fields (`company`, `role`, `team`, `location`, `description`, `criteria[]`, `skills_required[]`, `visa_restrictions`, `salary_min`, `salary_max`, `equity_pct`, `posted_at`). The canonical scraper-emit DTO `RawJob` (`src/scraper/types.py:29`) has 17 fields. The mismatch is by design — `ExtractedJob` was authored in plan 10 Wave 4 before `RawJob` existed — but it's now a drift surface.

**Option matrix.**

| Option | A — Replace `ExtractedJob` with `RawJob` as the LLM output schema (recommended) | B — Keep both; `ExtractedJob` for LLM output, adapter to `RawJob` | C — Promote `ExtractedJob` as canonical, adapt-down to `RawJob` |
| --- | --- | --- | --- |
| Capability | LLM emits a `RawJob` directly; the prompt asks for the exact 17-field shape; Pydantic v2 `extra="forbid"` catches every drift at validation time. | LLM emits an `ExtractedJob` (11 fields); a new `ExtractedJob.to_raw_job(seed: RawJob) -> RawJob` adapter merges scraper-known fields (`source` / `external_id` / `source_url` / `board` / `url_type`) onto the LLM-extracted fields. | LLM emits a renamed `ExtractedJob` (subset of `RawJob`); scrapers downgrade to consuming `ExtractedJob` shape; `SCRAPER_BASE.md` graduation rewinds. |
| Cost | Delete `ExtractedJob`. Rename `extract_job(provider, *, html)` → `enrich_raw_job(session, user_id, provider, raw_job, html)`. Adjust prompt to reflect 17 fields the LLM should emit (it only fills the ones it can — scraper-owned fields like `source` get re-supplied by the service). ~120 LOC + tests. | Keep `ExtractedJob`; write the adapter; document the merge contract. ~200 LOC + 2 schemas to maintain + double field-add cost on every future scrape-fields change. | Rewind `SCRAPER_BASE.md` graduation + redo `RawJob.to_upsert_payload()` adapter. ~400 LOC + design-doc churn. Hostile to engineer-onboarding ("which schema is canonical?"). |
| Risk | LOW — `RawJob.model_config` includes `extra="forbid"`, so the LLM-output validation catches every field-name divergence at construction time. The service supplies scraper-owned fields after the LLM returns (the LLM never sees / cares about `source` / `external_id` / `board`). | MEDIUM — two-schema systems silently drift over time. Every new `RawJob` field (e.g., `salary_currency` in future) requires an `ExtractedJob` field-add + an adapter update + a prompt update. Engineer-onboarding cost is high. | HIGH — bunch of upstream consumers (`SCRAPER_BASE.md § D.1` table; six site scrapers in `0.2.0.07`) hard-code on `RawJob`'s shape. Reverting that is a multi-PR cascade. |
| Maintenance | One Pydantic model + one prompt template. Field-adds happen in `src/scraper/types.py:RawJob` and the prompt is regenerated from `RawJob.model_json_schema()` (or hand-edited from the field table in `SCRAPER_BASE.md § D.1`). | Two Pydantic models + an adapter that needs unit tests of its own. | Three documents drift in parallel (`extract_job.py`, `RawJob`, `SCRAPER_BASE.md`). |
| Lock-in | None — the change is mechanical and reversible. | Soft lock — once 6 site scrapers ship in `0.2.0.07` calling the adapter, removing it is hard. | Hard lock — `SCRAPER_BASE.md § D.1` field table needs to stay aligned. |

**Recommendation: A — replace `ExtractedJob` with `RawJob`.** Three reasons:

1. **`RawJob` already graduated.** `SCRAPER_BASE.md § D.1` codifies which fields are "filled by scraper?" vs "refined by AI (`0.2.0.08`)?" — column 5 vs column 6 of the field table. The AI-refined column IS the extraction contract; restating it in a different Pydantic class is duplication.

2. **`extra="forbid"` is the structural enforcement layer.** Pydantic v2 raises `ValidationError` at construction time if the LLM hallucinates a `linkedin_apply_url` field; that's the same property `extra="forbid"` gives scraper authors. Single discipline, single failure mode.

3. **Adapter indirection costs more than it saves.** The `ExtractedJob → RawJob` merge is mechanical (LLM doesn't know `source` / `external_id` / `board` / `url_type` — service supplies them after the LLM returns). The merge can happen at the service-layer boundary by **constructing a new `RawJob`** from the seed RawJob + LLM-returned dict, rather than via a separate adapter class.

**Trade-off accepted.** Option B's "the LLM shouldn't see scraper-owned fields" appeal is real but illusory: the prompt simply asks the LLM to emit only the AI-refined subset, and the service merges the seed-supplied fields back in. The LLM's output schema is `JobExtraction` (a strict subset of `RawJob` — only the AI-refined fields, see § D.2 below); the service then constructs the enriched `RawJob` by spreading `seed_raw_job.model_dump() | llm_extraction.model_dump(exclude_unset=True)`.

**Rationale recorded for `memory`:** decision-id `0.2.0.08-schema-consolidation`, verdict `A`, captured at plan approval via `.claude/naavik-ops memory record-decision`.

### D.2 — `JobExtraction` Pydantic schema (the LLM-output strict subset)

A consequence of D.1: the LLM doesn't emit a full `RawJob` (it doesn't know `source` / `external_id` / `board` / `url_type`). It emits a strict subset of the **AI-refined** fields from `SCRAPER_BASE.md § D.1` column 6 plus the scorer-required fields the LLM is the only authoritative writer of (`skills_required[]`, `criteria[]`, `tags[]` — none of which are on `RawJob`; they're `Job` columns the LLM populates post-merge).

```python
# src/llm/prompts/extract_job.py (REPLACED skeleton)

from __future__ import annotations

from pydantic import BaseModel, ConfigDict, Field

from models import RemotePolicy, SeniorityLevel, VisaRestriction


class JobExtraction(BaseModel):
    """LLM-output schema for `services/job_extractor.enrich_raw_job`.

    Strict subset of the AI-refined columns in `RawJob` (per
    `docs/design/SCRAPER_BASE.md § D.1`), plus three scorer-required `Job`
    fields (`skills_required` / `criteria` / `tags`) the LLM is the sole
    authoritative writer of.

    Scraper-owned fields (`source` / `external_id` / `source_url` / `board` /
    `url_type` / `raw_meta`) are NOT in this schema — the extractor service
    re-supplies them when building the enriched `RawJob`.
    """

    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    # Normalized identity (overwrites scraper's best-effort reads)
    company_name: str = Field(min_length=1)
    position_title: str = Field(min_length=1)

    # Normalized location + structured time
    location_raw: str | None = None
    posted_at_text: str | None = None
    posted_at: str | None = None  # ISO 8601 string; service parses to datetime

    # Salary — LLM returns parsed bounds + raw passthrough
    salary_raw: str | None = None
    salary_min: int | None = None
    salary_max: int | None = None

    # Structured signals — overwrites RawJob `*_hint` trio with authoritative read
    remote_policy: RemotePolicy = RemotePolicy.UNKNOWN
    visa_restrictions: VisaRestriction = VisaRestriction.NOT_MENTIONED
    seniority_level: SeniorityLevel | None = None

    # Plain-text body (LLM strips boilerplate / normalizes whitespace)
    description: str = Field(min_length=1)

    # Scorer-required arrays (LLM is sole writer)
    criteria: list[str] = Field(default_factory=list)
    skills_required: list[str] = Field(default_factory=list)
    tags: list[str] = Field(default_factory=list)
```

**Why three new array fields not on `RawJob`.** `RawJob` is the **scraper-emit** DTO, not the **post-extraction Job-ready** DTO. The three new arrays (`skills_required[]`, `criteria[]`, `tags[]`) are written **only** by the LLM (no scraper can derive them from listing-card HTML), and they map onto `Job` columns by name via `to_upsert_payload()`. They live on `JobExtraction` because that's the LLM-output shape; they're spread into the enriched `RawJob.raw_meta` for transport to `upsert_job`, where `_create_payload` lifts them onto the matching `Job` columns. § D.5 ships the spread/lift wiring.

**Why `posted_at: str | None` not `datetime`.** Pydantic v2 *can* parse ISO 8601 into `datetime` directly, but Anthropic / OpenAI structured-output JSON-schema bindings emit dates as strings; the service parses (`datetime.fromisoformat(...)`) after validation, with a permissive fallback to `None` on parse failure. Keeps the LLM-output schema string-clean and the downstream `RawJob.posted_at: datetime | None` typing intact.

### D.3 — Service shape + signature

The extraction service is a new file `src/services/job_extractor.py`. Two options for where the logic lives, plus the rejected third (inline in scrapers).

**Option matrix.**

| Option | A — New `src/services/job_extractor.py` w/ `enrich_raw_job(...)` (recommended) | B — Add `enrich(raw_job)` method to `scraper_service.run_scraper` | C — Inline LLM call inside each per-site scraper subclass |
| --- | --- | --- | --- |
| Capability | Pure function: takes `RawJob` + `LLMProvider` + `AsyncSession` + `user_id` → returns enriched `RawJob`. Testable in isolation; reusable from `+ Add by URL` route + cron + per-site scrapers. | `run_scraper` grows a step: between `async for raw_job in scraper.scrape(query)` and `job_service.upsert_job(...)`, call `_enrich(raw_job)`. | Six per-site scrapers (`0.2.0.07`) each `await provider.structured(...)` inline. |
| Cost | ~150 LOC new file + ~20 LOC integration in `scraper_service` (single new `await job_extractor.enrich_raw_job(...)` line in the streaming loop). | `scraper_service.run_scraper` grows from ~85 LOC to ~140 LOC; the orchestrator now owns extraction. | 6× duplication; every scraper needs the prompt + tracker wrap + retry logic. |
| Risk | LOW — clean separation. Easy to mock in tests (just supply a `_FakeLLMProvider` that returns a canned `JobExtraction`). | MEDIUM — `scraper_service` was just shipped in `0.2.0.06` graduated to `SCRAPER_BASE.md § F`; adding extraction muddies the "orchestrator" framing. PR diff touches a doc graduation file's contract. | HIGH — 6× duplication; first scraper to forget the tracker wrap leaks cost. |
| Maintenance | One file owns extraction; future prompt iteration lands in one place. | Two responsibilities tangled (lifecycle + extraction). | Six places need to change in lockstep for any prompt iteration. |
| Lock-in | None — the service is pure-function and stateless apart from the tracker session. | Re-extracting from `+ Add by URL` (Phase 6) would need a duplicate codepath. | Multi-scraper drift is structural. |

**Recommendation: A — new `src/services/job_extractor.py`.** Service-layer cohesion: `scraper_service` orchestrates the run; `job_service` writes the Job; `job_extractor` runs the LLM. Three modules, three responsibilities, no overlapping ownership.

**Signature:**

```python
# src/services/job_extractor.py

async def enrich_raw_job(
    session: AsyncSession,
    *,
    user_id: int,
    provider: LLMProvider,
    raw_job: RawJob,
    settings: Settings | None = None,
) -> RawJob:
    """Run the LLM extraction on `raw_job.description_html` (or
    `description_text` if HTML is absent); return a new `RawJob` with:

    - `description_text` filled from the LLM plain-text body
    - `location_raw` overwritten if the LLM returned a normalized value
    - `posted_at` parsed from LLM's ISO 8601 string (best-effort, fallback None)
    - `posted_at_text` retained as scraper-supplied value if LLM did not overwrite
    - `salary_raw` / salary bounds (lifted into `raw_meta` if non-null)
    - `remote_policy_hint` / `visa_restriction_hint` / `seniority_level_hint`
      OVERWRITTEN with the LLM-authoritative `RemotePolicy` / `VisaRestriction` /
      `SeniorityLevel` reads (the "*_hint" suffix preserved for transport
      compatibility; AI is the authoritative writer per SCRAPER_BASE.md § D.2)
    - `raw_meta` MERGED w/ `{"skills_required": [...], "criteria": [...],
      "tags": [...], "salary_min": int|None, "salary_max": int|None,
      "description_extraction_model": "claude-3.5-sonnet-..."}` so
      `to_upsert_payload()` carries the scorer-required arrays through to
      `_create_payload(raw)` (which lifts known keys onto `Job` columns)

    If `raw_job.description_html` is None AND `raw_job.description_text` is
    None: returns `raw_job` unchanged (no LLM call), but appends a
    `raw_meta["extraction_skipped"] = "no_html_or_text"` marker so dedup +
    notifications downstream see the skip.

    Wraps `provider.structured(...)` via `services.llm_tracker.tracked_call`
    so ApiUsage rows persist (`prompt_name="extract_job"`).
    """
```

**Why the merge happens here, not at `upsert_job`.** `RawJob` is the scraper boundary; merging "LLM said the description is X" into `RawJob` keeps the boundary clean for `scraper_service.run_scraper` (which calls `raw_job.to_upsert_payload()` — already adapted to map onto `Job` columns per `SCRAPER_BASE.md § D.4`). Pushing the merge into `upsert_job` would mean `job_service` knows about LLM output, which violates the layer split.

**Why `Settings | None = None` parameter.** Reserves the future-future hook for per-user prompt tuning (e.g., `Settings.scraper_extraction_temperature: float = 0.0`). Not used in `0.2.0.08`; included to avoid signature churn when `0.2.0.13` ships rate-limiting + scraper settings.

**Public surface.** `__all__ = ["enrich_raw_job", "ExtractionSkipped"]` (the second is a sentinel exception for "no HTML and no text"; service raises if the caller wants strict mode — but the default path returns the unchanged RawJob with the `extraction_skipped` marker so the scraper pipeline doesn't die on every empty detail page).

### D.4 — HTML preprocessing strategy

Send raw HTML to the LLM (current `extract_job.py:48` cap is 30k chars) vs pre-strip via BeautifulSoup (already a transitive dep through Crawl4AI per `uv.lock:346`) vs pre-strip via BeautifulSoup + jusText (specialized HTML→text extractor).

**Option matrix.**

| Option | A — Send raw HTML (current); cap at 30k chars | B — bs4 strip `<script>` / `<style>` / `<nav>` / `<footer>` / SVG / img / form / aside, then cap at 30k chars (recommended) | C — bs4 strip + jusText readability pass for boilerplate detection |
| --- | --- | --- | --- |
| Capability | LLM sees raw HTML; structured-output guidance via prompt handles tag noise. | LLM sees clean body content w/ Tailwind classes still inline; same prompt, but the 30k cap rarely trips because we're starting from 30-50 KB instead of 80-120 KB. | LLM sees just the article body (jusText classifier removes templated boilerplate). |
| Cost | Zero impl cost. ~70% of payload is tag noise + scripts → wasted input tokens. | ~30 LOC `_strip_boilerplate(html: str) -> str` in `job_extractor.py`; uses already-available BeautifulSoup. Token savings 30-60% per call. | ~50 LOC + new dep (`jusText` ~ small but adds a wheel + version range to maintain). 60-80% token savings but ~3-5× CPU cost per call. |
| Risk | MEDIUM — LinkedIn / Workday job pages can hit 120-180 KB; the cap at 30k chars truncates ~25% of long JDs, removing the "Required:" section at the bottom. Recurring extraction failure mode. | LOW — `<script>` / `<style>` removal is mechanically safe; `<nav>` / `<footer>` / aside are by-class-or-tag heuristics that occasionally clip a non-trivial element (LinkedIn's "About this job" sometimes lives in `<aside>` on the right rail). Mitigation: keep `<aside>` but strip nav/footer/script/style/img/svg. | LOW — jusText is robust on news articles; less battle-tested on JD page templates. Heuristic boundary cases. |
| Maintenance | Status quo. | One file (`job_extractor._strip_boilerplate`) + 3-5 lines of fixtures in `tests/test_job_extractor.py` checking the strip preserved JD content. | New dep + jusText version pinning + version-bump churn for a token win that's incremental over Option B. |
| Lock-in | None | None | New dep — removing later is non-trivial. |

**Recommendation: B — bs4 strip with conservative heuristics.** The `_strip_boilerplate` helper removes:

```python
# src/services/job_extractor.py (helper)
_DROP_TAGS = ("script", "style", "noscript", "iframe", "svg", "img", "video",
              "audio", "canvas", "embed", "object", "form", "input", "button",
              "select", "textarea", "nav", "footer", "header")
# We KEEP <aside> because LinkedIn occasionally puts JD subsections there.
# We KEEP <main> and <article> obviously.

def _strip_boilerplate(html: str) -> str:
    soup = BeautifulSoup(html, "html.parser")
    for tag_name in _DROP_TAGS:
        for tag in soup.find_all(tag_name):
            tag.decompose()
    # Collapse whitespace
    text = soup.get_text(separator="\n", strip=True)
    # Then collapse repeated blank lines
    return re.sub(r"\n{3,}", "\n\n", text)
```

**Trade-off accepted.** Option C's jusText-grade extraction is overkill for `0.2.0.08`; if measured 30k-char truncation rate stays > 5% on Workday / LinkedIn detail pages after Option B ships, follow-up `0.2.0.NN` (cosmetic) adds jusText. Documented as a follow-up note in § Open questions OQ.4.

**Why `html.parser` not `lxml`.** `html.parser` is stdlib; `lxml` would force a new dep. Crawl4AI's own HTML processing uses both, but our preprocess is small enough that the stdlib parser is fine. Engineer can swap to `lxml` if the bs4 strip becomes a measurable bottleneck (which won't happen at ~80-120 KB / call).

**Rationale recorded for `memory`:** decision-id `0.2.0.08-html-preprocessing`, verdict `B`, captured at plan approval.

```python
# src/services/job_extractor.py

"""HTML → structured Job-field enrichment.

Per docs/design/JOB_EXTRACTION.md (graduated from plan 30 / 0.2.0.08).

Consumes a scraper-emitted `RawJob` (with `description_html` filled), runs
LLM structured-output extraction, and returns a new `RawJob` with:

- `*_hint` enum trio (remote_policy, visa_restrictions, seniority_level)
  overwritten with the LLM authoritative reads
- `raw_meta` merged with `skills_required[]`, `criteria[]`, `tags[]`,
  `salary_min/max`, `description_extraction_model` for downstream
  `_create_payload(raw)` lift into Job columns

Wraps every LLM call via `services.llm_tracker.tracked_call` so ApiUsage
rows persist for the daily cost cap.
"""

from __future__ import annotations

import logging
import re
from datetime import datetime

from bs4 import BeautifulSoup
from sqlmodel.ext.asyncio.session import AsyncSession

from llm.base import LLMProvider, LLMProviderError
from llm.prompts.extract_job import PROMPT, JobExtraction
from models import RemotePolicy, Settings, VisaRestriction
from scraper.types import RawJob
from services import llm_tracker

log = logging.getLogger(__name__)


class ExtractionSkipped(Exception):
    """Raised in strict mode when RawJob has neither description_html nor
    description_text. Default path swallows + marks `raw_meta`."""


# Conservative HTML strip — see plan 30 § D.4
_DROP_TAGS = (
    "script", "style", "noscript", "iframe", "svg", "img", "video", "audio",
    "canvas", "embed", "object", "form", "input", "button", "select",
    "textarea", "nav", "footer", "header",
)
_HTML_INPUT_CAP = 30_000   # post-strip cap; rarely trips after _strip_boilerplate


def _strip_boilerplate(html: str) -> str:
    """Drop nav/script/style/etc. + collapse whitespace.

    Returns plain text suitable for the extraction prompt. Token savings
    typically 30-60% on LinkedIn / Workday / Greenhouse detail pages.
    """
    soup = BeautifulSoup(html, "html.parser")
    for tag_name in _DROP_TAGS:
        for tag in soup.find_all(tag_name):
            tag.decompose()
    text = soup.get_text(separator="\n", strip=True)
    return re.sub(r"\n{3,}", "\n\n", text)


def _parse_posted_at(raw: str | None) -> datetime | None:
    """Permissive ISO 8601 parse; returns None on failure."""
    if not raw:
        return None
    try:
        return datetime.fromisoformat(raw.replace("Z", "+00:00"))
    except (ValueError, TypeError):
        return None


async def enrich_raw_job(
    session: AsyncSession | None,
    *,
    user_id: int,
    provider: LLMProvider,
    raw_job: RawJob,
    settings: Settings | None = None,  # reserved for 0.2.0.13
    strict: bool = False,
) -> RawJob:
    """Per plan 30 § D.3. Returns a new RawJob; never mutates the input."""

    # Pick the best input: prefer HTML for the boilerplate strip; fall back to
    # description_text if scraper already pre-stripped; else mark skipped.
    if raw_job.description_html:
        body_text = _strip_boilerplate(raw_job.description_html)
    elif raw_job.description_text:
        body_text = raw_job.description_text
    else:
        if strict:
            raise ExtractionSkipped(
                f"RawJob has no description_html or description_text "
                f"(source={raw_job.source.value}, external_id={raw_job.external_id})"
            )
        log.warning(
            "extraction_skipped no_html_or_text source=%s external_id=%s",
            raw_job.source.value, raw_job.external_id,
        )
        return _mark_skipped(raw_job, reason="no_html_or_text")

    body_text = body_text[:_HTML_INPUT_CAP]
    rendered = PROMPT.format(html=body_text)

    try:
        result = await llm_tracker.tracked_call(
            session=session,
            user_id=user_id,
            provider=provider,
            method="structured",
            prompt_name="extract_job",
            prompt=rendered,
            schema=JobExtraction,
            max_tokens=2048,
        )
    except LLMProviderError as exc:
        log.exception(
            "extract_job failed source=%s external_id=%s kind=%s",
            raw_job.source.value, raw_job.external_id, exc.kind,
        )
        if strict:
            raise
        return _mark_skipped(raw_job, reason=f"llm_failure:{exc.kind}")

    try:
        extraction = JobExtraction.model_validate(result.value)
    except Exception as exc:  # noqa: BLE001 — Pydantic ValidationError + edge cases
        log.exception(
            "extract_job schema_invalid source=%s external_id=%s",
            raw_job.source.value, raw_job.external_id,
        )
        if strict:
            raise LLMProviderError(
                f"extract_job schema validation failed: {exc}",
                kind="schema_validation",
            ) from exc
        return _mark_skipped(raw_job, reason="schema_invalid")

    return _merge_extraction_into_raw_job(
        raw_job=raw_job,
        extraction=extraction,
        model_name=provider.model_name,
    )


def _merge_extraction_into_raw_job(
    *,
    raw_job: RawJob,
    extraction: JobExtraction,
    model_name: str,
) -> RawJob:
    """Build a new RawJob from the seed + LLM extraction.

    LLM-authoritative fields (description_text, *_hint trio, location, posted_at)
    OVERWRITE the scraper-supplied values. Scraper-owned identity fields
    (source, external_id, source_url, board, url_type) are preserved verbatim.
    Scorer-required arrays (skills_required, criteria, tags) + salary bounds
    are merged into raw_meta for transport to _create_payload.
    """
    raw_meta = dict(raw_job.raw_meta)
    raw_meta["skills_required"] = extraction.skills_required
    raw_meta["criteria"] = extraction.criteria
    raw_meta["tags"] = extraction.tags
    if extraction.salary_min is not None:
        raw_meta["salary_min"] = extraction.salary_min
    if extraction.salary_max is not None:
        raw_meta["salary_max"] = extraction.salary_max
    if extraction.salary_raw:
        raw_meta.setdefault("salary_raw", extraction.salary_raw)
    raw_meta["description_extraction_model"] = model_name

    return RawJob(
        # Scraper-owned identity (preserved)
        source=raw_job.source,
        external_id=raw_job.external_id,
        source_url=raw_job.source_url,
        board=raw_job.board,
        url_type=raw_job.url_type,
        # User-visible — LLM may normalize over scraper's reads
        company_name=extraction.company_name or raw_job.company_name,
        position_title=extraction.position_title or raw_job.position_title,
        location_raw=extraction.location_raw or raw_job.location_raw,
        description_html=raw_job.description_html,
        description_text=extraction.description,
        # Time fields — LLM may overwrite from JD body
        posted_at_text=extraction.posted_at_text or raw_job.posted_at_text,
        posted_at=_parse_posted_at(extraction.posted_at) or raw_job.posted_at,
        # Salary raw stays available (preserved for diagnostics)
        salary_raw=extraction.salary_raw or raw_job.salary_raw,
        # *_hint trio — LLM authoritative read OVERWRITES scraper guess
        remote_policy_hint=extraction.remote_policy,
        visa_restriction_hint=extraction.visa_restrictions,
        seniority_level_hint=extraction.seniority_level,
        # Meta carries scorer-required arrays + model attribution
        raw_meta=raw_meta,
    )


def _mark_skipped(raw_job: RawJob, *, reason: str) -> RawJob:
    """Append `extraction_skipped` marker to raw_meta; return new RawJob unchanged otherwise."""
    raw_meta = dict(raw_job.raw_meta)
    raw_meta["extraction_skipped"] = reason
    return raw_job.model_copy(update={"raw_meta": raw_meta})


__all__ = ["ExtractionSkipped", "enrich_raw_job"]
```

**Why `_merge_extraction_into_raw_job` constructs a new `RawJob` rather than `model_copy(update={...})`.** Two reasons: (1) `model_copy(update=...)` skips field-level validation in Pydantic v2; passing through the constructor re-validates and catches any drift where the LLM returned an enum string the schema doesn't accept; (2) explicit construction makes the OVERWRITE vs PRESERVE semantics of every field obvious to the reader.

### D.6 — Fallback / degradation matrix

What happens when extraction fails. Spelled out so reviewers can verify the defaults match operator expectations.

| Failure mode | Default path (`strict=False`) | Strict path (`strict=True`) | Marker in `raw_meta` |
| --- | --- | --- | --- |
| `RawJob.description_html` AND `description_text` both `None` | Return `raw_job` unchanged with `raw_meta["extraction_skipped"] = "no_html_or_text"`. Scraper continues. | Raise `ExtractionSkipped`. | `"no_html_or_text"` |
| LLM provider unconfigured (no `ANTHROPIC_API_KEY` etc.) — `Settings.llm_provider` is None | `llm_tracker.tracked_call` raises `LLMProviderError(kind="auth_required")`. Default catches, logs, returns marked-skipped RawJob. | Re-raises. | `"llm_failure:auth_required"` |
| LLM provider returns invalid JSON / Pydantic `ValidationError` | Caught, logged, marked-skipped. After 1 tracker-internal retry per `llm_tracker._RETRY_ATTEMPTS["schema_validation"]`. | Wraps and re-raises as `LLMProviderError(kind="schema_validation")`. | `"schema_invalid"` |
| LLM 429 / rate-limit | `tracked_call` retries up to 3× with exponential backoff (per existing `llm_tracker` policy). If still failing, default returns marked-skipped. | Re-raises after retries. | `"llm_failure:rate_limit"` |
| LLM 500 / timeout | `tracked_call` retries once (timeout) or fails through to `fallback_provider` if configured (provider_error). Default catches the eventual `LLMProviderError`, marks skipped. | Re-raises. | `"llm_failure:timeout"` or `"llm_failure:provider_error"` |
| Insufficient fields post-extraction for `upsert_job` (e.g., `extraction.description == ""`) | Pydantic `extra="forbid"` + `min_length=1` catches at validation time → falls through to "invalid JSON" path. | Same. | `"schema_invalid"` |
| `description_html` present but `_strip_boilerplate` returns empty (page was just `<script>` tags) | Body text is `""`; LLM input is empty; LLM returns garbage / blank → schema validation fails (`description: str = Field(min_length=1)`). Default marks skipped. | Re-raises. | `"schema_invalid"` |

**Why `strict=False` is the default for site scrapers.** Per `SCRAPER_BASE.md § H.1` (Tier 1 per-listing errors): "The scraper subclass's `scrape()` catches per-URL parse failures, per-URL 429s, per-URL timeouts. Appends to `self._errors[]` and continues iterating." Extraction failures fit Tier 1: one bad JD should NOT fail the whole scrape run. The marker in `raw_meta` is visible to operators via `Job.raw_meta` JSONB.

**Why `strict=True` exists.** `+ Add by URL` (Phase 6) needs strict mode — if the user pasted a URL and the LLM choked, the UI must show an error toast rather than silently store an empty Job. The route handler at `/api/v1/jobs` (Phase 2.0.11) calls `enrich_raw_job(..., strict=True)` and handles `LLMProviderError` / `ExtractionSkipped` with a 422.

### D.7 — Integration with `0.2.0.07` (per-site scrapers)

This plan ships the extraction service standalone; it does NOT modify `scraper_service.run_scraper` (which lives at `src/services/scraper_service.py` per the locked `SCRAPER_BASE.md § F` contract). The integration point for `0.2.0.07` site scrapers is **inside the scraper subclass's `scrape()` generator** — the scraper yields enriched RawJobs, not raw ones.

**Why integration lives in scraper subclasses, not in `run_scraper`.**

- **Composition over orchestrator-feature-creep.** `run_scraper`'s job is open-stream-finalize the `JobScrapeRun` lifecycle. Adding "and call the LLM between yield and upsert" muddies that contract.
- **Some sources don't need extraction.** `JobSource.RSSHUB` feeds typically arrive with clean `<title>` + `<description>` from RSS; the LinkedIn RSShub-based scraper may skip extraction entirely. `JobSource.MANUAL` (`+ Add by URL` route) drives extraction from the route, not from scraper_service. Forcing extraction at the orchestrator layer denies these exemptions.
- **Per-source prompt tuning is a future-future feature.** When `0.2.0.10` cron firing brings rate-limiting + per-source budget accounting, some scrapers might prefer a cheaper provider for high-volume sources. Service-layer call sites let each scraper pick.

**The contract for `0.2.0.07` scraper authors.** Each per-site scraper invokes `enrich_raw_job` immediately after building the seed `RawJob` from listing-card HTML + detail-page fetch:

```python
# Example signature for 0.2.0.07 LinkedinScraper (NOT in scope for this plan,
# but documented here so 0.2.0.07's plan author has the contract locked):

class LinkedInScraper(ScraperBase):
    source = JobSource.LINKEDIN
    board = ApplicationBoard.LINKEDIN

    async def scrape(self, query: ScrapeQuery) -> AsyncIterator[RawJob]:
        async for url in self._iter_listing_urls(query):
            try:
                html = await self._client.fetch_html(url)
                seed = self._build_seed_raw_job(url, html)  # scraper-known fields
                if seed.description_html:
                    seed = await job_extractor.enrich_raw_job(
                        session=self._session,
                        user_id=self._user_id,
                        provider=self._provider,
                        raw_job=seed,
                        # strict=False default — survive per-listing extraction failures
                    )
                yield seed
            except (rate_limit, timeout, parse_failure) as e:
                self._errors.append(f"stage=detail url={url} kind=... msg={e}")
                continue
```

This requires `ScraperBase.__init__` to accept `session` + `user_id` + `provider` so subclasses have what they need to call `enrich_raw_job`. **That signature change is OUT OF SCOPE for this plan** — it lands as part of `0.2.0.07` and is documented in the § Open questions OQ.2 as the recommended path.

### D.8 — Prompt design

The prompt template in `src/llm/prompts/extract_job.py` (REPLACED) needs to:

1. Reference the 14 fields of `JobExtraction` explicitly (not the 17 fields of `RawJob` — the LLM doesn't see scraper-owned fields).
2. List the enum values for `RemotePolicy` + `VisaRestriction` + `SeniorityLevel` so the LLM emits valid strings (Pydantic enum validation catches drift, but explicit prompt guidance reduces retry cost).
3. Be agnostic to source — the same prompt runs against LinkedIn / Workday / Greenhouse stripped-HTML bodies. Per-source prompt variants are a future-future YAGNI.

**Skeleton.**

```python
# src/llm/prompts/extract_job.py (REPLACED)

PROMPT = """Extract structured job information from this job description.

Input:
{html}

Return a JobExtraction with these fields:

- company_name: Hiring company name. Normalize ("Anthropic, PBC" -> "Anthropic"; "Stripe Inc." -> "Stripe").
- position_title: Job title. Normalize abbreviations ("Sr. SWE" -> "Senior Software Engineer"; "SDE II" -> "Software Engineer II").
- location_raw: Job location as written (e.g. "San Francisco, CA" or "Remote — US" or "London, UK"). null if absent.
- posted_at_text: Verbatim "posted X days ago" / "posted on Jan 5, 2026" string if present. null if absent.
- posted_at: ISO 8601 date if you can derive it from posted_at_text (e.g. "Posted 3 days ago" + today -> ISO date). null if you can't.
- salary_raw: Verbatim salary string from the JD (e.g. "$180k-$240k base + equity"). null if absent.
- salary_min: Parsed lower bound in USD/year. null if missing or not USD.
- salary_max: Parsed upper bound in USD/year. null if missing or not USD.
- remote_policy: ONE of:
    - "remote" — fully remote
    - "hybrid" — 1-3 days in office expected
    - "onsite" — 4-5 days in office
    - "unknown" — JD doesn't say (default)
- visa_restrictions: ONE of:
    - "us_citizen_only" — JD requires US citizenship
    - "green_card_required" — JD requires green card / permanent residency
    - "sponsorship_available" — JD explicitly offers H1B / visa sponsorship
    - "not_mentioned" — JD does not say (default)
- seniority_level: ONE of: "entry" / "mid" / "senior" / "staff" / "principal" / "exec" / "unknown". null if you can't tell.
- description: Plain-text job description, with HTML stripped, sections preserved as headings ("Required:", "Nice to have:", "About the role:"). Trim boilerplate footers / equal opportunity statements.
- criteria: list of hard requirements ("5+ years experience", "Bachelor's degree in CS", "must be authorized to work in US"). Concise; one bullet per criterion.
- skills_required: list of named skills / technologies / frameworks ("Python", "Kubernetes", "PostgreSQL", "Distributed systems"). Lowercase singular nouns where natural.
- tags: list of broad categorical tags from this fixed vocabulary: ["ai-ml", "backend", "frontend", "devops", "data-eng", "genai", "leadership", "platform", "product"]. Choose 2-4 tags. Use only this vocabulary.

If a field is missing or ambiguous in the JD, use the schema's documented default rather than guessing.
"""
```

**Why the fixed `tags` vocabulary.** `AGENTS.md § Key Conventions § Resume/CV Data Model` lists the 9-tag bullet vocabulary. The same vocabulary applies to Jobs so the scorer (`services/scorer.py`) can compute set-overlap between bullet-tags and job-tags. The prompt enforces it explicitly because LLMs love to invent new tags otherwise.

**Why `description` is the LLM-normalized plain text.** Plan 27 § D explicitly says `Job.description` is the scorer-readable JD body. The scraper's `description_text` field on `RawJob` is best-effort scraper-side stripping; the LLM-normalized version (consistent section headers, trimmed boilerplate) is what scoring + UI consume.
