# 49 · 0.2.0.16 — Self-host first-run walkthrough

## Goal

Two surfaces ship: (a) `README.md` § Configuration + § Operations new sub-sections walking the first-time self-hoster through scraper config (5 env vars + LinkedIn/Indeed keywords + rate-limit JSONB) + a "verify scrapers run" recipe; (b) `Settings · Sources` sub-tab fully rewritten from its current 2-section stub into a 6-row per-source panel showing source name + Lucide icon + configured-vs-unconfigured indicator + last-scrape-run timestamp + status chip + "Configure" deep-link. No new on-disk artifact, env var, CLI command, port, or schedule introduced. Sole net-new partial: `components/_source_row.html` (registered in `docs/design/COMPONENTS.md` § Settings → group count 7 → 8 + total 88 → 89).

## Why

ROADMAP row `0.2.0.16` (line 210, HIGH priority, filed 2026-05-20 via #142 release-readiness audit). First-time self-hoster currently lands at `/discover`, queue is empty, no UI tells them why. Substrate is rich — `Settings.sources_enabled`, `source_schedules`, `linkedin_keywords`, `linkedin_location`, `indeed_keywords`, `indeed_location`, `workday_companies`, `scraper_rate_limits`, `consecutive_scrape_failures` all shipped 0.2.0.10 / 0.2.0.13; `JobScrapeRun` rows exist; `config.greenhouse_companies` / `lever_companies` / `ashby_companies` / `scraper_rsshub_url` env-load. But: (1) README never tells the operator any of this exists, (2) `_settings_sources.html` currently renders only `sources_enabled` toggles + a `workday_companies` chip section — no last-run state, no LinkedIn/Indeed keywords, no Greenhouse/Lever/Ashby env-presence indicators, no Indeed at all. This plan closes both gaps in one PR and graduates the design contract for the Sources tab so future enhancements (per-source charts in 0.2.5.04; operator scheduler endpoints in 0.2.0.10a) compose against a stable surface. Composes with — does not block on — 0.2.0.10a (operator scheduler `/api/v1/scheduler/jobs` endpoints; this plan deep-links to the source-specific scheduler control surface but does not implement it) and 0.2.5.04 (full scrape-run history table; this plan surfaces only the latest run per source).

## Proposal

### A · Decision — where rate-limit JSONB edits live (option matrix)

Three viable surfaces for editing `Settings.scraper_rate_limits` (the nested `{"linkedin": {"rpm": 0.4, "delay_lo": 1.0, "delay_hi": 3.0}, ...}` JSONB shipped in 0.2.0.13). This plan must pick one, even though the edit UI is itself out of scope.

| Option | Capability | Cost (this plan) | Risk | Maintenance | Lock-in |
|---|---|---|---|---|---|
| **A1 — Inline on Sources panel** | Edit rate limits per-source in the same row that shows configured/last-run state | +200 LOC partial + per-row PUT endpoint + 4 input validators per row | Form complexity per row balloons panel into a 6×4 input grid. Mixes read-only telemetry (last-run) with mutable config (rate limit) in one UI surface. | Each future per-source axis added (rotation policy, undetected-adapter toggle) pushes inline form deeper | High — once inline, hard to extract to a dedicated panel without breaking deep-links |
| **A2 — Separate `/settings/rate-limits` panel (recommended)** | Dedicated panel; Sources panel shows resolved value read-only + "Configure" link to A2 panel | +0 LOC this plan; A2 panel ships in a new ROADMAP row `0.2.5.05` | Slightly more click depth for the operator (Sources → Rate limits) — acceptable; rate-limit tuning is rare | Each future per-source config axis composes into A2 panel — Sources stays a status surface | Low — Sources panel API doesn't depend on A2 panel existing |
| **A3 — API-only (`PUT /api/v1/settings/sources` with full JSONB body)** | Already implemented as stub; operator edits via `curl` or future API console | +0 LOC; defers UI indefinitely | Operator-facing utility belongs in the UI, not behind a JSON POST. First self-host audit (#142) explicitly cites Sources panel as the canonical surface. | Same as A2 from this plan's POV; A2 is the eventual UI for A3 | None — A3 is the always-present backstop |

**Recommendation: A2 — separate `/settings/rate-limits` panel (deferred).** Sources panel stays a status + entry-point surface. Rate-limit JSONB editor ships in a follow-up row (`0.2.5.05`, filed during this plan's BOOKKEEPING). The Sources panel's "Rate limit" cell renders the resolved value (read-only `rpm / delay_lo–delay_hi s`) with a "Configure →" link to `/settings/rate-limits`. Until A2 ships, the link points to a `<details>` popover that shows the JSONB-shape and the env-var equivalents (none — `scraper_rate_limits` is DB-only) plus a one-line "Editable via `PUT /api/v1/settings/sources` with `scraper_rate_limits` body until `0.2.5.05` ships". This degrades cleanly: the Sources panel is complete in itself; the rate-limit editor composes on top later without restructuring.

Rationale: rate-limit tuning is rare (operator hits the panel once-per-source after observing 429s from telemetry); mixing it with the always-visible Sources status panel raises the cognitive cost of the every-visit case to optimize the once-per-year case. Per `manager.md § Doc-sizing matrix`, this plan stays MEDIUM (one panel rewrite + 6 README sub-sections) instead of LARGE (panel rewrite + editor + validators).

#### C.1 · § Configuration → new sub-section "Scraper sources"

**Sub-section contents** (~70 lines of markdown, including code blocks):

```markdown
### Scraper sources (plan 33 / 0.2.0.07, plan 35 / 0.2.0.10, plan 38 / 0.2.0.13)

Each scraper is configured through a mix of env vars (company watchlists,
RSShub fallback URL) and per-user `Settings` rows (LinkedIn/Indeed keywords,
per-source enable toggle, rate-limit overrides). The split: env vars
hold operator-deployment-wide config (the company list a Workday tenant
follows is a deployment concern); the Settings row holds per-user search
intent (which keywords this user wants LinkedIn searched for).

**Per-source config matrix:**

| Source | Companies (env) | Keywords (DB) | Location (DB) | Schedule (DB) | Rate limit (DB) |
|---|---|---|---|---|---|
| LinkedIn | — | `Settings.linkedin_keywords` | `Settings.linkedin_location` | `Settings.source_schedules["linkedin"]` (cron) | `Settings.scraper_rate_limits["linkedin"]` |
| Workday | `WORKDAY_COMPANIES` | — | — | `Settings.source_schedules["workday"]` (cron) | `Settings.scraper_rate_limits["workday"]` |
| Greenhouse | `GREENHOUSE_COMPANIES` | — | — | `Settings.source_schedules["greenhouse"]` (cron) | `Settings.scraper_rate_limits["greenhouse"]` |
| Lever | `LEVER_COMPANIES` | — | — | `Settings.source_schedules["lever"]` (cron) | `Settings.scraper_rate_limits["lever"]` |
| Ashby | `ASHBY_COMPANIES` | — | — | `Settings.source_schedules["ashby"]` (cron) | `Settings.scraper_rate_limits["ashby"]` |
| Indeed | — | `Settings.indeed_keywords` | `Settings.indeed_location` | (IntervalTrigger 90m, fixed) | `Settings.scraper_rate_limits["indeed"]` |
| LinkedIn (RSShub fallback) | — | (reuses `linkedin_keywords`) | (reuses `linkedin_location`) | (same cron as LinkedIn) | (no rate limit; RSShub server) |

**Operator workflow:**

1. **Pick which sources to enable.** All 6 default to enabled; toggle off
   on the Settings · Sources sub-tab in the UI for any source you don't
   want to scrape.
2. **For Workday / Greenhouse / Lever / Ashby:** set the company watchlist
   in `.env` (CSV, e.g. `GREENHOUSE_COMPANIES=anthropic,scale,databricks`).
   Cron skips a source silently when its watchlist is unset. **Restart the
   app** after editing `.env` — `pydantic-settings` loads env once at boot.
3. **For LinkedIn / Indeed:** set keywords + location in the UI (Settings ·
   Sources panel, "Configure →" link per source — surfaces the per-source
   keywords/location editor; landing here until `0.2.5.06` ships writable
   inputs).
4. **For LinkedIn RSShub fallback:** set `SCRAPER_RSSHUB_URL` in `.env` to
   your RSShub instance base URL (e.g. `https://rsshub.luminolab.net`).
   This is a fallback path used by `LinkedinRSScraper`; the primary
   `LinkedinScraper` does not use it.

**Verifying a source is configured:**

The Settings · Sources sub-tab in the UI is the canonical surface — each
row shows configured/unconfigured + last-scrape-run timestamp + last run
status. From the CLI / API:

```bash
# Read current Settings JSON (requires authed session cookie):
curl -b cookies.txt http://localhost:8000/api/v1/settings/scraper-config
```

**Anti-detection / rate limiting** is documented in
`docs/design/SCRAPER_BASE.md § G`. Per-source overrides live in
`Settings.scraper_rate_limits` (JSONB shape:
`{"linkedin": {"rpm": 0.4, "delay_lo": 3.0, "delay_hi": 7.0}, ...}`).
The Sources panel surfaces the resolved value read-only; the writable
editor lands at `/settings/rate-limits` per `0.2.5.05` (deferred).
```

#### C.2 · § Operations → new sub-section "Verify scrapers run"

Insert position: between `### Rotating SECRET_KEY` and `### Upgrading from 0.1.x with a populated vault` (lines 415-429). Sub-section sits just below the SECRET_KEY rotation recipe; topically adjacent (both are post-config sanity checks).

**Sub-section contents** (~40 lines):

```markdown
### Verify scrapers run (plan 35 / 0.2.0.10, plan 49 / 0.2.0.16)

After configuring `.env` + per-user keywords (§ Scraper sources above),
verify the chain end-to-end:

1. **Check the Settings · Sources sub-tab** (`/settings/sources`). Each
   row shows: configured/unconfigured (env-based for company-list sources;
   DB-based for LinkedIn/Indeed keywords); last-scrape-run timestamp +
   status chip; "Configure →" deep-link. A source row marked
   "Not configured" means the watchlist (Workday / Greenhouse / Lever /
   Ashby) or keywords (LinkedIn / Indeed) is empty — cron will skip it
   silently.
2. **Trigger one-off run** via the API:

   ```bash
   # Requires authed session + CSRF (operator scheduler endpoints — 0.2.0.10a)
   curl -b cookies.txt \
        -H "X-CSRF-Token: $(jq -r .csrf cookies.txt)" \
        -X POST \
        http://localhost:8000/api/v1/scheduler/jobs/scraping.linkedin/run
   ```

   (The `/api/v1/scheduler/*` endpoints ship in `0.2.0.10a`; until then,
   cron firings on the BACKEND.md § I.1 default schedule are the only
   trigger — LinkedIn every 30 min, others hourly, Indeed every 90 min.)

3. **Check `/discover`** for new jobs. Empty queue with sources marked
   "configured" + last-run "SUCCESS" means the source returned zero
   matching listings — try broader keywords or add more companies.
4. **Check the Sources panel** for last-run timestamp + status. Status
   chips: `SUCCESS` (emerald), `PARTIAL` (amber — some listings failed
   extraction), `FAILED` (rose — top-level scrape error; the
   consecutive-failure counter is incrementing, Discord admin alert fires
   at 3), `TIMED_OUT` (rose), `RUNNING` (indigo). The Discover queue
   surfaces jobs across all sources; the per-source counter lives only on
   the Sources panel.
```
