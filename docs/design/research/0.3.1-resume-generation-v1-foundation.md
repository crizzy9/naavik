## A · Executive summary + 3 critical decisions

The current `0.3.1` ledger has 4 rows (`.01` bullet selection → `.02` bullet trim → `.03` Typst page-count loop → `.04` one-click endpoint). That ledger is correct as a baseline but **leaves four gaps** the user-locked SOTA brief explicitly requires:

1. **ATS parser fidelity.** Typst defaults to PDF (1.7); we have one `onepage.typ` template the existing test corpus has never validated against the 9 named ATS. Without a parser-fidelity stage, we can't know whether the PDF actually reaches a human reviewer.
2. **AI-detection evasion.** The current `trim_bullet` + `draft_cover_letter` prompts produce text that — per Originality.ai's own published benchmark of cover-letter detection rates and the Stanford 61.3% false-positive rate — will pattern-match as AI-generated to 65% of Fortune 500 ATS-integrated detectors. Em-dashes, "delve," uniform sentence length, low perplexity.
3. **Recruiter pre-screen optimization.** The Ladders 2012 eye-tracking + 2018 update + InterviewPal 2025 follow-up converge on: name + most-recent-title + dates + education get 80% of attention in the first 6-11 seconds. The current `onepage.typ` has the name + headline + contact line in the header block but doesn't pin the strongest bullet first in Experience, doesn't front-load JD-required keywords in the Skills section, and doesn't emit a "headline" line that includes years-of-experience + sponsorship signal in one scannable string.
4. **Cover letter generation.** `draft_cover_letter` exists as a skeleton but produces generic 4-paragraph output without hiring-manager-name personalization (50% callback uplift per TopResume + SHRM), without the JD's pain-point hook (25% callback uplift per Liz Ryan pain-letter studies), and without voice-grounding from the user's own writing.

**Three critical decisions for the user:**

1. **Ship an ATS-friendly Typst template variant + open-source parser-fidelity validator (TIER-1 legitimate optimization).** Add `src/typst/templates/onepage_ats.typ` (strict single-column, plain `•` bullets, standard section headings exactly matching the ATS allowlist, MM/YYYY dates, no ligatures, embedded Helvetica/Arial, Typst PDF/A-2b output mode). Add `src/services/ats_parser_fidelity.py` that runs the generated PDF through 2-3 open-source parsers (pyresparser / OpenResume / pdfplumber-+-heuristics) and asserts the canonical fields (`name`, `email`, `phone`, `most_recent_title`, `most_recent_company`, `start_date`, `end_date`, `education[0].institution`) round-trip. Reject + retry with a different template OR surface to user as warning. **Recommended: fail-soft (warn-but-ship) for v1; fail-hard (retry-with-template-B) when we have 2+ templates.** See § B for the parser-by-parser landscape.

2. **Layer-1 + Layer-2 AI-detection evasion (TIER-1 legitimate, default-on) + optional Layer-3 detector roundtrip (TIER-2 gray-area, opt-in).** Voice-grounding via 2-5 user-writing samples (the `Profile.summary_full` + any past cover letters in `Profile.notes` if present) → injection of natural sentence-length variance + em-dash removal + AI-tell vocabulary blocklist + Flesch reading-ease match. Optional Originality.ai API roundtrip ($179/mo Enterprise tier OR $30 PAYG for 30k words) before persisting. **Tier-3 (homoglyph / zero-width-character injection, adversarial paraphrasing) surfaced + explicitly flagged blacklist-risk + NOT default; user opt-in only with informed-consent dialog.** See § C for the full TIER-1/2/3 tree + ethics framing.

3. **Grow 4 rows → 8 rows; split into `0.3.1` (substrate, ATS-passable PDF) + `0.3.1+a` (stylistic SOTA: evasion + recruiter optimization + cover letter SOTA).** The current 4 rows ship a one-click PDF that compiles. The new 4 rows ship the SOTA layer. `0.3.1` is 4-5 dev-days; `0.3.1+a` is another 5-7 dev-days. **Recommended: ship `0.3.1` first as the user-visible payoff; then ship `0.3.1+a` as the "real-world success-rate" follow-on once we have an end-to-end loop to measure against.** See § H for row breakdown.

**Total revised 0.3.x scope:** existing 0.3.0 (6 rows shipped) + revised 0.3.1 (4 rows substrate) + new 0.3.1+a (4 rows SOTA) + 0.3.2 (4 rows UI/analytics) + 0.3.3 catch-all (4 rows already filed) = **22 rows** across 4 sub-releases (down from current ROADMAP's 18 if we add 4 rows; up from current 0.3.1's 4 if we hold sub-release count constant).

### B.2 PDF format choice — PDF/A-2b vs raw PDF vs DOCX

**Typst's PDF capability (verified via Typst docs):**
- Default output: PDF 1.7.
- **PDF/A-1b** (ISO 19005-1; basic conformance level; based on PDF 1.4): supported via `--pdf-standard a-1b` on `typst compile`.
- **PDF/A-2b** (ISO 19005-2; based on PDF 1.7): supported via `--pdf-standard a-2b`.
- **PDF/A-3b** (ISO 19005-3; allows file attachments): supported.
- **PDF/A-4** (ISO 19005-4; based on PDF 2.0): supported.
- **PDF/A-1a accessible variant** (tagged-PDF; for screen readers): supported.

**Recommendation: PDF/A-2b** for our `onepage_ats.typ`. Rationale:
- PDF/A-2b is the industry archival default (basis: PDF 1.7, the same version used by virtually all modern ATS).
- It forces fully-embedded fonts (no font substitution at parse time; critical for Helvetica being available everywhere).
- It disallows embedded JavaScript (security boundary; some ATS sandbox PDFs).
- It does NOT impose accessibility tagging (which `a-1a` does, and which Typst's tag emission is still maturing); accessibility tagging is a Phase 6+ enhancement.
- PDF/A-2b vs raw PDF parse difference is statistically zero in the ATS papers — but PDF/A discipline forces font embedding + ligature awareness during template authoring, which is the real win.

**DOCX as fallback** for Taleo-/SuccessFactors-heavy job universes — out of scope for `0.3.1` (Typst → DOCX is non-trivial; defer to `0.3.3` catch-all as a row if user demand surfaces).

### B.3 Section headings — exact-string allowlist

Cross-ATS allowlist (every name appears in ≥ 3 ATS docs):
- **`Work Experience`** or **`Professional Experience`** or **`Experience`** (Workday + Lever + Greenhouse all explicitly recognize all three; Taleo prefers `Work Experience`).
- **`Education`** (universal).
- **`Skills`** or **`Technical Skills`** (Workday + Greenhouse + Lever recognize both).
- **`Certifications`** (universal).
- **`Awards`** (universal).
- **`Volunteer Experience`** (universal).
- **`Projects`** (less-recognized; ATS-passable per Greenhouse; use cautiously — current `onepage.typ` already emits it).

**Anti-pattern (current `onepage.typ` is clean on this):** `Summary` is recognized — current template emits it. Don't change to "About" or "Career Journey."

### B.4 Bullet markers — what survives PDF→text extraction

Cross-ATS safe list:
- **`•`** (U+2022 BULLET) — universal. Typst's `bullet_line` macro already uses this. Pass.
- **`-`** (ASCII hyphen-minus U+002D) — universal. Safe.
- **`*`** (ASCII asterisk U+002A) — universal but renders as `*` in PDF output (less visual polish).

Reject:
- **`★ ➤ ▸ ✓ ◆ ●`** — iCIMS flags as `_flagsForReview` (bullet normalization); Taleo skips line; Workday treats as garbage character.
- **`o`** (ASCII letter "o" as bullet) — gets concatenated into adjacent text.
- **`–`** (en-dash U+2013) or **`—`** (em-dash U+2014) as bullet — readers don't expect this; some ATS skip.

**`onepage_ats.typ` recommendation: explicit `•` only; no fallback chain.** Current `onepage.typ` already uses `•` — preserve.

### B.5 Date formats — what parses reliably

Cross-ATS safe formats:
- **`Jan 2024 – Present`** — universal (with full month name OR three-letter abbreviation). Current `onepage.typ` uses `%b %Y` → `Jan 2024` format. Pass.
- **`01/2024 – Present`** — universal but slightly less recruiter-friendly.
- **`January 2024 – December 2023`** — full names; safer on Taleo + JazzHR.

Reject:
- Year-only (`2024 – Present`) — Workday + Lever can't compute years-of-experience.
- `Current` / `Ongoing` / `Now` — some ATS reject; `Present` is the universal-safe sentinel.
- Inconsistent formats within one resume (`January 2024` + `Jul 2023`) — most ATS fall back to "best-effort" extraction; some return null.

**Current `onepage.typ` uses `%b %Y` → "Jan 2024" + "Present" — pass on this dimension.**

### B.6 Two-page rule for senior engineers

Owner profile is **Shyam Padia, 8+ years experience (5.5+ at Intuit)** — solidly in the "2-page is acceptable" zone per all 2026 sources. But the existing `onepage.typ` enforces 1-page (with overflow retry-drop). Decision: **stay 1-page for `0.3.1`**. Justifications:
- Most ATS read the full PDF (page count doesn't affect parser fidelity).
- Recruiter eye-tracking shows page 1 gets 80% of attention; page 2 is "deepen the case" only.
- "475-600 word resumes get 8.2% interview rate" (~double the rate of outside-this-range per Wobo) — 1-page constrains to ~500 words naturally.
- Adding 2-page support is `0.3.3` material (typst template variant; selection logic).

### B.7 Skills section format

Cross-ATS safe pattern (current `onepage.typ` already uses this — pass):
```
Skills:
  Programming: Python, TypeScript, Go, Rust
  Cloud: AWS (Lambda, S3, ECS), GCP
  ML/AI: PyTorch, TensorFlow, scikit-learn, Pinecone
```
- Category prefix (bold): `Programming:` / `Cloud:` / `ML/AI:` — JobScan + Greenhouse recognize category-headed lists.
- Comma-separated items within category — universal.
- AVOID: tag-cloud visual blocks; rated star icons next to skill names (✓✓✓✓); pie-chart skill bars.

**Tuning for SOTA: front-load JD-required skills in the FIRST category line.** If the JD requires "Python + PyTorch + GCP," the resume's first Skills line should lead with those three exact keywords. This is keyword-density-by-placement (§ D.5), not keyword-stuffing.

## C · AI-detection evasion — TIER-1 / TIER-2 / TIER-3 + ethics framing

### C.1 Ethics framing (read FIRST)

**Naavik never lies about credentials.** The AI is *tailoring* what the user actually did into the language the JD speaks. Anti-detection is about getting **human-with-AI-assist past false-positive screening**, NOT pretending no AI was used.

**Key context:**
- **Stanford Liang et al. 2023:** 61.3% false-positive rate on non-native-English TOEFL essays vs near-zero on native-English. Academic + medical writing flagged 2-4× more than creative writing. **AI detectors are unreliable enough that lossy human-written cover letters get false-flagged anyway.**
- **2026 industry consensus** (per WasItAIGenerated + Gem + AI Career Lab): the meaningful distinction is **AI-assisted writing of accurate information** (legitimate; ATS vendors like Oracle invite candidates to use ATS-integrated AI) vs **AI-fabricated credentials** (fraud; 18 USC §1001 felony; FCRA implications; permanent blacklist).
- **65% of Fortune 500 companies** use AI-content detection in their screening (humanizerai.com aggregate). **62% of resumes flagged are rejected** (resumegeni.com). 33.5% of hiring managers say they can spot AI-generated content in <20 seconds (gem.com).
- **No major ATS itself runs AI-content detection** (Workday/Greenhouse/iCIMS/SSF use AI for *matching*, not for *who wrote it*). But integrators (Originality.ai, Copyleaks via Workday Marketplace, Turnitin Workforce edition) wire detection in via webhook.

**Naavik's stance:** TIER-1 default-on (legitimate optimization; voice-grounding + AI-tell removal). TIER-2 opt-in with cost-cap awareness. TIER-3 surfaced + warned + NOT default. The user owns the choice.

### C.2 What AI detectors actually measure

Cross-source (GPTZero / Originality.ai blog / Copyleaks / academic):

| Detector | Primary signal | Secondary signals | Architecture | 2026 false-positive rate | API access |
|---|---|---|---|---|---|
| **GPTZero** | Perplexity + burstiness | Sentence-length variance + lexical diversity + word-rarity | Deep classifier trained on 600M+ documents | 9.2% on non-AI text | Yes ($14.99/mo+) |
| **Originality.ai** | Proprietary multi-feature ensemble (perplexity + n-gram + style fingerprint + watermark detection) | Self-reported 99%+ on GPT-3.5, drops to 31.7% on GPT-5 detection per their own Chicago Booth 2026 benchmark | Closed proprietary | 2.1% | Yes ($179/mo Enterprise; $30 PAYG 30k words = ~$0.001/cover-letter) |
| **Copyleaks** | Proprietary multi-feature (probably similar to Originality + plagiarism-DB cross-reference) | Closed | Closed | 5.8% | Yes (commercial) |
| **Turnitin (workforce edition)** | Sentence-level entropy + semantic coherence (v4 in 2026) | Fine-tuned on student-essay corpus; may not generalize well to job-app text | Proprietary | 4% (claimed; academics dispute) | Yes (enterprise-only) |
| **Winston AI** | Proprietary | — | Proprietary | ~10% | Yes |

**Key insight:** the underlying signal across all of them is perplexity + burstiness + style-fingerprint. Defeat those three and you defeat ~90% of detection signal.

### C.3 TIER-1: Legitimate optimization (default-on; ship in `0.3.1+a`)

These are the techniques the academic literature + practitioner consensus agree are "good writing" — not "evasion."

**T1-A. Voice grounding from user's writing samples.**

Per arxiv 2509.14543 (Bao et al. 2025) + arxiv 2604.24444 (Post-Editing LLM-Generated Text for Personal Style) + arxiv 2604.26460 (Theory-Grounded Evaluation):
- LLMs plateau at 4-5 demonstrations for style imitation (sample efficiency).
- Style imitation works well on structured formats (cover letters fit this); plateaus on informal blogs.

**Implementation:** Add to the prompt a 2-5 sample block sourced from:
- `Profile.summary_full` (the user's own first-person summary; usually a paragraph the user wrote)
- `Profile.summary_short` (one-liner the user wrote)
- (optional) Past cover letters: if the user has uploaded any past cover letters during `0.1.0.19` extraction OR pasted past samples via a new Profile "Writing samples" textarea, include them as samples.
- (optional) `Bullet.text` of the highest-tagged-relevance bullets (a writer's experience descriptions are voice-revealing).

Prompt pattern (extends `draft_cover_letter.py`):
```python
PROMPT = """Draft a cover letter for this candidate × job pair.

THE CANDIDATE'S OWN VOICE — Use these samples to ground style:
{user_writing_samples}  # 2-5 paragraphs the user wrote

Match the user's sentence-length variance (avg sentence length: {avg_sentence_length:.1f} chars; std dev: {std_sentence_length:.1f}).
Match the user's reading-ease (Flesch: {flesch_reading_ease:.1f}).

Avoid AI-tell vocabulary and structures:
- Do NOT use: "delve", "leverage", "robust", "intricate", "in conclusion", "furthermore", "moreover", "stark", "navigating", "underscore", "harness the power".
- Do NOT use em-dashes ( — ); use commas, periods, or rephrase.
- Do NOT open paragraphs with "I am excited" / "I am writing to express" / "It is with great enthusiasm".
- AVOID balanced clauses ("X is critical, and Y is equally critical").
- VARY sentence length; don't write three medium sentences in a row.

CANDIDATE PROFILE:
{profile}

JOB:
{job}

TONE: {tone}
...
"""
```

**~200 LOC** added to `draft_cover_letter.py` (style-feature extractor + sample selection) + ~100 LOC in `services/voice_grounding.py` (compute Flesch score + sentence stats via `textstat` library — MIT-licensed).

**T1-B. AI-tell vocabulary blocklist + em-dash removal.**

A curated list of AI-overused tokens to forbid in prompt + post-process strip:
- `delve`, `delves`, `delving` — top em-dash equivalent for vocabulary (Hacker News 45045897, em-dash effect LinkedIn post)
- `leverage`, `leveraging`, `leveraged` (overuse in business writing now reads AI)
- `robust`, `seamless`, `crucial`, `pivotal`, `intricate`, `comprehensive`, `multifaceted`
- `landscape` (as in "the evolving landscape of...")
- `navigate`, `navigating` (overused)
- `tapestry` (AI generative-art tic)
- `dive deep into`, `it's important to note that`, `it goes without saying`, `in today's fast-paced world`
- Em-dash ` — ` (replaced with `, ` or `. ` or removed)

Post-process: regex-scan the LLM output; if any blocked token is found, re-prompt the LLM with "rewrite without using these words" OR pass through a small post-edit transform that swaps them for synonyms.

**~50 LOC** in `services/ai_tell_blocklist.py`. ~30 entries (blocklist) + post-process regex.

**T1-C. Burstiness + perplexity injection — natural variance.**

Per DIPPER paper (arxiv 2303.13408 Krishna et al. NeurIPS 2023) + arxiv 2506.07001 (Adversarial Paraphrasing):
- AI tends to uniform sentence length.
- Human writing has high variance (some 8-word sentences, some 28-word, in the same paragraph).
- Injecting variance is the simplest effective evasion technique.

**Implementation: prompt instruction-level injection** (NOT post-process rewriting — too lossy):
- Tell the LLM in the prompt: "Write 1 short sentence (8-12 words), then 1 long sentence (22-35 words), then 1 medium sentence (15-20 words). Repeat with varied order in each paragraph."
- Validate: post-generation, compute the std-dev of sentence lengths. If < 6 chars (uniform), regenerate with explicit nudge ("the previous draft was too uniform; vary length more").

**~80 LOC** in `services/burstiness_check.py`.

**T1-D. Perplexity matching — lexically uncommon-but-natural word choice.**

Too-low perplexity = AI tell. Inject lexically rare-but-natural words from the user's own vocabulary (extracted from voice-grounding samples):
- Extract user's top-100 unique non-stopword tokens from their writing.
- Tell the LLM: "Bias word choice toward this user-specific vocabulary list when natural: {vocab_list}".

This is meaningfully different from "inject random rare words" — we're matching the user's actual vocabulary. Stays within voice.

**~60 LOC** in `services/voice_grounding.py` (TF-IDF extractor against a generic corpus; identify what's distinctive about the user's writing).

### C.4 TIER-2: Gray-area but defensible (opt-in toggle in Settings; informed-consent dialog)

**T2-A. Detector-roundtrip validation (run output through Originality.ai API; regenerate if flagged).**

Per Originality.ai pricing: $30 PAYG = 30k words = ~$0.001/cover-letter for AI-detection check. Negligible cost.
- If output > 0.30 AI-likelihood probability, regenerate with stronger style anchoring (e.g., paste 2 more user samples).
- Hard cap: 3 retries before giving up (avoid infinite loop).

**Trade-off (TIER-2 because gray-area):**
- Pro: catches detector-positive output before submission.
- Con: detector returns False-Positives on 2.1-9.2% of human-written text already (per Stanford); regenerating *might* introduce new tells.
- Con: takes a $0.001 per check × N retries.
- Con: implies "we're playing the detection arms race" — some users will find this distasteful.

**Recommendation:** Ship as **Setting toggle (off by default)** — "Run AI-detection check before save (uses Originality.ai API)". When on, attach `ai_detection_score` to `GeneratedDocument.bullet_selection` JSONB for auditability. Cost surfaces in the daily cost cap.

**~120 LOC** in `services/ai_detection_check.py` + new `Setting.ai_detection_check_enabled` + new env var `ORIGINALITY_AI_API_KEY` (per the AGENTS.md vault-sunset pattern; `.env.example` slot).

**T2-B. 2-pass paraphrase via secondary LLM.**

Per arxiv 2506.07001: adversarial paraphrasing drops detection rates by 87.88% on average. BUT — the same paper warns: "mostly a slight degradation in text quality." For a cover letter, slight degradation = loss of professionalism.

**Recommendation:** NOT default; NOT in `0.3.1+a`. Defer to `0.3.3` catch-all as a possible enhancement.

**T2-C. Mix-in human seed — 30-50% verbatim user-written sentences.**

Take the user's `Profile.summary_full` + their best-tagged bullets — verbatim — and weave them through the cover letter. The detector struggles when 50% of the text is provably user-written (because it IS).

**Recommendation:** Ship as **partial-implementation** in the cover letter draft prompt — instruct the LLM to "incorporate verbatim phrases from the candidate's profile when natural; prefer the candidate's own words over rephrasing them." Don't add a separate detection-evasion module; bake this into the prompt's voice-grounding section (T1-A).

### C.5 TIER-3: Black-hat / blacklist-risk (SURFACE + WARN + NOT DEFAULT)

> The user MUST opt-in to TIER-3 via an explicit two-toggle dialog ("I understand this carries blacklist risk and may be detected"). NOT shipped in `0.3.1+a`. Mentioned here for completeness only.

**T3-A. Invisible-text keyword injection** (white text on white background; zero-width characters between letters; homoglyph substitution; metadata-only keyword injection).

**Status: BLACKLIST RISK; possibly resume-fraud-adjacent.**
- iCIMS in 2026 flags resumes with hidden text as "Suspicious Content" + routes to spam queue. Modern ATS detect white-on-white (font-color matching background). Some companies maintain internal blacklists of candidates who used deceptive practices.
- Industry consensus 2026: hidden text is the fastest path to permanent rejection.
- AirResumeGuru: "this trick worked briefly around 2010; today it's the fastest way to get your resume thrown in the trash and possibly blacklisted from the company forever."
- Naavik MUST never default-enable.

**T3-B. Adversarial paraphrasing (DIPPER-style; multi-round detector-guided rewriting).**

**Status: Detectable as 2-pass artifact; possibly inflates the cost cap.**
- Drops detection 87.88% (powerful) — but text quality degrades meaningfully.
- Requires running the output through TWO LLM passes per generation.
- For a cover letter where the user must own the words, this is borderline fraud-adjacent.
- Defer to user-research.

**T3-C. Metadata injection.**

PDF metadata fields (`Author`, `Title`, `Keywords`, `Subject`) — some legacy ATS extract these.
**Status: Modern ATS extract + flag as part of "Suspicious Content."** Don't ship.

**TIER-3 recommendation:** Document in this memo. Do NOT add a ROADMAP row. If the user ever asks for TIER-3, file at that point.

## D · Recruiter pre-screen optimization (the "potential hire" flag)

### D.1 The 6-second skim — what's actually true

| Study | N | Median scan time |
|---|---|---|
| Ladders Inc. 2012 (original eye-tracking) | 30 recruiters × 10 weeks | **6.0 seconds** |
| Ladders Inc. 2018 update | Larger sample, same methodology | **7.4 seconds** |
| InterviewPal 2025 | 4,289 reviews × 312 recruiters (US/UK/SEA) | **11.2 seconds** |

Pattern: scan time has **increased**, not decreased, with the rise of ATS auto-screening (recruiters spend more time per resume that survives the ATS filter, because there are fewer of them to look at).

**Naavik design implication:** target the 6-11 second skim window, not the 6-second one. Optimize for "what gets read in the first 8 seconds."

### D.2 The 6 eye-tracking fixation points (Ladders 2018)

In order of attention (heat-map clusters):
1. **Name** — center-top, ~1.0 sec
2. **Most-recent job title** — top-left below name, ~1.5 sec
3. **Most-recent company** — same line as title, ~0.5 sec
4. **Most-recent dates** — right-aligned, ~0.5 sec
5. **Previous job title + company + dates** — second Experience entry, ~1.5 sec
6. **Education line** — bottom-left, ~0.5 sec

**80% of 6-second attention** lands on these 6 fixation points. The remaining 20% scatters across skills + bullets-of-experience-#1.

**Current `onepage.typ` (verified):**
- Name in 14pt bold center (clear visual hierarchy) ✓
- Headline immediately below ✓
- Experience block — title + company on one line, location + dates on same line ✓
- Education at bottom ✓

**Pass on structure; tune the content.** See D.3 + D.4.

### D.3 Name + title + headline (the recruiter-pre-screen lever)

**Current `onepage.typ` emits:**
```
{full_name}
{headline}
{email} · {phone} · {location}
{linkedin} · {github} · {portfolio_url}
```

**Recommendation: extend `headline` to be a **JD-tailored 1-line pitch**, not a static profile field:**
```
Senior ML/AI Engineer · 8+ years · ML platform + LLM systems · Open to ML/AI roles · H1B requires sponsorship
```

This is a SOTA pattern (zety, Resume Optimizer Pro, novoresume all converge):
- **Job title** (matching the JD's target title where ethical) — 10.6× interview signal per research (jobshinobi).
- **Years of experience** (numeric; recruiter pattern-matches "8 years" to seniority requirement).
- **Specialty / domain** (1-2 phrases the JD specifically calls for).
- **Sponsorship signal** (only when relevant — `H1B requires sponsorship` if visa concern; `Work-authorized in US` if not). Saves the recruiter a click; gets the candidate filtered IN (or OUT) cleanly.

**Naavik implementation:** new prompt `tailor_headline.py` (LLM call gated on `JobScore.score >= 0.50`):
- Input: `Profile.headline` + `Profile.summary_full` + `Job.role` + `Job.role_family` + `Job.description` + `Profile.work_authorization`
- Output: `TailoredHeadline{headline: str (max 100 chars), keywords_emphasized: list[str]}`
- Validates: each ` · `-separated chunk ≤ 30 chars; total ≤ 100 chars (one-line constraint).

**~80 LOC** in `services/recruiter_optimization.py` + `llm/prompts/tailor_headline.py`.

### D.4 Top-of-section emphasis + strongest-bullet-first

Within `Experience` entry, the FIRST bullet receives the most attention (Ladders + Wonsulting).
- Current `select_bullets` + `trim_bullet` return bullets in priority order from LLM. **Pass on this — already correct.** But verify: `select_bullets.BulletSelection.selected_ids` is "in order of priority" per the prompt template; resume rendering preserves that order. ✓

**Tuning for SOTA:** when selecting bullets for the most-recent Experience, **prefer bullets containing JD-required-skill mentions** even if their independent tag-relevance is lower. Bake into `select_bullets` prompt with explicit instruction: "for the candidate's most-recent role, prefer bullets that mention specific skills required by the job ({skills_required}) over more generally-relevant bullets."

**~30 LOC** in `select_bullets.py` (prompt template change only; no new service).

### D.5 Keyword density placement — top-30% must contain all must-have JD keywords ≥ 1×

Cross-source (jobshinobi.com + resumeoptimizerpro + uppl.ai + theinterviewguys):
- Recommended distribution: 20% summary / 30% skills / 40% experience-bullets / 10% education.
- Each must-have keyword from the JD should appear ≥ 1× in the top 30% of the resume.
- 75% match-rate threshold is the JobScan-recommended target (proprietary algorithm but widely used).

**Naavik implementation:** during `select_bullets` + `tailor_headline`, the LLM receives the explicit JD-required-skills list (from `Job.skills_required` already populated by `0.2.0.08` extract_job). Naive placement: ensure top-3 must-have keywords appear in either the headline or the first 3 bullets of the most-recent Experience.

**Validator:** new `services/keyword_coverage.py` computes the "top-30%-keyword-presence" score post-generation. Surfaces in the review-bundle UI: "Resume covers 7/8 JD must-have keywords in the top 30%."

**~100 LOC** in `services/keyword_coverage.py`.

### D.6 Quantification — numbers + percentages + scale

Per resume.io + wahresume + linkedin (LinkedIn News): 48% more likely to rank in AI top-third; 34% pass-over on low-metric resumes. **Bullets with numbers (%, $, team-size, scale) pass recruiter speed-skim 2× better than qualitative bullets.**

**Naavik implementation:** the AGENTS.md § Resume/CV Data Model already says "Each experience bullet is a single field — the **long, full version**. AI trims it at apply time to fit one line on the tailored 1-page resume, **preserving numbers and verbs**." Existing `trim_bullet.py` already says "Preserve every number, every verb, the most concrete result." ✓

**Tuning for SOTA: when bullet contains no number, prefer not selecting it for the resume.** Bake into `select_bullets` prompt: "Prefer bullets that contain quantifiable metrics (%, $, team-size, scale). Among equally-relevant bullets, the one with a concrete number wins."

**~20 LOC** in `select_bullets.py` prompt template.

### D.7 Cover letter as recruiter-priority lever

Per Liz Ryan pain-letter research (themuse, lkinpost) + topresume + SHRM (50% callback uplift on personalized greeting):
- Pain letter: 25% reported callback rate (Liz Ryan, anecdotal-but-widely-cited).
- Personalized greeting: 50% more positive responses (TopResume; SHRM 42%; JobScan 42%).
- Recruiters spend longer with cover letters than resumes (CL-attached applications cluster in top of inbox).
- 72% of hiring managers prefer personalized greetings (Indeed).
- 87% notice when candidates find the right name (SHRM 2026).

**Recommendation: ship a SOTA cover letter as `0.3.1+a.03` + `0.3.1+a.04`:**

`0.3.1+a.03 — Cover letter SOTA — voice-grounded 4-section + hiring-manager personalization.`
- Replace current 4-section template ({intro, body, why_company, close}) with a SOTA 3-paragraph + signature structure:
  - **§1 The Hook (2-3 sentences):** Open with a specific JD-pain-point reference + 1-line achievement-story that matches that pain. NOT "I am writing to apply for..." — start with the company's challenge.
  - **§2 The Match (3-4 sentences):** 2-3 verbatim achievements from `Profile.experiences` + their numeric outcomes. Verbatim — voice grounding T1-A baked in.
  - **§3 The Close (2 sentences):** Specific ask — "I'd love 20 minutes to discuss how my X work on Y might fit your Z initiative" — NOT "I look forward to hearing from you."
  - **Signature:** name + signature block.
- Personalization: when `Job.hiring_manager_name` is available (via Phase 5 LinkedIn MCP for the future; for now, manually entered by user on the bundle review page OR scraped from `Job.description` heuristically), use it: `Dear {first_name},`. Otherwise fall back to `Dear {Job.company} Hiring Team,` (better than `Dear Hiring Manager,`).

Pain-letter variant (`0.3.1+a.03` extension): operator toggle "Aggressive — pain-letter format". Generate the pain-letter version when the user enables it (some users find it gimmicky; others swear by it).

**~250 LOC** total: new `llm/prompts/draft_cover_letter_sota.py` (replaces existing) + ~50 LOC `services/hiring_manager_extractor.py` (regex + LLM-extract of hiring-manager name from `Job.description`).

## F · Anti-patterns + ethical constraints (DO NOT SHIP DEFAULTS)

**Hard anti-patterns (red lines):**

1. **White-text-on-white keyword stuffing** — blacklist-risk; iCIMS flags; 2010 trick that doesn't work in 2026. **NEVER ship.**

2. **Hidden metadata keywords** — modern ATS extract + flag.

3. **Tables + multi-column layouts** — Workday + Taleo + SuccessFactors break these. **Don't ship tables in our templates.**

4. **Image-rendered resumes** — most ATS reject. Typst PDF is text-extractable; pass.

5. **Fancy fonts + ligatures** — `fi`/`fl`/`ff` ligatures map to PUA Unicode that Taleo + old iCIMS can't parse. **Use Helvetica/Arial with `ligatures: none` Typst directive on `onepage_ats.typ`.**

6. **Headers/footers with content** — most ATS skip these regions. Current `onepage.typ` has no header/footer content (page-count metadata is `<naavik-meta>` invisible element). Pass.

7. **Inflated titles / fabricated credentials** — 18 USC §1001 felony exposure; FCRA implications; permanent termination + blacklist risk. **AI tailoring NEVER changes facts**, only the language framing facts. The prompt enforces: "Use only facts present in the candidate's profile. Do not invent or exaggerate."

8. **Homoglyph + zero-width-character injection (TIER-3 evasion)** — possibly resume-fraud-adjacent; iCIMS flags as Suspicious Content. **SURFACE in research but NEVER default; not in `0.3.1+a` scope.**

**Soft anti-patterns (avoid in TIER-1 defaults):**

9. **Pain-letter format default-on** — some recruiters find it presumptuous; works for some industries (consultative B2B sales), backfires for others (FAANG eng). Ship as opt-in, NOT default.

10. **5+ "soft skills" in Skills section** — recruiters discount these; ship max 1-2 soft skills.

11. **Year-only dates** — `2024 – Present` doesn't help ATS compute experience. Ship `Jan 2024 – Present`.

12. **Photo / personal info on resume** — illegal in some jurisdictions (US discrimination claim risk for the employer; UK/EU GDPR concerns). Already absent from `onepage.typ`. Keep absent.

**Ethical constraint (Naavik product principle):**

13. **All shipped artifacts are user-reviewable BEFORE auto-submit.** The Discover review-and-apply flow already specs this (`SCREENS.md § 8`). The bundle endpoint produces draft documents; user reviews; user clicks submit. NO silent submission of unreviewed AI-tailored artifacts. This is the AGENTS.md § 0.4.0 design — preserved in `0.3.1`.

### OQ-1: Detector roundtrip (T2-A) — ship the Originality.ai integration in `0.3.1+a` OR defer to `0.3.3`?

**Pro ship now:**
- Cost is negligible ($0.001/cover letter at PAYG; ~$30/mo at any reasonable usage).
- Gives users an explicit "AI-detected? Y/N" gate before submission.
- Single env var + Settings toggle; small surface area.

**Pro defer:**
- Detector roundtrip is the "playing detection arms race" framing; some users (privacy-sensitive, principled) will find it distasteful.
- Adds external dep to a third-party SaaS (Originality.ai); operational complexity.
- TIER-1 alone (voice grounding + AI-tell blocklist + burstiness) achieves most of the lift.

**My recommendation: DEFER to `0.3.3`.** Ship TIER-1 first; observe internal "what % of generations pass GPTZero out-of-the-box?" via spot-check. If <80%, file T2-A as a follow-up. If ≥80%, T2-A is unnecessary complexity.
