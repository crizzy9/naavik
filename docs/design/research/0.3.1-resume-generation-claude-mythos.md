## A · Executive summary

The current `0.3.1` ledger has 4 rows that read as "bullet selection + bullet trim + page-count loop + one-click endpoint" — a thin wrapper around `select_bullets.py` + `trim_bullet.py` + the existing Typst compile loop. That framing badly under-scopes the user's actual ask: **a tailored PDF that (a) survives parsing across 9 ATS systems with > 85% field-extraction fidelity, (b) evades the 5 major AI-detector classifiers without crossing into fraud, and (c) lands the candidate's name in the recruiter's 6-second-skim "potential hire" attention zone.** Doing this well in 2026 — where 76% of applications are AI-detected and 49% of hiring managers auto-reject suspected AI-generated material ([WasItAIGenerated 2026 study](https://www.wasitaigenerated.com/research/ai-detection-hiring-recruitment)) — requires a substantially deeper pipeline than the 4-row sketch.

**Three critical decisions for the user:**

1. **Adopt the 2-tier FREE / PREMIUM architecture (§ R Stage 1-9).** FREE-mode is SOTA-only: corpus-grounded constitution preamble, 1 generation pass, ATS-friendly Typst template, page-count retry-drop loop. ~$0.06 per application. PREMIUM-mode layers the Claude-mythos stack on top: 3-agent voting council for bullet selection (§ F), adversarial generator-critic loop for AI-detection burstiness injection (§ F), multi-persona recruiter critique council for the final draft (§ J), tool-loop orchestrator running ATS-parse-test + detector-test + recruiter-skim-score + defensibility-check until convergence (§ L). ~$0.40–$1.20 per application. **Default is FREE; user toggles PREMIUM in Settings · Generation tab OR per-app for jobs scoring > 0.85.** This split honors the daily cost cap, gives users predictable cost per app, and concentrates Claude-mythos spend where it converts.

2. **Adopt PDF/A-1b + ATS-friendly Typst variant + voice-grounded constitution as the FREE baseline.** PDF/A-1b is the documented best-fit for ATS readability (≥85% parse scores per [ResumeAdapter 2026](https://www.resumeadapter.com/blog/ats-resume-formatting-rules-2026)). The new `onepage_ats.typ` template strips the current single-column grid to even more parser-friendly form (no columns, no boxes, plain bullet markers, MM/YYYY dates) — Workday + Taleo + iCIMS strict parsers handle this cleanly per [Resume Optimizer Pro testing of 8 ATS systems](https://quickcv.io/blog/i-tested-8-ats-systems-to-see-how-they-actually-parse-resumes). Voice grounding from corpus + constitution-preamble (§ G + § H) is the *biggest single lever* for AI-detection evasion because it grounds bullets in the candidate's own past writing, making them inherently human-burstiness compliant.

3. **Reject TIER-3 (black-hat) techniques as default; surface them with explicit opt-in + blacklist warning.** White-text keyword stuffing, zero-width unicode injection, homoglyph substitution, hidden-metadata keyword spam all cross into deception territory. Per [airesume.guru blacklist study](https://airesume.guru/blog/hidden-keywords-white-text-on-resumes-the-myth-that-gets-you-blacklisted), modern ATS reads these AND many recruiter networks share blacklists across companies. They can mass-blacklist the candidate. **Naavik never recommends these; we surface them in Settings · Advanced with a blacklist-risk warning + require explicit opt-in.** No exceptions.

**Total estimated 0.3.x payload growth:** the original 4-row 0.3.1 explodes into 6 rows for 0.3.1 (core ATS + voice + cover letter + endpoint) plus 6 rows for a new 0.3.4 (Claude-mythos premium tier). Net ~12 rows across 2 sub-releases, ~12 dev-days, ~3 reviews. The mythos rows are independently valuable (premium mode toggleable) — they don't block the FREE-tier path.

A resume that perfectly tailors content but fails parser extraction is worthless. Below is the per-system fidelity map, evidence-grounded, with the actionable rules.

### B.2 Universal rules (apply to all 9)

These rules combine the lessons across the 9 systems — getting these right pushes parse fidelity from ~70% (creative templates) to ~95% (ATS-friendly):

1. **Single-column layout.** No tables, no text boxes, no columns. Taleo will silently fragment; Workday will interleave; iCIMS may flag for manual retype. [Source: Jobscan 2026](https://www.jobscan.co/blog/resume-tables-columns-ats/) — 23% of ATS parse failures are formatting-driven.
2. **Standard section headings.** `EXPERIENCE` (not "Career Journey"), `EDUCATION` (not "Academic Background"), `SKILLS` (not "Capabilities"), `PROJECTS` (not "Things I've Built"). Taleo's exact-match-only is the strictest case.
3. **MM/YYYY or "Month YYYY" dates.** "Jan 2024 — Present" parses across all 9. Avoid "January '24" / "Q1 2024" / "2024 (ongoing)".
4. **Plain bullet markers.** `•` (U+2022) or `-` only. Avoid Unicode arrows (→), checkmarks (✓), decorative dots, emoji — iCIMS flags, Taleo fragments.
5. **No header/footer content.** Workday + most parsers ignore PDF header/footer XML nodes. Contact info must be in the body, top-of-page.
6. **Web-safe fonts.** Helvetica / Arial / Calibri / Times New Roman / Georgia. The current `onepage.typ` already uses `Helvetica, Arial, Liberation Sans` — keep this.
7. **PDF/A-1b output.** Achieves ≥85% parse scores on most ATS checkers per [ResumeAdapter 2026](https://www.resumeadapter.com/blog/ats-resume-formatting-rules-2026). Typst output is already text-based PDF; verify it qualifies as PDF/A-1b in the compile call.
8. **No fancy ligatures, no kerning quirks.** Some PDF parsers tokenize ligature glyphs (fi, fl) as separate characters. Typst default rendering is safe; verify.
9. **Contact info in canonical pattern.** Name on first line (bold, 14pt). Email + phone + location on second line, separated by middle dot or comma. LinkedIn handle / GitHub handle / portfolio URL on third line. Current `onepage.typ` already does this — keep.
10. **No "PII" beyond canonical fields.** No date-of-birth, marital status, photo, nationality — some ATS flag for review.

Score < 90% on any parser → retry with an even-more-conservative template variant. Score < 80% → fail-soft with a warning banner. **Not a TIER-1 priority** — ship after the core pipeline; in 0.3.1.05 (or could defer to 0.3.4).

### B.4 The DOCX question

[Resume Optimizer Pro testing](https://resumeoptimizerpro.com/blog/how-resume-parsers-actually-work) found DOCX outperformed PDF in 6 of 8 systems. **Should Naavik ship DOCX output?**

| Option | Pro | Con |
|---|---|---|
| **Ship only PDF/A-1b** (current) | One template, one validation path; Typst native | DOCX-only ATS configs may parse worse |
| **Ship PDF + DOCX (both)** | Maximum compatibility; user uploads whichever the JD wants | 2× template maintenance; Typst → DOCX requires `pandoc` or `typst2docx` shim — neither is mature |

## C · AI-detection evasion (ethics-aware, 3-tier categorization)

### C.1 Detector landscape

| Detector | Detection method | Reported accuracy | Detector-specific bypass surface |
|---|---|---|---|
| **GPTZero** | Perplexity (predictability) + burstiness (sentence-length variance) + 600M-doc deep classifier + Paraphraser Shield trained on 12+ humanizer tools | 99.5% on Chicago Booth 2026 benchmark | Burstiness injection (real, not synonym-swap); paraphraser-shield-aware |
| **Originality.ai** | Modified BERT + RoBERTa supervised classifier | Flags simple human text as AI; high false-positive | "Style-natural" writing helps; vary vocabulary |
| **Copyleaks** | Linguistic patterns (perplexity) + deep-learning + semantic fingerprinting | Aggressive; flags clean human text too | Avoid semantic predictability; vary structure |
| **Winston AI** | Perplexity + burstiness + stylometric cues | Similar to GPTZero | Same techniques work |
| **Turnitin AI** | Proprietary classifier (academic-focused) | High false-positive on polished writing | Less relevant for job applications |

**The pattern is universal:** all 5 detectors converge on **perplexity (how predictable is each word) + burstiness (how varied is sentence length and complexity)** as the primary signals. Secondary signals: vocabulary fingerprint, sentence-structure parallel-clause habit, and the dead-giveaway phrases ("delve", "in conclusion", "tapestry", "in today's fast-paced world").

[Source: GPTZero on perplexity + burstiness](https://gptzero.me/news/perplexity-and-burstiness-what-is-it/); [Langvault practical guide](https://langvault.com/how-perplexity-and-burstiness-expose-ai-writing/).

### C.2 The detection-rate climb

| Period | Detection rate | Source |
|---|---|---|
| H1 2024 | 53% | [WasItAIGenerated 2026 study](https://www.wasitaigenerated.com/research/ai-detection-hiring-recruitment) |
| H1 2026 | 76% | same |
| Future trajectory | Likely 85-90% by H1 2027 | (extrapolation) |

**49% of hiring managers auto-reject AI-flagged resumes.** [Resume.io study](https://resume.io/blog/resume-rejections). 62% reject AI-generated resumes without personalization per [Resume-Now survey](https://www.resume-now.com/job-resources/careers/ai-applicant-report). 43% of large employers use automated AI-detection tools (SHRM 2026); 65% of Fortune 500 do.

**The opening for honest tools:** the detection spectrum spans "100% AI-from-blank-prompt" (easily caught) to "human-written with AI optimization" (nearly undetectable). The key variable is **how much content comes from real career data vs AI invention**. Naavik's substrate is built for the latter: every bullet derives from a user-owned `Bullet` row. The challenge is the LLM-trim layer — making the trim sound human, not statistically smooth.

### C.3 TIER-1 LEGITIMATE techniques (default-on, ship by default)

1. **Voice grounding from user's corpus.** Profile bullets + past cover letters + onboarding intake responses + past application screener answers are already in Naavik's DB. Pre-load them into Claude's context (§ G). The output matches the user's natural sentence-length distribution and idiomatic phrases. **This is the single most powerful evasion technique because it's not evasion — it's truth.**
2. **Burstiness injection.** Naavik's bullet trim should target variance, not minimum-character-count. Some bullets land in 60 chars, others in 130. Some lead with a number, others with a verb. Some have a clause, others are punchy 5-word fragments. [Source: Intellectual Lead practical guide](https://intellectualead.com/perplexity-burstiness-guide/) confirms structural variance is what matters, not synonym-swap.
3. **Constitution preamble** (§ H). System message says: "Match the voice of this corpus. Avoid em-dashes. Avoid 'delve', 'tapestry', 'in today's...'. Use the candidate's natural vocabulary as derived from corpus."
4. **Quantification.** Every bullet has a number. Numbers are inherently non-AI-tellable. Recruiters love them (40% callback uplift per [Jobscan study](https://resume.io/blog/quantify-your-resume-bullets)).
5. **Defensible reduction not invention.** AI trims the user's existing long-form bullet to a tighter version. The semantic content was the user's; AI just compresses. AI-detectors trained on "AI invented this" patterns miss "AI summarized this" patterns at a lower rate.
6. **Avoid AI-tell phrases.** Hard-coded blacklist of phrases that scream LLM output: em-dashes inside sentences, "delve", "tapestry", "fast-paced", "robust", "in conclusion", "moreover", "furthermore", "elevate", "leverage" (as a verb), "spearhead". Inject as constitution constraint.

### C.4 TIER-2 GRAY-AREA techniques (opt-in, surface in Settings · Advanced)

1. **Adversarial paraphrasing (DIPPER-style).** [Krishna et al. DIPPER paper](https://arxiv.org/abs/2303.13408) — fine-tuned T5-XXL paraphraser drops DetectGPT accuracy 70.3% → 4.6% without modifying semantics. Naavik could use an in-house or HuggingFace-hosted DIPPER for any bullet that scores AI-tell-high after trim. **Cost:** runtime is non-trivial (T5-XXL inference); needs a sidecar service. **Risk:** "adversarial paraphrasing" sounds bad. Mitigation: surface it as "humanize this bullet" with the bullet displayed before + after; user opts in per-app. The 2026 [arXiv 2506.07001 Adversarial Paraphrasing Universal Attack](https://arxiv.org/html/2506.07001v1) is the latest published universal attack — but using it crosses an ethical line we'd have to defend.
2. **Synonym-swap walks.** Replace high-AI-tell vocabulary with user's corpus-vocabulary. Less aggressive than DIPPER. Probably TIER-1 if grounded in user's actual word usage.
3. **Sentence-shuffling within bullets.** "Built X to do Y, reducing Z by 40%" → "Reduced Z by 40% by building X to do Y." Re-orders cause-effect to vary structure. TIER-1 if subtle.
4. **Human-seed mix-in.** The user provides one paragraph of writing (e.g., a paragraph from their LinkedIn About or a personal blog post). Naavik mixes that paragraph into the system message as voice anchor. TIER-1 grade.
5. **Detector roundtrip with paraphrase loop** (§ F). Run output through a Claude-as-detector + iteratively refine until detector flag-confidence drops below threshold. **The grey-area part is "engineering output specifically to defeat a detector."** Naavik's framing should be "ensure output reads naturally" not "evade detection."

### C.5 TIER-3 BLACK-HAT (DO NOT DEFAULT-ON; warn loudly if surfaced)

These cross the line from "honest tool that helps" into "deception":

1. **White-text keyword stuffing.** Hidden text in white-on-white. Modern ATS read all text regardless of color. [Source: airesume.guru blacklist study](https://airesume.guru/blog/hidden-keywords-white-text-on-resumes-the-myth-that-gets-you-blacklisted): recruiters maintain internal blacklists shared across companies in the same network. **Risk: permanent blacklist from a company AND its peer network.**
2. **Zero-width unicode injection.** U+200B / U+200C / U+200D / U+FEFF inserted into the resume body or PDF metadata. Detection tooling (Originality.AI Invisible Text Detector, K-Lab.dev inspector) catches these instantly.
3. **Homoglyph substitution.** Replacing Latin 'a' with Cyrillic 'a' (U+0430). Same blacklist risk.
4. **PDF metadata keyword spam.** Stuffing PDF Title/Subject/Keywords metadata fields with JD keywords. Modern ATS extract metadata.
5. **Inflated job titles or fabricated credentials.** Illegal in some jurisdictions (employment fraud); instant blacklist; permanent recruiter-network share.

**Naavik policy:** SURFACE these with a `⚠ BLACKLIST RISK` warning + require explicit opt-in checkbox + log every opt-in to `traces/<run-id>/architect.log` (no, to a proper audit log) for post-fact review. **Never default-on. Never silent-enable. Document the risk in Settings · Advanced.**

## D · Recruiter pre-screen optimization (the "potential hire" pile lever)

### D.1 The 6-second skim is real

[Ladders 2012 study (the original), Eye-tracking 2026 follow-up](https://www.hrdive.com/news/eye-tracking-study-shows-recruiters-look-at-resumes-for-7-seconds/541582/) finds recruiters spend 6-8 seconds on initial scan. 94% complete the initial scan in < 10 seconds. Those who reject at this stage average 5.2 seconds.

### D.2 What they look at (F-pattern / Z-pattern)

[Source: A4CV eye-tracking study 2026](https://a4cv.app/blog/six-second-resume-scan-eye-tracking-reveals-what-recruiters-see/):

- **80% of viewing time is in the top third of page 1.**
- F-pattern: eyes scan top horizontally, drop down 2-3 lines, scan again, drop further, taper.
- Z-pattern variant: top-left → top-right → diagonal to bottom-left → bottom-right.
- **The bottom 30% is often completely ignored** in the initial skim.

The 6 fixation points recruiters consistently hit (per [ResumeHeatMap eye-tracking 2026](https://resumeheatmap.com/eye-tracking-study)):

1. **Name** (font-size + bold weight → fixation 1)
2. **Current/most-recent job title + company** (fixation 2 — answers "who are they working at now?")
3. **Dates of current role** (fixation 3 — answers "for how long?")
4. **Education institution** (fixation 4 — name-of-school is heuristic for "good")
5. **Previous job title or industry signal** (fixation 5 — answers "what was their trajectory?")
6. **Skills list** if visually distinct (fixation 6 — quick keyword scan against the JD)

### D.3 The name + headline + summary lever

The user's directive is to "land the candidate's name in the recruiter's potential-hire pile within 6 seconds." Concretely:

**Headline format ([Title] | [Years/Credential] | [Signature Achievement])** per [Resume Optimizer Pro headline guide](https://resumeoptimizerpro.com/blog/resume-headline-examples). Example for the owner profile:

> **Senior Software Engineer | 8+ yrs | Personalization at scale, Intuit/Northeastern MSCS, H1B i-140**

This packs into 1 line: role match (Senior Software Engineer = JD title), seniority (8+ yrs), differentiator (Personalization at scale, big-name employer + MSCS), and the visa flag (i-140 = sponsorable). Recruiter at second 2 of the skim knows the candidate is plausible and sponsorable.

**Naavik's job in Stage 4:** auto-generate the headline + summary from JD + profile + constitution. Headline updates per-application (current `Profile.headline` is generic; the apply-time headline is JD-tailored).

### D.4 Top-of-experience-section emphasis

Recruiters' F-pattern scan reads the first 1-2 bullets of the most-recent role and skips the rest. **Therefore the strongest, most-quantified, most-JD-aligned bullet must be FIRST**, not chronologically-first. The current `select_bullets.py` returns `selected_ids` in priority order — Naavik just needs to honor that ordering in the rendered output (not re-sort by chronology).

### D.5 Keyword density placement

[Jobscan State of Job Search 2025](https://www.jobscan.co/blog/what-jobscan-match-rate-should-i-aim-for/) and supporting studies find:

- **80% match rate target** on Jobscan (proxy for ATS keyword scoring).
- Skills integrated into work-experience bullets convert 67% better than standalone skills section ([Resumly research](https://www.resumly.ai/blog/analyzing-recruiter-eye-tracking-to-optimize-resume-order)).
- ATS parsers weight keyword position — top-third placement scores higher than buried in old job bullets.
- Top 30% of resume should contain ALL must-have JD keywords ≥ 1×.

**Naavik's job in Stage 4 (headline + summary):** the auto-generated headline + summary must include every "must-have" keyword from JD's "Required:" section + the role title verbatim. The bullet trim layer (Stage 3) ensures the top 2-3 selected bullets carry JD-aligned keywords too.

### D.6 Quantification

**40% callback uplift on quantified resumes.** [Jobscan study cited in Resume.io](https://resume.io/blog/quantify-your-resume-bullets). 34% of hiring managers pass over resumes with few/no measurable results.

**Naavik's job:** the bullet-trim prompt must explicitly preserve numbers. Current `trim_bullet.py` says "Preserve every number, every verb" — keep this. Add to constitution: "Every bullet has a number when one exists in the source."

## F · Anti-patterns + ethical constraints

These are what NOT to do. Naavik should code-enforce avoidance:

| Anti-pattern | Why it fails | Naavik enforcement |
|---|---|---|
| White text on white background | Modern ATS read all text regardless of color; blacklist-risk per [airesume.guru](https://airesume.guru/blog/hidden-keywords-white-text-on-resumes-the-myth-that-gets-you-blacklisted) | Code-check: any text element with color matching background → reject template; surface error |
| Hidden PDF metadata keyword spam | Modern ATS extract metadata; flagged as deception | Code-check: PDF metadata Title/Subject/Keywords fields are populated with canonical Profile data only — no JD keywords |
| Tables / multi-column | Taleo + iCIMS + Workday strict tenants all break | Code-check: `onepage_ats.typ` template provably ships single-column structure |
| Image-based resumes (PDFs that are scanned images, no text layer) | ATS can't OCR fast; instant rejection | Code-check: Typst output has text layer (verify) |
| Fancy fonts / ligatures | Parse failures | Code-check: template uses only Helvetica/Arial/Times/Calibri/Georgia |
| Headers/footers with content | XML-node-mismatch; ATS skip | Code-check: `onepage_ats.typ` has no header/footer |
| Inflated job titles / fabricated credentials | Illegal; instant blacklist; permanent record | Defensibility tool (§ L.5): every bullet must trace to a user-owned `Bullet` row; constitution forbids invention |

**Ethical north star** (formalize in code as `constitution.md` loaded into every Claude call):

> Naavik never lies about the candidate's credentials. AI assistance is for compressing, ordering, and presenting truths the candidate already owns. If a JD requires something the candidate doesn't have, the gap is surfaced honestly in the `JobScore.gaps` array shipped 0.3.0.05 — not invented in the resume.

This is non-negotiable. Code-enforce via the defensibility tool (§ L.5): every bullet emitted by the LLM is matched back to an originating `Bullet.id`; bullets with no provenance are rejected pre-render.

# PART 2 · CLAUDE-MYTHOS-TIER TECHNIQUES (the force multiplier)

This is the layer the user explicitly asked for: techniques that lean on Claude's specific capabilities (multi-agent, 1M context, extended thinking, structured outputs, tool use, prompt caching) as a tactical substrate. Each technique is paired with its cost multiplier so the user can lock-in which ship in FREE-mode vs PREMIUM-mode.

## G · Long-context profile grounding (Claude's 1M context window)

**The technique:** every Stage 1-5 LLM call gets the user's entire writing corpus injected into the system message as voice anchor. Cached via Anthropic prompt caching (90% off on cache reads, $0.30/MTok).

**The corpus inputs:**

- All `Bullet.text` rows for the user (~50-100 bullets × ~200 chars = ~12K chars)
- `Profile.summary_full` + `Profile.summary_short`
- All `ProfileAnswer.answer` rows (shipped 0.2.7.14) — the user's prior screener responses (~20-100 × ~300 chars = ~10K chars)
- Past cover letter sections (when we eventually have multi-app history)
- Onboarding intake responses (Profile · open-text fields)
- Optional: a single user-uploaded "writing sample" (~500-2000 chars)

**Total corpus:** ~25-50K tokens. At Claude Opus 4.7 / Sonnet 4.6 input rates ($5 / $3 per MTok respectively), one fresh load is $0.075 (Opus) or $0.045 (Sonnet) per call. **With prompt caching enabled (cache_read $0.30/MTok), the second-and-subsequent calls cost ~$0.008 per call.** For multi-stage generation (5-9 stages per app), the cache amortization is huge.

**System message preamble (the "voice anchor"):**

```
Below is the candidate's complete corpus of authored writing. Match this voice exactly when generating any output. Key voice signatures:
- Sentence-length distribution: [histogram extracted from corpus]
- Idiomatic phrases: [extracted from corpus]
- Vocabulary: [vocab-fingerprint extracted from corpus]
- Tendencies: [pattern extracted, e.g. "leads with verb 70% of time, with number 50%"]

CORPUS:
[full bullets + past answers + cover letter sections]

CONSTITUTION:
[see § H]

TASK:
[stage-specific user message]
```

**Cost projection (5 stages per app, Sonnet 4.6, caching enabled):**

- Stage 1 cache write: $0.045 (cache_write 1.25× base, ~24K input tokens)
- Stages 2-5 cache reads: 4 × $0.008 = $0.032
- Output tokens per stage (~500 tokens × 5 stages × $0.015/Ktok): $0.038
- **Total: ~$0.115 per app for the voice-grounded generation (vs ~$0.045 / $0.06 without caching).**

**Recommended for FREE-tier** — voice grounding is the single highest-ROI technique because it kills AI-detection at the source. Cache hit rate determines cost; with 5-stage pipeline + 5-minute cache TTL ([source: Anthropic prompt cache docs](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)), all 5 calls hit the cache.

**Open question OQ-7:** load full corpus every call (max quality, max cost-per-app) OR cache a "style fingerprint" extracted once per user and reload only the fingerprint (much cheaper but lower quality)?

## H · Constitutional AI generation

**The technique:** every Claude call's system message includes a "constitution" — a structured set of constraints and persona-definitions that bound the output's behavior. Inspired by [Anthropic's own 80-page Claude Constitution (Jan 2026)](https://natesnewsletter.substack.com/p/what-anthropics-new-constitution).

**Naavik's per-user constitution structure:**

```yaml
identity:
  i_am: Shyam Padia
  role: Senior Software Engineer at Intuit (Personalization/Marketing Tech)
  experience: 8+ years, 5.5+ at Intuit US
  education: MS CS Northeastern, BE CE Mumbai
  visa: H1B with i-140 pending — REQUIRES SPONSORSHIP

voice:
  sentence_length_distribution: {short: 35%, medium: 50%, long: 15%}
  preferred_idioms: ["built", "shipped", "led", "designed", "scaled"]
  avoided_phrases: ["delve", "tapestry", "in conclusion", "leverage", "elevate", "robust",
                    "spearhead", "in today's fast-paced", "moreover", "furthermore"]
  preferred_punctuation: "commas for clauses; em-dashes ONLY for parenthetical asides (rare)"
  number_preference: "every claim with a number, when a number exists in source"

honesty_constraints:
  no_fabrication: "Every claim must trace to a Bullet/Profile field. Never invent."
  no_inflated_titles: "Use job titles as recorded in the Profile; do not embellish."
  defensibility: "If the candidate is asked about any claim in interview, they can defend it."

style_constraints:
  bullet_format: "Verb-first 50% of time. Number-first 30% of time. Subject-first 20%."
  bullet_length: "Single line, 60-130 chars. Vary."
  parallel_clause_habit: "Avoid LLM's parallel-clause habit; mix structures."

forbidden:
  - em_dash_inside_sentence
  - the_blacklist_of_AI_tell_phrases (see voice.avoided_phrases)
```

The constitution sits at the SYSTEM message in every Claude call. The user message is the stage-specific task.

**Cost impact:** ~1-2K tokens added to system message. Cached via prompt caching. Marginal.

**Refinement loop:** extract the constitution from the user's existing writing samples **once per user** (background job, run when Profile is created or significantly edited). Cache the constitution in a new DB column (or in `Settings.generation_constitution` JSONB) and re-use across all 0.3.1 generations. Update incrementally when new corpus arrives.

**Recommended for FREE-tier.**

## I · Self-consistency sampling (N-vote council)

**The technique:** for high-stakes decisions (which 8 bullets, which JD pain points the cover letter addresses), generate N variants (temperature ~0.7-0.9) and have Claude-as-judge pick the best.

**Two variants:**

| Variant | N | Cost multiplier | Quality gain |
|---|---|---|---|
| **Self-consistency (1 prompt, N samples)** | 3-5 | ~3-5× | Catches obvious bad samples |
| **Multi-agent council (N different personas, voting)** | 3-7 | ~3-7× | Distinct perspectives; better quality |

**Naavik's premium-tier choice: 3-agent council with distinct personas.** Per [LLM Council paper](https://arxiv.org/pdf/2604.02923), heterogeneous personas (different roles, not different models) beat same-model multi-instance.

**The 3 council members for bullet selection (Stage 2):**

- **Persona A — Pragmatic recruiter:** "Pick the 8 bullets that read as the strongest match to the JD's required skills. Prioritize quantification + alignment."
- **Persona B — Hiring manager:** "Pick the 8 bullets that showcase the candidate's most transferable + senior-level impact. Prioritize ownership + scope + leadership."
- **Persona C — Cultural-fit assessor:** "Pick the 8 bullets that align to the company's culture signals (work style, values, scale). Prioritize fit + curiosity."

Each persona returns an ordered list of bullet IDs. The merge algorithm: borda count vote — each bullet gets a score = N - rank_in_each_persona; bullets ranked highly by all 3 win.

**Cost projection (per app):**

- 3 Claude calls × ~500 output tokens × Sonnet 4.6 ($3 in / $15 out)
- Voice grounding cached: ~$0.025 per call
- Total: ~$0.075 for the bullet-selection vote stage (vs ~$0.025 for single-shot)

**Recommended for PREMIUM-tier; opt-in default.**

## J · Multi-persona recruiter critique council

**The technique:** after the draft resume is rendered (Stage 6), submit it to N=3 Claude instances each embodying a distinct recruiter persona. Each returns specific feedback. Merge feedback → identify high-confidence issues (all 3 flag the same thing) and surface to user OR auto-refine.

**The 3 personas:**

| Persona | Goal | Output |
|---|---|---|
| **FAANG L5/L6 hiring manager** | 6-second skim simulation | Flags: name/role/years/seniority clarity, signature-achievement-in-headline check, scale-of-impact, sponsorship-status-readable |
| **Series A/B startup founder** | Same 6-second simulation, startup priorities | Flags: ownership clarity, range of experience, generalist signal, scrappiness |
| **Fortune-500 HR-screener (Workday-using)** | Parser fidelity + keyword match | Flags: JD-keyword density, sponsorship clarity, education + visa visibility |

**Cost projection (per app):** 3 calls × ~800 output tokens × Sonnet 4.6 = ~$0.04. Voice grounding cached.

**Recommended for PREMIUM-tier.**

## K · Extended thinking / chain-of-thought (Claude Opus 4.7 adaptive thinking)

**The technique:** Anthropic's extended-thinking API lets Claude run a long "scratchpad" reasoning phase before emitting the final structured output. [Claude Opus 4.7 + Sonnet 4.6 use `thinking: {type: "adaptive"}`](https://platform.claude.com/docs/en/about-claude/models/whats-new-claude-4-7); older Claude 4 models use the explicit budget. The model dynamically decides how much to think.

For Naavik's bullet selection (Stage 2), the scratchpad prompt:

```
Reason about which 8 bullets from these 50 most-strongly align with this JD's specific pain points. Consider:
- Visa constraint (candidate needs sponsorship; JD must allow)
- Seniority signal (JD says "Senior"; candidate is 8 yrs)
- Recency (recent bullets > old ones)
- Quantification (numbers > qualitative)
- Recruiter pre-screen heuristics (top of resume = top-third skim zone)
- Defensibility (can the candidate defend in interview?)
Show your reasoning. Then return BulletSelection.
```

For cover letter (Stage 5), extended thinking surfaces the pain-point identification + hook-paragraph candidates + defensibility check per claim.

**Cost projection:** thinking tokens are billed at output rate. Adaptive thinking dynamically scales (~500-3000 thinking tokens per Stage 2 call). At Sonnet 4.6 output rate ($15/MTok), $0.0075 - $0.045 per stage.

**Recommended:** PREMIUM-tier for Stage 2 (bullet selection) and Stage 5 (cover letter). FREE-tier could skip thinking for cost.

**Interleaved thinking** ([beta header `interleaved-thinking-2025-05-14`](https://platform.claude.com/docs/en/build-with-claude/extended-thinking) for Claude 4 models other than 4.6+ which auto-enable) lets Claude think between tool calls. Critical for § L tool-loop refinement.

## L · Tool-use orchestration (the refinement loop)

**The technique:** Claude orchestrates a tool loop where each tool returns a structured signal and Claude decides "ship" or "iterate."

**The 5 tools:**

| Tool | What it does | Returns | Stage where called |
|---|---|---|---|
| **`ats_parse_test(pdf_bytes)`** | Runs N open-source parsers (§ B.3) on the PDF | Per-parser field-match score + overall | After Stage 7 render |
| **`ai_detector_test(text)`** | Runs Claude-as-detector OR a real GPTZero/Originality.ai API roundtrip | Per-detector AI-flag confidence | After Stage 3 trim |
| **`recruiter_skim_score(text)`** | Claude-as-recruiter simulating 6-second skim | Score 0-100 + 3-bullet feedback | After Stage 7 |
| **`keyword_density_check(text, jd)`** | Computes JD-keyword coverage in top 30% | Per-keyword pass/fail | After Stage 3 |
| **`defensibility_check(bullet_text, profile)`** | Verifies bullet derives from `Bullet.id` (no invention) | Per-bullet provenance | Pre-Stage 7 |

Claude orchestrates: emit tailored draft → call all 5 tools → decide ship-or-iterate → if iterate, emit refined draft and repeat.

**Implementation via Anthropic's tool_use:** define the 5 tools as structured-output tools. Use `interleaved-thinking-2025-05-14` beta header (for Claude 4 models that don't auto-enable) so Claude reasons between tool calls. ([Source: tool_use docs](https://docs.anthropic.com/en/docs/build-with-claude/tool-use)).

**Iteration cap (OQ-2):** 3 iterations max. Each iteration ~2-4 Claude calls (the orchestrator + the tools) → ~$0.04-0.10 per iteration.

**Recommended for PREMIUM-tier.**

**Open question OQ-3:** call live AI-detector APIs (real GPTZero, Originality.ai) at $0.001-0.01/call OR trust the Claude-as-detector-critic loop (cheaper but model-self-critique risks model-self-cooperation)?

## M · Citation-grounded generation (the defensibility lever)

**The technique:** every output bullet carries provenance — the source `Bullet.id` it derived from + the specific JD signal (keyword / pain point) it addresses. Enforced via Pydantic structured output.

**The shape:**

```python
class TailoredBullet(BaseModel):
    source_bullet_id: int  # FK to Bullet.id, must exist for this user
    output_text: str  # the trimmed/rewritten bullet
    jd_signal_addressed: str  # which keyword/pain-point this addresses
    defense_note: str  # 1-line: "how would the candidate defend this?"
```

**Code enforcement:** `defensibility_check` tool (§ L.5) verifies `source_bullet_id` is a real `Bullet.id` for this user. If LLM hallucinated an ID, reject and re-prompt.

**User-facing surface:** Discover · review & apply screen shows each bullet alongside its citation: "← derived from your Intuit bullet #47, addresses 'distributed systems' keyword." User can click to see source bullet. **This is the trust feature** — Naavik isn't generating fictional achievements; it's selecting + compressing user's real ones, with audit trail.

**Side-note:** Anthropic structured outputs DO NOT work with the `citations` feature ([400 error](https://towardsdatascience.com/hands-on-with-anthropics-new-structured-output-capabilities/)). We use structured-output-only and roll our own citation field; we don't use Anthropic's native citation feature.

**Cost impact:** marginal (~200 tokens for the citation field per bullet).

**Recommended for FREE-tier (mandatory).** This is the honesty constraint.

## N · Multi-Claude council voting (Borda count consensus)

**The technique:** for high-stakes decisions, 3+ Claude instances each emit a candidate output; consensus is computed via Borda count or majority vote. Inspired by [Council Mode arXiv 2604.02923](https://arxiv.org/pdf/2604.02923) — heterogeneous personas explicitly outperform same-prompt multi-instance.

**Already covered in § I (bullet selection) and § J (recruiter critique).** Mentioned here for completeness as a distinct pattern from § F (adversarial generator-critic loop).

**Anthropic Batch API support:** Anthropic supports parallel calls via `messages.batches.create` ([Vertex AI batch predictions docs](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/partner-models/claude/batch)). 50% discount on batch API submissions. **For premium-tier 3-agent council, batch-API the 3 calls** to cut cost in half. Synchronous mode adds latency (~2s vs 100ms); the user is waiting for the resume so latency budget is real.

**Recommended for PREMIUM-tier.**

## O · Embedding-similar-success retrieval (forward-looking)

**The technique:** when Naavik has multi-user cloud data, retrieve "users who got an interview for similar roles" + extract their resume style fingerprint + use as few-shot in-context examples.

**Out of scope for 0.3.1:** Naavik is single-user self-host today; no multi-user dataset yet. **File as 0.5.0+ row when cloud-tier data scale arrives.**

**Privacy:** opt-in only; only style metrics (sentence-length distribution, lexical diversity), never raw bullet content.

## P · Anthropic Computer Use (forward-looking)

**The technique:** Claude operates the ATS form via the Computer Use API — clicking buttons, filling fields, uploading the PDF. Bypasses Playwright form-fill brittleness.

**Out of scope for 0.3.1:** Computer Use is overkill for resume generation. File as `0.4.0.NN` (auto-apply) where it's more relevant.

## Q · Constitutional ethics layer (pre-flight check)

**The technique:** before any output ships, run a final pre-flight check via a separate Claude call: "Does this output (a) make any factual claim not grounded in the candidate's profile? (b) inflate any title or credential? (c) imply experience the candidate doesn't have?" Output: green-light or red-flag-list.

**Enforcement:** if red-flag-list is non-empty, refuse to ship + surface to user with the specific claim flagged + ask user to confirm or refine.

**Cost:** ~$0.01 per pre-flight call.

**Recommended for FREE-tier (mandatory).** This is the safety net. Combined with citation-grounding (§ M), it's the defensibility-and-honesty backbone.

## W · Risks + mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Anthropic prompt cache 5-min TTL expires between stages | MEDIUM | Cost balloons by 5-10x | Run stages sequentially (no long human-in-loop pauses); time the multi-stage pipeline to complete in < 5 min |
| Claude-as-detector underestimates real-detector flag rate | HIGH | False sense of security | OQ-3 hybrid recommendation: spot-check with real detector API at convergence |

| TIER-3 (white-text, homoglyph) user demand creep | LOW | Brand damage | Hard refusal; surface blacklist warning; require explicit checkbox + audit-log opt-in |
| ATS-friendly Typst template loses brand differentiation | LOW | Resume looks generic | Keep current `onepage.typ` as parallel "creative" variant (OQ-8 B); user/auto-selects |
| Multi-agent council adds 20-50s latency | HIGH | UX degradation | Batch API for parallel calls; SSE progress streaming to UI; clear PREMIUM-mode UX expectation |
