## A · Executive summary

The current `0.3.0` ledger has 7 high-level rows (`0.3.0.01–07`) which read as "tag matching + AI scoring + visa filter + tailored resume preview + one-click generation + analytics + UI." That phrasing leaves four big questions unanswered: (1) **which scoring algorithm** (tag-only Jaccard? semantic cosine? LLM-as-judge? hybrid?), (2) **which LLM tier** for the judge call given the daily cost cap, (3) **whether to integrate the LinkedIn MCP** as a job-source augmentation in this release, and (4) **whether 0.3.0 ships as one release or splits into 0.3.0 + 0.3.1 + 0.3.2 sub-cuts** — current 0.2.x design-heavy work suggests the answer is split.

**Three critical decisions for the user:**

1. **Scoring architecture — pick the hybrid layered approach (Option 4 in § C).** Tag overlap (cheap pre-screen, deterministic) → semantic embedding cosine (re-uses the just-shipped JobEmbedding) → LLM-as-judge final pass (top-K only, gated on score-min threshold + daily cap). Per-dimension breakdown surfaced in the UI as `MATCH · 0.86 / ai-ml 0.95 / platform 0.88 / leadership 0.82 / visa 0.70` — that's already what `SCREENS.md § 7` mockup specifies. The visa filter remains the deterministic LLM-free zero-out per `services/scorer.py` (shipped). Recommended LLM tier: **Anthropic Claude Sonnet 4.6 ($3 in / $15 out per MTok)** for the cloud default + **Ollama llama3.1:70b** for self-host air-gapped users. Falls back to tag+semantic only when LLM cost cap is exhausted (graceful degrade, never silent-blackhole).

2. **LinkedIn MCP — DEFER to Phase 5 (0.5.0+), NOT in 0.3.0.** The stickerdaniel/linkedin-mcp-server is the production-grade option (Apache-2.0, Patchright-based, 17 tools, May 2026 active). But its job-search surface duplicates work already shipped in `0.2.0.07` (LinkedIn guest API + Crawl4AI stealth) and its real value (DM, connection-request, employee-search) lights up only in Phase 5 outreach (rows 0.5.0.10–14). Adopting it for `0.3.0` adds a sidecar Docker service + per-user cookie capture flow + browser-instance management for zero net scoring benefit. **The LinkedIn-side "skill match %" is not exposed via this MCP** (LinkedIn doesn't surface it to the guest API or to authenticated-session scraping); Naavik's per-dimension score is computed in-house regardless. Park MCP integration for plan `0.5.0.12` outreach work.

3. **Release sub-cut — split into 0.3.0 / 0.3.1 / 0.3.2.** Pattern matches 0.2.7 (which closed as five design-heavy plans). Proposed cut:
   - **0.3.0 — Scoring substrate (CRITICAL):** tag matching + semantic embedding wire-up (re-uses JobEmbedding) + LLM-as-judge with structured output + visa filter consolidation. 6 rows, ~6 dev-days estimate.
   - **0.3.1 — Tailored resume preview + one-click generation (HIGH):** wire `select_bullets` + `trim_bullet` end-to-end + Typst compile + page-count validation. 4 rows, ~4 dev-days.
   - **0.3.2 — UI polish + score analytics (MEDIUM):** score card + match breakdown component + per-tag bar visualization + score history time-series + calibration. 4 rows, ~4 dev-days.

**Total estimated 0.3.x scope:** 14 rows across 3 sub-releases, ~14 dev-days (each sub-cut shippable independently, with 0.3.0 unblocking auto-apply in 0.4.0).

## C · Scoring approach option matrix

Five viable scoring architectures. Dimensions: **Capability** (does it pick the right job?), **Cost per job** (USD + latency), **Accuracy** (qualitative, based on competitor research + academic benchmarks), **Maintenance** (LOC + breakage cadence), **Lock-in** (vendor / model). Scores: ✅ good · ⚠ caveat · ❌ blocker.

### C.1 The five options

| # | Approach | One-line shape |
|---|---|---|
| **1** | **Tag-only (Jaccard / weighted overlap)** | JD → LLM extracts tag set (already shipped via `extract_job.py`) → Jaccard or weighted-overlap with profile bullet tags → `score = |J ∩ P| / |J ∪ P|` with optional per-tag weights (e.g. `ai-ml` weight = 1.2 if profile leans there). Visa filter zeros out. |
| **2** | **Semantic-embedding cosine (re-uses JobEmbedding)** | JD embedding (via `embedding_service.embed_job`) × profile embedding (NEW: `embed_profile`) → cosine similarity in `[0, 1]`. Top-K nearest profile-bullets are the "matched" bullets. |
| **3** | **LLM-as-judge (single-shot)** | Send JD + profile summary + skills + bullets to Claude/GPT → return structured `{score, explanation, matched_tags, per_dimension_scores, gaps, suggested_bullets, visa_concern}` Pydantic output. (`score_job.py` skeleton exists.) |
| **4** | **Hybrid layered (RECOMMENDED)** | Layer 1: Tag-only (cheap pre-screen, all jobs). Layer 2: Semantic cosine for top-K-by-tag. Layer 3: LLM-as-judge for top-N-by-semantic-cosine (`N << K`). Gated by daily cost cap; falls back to layer 2 alone when LLM exhausted. |
| **5** | **Multi-criteria explicit aggregator** | Separate scorers for `{tech_fit, role_fit, location_fit, salary_fit, visa_fit, seniority_fit, company_fit}` → each in `[0, 1]` → weighted aggregate via user-tunable weights. Per-dimension surface is direct. |

| Dimension | 1 — Tag-only | 2 — Semantic | 3 — LLM-as-judge | 4 — **Hybrid layered** | 5 — Multi-criteria |
|---|---|---|---|---|---|

### C.3 Recommendation: Option 4 (hybrid layered)

**Layered architecture:**

```
For each Job to be scored (cron: jobs.score_pending every 15min):

  Layer 1 — Deterministic visa filter (existing services/scorer.py):
    if needs_visa_zero_out(profile, job):
      score = 0.0; explanation = "Visa filter ..."; STOP.

  Layer 2 — Tag overlap (NEW):
    job_tags = job.tags  # already populated by 0.2.0.08 extract_job
    profile_tags = profile.aggregated_tags  # NEW: derived from bullet tags + headline LLM extract
    tag_score = jaccard(job_tags, profile_tags)
    if tag_score < TAG_FLOOR:  # default 0.10 (configurable)
      score = tag_score; explanation = "Below tag threshold"; STOP.

  Layer 3 — Semantic cosine (existing JobEmbedding + NEW Profile embedding):
    job_emb = embedding_service.embed_job(job)  # already shipped
    profile_emb = embedding_service.embed_profile(profile)  # NEW: 1 embedding per profile, cached
    semantic_score = cosine(job_emb, profile_emb)
    composite = 0.4 * tag_score + 0.6 * semantic_score
    if composite < LLM_GATE:  # default 0.50
      score = composite; STOP (cheap-only path; "LLM judge skipped — score below threshold").

  Layer 4 — LLM-as-judge (NEW: extends services/scorer.py):
    Call llm_tracker.tracked_call(
      provider=user_provider,
      method='structured',
      prompt='score_job',  # existing prompt module, expanded
      profile=profile_summary,
      job=job,
      candidate_bullets=top_K_by_tag_match(profile.bullets, job, k=12)  # narrows context
    ) -> JobScore (existing schema, expanded):
      {
        score: 0.86,  # final overall, derived
        explanation: "Strong AI/ML + platform alignment...",
        per_dimension: {
          'ai-ml': 0.95, 'platform': 0.88, 'leadership': 0.82,
          'visa': 0.70, 'role_fit': 0.90, 'seniority_fit': 0.85
        },
        matched_tags: [...],
        gaps: ['Kubernetes', 'GCP'],  # what JD wants that profile lacks
        suggested_bullets: [b_id_3, b_id_7, b_id_12],  # IDs to include in tailored resume
        visa_concern: false,
      }
    Final score = JobScore.score (LLM-overall); persist per_dimension in match_breakdown.
    
  Cost-cap fallback: if daily LLM spend > Settings.daily_llm_cost_cap_usd:
    Skip Layer 4. composite = Layer 3 score. Log a Settings.cost_cap_exceeded event;
    surface in UI "LLM judge paused for today — cost cap reached."
```

**Why this wins:**

1. **Cost-conscious by construction.** Tag-only path is free; semantic is cheap; LLM is reserved for top-N. 1k jobs/day at <$1/day on Anthropic Sonnet + free on Ollama.
2. **Graceful degradation.** Cost cap exhaustion = silent fallback to layer 3 score, not a blackhole. User sees a Settings banner.
3. **Re-uses everything just shipped.** `JobEmbedding` (0.2.7.16), `services/scorer.py` visa filter, `services/llm_tracker.tracked_call`, `Settings.semantic_match_enabled`, `Settings.daily_llm_cost_cap_usd`, the 9-tag vocabulary. The 0.2.7 design-heavy sweep was preparing exactly this.
4. **Explainable per-dimension.** The mockup contract (`SCREENS.md § 7` `MATCH · 0.86` per-dim bars) is satisfied — `per_dimension` map from layer 4 renders as the bars; `gaps` renders as "what's missing"; `suggested_bullets` drives the bullet-selection preview.
5. **Aligns with the strongest competitor pattern (hybrid BM25 + dense + rerank).** Public research (Anthropic Contextual Retrieval, Cohere rerank pairing) shows hybrid → 67% reduction in retrieval failures vs dense-only. Naavik's tag-as-pre-filter mirrors BM25's role; semantic cosine mirrors dense; LLM-as-judge mirrors a cross-encoder reranker but explainable.

**Trade-off accepted:**

- ~750 LOC across 3 layers (vs ~150 for option 1). Manageable: each layer is < 250 LOC + isolated + testable.
- LLM cost is non-trivial under heavy daily volume. Mitigated by gated layer 4 + daily cap surfacing in UI.

**Rejected alternatives:**

1. **Option 1 (tag-only)** — too low precision; competitor research (JobScan style) shows users chase keyword scores instead of fit.
2. **Option 2 (semantic-only)** — misses hard skill checks (the visa filter is the canonical example: a 0.95 semantic score on a "ML engineer" JD that says "US citizens only" is wrong). Also no explanation.
3. **Option 3 (LLM-as-judge single-shot, no layering)** — cost-prohibitive at scale + no fallback if cap hits.
4. **Option 5 (multi-criteria with per-dimension LLM calls)** — over-engineered; layered approach achieves the same per-dimension output (`per_dimension` map in `JobScore`) with one LLM call instead of N.

## D · Competitive product deconstructions

### D.1 JobScan

**Public algorithm:** Pure keyword-overlap. Hard skills + soft skills + keywords from JD matched against resume. Score = % match. Recommended target = 75-80%. JobScan **does not use company-specific configurations** (their score does not reflect any specific ATS's algorithm).

**Verdict:** Closest to Option 1 (tag-only). Naavik's tag-overlap layer is a comparable layer-1 pre-screen; we then layer in semantic + LLM that JobScan does not have.

### D.2 LinkedIn Easy Apply skill match %

**Public algorithm hints:** Combines (a) explicit skills (member's skills section, standardized via LinkedIn's Knowledge Graph), (b) implicit skills (extracted from headline/summary/role text), (c) location match, (d) experience relevance (job-title overlap), (e) education match, (f) endorsements + recommendations, (g) profile completeness. **Shift in 2026: from keyword matching to "Semantic Entity Mapping" via the LinkedIn Knowledge Graph** — synonyms (e.g., "Software Engineer" → "Developer" → "Engineer") collapse to canonical entities.

**Verdict:** LinkedIn is doing what Naavik's hybrid layered architecture (Option 4) approximates — explicit + implicit + semantic + categorical filters. The MCP doesn't expose this signal; we compute our own.

### D.3 Indeed match score

**Public hints:** ML-based ranking using extracted entities (skills, titles, certifications), with synonym mapping and weighted factors (hard skills + soft skills + experience + location + cultural-fit signal). Public benchmark accuracy reports 85-92% for "top job" identification.

**Verdict:** Same shape as LinkedIn. Same architecture as Option 4.

### D.4 Greenhouse + Lever + Ashby

- **Greenhouse:** Does NOT algorithmically score. Every rejection is a manual recruiter decision via structured scorecard + Boolean search.
- **Lever:** Uses AI ranking on the parsed profile (not the PDF) — historical pipeline data + JD semantics. Surfaces candidates "most likely to match."
- **Ashby:** Unclear (vendor doesn't publish), assumed similar to Lever's AI-ranking shape.

**Verdict:** Confirms that ATS-side scoring is opaque + recruiter-driven. Naavik's own scoring is what the user-side surface is for — Greenhouse won't show us their score even if they have one.

### D.5 Teal + Resume Worded + Sonara

- **Teal:** Per-job match score + AI-suggested edits to close keyword gaps. Tag-based + keyword-overlap centric.
- **Resume Worded:** 20-30 checks across impact / brevity / style / soft skills / ATS readiness. Per-resume scoring, not per-job-match.
- **Sonara:** Auto-apply / search-and-submit. Less scoring focus; more execution.

**Verdict:** Teal is closest competitor on the matching axis; Sonara is closer on the auto-apply axis (Naavik is more like Teal+Sonara combined w/ self-host). Naavik's per-dimension explainability is wider than Teal's keyword-gap surface.

### D.6 Hybrid retrieval (Anthropic + Cohere ecosystem)

**Pattern from 2026 RAG research:** Hybrid BM25 (sparse / keyword) + dense embeddings (semantic) + reciprocal-rank-fusion or weighted-sum + optional cross-encoder rerank → **67% reduction in failed retrievals** vs dense-only. Cohere rerank v3.5 @ $2/1k queries; Anthropic Contextual Embeddings pattern.

**Verdict:** This is the academic underpinning of Option 4. Naavik's tag-layer plays the BM25 role; semantic-cosine plays the dense layer; LLM-as-judge plays a (much richer) reranker. We're not inventing — we're adapting the canonical pattern to the job-matching domain w/ an explanation surface that pure rerankers don't provide.

### D.7 Academic baseline (conSultantBERT / Sentence-BERT)

**Best published accuracy:** Siamese Sentence-BERT fine-tuned for resume-job matching hits **89.47% accuracy / 88.63% recall / 89.04% F1** on TalentCLEF-style benchmarks. Cross-encoder reranking adds 2-3% gain.

**Verdict:** Our semantic layer (using OpenAI/Ollama embeddings vs domain-fine-tuned Sentence-BERT) is somewhat below academic-best at the semantic-only layer, BUT the LLM-as-judge layer (Claude Sonnet 4.6) is far stronger than a cross-encoder reranker on the explainability axis. Net: probably comparable F1, with explainability + visa-filter advantage Sprout / Teal / academic baselines lack.

### D.8 Sprout (USESPROUT_COMPARISON.md confirms)

**Public algorithm:** Undisclosed (server-side, opaque). Onboarding collects visa status but does NOT score on it. "Occasional irrelevant job suggestions" per third-party review.

**Verdict:** Naavik's H1B/i-140-aware visa-first scoring is the strongest single competitive axis. Sprout's lack of explainability ("regenerate is the only knob") is the second.
