## Background — hacker MEDIUM finding 1 verbatim (PR #69)

```
Finding 1 — MEDIUM: flagged users can bypass the gate via /api/v1/profile/from-extraction
file: src/ui/routes/auth.py:223-238

impact: The 2 routes engineer skipped on the onboarding deviation aren't just
"no gate yet"; one of them, post_profile_from_extraction, is an UNAUTHENTICATED
POST that explicitly response.set_cookie(SESSION_COOKIE, FAKE_SESSION_VALUE,
httponly=True, samesite="lax", path="/"). Concrete bypass scenario:

  1. Operator logs in with the seeded password → real JWT issued,
     must_change_password=True.
  2. Operator hits / → PC.6 / PC.6a 303s them to /auth/change-password.
  3. Operator (or attacker via XSS / shared browser / leftover session)
     navigates to /onboarding (publicly reachable, GET-only, no auth).
  4. Operator submits any junk via POST /api/v1/profile/from-extraction.
  5. Server REPLACES the real-JWT cookie with naavik_session=fake-1.
  6. From this point on, EVERY require_authed_session-gated route returns
     the fake-session branch (returns None, gate passes) and the flagged-user
     redirect never fires.

The exploit doesn't even require malicious intent — a confused-deputy
operator who clicks "Get Started" on the onboarding page would silently
degrade their auth posture from real-JWT-flagged to fake-session-unflagged.

fix: Add a precondition to post_profile_from_extraction that no User row
already exists in the DB (extraction is meant to bootstrap a fresh install,
not re-cookie an existing operator). One-line check around
await session.exec(select(func.count()).select_from(User)); return 409 +
"user already exists" error card if a user exists.
```

## Background — 3 hacker LOW non-blocking notes verbatim (PR #69)

```
LOW Note 1 — tests/test_auth.py:1217-1233
  the test_require_authed_session_invalid_jwt_401 test monkeypatches
  auth_svc.verify_jwt to always return None. The wrapper imports verify_jwt
  into its own module namespace (src/services/auth.py:338 calls bare
  verify_jwt(...)), so monkeypatching auth_svc.verify_jwt does affect the
  wrapper's call site. Verified by inspection. The pattern is fragile to
  future refactors that move verify_jwt to a sibling module — engineer
  should leave a comment on the monkeypatch line so a future refactor
  doesn't silently no-op the test. Not a blocker.

LOW Note 2 — tests/test_auth_gate.py:184-237
  the test_fake_session_caller_unaffected_across_groups test asserts
  r.status_code not in gate_codes where gate_codes = {303, 307, 401, 403}.
  This is correct for the gate's behavior but does NOT pin the positive
  route response. A future change that converts (e.g.) /_fragments/settings/
  test-connection into a route returning 500 on missing-DB would still
  pass this test. Consider tightening at least one route assertion to
  r.status_code in {200, 204, 422} to catch real-route regressions.
  Cosmetic, not a blocker.

LOW Note 3 — src/services/auth.py:307-308 (wrapper docstring)
  Wrapper docstring says "Search-replace target at that time:
  Depends(require_authed_session) → Depends(require_password_complete)."
  Worth noting in the docstring that the _user: User | None annotation
  will also need tightening to User at that time (because
  require_password_complete returns User, not User | None). Trivial
  future-engineer ergonomic. Not a blocker.
```
